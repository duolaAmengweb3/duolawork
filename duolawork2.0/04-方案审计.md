# DuolaWork 2.0 方案审计

2026-11-25 · 审计对象为产品定义、架构方案、实施清单和交互原型。以下用例是建议补入的验收条件。

**产品方向通过，工程定稿需修订。** 一个「新对话」入口、对话内换负责人、需要分工或定时执行时建任务、结果交回来源对话，这四点符合需求。任务看板也有明确用途。影响开工的缺口主要集中在真实运行端、断线恢复、任务权限和接力时的数据归属上。[产品定义](./README.md#L118)

## 会导致验收误判的五处缺口

1. **Token 验收混用了三种计量。** 架构承诺缓存 100% 命中、一次交互严格一次原生请求。ACP 明确一个回合可以包含多次模型交互。项目自己的历史记录里，同一个 Codex 文件任务直用和经 Hub 都各用三次模型请求。建议分别记录工作台派发次数、原生回合数、提供方实际请求和用量。测普通消息只派发给选中成员一次、空闲零模型唤醒，再以相同任务、模型、初始上下文和完成结果对照开销。平台未提供的指标标为不可观测。 [架构承诺](./02-开发架构与连接器选型方案.md#L16) · [项目历史对照](../通知与收件箱机制设计.md#L96) · [ACP 回合定义](https://agentclientprotocol.com/protocol/v1/prompt-turn)
2. **长对话和失败交接没有验收。** 新接手成员可能首次面对几百条未读消息。按序号截取全部增量没有输入预算，也未说明投递失败何时推进游标。建议定义交接大小、必带的最新用户要求及稿件版本、按需读取旧原文的方法，以及确认收到后推进游标的时机。补测长历史、B 离线后重连、A 的迟到结果和连续切回。 [增量算法](./02-开发架构与连接器选型方案.md#L52) · [切换用例](./03-Phase1-4工程实施与反作弊验收清单.md#L50)
3. **任务到交付还有中断点。** 状态表有 `waiting_user`，四类唤醒规则没有明确用户答复后怎样恢复该任务；并发通过最后两个步骤时怎样只结单一次也未规定。代码任务可以各用 worktree，但验收只检查能隔离创建，没有规定获准改动怎样汇集到可交付的版本。补测等待人工答复后续跑、两步并发验收只生成一张卡、并行代码修改在合并后的版本通过集成测试。 [状态与事件](./README.md#L154) · [分工及交付门槛](./03-Phase1-4工程实施与反作弊验收清单.md#L59)
4. **施工顺序和旧版接管口径冲突。** README 的第一阶段要求切人，第二阶段要求单次任务；施工清单的第一阶段是驱动，第二阶段才切人。README 要复用既有连接器，架构方案要求重写。归档只读、旧定时计划由谁继续触发、已在执行的旧任务怎样收尾，也缺少对应的交付项。建议统一阶段编号，逐运行端标明保留什么身份和原生会话、替换哪段适配代码、历史与定时任务如何接管。用一条正在执行的旧任务和下一次定时触发验证能查历史、单次交付以及可回退。 [产品分期与继承](./README.md#L178) · [架构取舍](./02-开发架构与连接器选型方案.md#L72) · [施工分期](./03-Phase1-4工程实施与反作弊验收清单.md#L35)
5. **原型有会把改稿送错对话的交互。** 两个对话共用消息流与当前成员变量；「新对话」聚焦已有对话；从每日早报点「发回对话继续改」固定返回连接器对话；切换第 25、26 期只改步骤文字，右侧仍取同一份第 26 期文稿。建议把原型里的导航、改稿来源和成果选择分别绑定到对话 ID、Run ID、文稿版本。用两段对话和两期不同成果逐次点击，检查标题、消息、接手人和改稿去向。 [对话导航与新建](./prototype-v2.html#L694) · [期次切换](./prototype-v2.html#L817) · [改稿返回](./prototype-v2.html#L867)

**建议的首个开发里程碑**是用实际的本机 Codex 和 Gemini2VPS，在同一对话完成一次换人、一项独立派工和一次断线恢复。证据应能串起原始消息、实际成员、原生回合、验收意见和最终成果版本。这样能在铺开三栏 UI 和更多连接器之前，验证当前架构能否服务用户已有的工作环境。
