## 独立补测的发现

| 高 | **验收拒绝被登记为通过。** 执行人交草稿，负责人回复「未通过。数据缺失，不能交付。」系统记录 `accept`，保留这句拒绝意见，同时把整单标为 `completed`。单人任务中执行人交空字符串，也得到完成状态，提交正文长度为 0。[裁决解析](../../src/server/tasks-fsm.ts#L1387) · [单人验收](../../src/server/tasks-fsm.ts#L675) | 有明确有效的通过裁决、有符合任务要求的成果，才能生成完成卡；语义不明或格式错误时等待核验。 |
| 高 | **重复请求会建出两份定时计划。** 对同一条建计划消息发送两次相同请求键，驱动共执行一次，工作台出现两个用户气泡、两份同名计划。去重发生在派发层，消息落库和回复里的建单操作没有共享同一去重结果。浏览器发送时也没有提交稳定的请求键。[消息落库](../../src/server/threads.ts#L494) · [处理回复中的操作](../../src/server/threads.ts#L751) · [浏览器发送](../../src/web/App.tsx#L717) | 模拟「服务端完成、客户端未收到响应」并重试，最终只有一条消息、一份计划、一张任务卡。 |
| 高 | **重启后任务会一直显示进行中。** 在测试执行人开始工作后退出隔离服务进程，保留数据库重启。经过 17 秒，覆盖两次后台对账间隔，派发记录已经是 `failed`，任务和步骤仍同时为 `running`。启动对账会同步对话消息，任务步骤没有对应的恢复路径。[后台对账](../../src/server/app.ts#L670) · [遇到忙步骤时返回](../../src/server/tasks-fsm.ts#L413) | 对账结果推进相应步骤和整期状态；已执行但回执不明的动作能核实归属并避免重做。 |
| 高 | **修改未来计划会影响已生成的旧期。** 按 v1 模板生成一期，原负责人为 A；将模板更新为 v2、负责人改为 C，然后执行旧期。旧期仍显示模板 v1，实际验收人却是 C。另外，两期使用不同执行步骤，但同一负责人两次验收使用了相同的原生会话 ID。[生成当期](../../src/server/tasks-fsm.ts#L330) · [执行时重读当前任务](../../src/server/tasks-fsm.ts#L489) · [验收会话绑定](../../src/server/tasks-fsm.ts#L783) | 已生成期次使用创建时的负责人、验收规则和本期验收会话；改模板影响新期次。 |

| 中 | **手机初次打开被协作空间遮住。** 在 390 × 844 的移动视口，默认的协作空间覆盖聊天和发送按钮。对发送按钮做实际点击，命中的是协作空间；点右上角关闭空间后即可发送。[实测截图](./product-audit-mobile-390.png) · [默认打开设置](../../src/web/App.tsx#L184) | 手机初次打开能看到聊天并点发送，点资料时再显示协作空间。 |

## 静态审阅发现

- **一次性登录码及节点配对码缺少应用层失败次数限制。** 密码入口有锁定计数，短码兑换路径只检查有效期和是否已消费。仓库中的 Nginx 配置未见对应限流规则，外部网关的实时策略未核实。建议补两类兑换的服务端失败限额和审计。[验证码兑换](../../src/server/auth.ts#L245) · [部署配置](../../deploy/nginx/work.manyaitool.com.conf)
- **撤销设备会话没有同步关闭既有实时订阅。** 会话撤销会更新数据库；事件广播保存的是响应连接，没有会话标识用于关闭该设备订阅。建议让撤销和过期同时终止对应的长连接。[撤销入口](../../src/server/app.ts#L869) · [实时订阅登记](../../src/server/app.ts#L1010)
- **发版记录不能还原这份源码。** 构建信息记录的 Git 提交为 `c90002e`。在本机项目仓库查询该提交及当前索引，`duolawork2.0/` 下都为 0 个受跟踪文件。建议将审阅过的源码、测试和锁文件纳入版本控制，之后按可核对的提交打包。[构建信息](../../dist/build-info.json)

**修复顺序建议。** 先封住错误交付和重复建单，同时补短码兑换与撤销会话的防护。随后补任务重启恢复、当期模板快照，再修浏览器重连、移动端和节点交接预算。
