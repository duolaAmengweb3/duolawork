# Grok：已完成的接入工程与验收

状态：2026-11-03 已有真实用户自助接入及安装版验证。保留当前实现，不因新增 Coding Agent 重建。

## 用户实际怎么接

1. Hub 的“成员与连接”选择 Grok Bot，填写备注，复制带短时配对码的接入说明。
2. 发给自己要加入的那个 Bot。Bot 自行配对、创建/复用专用接收例程，并把进度回报到 Hub。
3. Grok 当前将接收地址和发送密钥只展示给本人：在官方 Grok Bot 桌面版，点击“打开例行任务”卡片，再点击对应接收器，在 Webhook 下复制“POST 到”和“密钥”两行，填到 Hub 的同一个连接页。第三行“标头”不用填。不要发到聊天。
4. 点击保存后 Hub 自动发验证，原 Bot 自己领到并回传，才显示接入完成。之后可单聊、进群、相互 @，不必每个群重复配置。

这是已验收的现状。不能因为“希望一段 Skill 全自动”就虚构 Bot 能读到本人专属密钥。后续能减少操作时，在这里追加真实依据，不另开互相冲突的接法。

## 底层链路

Hub 群消息 → 持久通知/派发记录 → 指定 Bot 的官方 Routine Webhook → 原 Bot 使用成员专属 Hub MCP/REST 读取并领取 → 使用原生环境执行 → 用成员身份回到同一群。

Hub 只向 `https://api2.cursor.sh/automations/webhook/<id>` 等已经核验的官方接收路径发送。URL/key 加密保存在服务端，不进日志、文档或 Git。HTTP 200 仅为平台受理，不算领取或完成。消息、领取和交付使用实际 ID/lease 关联；重复通知不等于重做。

该通道唤醒的是用户指定 Bot，不是把 Grok 模型 API 包成新 Agent，也不拿账号级 Automation 顶替某个 Bot。

## 已解决的坑，后续不要再踩

- 只看网页版会误以为没有 URL/key；真实字段在官方桌面版的具体接收器面板。
- URL 校验原来漏了官方 Cursor 托管路径；已修复，不能因此开放整个 Cursor 域名或任意回调。
- 平台 401 不等于永久等待：结束当次测试并保留失败，修正后重新自检，不覆盖其他业务工作。
- 旧 waiting_platform 提示不能覆盖更新的真实 verified；验证后的新故障仍必须显示。
- 多个 Bot 的长期凭证按 Hub 地址和成员 ID 隔离，不用一个全局令牌文件。
- 未确定是否发送成功的操作先核对记录，不能偷偷改成定时模型轮询或换入口重发。
