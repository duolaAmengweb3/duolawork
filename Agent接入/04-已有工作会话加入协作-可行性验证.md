# 已有工作会话加入协作：方案与可行性验证

核验日期：2026-11-03。本文是用户新确认的产品层补充，不替换原有接入。当前交付为调研、真实探针及证据；不是宣称已把新入口装进正式软件。

## 结论先看

**可行，有官方接口可以复用，不需要重做 IDE 或 Agent 引擎。** 本轮已验证两个不同层次：

| 对象 | 本轮明确结果 | 还不能宣称什么 |
|---|---|---|
| Antigravity 桌面 App 2.28.0 | **真实原 GUI 工作会话通过**：先在本地项目改代码、测试；外部消息进入同一会话；它记得先前上下文，自己领取并回 Hub；之后原 GUI 继续原项目测试 | 不扩大到 VSCode 扩展、独立 IDE 或所有版本；正式用户接入与长期恢复尚未产品化 |
| Codex VSCode 官方扩展 26.1021.22027，内置 CLI 0.164.0-alpha.11.1；外部 queue CLI 0.165.0 | **真实原 VSCode GUI 会话往返通过**：原会话先改项目并测试；外部 queue 发消息到同一会话，它记得先前上下文并亲自领取、回 Hub，原 GUI 随后继续项目测试通过；无需预先登记 Hub 动态工具 | 本轮使用隔离测试配置与项目，开发者处理了原生沙箱的本机网络批准；正式一键接入和恢复未交付；不扩大为 Codex 独立桌面 GUI 已验 |
| Claude Code | **官方 Channels 机制确认**：可向正在运行的交互会话推事件，并通过工具回复；自定义 Channel 受研究预览限制 | 按用户要求，仅查公开官方资料；未运行 Claude、未查本机登录/配置、未连 VPS，未实测其原会话或 IDE 侧栏 |
| DeepSeek Harness（DSH） | **官方源码确认**：按 sessionId 寻址、prompt queue/steer、历史跟随及状态接口存在；普通原会话可恢复，只有 create/fork 直接创建新 Agent | 未安装、未登录、未运行真实 DSH 会话；Host 认证、插件及 Hub 往返仍需联测 |

所以不是“四家都已支持”。目前 Antigravity **桌面 App**与 Codex **VSCode 官方扩展**均已有原 GUI 会话真实往返证据；Codex 另外还保留原生协议会话验证。Claude 和 DSH 有明确官方路线，但仍属于未联测适配目标。

## 1. 产品到底增加什么

用户正在本机项目里用 Codex、Antigravity 或 Claude 干活，现在想让**干这份活的 Agent**进入群讨论。它应知道刚改了什么、测了什么、还缺什么；讨论后仍在原项目继续。Hub 负责沟通、共享资料和可选协作工具，代码编辑、终端和原生执行环境仍属于原 Agent。

保留两种有不同价值的接入，不暗中替换：

1. **连接一个 Agent**：目前已有实现。Hub 保存自己的原生会话，适合通用助手、研究、独立委派等使用。
2. **让正在工作的 Agent 加入**：本轮新增设计。绑定用户选中的具体原生会话与环境，不默认新开一个同账号会话代替它。

同一个品牌或账号可以有多个工作会话。例如“Codex · bubu 后端”和“Codex · 官网”可作为不同成员加入。身份依据原生会话和环境，备注只影响显示名称。不能因为工作目录相同，就把两个不同会话当作同一个 Agent。

用户继续使用原 IDE。Hub 不镜像整个 IDE，也不复制一份聊天记录后假装是原 Agent。仅把明确发往 Hub 的消息和成果同步出来；本地完整历史与项目文件不默认上传。

## 2. 用户流程建议

这是待实现的产品流程，不能把下列步骤写成当前安装版已经具备：

1. 在“成员与连接”或群内添加成员，选择“正在工作的 Agent”。
2. 用户在想加入的**那个原生会话**发送一段接入说明，或通过官方扩展/插件执行“加入 Hub”。平台适配层完成身份与会话识别，不让用户找 sessionId、端口或密钥。
3. Hub 显示可确认的原会话标题、项目及运行位置。由官方运行接口核对返回的具体会话，不能只相信模型自己编写的 ID。
4. 使用该会话完成一次真实领取和回群，才显示可用。用户之后在群内正常沟通；Agent 使用原工具继续工作。

首次使用可能需要原平台支持的插件启用或官方授权。已经授权过的成员不反复要求登录。Claude 的预览限制需要真实处理，不能用一段 Skill 冒充能跨过官方加载限制。

## 3. 最小工程实现

复用当前消息、成员权限、领取、回复和持久恢复；新增“已有工作会话”适配能力，不重建任务系统。

### 绑定与发送

保存 `memberId + adapter + hostLocator + nativeSessionId + canonicalWorkspace + connectionId`。这些是内部字段，前端只展示 Agent、会话、项目和运行位置。远端运行环境不能被本地同名路径替代。

Hub 群/单聊关联具体成员绑定。有多个候选时由用户选择，不猜“最近一次”。若同一工作会话主动加入多个群，其上下文会接收到多个群的获授权内容；不能对用户承诺这些群仍像 Hub 新建独立会话一样隔离。

消息链路：**Hub 消息 → 本机/原环境连接器 → 指定原生会话 → Agent 自己调用 Hub 工具 → 原群回复**。Agent 可相互 @，文档、事项、会议继续是工具，普通聊天不强制变成任务模板。

### 原 Agent 正在干活时

默认排队沟通，不中断原执行。Hub 可显示“已送达，Agent 正在处理原工作”，并保留可追踪消息 ID；不把“排队成功”显示成已经回复。不自动复制会话、重开另一个模型或代 Agent 写答复。

用户明确要求打断时，只有平台提供了可验证的原生 steer/cancel 接口，才提供相应操作。DSH 源码确认了 queue/steer；本轮未据此承诺其他平台有完全相同的能力。

### 生命周期与故障

- 原运行端关闭或原会话不存在：保留消息，说明等待哪个原 Agent；重连后核对原 ID 和回执再继续，不偷偷换会话。
- Hub 更新/重开：恢复绑定，不停止用户 IDE 或替换原运行端；解除 Hub 连接只撤销协作权限。
- 重试沿用同一请求 ID，先查是否已经收到/回复，避免重复执行。不能仅靠重发整段提示词恢复副作用。
- 不读提供方登录文件，不把原生进程认证凭据复制进 Hub。使用官方授权/插件所提供的本地接口。

## 4. Codex 实际怎么验证的

证据：[working-session.json](../evidence/working-session.json)。探针：[verify-working-session.mjs](../scripts/verify-working-session.mjs)。

1. 在临时 Git 项目创建受控原生工作会话；先读项目规则，将 `scale.mjs` 从乘 2 改为乘 3，实际运行 `npm test`。
2. 测试前保留未提交的 `notes.txt`，原分支为 `proof-existing-work`。给会话一个只在对话中出现的识别词，不写到文件。
3. 官方 `codex queue --remote unix://… --thread <原 ID>` 向同一已存在会话发送协作请求。Agent 实际调用隔离真实 Hub Worker/D1 的 `list_work`、`claim_work`、`post_message`，在群回复先前修改、测试和识别词。
4. 原协议客户端在同一 thread 继续开发，增加 `scale(0) === 0` 测试，实际测试通过；原项目、分支及未提交笔记保持。

使用原本机 daemon 的模型与身份，未修改 provider 或模型。这里的 Hub 是隔离测试实例，非生产群。测试中的会话先由受控协议客户端创建，建会话时已登记 Hub 动态工具，完成本地工作后才收到外部协作请求。因此证明了原生同一会话接收与继续工作，**没有证明给任意未准备的旧会话热补工具**；更不能包装成官方 GUI 已接好。

实际遇到的错误也保留：最初隔离平台未登记；将 supervisor/普通 NDJSON 与 application socket 混淆导致 initialize 超时；macOS `/var` 与 `/private/var` 别名导致目录断言误判。最后一项以 realpath 只读核对恢复证据，没有重跑模型动作。

曾尝试通过电脑操作工具核对 Codex 官方 GUI，但工具明确禁止控制该应用。本轮没有换通道绕过；这是本次验证手段的限制，不能推导为 Codex 产品不支持。

### 同日补验：真正的 VSCode GUI 原会话

证据：[codex-gui-working-session.json](../evidence/codex-gui-working-session.json)。探针：[verify-codex-existing-gui.mjs](../scripts/verify-codex-existing-gui.mjs)。这项新增结果补上了上段当时尚未验证的 VSCode 层，不删除原先的范围限制。

- 官方扩展安装在专用“Hub 原工作会话验收”配置，日常项目、Claude、原提供方登录与模型配置不变。临时项目中的原 GUI 会话先完成乘 3 修改并实际测试通过。
- 原生管理接口确认这个 thread 的 `source` 为 `vscode`，并且 cwd 对应唯一测试项目。外部 `codex queue --thread <该 ID>` 把消息送入该会话，没有 `--resume`，没有创建、复制或接管另一个 Agent。
- 该会话建立时**没有 Hub 动态工具**。接到消息后运行只访问隔离 Hub 的临时工具，自己领取并回群；返回只在原 GUI 对话里出现的识别词及实际工作事实。
- 首次尝试原生沙箱阻止本机网络，等批准时测试端 120 秒到期，提前清理了工具。这个失败原样保留。修正测试等待时间后，在原会话重试，三次工具调用分别获得开发者的本次批准，完成真实往返；没有关闭原生安全配置冒充免确认。
- 回群后由用户方式在原 GUI 输入继续开发请求，该会话在 test.mjs 实际增加 `scale(0) === 0` 断言并运行测试通过；notes.txt、scale.mjs 和原分支保留，界面显示该轮 14 秒，没有调用已结束的 Hub 工具。
- 因此已经证明“原 VSCode 会话可以加入协作”。**正式用户流程的权限一次配置、工具持久化、自动识别及重开仍需产品化验收**；这次开发者辅助批准不算普通用户一键接入已通过。

## 5. Antigravity 实际怎么验证的

证据：[antigravity-working-session.json](../evidence/antigravity-working-session.json)。探针：[verify-antigravity-working-session.mjs](../scripts/verify-antigravity-working-session.mjs)。

1. 官方桌面 App 2.28.0 中，在同一临时项目开启受控 GUI 会话。原 GUI Agent 增加 `scale(-2) === -6` 测试并实际执行通过，记住仅在对话里的识别词。
2. 使用官方 **Sidecar + agentapi**。Sidecar 由原 App 自己启动并继承本地原生接口授权，向这个**已存在的确切 conversationId** 发送消息。未提取 Google 登录或原生 CSRF 凭据。
3. 原 GUI 会话实际领取隔离 Hub 消息，自己调用 Hub 工具回群；返回内容同时包含先前代码、测试结果及只在原会话出现的识别词。不是开发者代写，也不是新建会话读项目后猜测。
4. 随后在原 GUI 输入一次继续工作请求。它在原目录实际再次运行 `npm test`，通过，退出码 0；原分支与 `notes.txt` 保持。界面显示该次工作 18 秒，这是收尾测试样本，不是消息响应速度承诺。
5. 临时启用的自有 Sidecar 项目和目录均已移除；只加在临时项目中的 Stop hook 也已清理。没有修改原模型、账号、日常权限或现有连接。

失败路线：外部直接调用 agentapi 缺少原生地址/CSRF；项目 Stop hook 虽然拿到原 conversationId，却没继承本地 API 环境。没有通过导出凭据补洞，而是改用官方 Sidecar 的运行机制。官方文档明确 Sidecars 适用于 **Antigravity App**，因此这个通过结果不覆盖 VSCode 扩展。扩展需要独立验证同会话入口。

## 6. Claude 与 DeepSeek 的具体路线

### Claude：Channels，先只研究

官方机制是本地 MCP Channel 服务向正在运行的交互会话推事件，暴露回复工具。它与把模型 API 接到另一个 Agent 不同，也与另开 `-p` 任务不同。

当前官方文档注明研究预览；自定义 Channel 不在默认允许列表，测试需开发 Channel 参数，组织账号还可能要求管理员启用。该参数不作用于 `-p` 或 Agent SDK。官方步骤明确在启动时加载 Channel 并确认使用，因此不能承诺把任意未启用 Channel 的已打开会话零配置热接入。原会话恢复时带上该接入配置是候选实现，仍按约定不运行 Claude 验证。官方 Remote Control 是官方网页/移动端控制本地会话的能力，不能直接当成任意第三方 Hub 的公开接入 API。VSCode 原生侧栏也没有在本轮得到实测证明。

按用户要求：**Claude 全部不动**。本轮没有运行 CLI/help、读取其本机配置或登录、启动进程、连接 VPS 或消费订阅。

### DeepSeek：接的是 Harness，不是模型 API

应列为 **DeepSeek Harness（DSH）Agent**。DeepSeek 模型 API 只是推理接口；DSH 才包含会话与工具运行环境。`dsh-superagent-prototype` 则是建立在 Harness 上的研究原型，README 明确其不是正式 DeepSeek 产品，也不是生产就绪保证。

在官方仓库固定版本 `8bd073392eef6f54e921a093b95076248eb08cbb` 核对了：

- `session-controller`：按原会话地址操作；普通 prompt 可解析/恢复原会话；只有 create/fork 直接创建新 Agent。
- `ISession.prompt`：具有 `queue` 和 `steer` 两种发送方式；包含请求 ID、取消与队列操作。
- 历史/follow、状态与投影接口：可观察原会话，不需要为看列表启动新 Agent。
- 远端调用有 Host/Peer 访问控制，不能认为知道 sessionId 就可以操作。

建议利用其插件/原生 Gateway 在原 Host 内接入消息和工具，绑定 sessionId；保留原工作目录和模型。需要真实验证 Host 建连、授权、同会话提示、Agent 回 Hub、原客户端继续工作。**这套实现尚未安装或联测**，不拿源码方法存在代替结果。

同日补查得到明确前置条件：官方 Python SDK 教程要求兼容模型端点与凭证，支持显式 `dsh_home` 和 `session_id`；不会因为能安装 Harness 就自动获得模型额度。本机检查：PATH 无 dsh、Python 无 deepseek_harness、默认 ~/.dsh 不存在，当前进程没有 DEEPSEEK_API_KEY。这里只检查存在与否，没有读取或搬运其他产品的凭据。要补真实模型联测，需要一个获授权的 DSH 实例或专用模型配置；这属于缺少测试环境，不是已发现协议不能接。

## 7. 后续实施与验收不跑偏

基于这次证据，产品化先落到明确版本的 Codex VSCode 扩展 / 原生会话和 Antigravity 桌面 App；保持通用 Agent 接入。Antigravity VSCode 扩展、Codex 独立桌面 GUI、Claude、DSH 分别按真实验证结果开放入口，不挂“全部支持”的招牌。

| 必验场景 | 合格结果 |
|---|---|
| 原会话正在开发 | 加群前已有代码修改、测试和只在对话里的上下文，不能只选择一个空白目录 |
| Hub 沟通 | 原会话自己领取、回答；原会话 ID、环境和项目保持；回同群 |
| 原端继续 | 用户在原 IDE/客户端继续执行测试或编辑，保留讨论上下文与未提交工作 |
| 原端忙碌 | 排队而非打断；一次消息只产生一份可追踪处理，不制造第二个执行者 |
| 同账号多会话 | 能选择准确工作会话，不串项目、不猜最近会话；多个成员身份独立 |
| 重开与短断 | Hub 重开及网络短断后沿用原绑定和回执，不重登、不换模型、不重复副作用 |
| 用户自己完成接入 | 从普通入口开始，不依赖开发者手填本机路径、端口、ID 或令牌 |

本轮已覆盖受控同会话、本地修改/测试、原生回群与原端继续；**尚未完成**正式接入 UI、多会话选择、忙碌/短断/重开全量联测及生产交付。当前安装版既有功能不变；这份文档与探针不触发打包或重启。
