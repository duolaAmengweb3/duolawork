## 交互说明

### 图 01：开始前
目标 → 可修改的安排 → 节奏 → 开始。默认安排来自固定规则，应明确注明，不能装作模型已经分析。用户不必自己搭节点或写岗位职责。选择「各自提交，并排对比」后，隐藏协作方式和汇总成员；「让团队安排」只调用已选成员中的一位，迟到草案只保留为建议。

### 图 02：默认交付
交付前依照合格标准自查并按上限内部修订；部分达标必须列出缺口。图中呈现的是默认的一份最终稿。资料出处与本轮记录展开查看。事实真假走补证或标未知，只有路线、成本和偏好的取舍进入正文决策卡。人工编辑后的返工返回候选版本，保护现有工作稿。

### 图 03：另一种交付
只有用户明确选「各自提交，并排对比」才出现该视图。这不是“基准 / 当前 / 候选”的版本冲突界面。对比时同结构对齐，可逐段采用到独立工作稿；未采用的原始交付仍保留。

### 图 04：下一次少交代
待确认规则可修改范围与措辞。默认只作用于本项目；确认后生效，可撤回。实际任务显示采用的规则版本；「本轮已带入」需要派发记录，「结果已符合」需程序检查或注明成员审阅结论。成果用于新任务时选择具体版本与资料，时效性事实重新核查。

## 请评审者回答

1. 是否准确表现了「默认只交最终结果 / 明确要求时并排交付」两种交付形式？
2. 入口和信息层级是否让用户知道下一步能做什么？有没有强迫用户管理过多流程？
3. 哪处偏离 v1 定稿？请写出图号、具体位置、对应条款、修改建议。
4. 视觉上哪些文字不清楚、密度过高或装饰抢过正文？请指出具体区域。
5. 哪些关键交互尚需补图？不要把图中没有画出的能力直接判为已经实现。

回复可以是赞同或反对，但请附具体理由，不以“高级”“成熟”“全部闭环”替代评审。

## 范围

- 本轮没有改正式客户端、后端、账号、代理或登录资料。
- 仍需单独评审的状态：平台接入向导、排队与掉线、部分达标、人工稿冲突、暂停与原平台停止的区别、两轮真实唤醒返工。
- 本轮目标是让所有者、Claude、Gemini 对齐视觉与主路径，不能据此认定技术可行、账号已接通或产品已验收。
- AI 图中的精确字号、文案或控件细节若有偏差，以本说明和 v1 定稿为准；在视觉检查中记录明显偏差，不把效果图当像素级实现规格。
