# Agent Hub 原生接入范围核验

作者：Codex。核验日期：2026-10-28。用途：先决定这个产品能覆盖谁，再决定是否继续投入；本文不把官方能力当作本产品已经接通。

> **产品定位更新：** 所有者已在 [Issue #1 最新讨论](https://github.com/duolaAmengweb3/agent-hub/issues/1#issuecomment-6468757003) 明确：做“Agent 协作台”，不按 Agent 类别限制接入。下文按产品类型分组仅供核对研究证据，不是前端分类、成员类别或准入规则；不再把“个人 Agent 覆盖面”单独作为项目继续与否的门槛。正式设计按直接调用、事件唤醒、定时自查、浏览器适配组织；常见平台是预设。浏览器可作为某成员独立选定且验收的方式，不是运行时自动回退。

## 结论先看这里

**停止把网页点击、页面抓回复作为主执行方案，这个取舍成立。但“换成 MCP 就能接所有个人 Agent”不成立。**

不靠网页操作，当前有明确官方接入依据的通用产品候选是 **Perplexity Computer、Grok Bot、ChatGPT Dots、Manus、WorkBuddy、千问办公**。其中前四个有直接派发或事件启动入口，后两个主要是定时查任务，不能混称实时。**这六个是值得联测的候选，不是六个已通过验收的平台。** Kimi Work 再列为组合待证候选；Gemini 只能先按半自动；Muse 不列入普通 Mac 用户的原生支持承诺。

**按最新定位，原生接口、CLI、可唤醒和定时参与的 Agent 都是目标接入对象，路线有继续验证的基础。** “所有热门个人 Agent 都能实时、无人值守地协作”仍不是已证实的能力，也不是当前产品范围要求。研究统计应注明实际对象和证据等级；不能因一种接入成功就推断任意平台已兼容。

目前我们手上的 Grok、Muse 真实成功记录仍来自网页执行。本轮没有将其改名为原生成功。商业云端 Agent 的完整原生链路，当前本项目仍没有通过记录。

## 怎样才算“能接”

完整链路为：指定真实 Agent → 外部启动或按约定查任务 → 读取本次输入 → 使用原 Agent 的工具执行 → 关联到本次任务的完整交付 → 自动推进下一位。还要核验持续授权、同会话追问、失败恢复和重复通知。

- **直接调用**：平台把完整 Agent 暴露为官方 MCP/API，Hub 派活并查结果；不必强行再加一套唤醒。
- **事件唤醒＋工具**：事件叫醒原 Agent，再由它调用 Hub MCP 领取、交付。
- **定时＋工具**：Agent 定期查 Hub，有等待成本，也有空跑额度成本。
- **半自动**：能做任务，但领取/交付仍需用户确认。不能承诺无人值守。

登录、发现工具、HTTP 200、CLI 退出码为 0 都不是完整交付证据。保留一套任务协议；每位成员只有一条生效执行通道，不在失败时偷偷退回网页重发。

## 通用 Agent：逐家判断

| 产品 | 官方已经证实的入口 | 完整自动接力的关键条件 | 本次定档 |
|---|---|---|---|
| **Perplexity Computer** | 官方 Computer MCP 可启动/续聊、查任务、取成果、处理批准和取消；账号 OAuth，消耗账号 credits。不是 Search API。[S1] | Hub 需要作为 MCP 客户端；获得 OAuth 授权后测试任务和成果。保留 thread ID，超时只查原任务，不重新派发。网页个人设置/具体连接器继承范围仍需任务核验 | **优先联测；直接调用路径最完整。真实端点已测到 OAuth 401，任务未获授权，未执行** |
| **Grok Bot** | 官方支持自定义 MCP；Routine 支持带认证 webhook，并能调用 connected tools。[S2][S3] | 对当前账号测 webhook → 同一个 Routine → Hub MCP 的领取与交付。工具批准是否阻塞也要一起看，不能只测普通聊天 | **重点联测；事件入口明确，组合仍待本项目实测** |
| **ChatGPT Dots** | OpenAI 官方 MCP Events 支持 dots：服务器提供事件，订阅时获得回调，推送后在订阅会话执行指令。Slack/Teams 也有联系入口。[S4][S5] | 优先测 MCP Events，不把 Slack 当唯一方案。需要事件发现、订阅、回调验证/签名、持久化与权限；当前 Hub 没实现事件服务。Dots 账号实际开放资格及后台写工具授权仍需核验 | **重点联测；有官方原生事件方案，不能写“没有任何接口，只能 Slack”** |
| **Manus** | 官方 Agent Tasks API 可创建任务、续聊和取结果；webhook 通知完成或需要输入。[S6] | API 授权与余额；确认调用的是需要的 Agent/项目/技能，不能预设继承网页所有私人状态；真实任务与结果联测 | **直接调用候选；有接口不等于已集成，也不保证订阅包含 API 费用** |
| **WorkBuddy** | 消费产品官方文档有自定义 MCP；定时任务沿用登录身份调用 MCP/连接器。另有云端定时任务，关机仍能运行。[S7][S8] | 本地定时＋自定义 MCP 的组合有文档依据；云端能用哪些自定义连接器、写工具授权能否持续，尚需账号联测。没查到可供 Hub 使用的通用即时触发契约 | **定时参与候选。旧“只能电脑开着跑”“仅企业 MCP”说法过度** |
| **千问办公 QwenWork** | 官方支持自定义远程 HTTP/SSE MCP、请求头和 STDIO；定时任务明确拥有与手动任务相同的 MCP/连接器能力。[S9][S10] | 本地客户端保持运行且不睡眠；每轮消耗 credits。最小间隔和无人工交付要实测；未确认 Hub 可用的即时外部触发入口 | **定时参与候选，官方组合依据充分；不是即时协作** |
| **Kimi Work** | 官方支持个人插件中的 MCP；桌面 Work 有后台定时任务。[S11][S12][S13] | 文档确认两项能力，但本轮未找到明确保证“定时执行继承该个人 MCP 及持续写权限”的说明。需装客户端/登录后组合测试。Kimi Claw、Plus 会话不支持插件，不能混用 | **组合待证候选；旧“只有 Kimi Code 支持 MCP”已过时** |
| **Gemini Tasks** | 自定义应用接受 MCP URL；Tasks 有定时/事件。自定义应用仍限美国成年个人账号、英文，官方明确任何写操作要手动确认。[S14][S15] | Hub 的 claim、submit 都是写操作，不能改标只读来规避确认。Tasks 更广的地区支持不代表自定义 MCP 同样可用 | **半自动。当前不计入全自动接力名单** |
| **Meta Muse** | Connector 平台有 MCP；官方 Gadget SDK 有消息通道，但首次配对有 Linux、蓝牙和手机要求。[S16][S17] | 开发者连接器上架≠普通用户自加。SDK 路径的 Mac 首次使用、后台调用、权限/记忆继承尚未实测 | **无已证实的普通 Mac 用户原生链路。不能断言永远没有，也不能列“已支持”** |
| **豆包工作** | 官方开放平台展示 Skill、Plugin（含 MCP/CLI）、OpenAPI，仍在内测。[S18] | 本轮官方材料未给出普通账号可直接使用的完整自定义 MCP＋后台唤醒＋交付契约。第三方教程不能补成已验证支持 | **等待具体开放文档/账号入口，不列首批承诺** |
| **Microsoft Copilot / Cowork** | 官方已有 Cowork 工作、批准及自动化说明；企业开发资料也有 MCP 插件。[S19][S20] | 不能混同 Copilot Studio 自建 Agent 与用户的个人 Cowork。版本、管理员开放、计划运行时可用插件和交付授权尚未核实 | **企业扩展线索；个人版未确认，旧“完全没有 MCP”结论撤回** |
| **Instinct / AutoGLM** | 本轮没有取得可支撑本产品完整链路的官方契约 | 不把“没找到”写成“没有/永远不支持”；同名 InstinctGTM 等无关产品排除 | **不列支持承诺** |
| **Claude Duet** | 沿用所有者此前“不做”的决定 | 若重新纳入需另核验，不能用 Claude Code 的测试代替 | **本轮不计数** |

### 其他接入对象，同样属于产品范围

| 类别 | 对象 | 核实结论 |
|---|---|---|
| 自部署完整 Agent | **OpenClaw、Hermes** | 官方都有自定义 MCP 与入站 webhook。OpenClaw 的完成回执不含成果正文，仍需 MCP/其他已授权成果出口；Hermes 还需配置 webhook 路由工具范围。需现成实例及模型服务，不是免费多出两个消费账号。[S21]—[S24] |
| 本地代码 Agent | **Claude Code、Codex、Gemini CLI** | 可以启动完整 CLI；但不同批准机制会影响自动交付。Claude 提交了真实 Claude Code 两成员测试；本轮 Codex 采用薄执行器后也真实交付成功，原始直领方式的批准阻塞同时保留记录。Gemini CLI 尚未实测。不能将三个 CLI 等同三家个人云 Agent |
| 云端代码 Agent | **Devin、Cursor Cloud Agents、Jules** | 官方有创建任务/会话接口，具有开发方向价值；API 版本、仓库授权与费用独立处理。未做账号任务测试，不计首批通用消费 Agent。[S25]—[S27] |

## 对旧清单与 Issue 结论的更正

1. `docs/支持的Agent.md` 的“第一档能接”应理解为历史调研线索，不能当当前验收白名单。
2. Dots 不应只围绕 Slack 设计：官方已有适用于 dots 的 MCP Events，协议要求 MCP 2.0 / `2026-07-28`。现有库版本不是主要障碍，Hub 缺的是事件能力与订阅处理。[S4]
3. WorkBuddy 已有消费产品的自定义 MCP 和官方定时说明，且有云任务；千问的自定义 MCP 也已有官方依据。Kimi Web/Work 插件支持现状也应更新。
4. Gemini 的“Tasks 地区变广”不能覆盖掉自定义应用的美国/英文及逐次写确认限制。它当前不符合我们的无人值守要求。
5. Muse 的“未找到普通用户原生链路”不能写成“绝对没有原生通道”；SDK 是存在但尚不适合直接承诺的候选。
6. “至少 12 家原生支持、通道稳”超出证据。应分别报候选数、真实完成数、待授权数，CLI/代码产品与通用个人 Agent 分开。

## 固定下来的开发取舍与验收

**先做原生接入联测，不为了凑平台数扩张网页执行，不先做大面积 UI/运行层重写。** 没有原生入口且确有需求的平台，浏览器可作为独立方式另行适配验收。一个成员验收前只显示候选，不点亮就绪。认证及参数由产品维护，只有必要的本人登录/授权交给用户。自定义 API 的鉴权、输入、进度和成果格式不同，仍需满足适配契约；不是任意 URL 填入即可接通。

联测优先级：Perplexity 直接调用 → Grok Routine＋MCP → Dots Events；WorkBuddy、千问单列定时能力，Kimi 单列组合测试。三个即时入口中任何一个不成立，记录具体失败，不自动换网页来凑通过。

每家都用同一项真实任务验：取得三条带原始链接的资料，交给另一种产品自动整理，完整正文进入 Hub。至少连续三次，并包含同会话补充、重复通知不重复执行、超时后查询原任务、需要批准时明确暂停。记录创建、受理、领取、交付、下游开工各时间与人工介入次数。**连续三次只是接入验收，不是长期稳定率证明。**

需要的账号条件直接列明：Perplexity OAuth 与可用 credits；Grok 当前账号的自定义 MCP/Routine 授权；Dots 的实际开放资格与自定义插件/事件权限；桌面两家的登录客户端。没完成这些条件就保持“未联测”，不让用户拿自己的正式任务猜能否工作。

产品范围按所有者最新决定统一为 Agent 协作台。当前足以确定的是**多家原生入口真实存在，已有完整 CLI 的真实交付证据**；尚不足以确定的是**所有候选已经完成适配、跨平台自动接力或长期稳定性验收**。
