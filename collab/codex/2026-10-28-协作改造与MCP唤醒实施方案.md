# Agent Hub：协作改造与 MCP＋原生唤醒实施方案

作者：**Codex**。日期：2026-10-28。对应 [Issue #1](https://github.com/duolaAmengweb3/agent-hub/issues/1)。

> **最终研究取舍（2026-10-28）：以第 11 节为准。** 产品主攻 Personal Agent 跨生态协作；技术接口兼容其他 Agent，但不以接入全部 Agent、18 个候选或编程团队编排为首版目标。首版接入目标为 Grok Bot、Muse、ChatGPT Dots、Perplexity Computer，这是研发与验收范围，不是已支持名单。采用原 Agent 的原生连接、通知和交付契约，Hub 不再默认托管网页登录。以下第 1–10 节保留技术讨论依据，其中旧的“全 Agent”“先双 CLI/Grok→CLI”优先级由第 11 节替代。

> **所有者最新测试限制：** 云端 VPS 的订阅 Claude Code 不使用、不连接、不修改。Codex 保留原订阅与模型/provider。下文 Claude Code 的未来测试仅可在本地独立配置、使用另行提供的测试模型 API；不得拿原订阅实例兜底，测试结论须注明实际模型。跨平台首次验收可以用云端原 Agent → Codex，不能为凑双 CLI 接力动用被排除的实例。当前没有专用替代模型 API，不安排这条扩展测试，也不阻塞 Personal Agent 主线。

本文是实施方案，代码基线为 `c618342`；当前 `product-docs` 的后续提交只增加了 Claude、Gemini 协作文档。本文不代表下列改造已完成。

本次修订吸收 [Claude 对本方案的评审](https://github.com/duolaAmengweb3/agent-hub/issues/1#issuecomment-6466583529) 与 [Gemini 的回复](https://github.com/duolaAmengweb3/agent-hub/issues/1#issuecomment-6466592454)：早期首次接力曾安排为 **Grok → Codex / Claude Code**，现由第 11 节的 Personal Agent 范围替代；N1 的 Routine＋自定义 MCP 组合必须先核实，不等待 Muse 才验证产品价值。

## 1. 结论与最新取舍

产品目标：**用户交代一个目标，几位原 Agent 自动分工、执行、交接，在同一个工作空间交付共同成果。**

- 保留 B 版左侧对话、右侧成果的布局，默认工作对象改为团队目标；单成员工作仍可用。
- 统一任务交接协议、状态机与成果存储。MCP 负责领任务、读资料、交结果；平台原生入口负责让 Agent 开工。
- **每个成员只有一条生效通道。** 更好的原生通道通过真实验收后，替换同平台的旧浏览器执行逻辑；旧代码留在 Git 历史，新版本不长期运行双轨，也不自动回退到网页重发任务。
- 首版固定实现 Grok Bot 的 MCP＋Routine、Muse 的 REST connector＋hook/定时、ChatGPT Dots 的插件＋MCP Events，以及 Perplexity Computer 官方 MCP；不得以 CLI 或网页成功替代这四家的原生验收。
- 没有合格原生入口的平台，若确有需求可按浏览器适配独立验收；未验收保持待验证，不为了凑平台数扩充网页适配，不在原生通道故障时静默切到浏览器。现有账号身份、历史成果和本地登录资料保留。

已读 Claude 和 Gemini 的新增评审。采纳按动作管理 pending、请求限时、异步操作和独立格式化的建议；不采用“有输入框就等于已登录”的判定，也不沿用尚无本项目测量依据的“CLI 3～5 秒、成功率 99% 以上”说法。CLI、API 和网页的稳定性由同一真实任务验收，不预先写结论；纯模型 SDK 请求不能冒充原 Agent。

## 2. MCP＋唤醒可不可行：本轮查证

| 对象 | 查到的事实 | 本项目的结论 |
|---|---|---|
| MCP 协议 | 官方定位是应用与工具、上下文之间的协议；不规定宿主怎样启动、调度模型 | MCP 工具接通后还需要独立的开工入口。工具列表变化通知不能当成宿主已经启动一个任务。[S1] |
| Grok Bot | 官方分别明确可添加自定义 MCP、Routine 可由 webhook 触发；HTTP 200 仅表示接收并启动，不表示做完。尚未找到明确说明 Routine 运行时能调用用户自定义 MCP 的依据 | **两项能力分别有依据，组合链路尚待验证。** N1 必须先在当前账号实测这一个交点，不能先假设能组合，再投入全部架构改造。[S2][S3] |
| Cursor Automations | 官方同时提供 webhook 触发和 MCP 工具配置 | 是另一份官方可行实例；Cursor Cloud Agent 和个人 Grok Bot 的账号、运行、计费不能混写。[S4] |
| Muse | 官方 Connector 文档已提及 API/MCP；非敏感工具允许用户选择 Always allow；官方 Gadget SDK 提供程序向 Muse 发消息的入口，但初始配对要求 Linux、BLE 和手机 App | 不能继续笼统写“官方完全没提 MCP”。但 Connector 平台文档不等于当前消费账号已有通用配置入口，也不等于能被即时唤醒。MCP、原生消息触发、原会话和完整工具能力必须联测。[S5][S6] |
| Claude Code / Codex | 官方提供非交互和会话能力；已有 Codex 完整 CLI＋薄执行器单任务真实交付，以及 Claude 报告的两个 Claude Code 人工依次启动接力记录 | 由本地薄执行器接同一个 Hub 协议，不替换成裸模型 API。单成员或手动启动的记录不等于产品已经实现自动接力，详情见接入核验。 |

**修正初稿的“平台能力上成立”：接口分别存在，还不能确认 Routine 内的组合可行。** 当前证据只证明 Grok/Muse 的网页路径分别可用，原生 Routine＋MCP 和跨平台接力仍未验收。

纯云端的 MCP＋原生唤醒链路可以在 Mac 关机后继续；一旦某一步使用本地 CLI、SDK 服务或本机文件，就必须显示“等待这台电脑上线”。不把某一条云端链路的能力推广到整个团队。

## 3. 用户最终怎么用

1. 添加成员、给备注名称，完成平台要求的一次性授权。产品生成连接信息和专用 Routine 的配置引导，普通页面不要求用户理解 MCP、Bearer 或进程参数。
2. 左侧输入“找三个 AI 热点并写成推文草稿”，默认交给团队。由真实牵头 Agent 结合已验证的成员能力拟分工。
3. 右侧展示每一步做什么、谁负责、为什么、交付物及确认关卡；用户可修改后执行。
4. 工作台自动唤醒第一位成员；它交回合格成果后，自动唤醒下一位。对话中出现有事实依据的交接卡片。
5. 右侧形成按步骤标注成员与来源的共同成果；人工修改自动保存，与原始交付分开。
6. 用户可写“@Grok 替换第二条来源”或选中某段说“换个角度”。只修改对应部分；存在下游依赖时说明哪些部分需要重做，不覆盖无关人工内容。

首次授权可能包括添加连接器、允许任务领取/回传、启用原生 Routine。平台没有配置 API 时，需要用户在官方页面完成对应授权步骤，不能承诺只登录网页就自动获得全部权限。非敏感工具可在平台允许时一次授权；强制逐次确认的操作仍显示等待本人处理。

## 4. 一个内核、一条领取规则

```text
目标 → 真实分工方案 → 用户确认 → 步骤就绪并持久化
                               ↓
                        原生唤醒执行侧
                               ↓
              MCP：list_my_work → claim → read_artifact
                               ↓
                    原 Agent 使用自己的工具执行
                               ↓
              MCP：report_progress / submit / report_failure
                               ↓
                  校验本次成果 → 下一步就绪 → 共同成果
```

**统一由执行侧领取，Hub 调度器不预先领取。**

- Grok：原 Bot 是执行侧，收到 Routine 通知后通过 MCP 领取。
- CLI：薄执行器是该成员的执行侧，通过同一个 MCP 接口领取，再启动 CLI；CLI 专注执行，不再第二次领取。桥接器保留 lease、关联进程和结果，将交付提交回同一接口。
- 未来 SDK/API/A2A：遵守相同领取、版本和交付规则；有对应账号和真实验收才登记为支持。

这是对现有实现的必要修改：`local/runner.mjs` 的 `execute()` 目前先领取再触发 webhook，而 `connector` 成员只等待自己领取却没有主动唤醒。统一后，Hub 负责就绪与唤醒，领取和提交只有执行侧一个入口，避免 Hub 与 Agent 抢同一步。

保留已有 `task / steps / attempts / artifacts`、成员凭证、原子 claim、版本校验、前序全文与来源。新增进度/失败回传工具时必须绑定当前成员、attempt、lease 和版本。声明“完成了”或返回进程退出码 0，均不能代替成果验收。

同一 attempt 重复提交同一成果应返回已保存的 artifact，不重复生成交付；正文冲突或旧版本提交则明确拒绝，不能覆盖已保存成果。领取冲突与提交去重都由同一控制面处理，各通道不另做一套任务状态。

## 5. 原生唤醒怎样做稳

1. **先落任务，再发通知。** 步骤进入 ready 时，同时持久化一条 wake 记录；事件或事务没有提交成功就不外发。
2. 先复用现有 Cloudflare Worker、D1 和定时检查：提交后立即尝试派送，定时检查补偿未送达记录。实现前核验当前 D1 CAS 批处理，保证状态与通知记录一起提交，无需先另建一套调度服务。
3. 通知包含成员、工作、步骤、版本和 delivery ID；完整资料由已授权成员通过 MCP 拉取。Webhook 密钥保留在受保护配置，不能进入正文、仓库或普通日志。
4. webhook HTTP 200 后显示“已通知，等待领取”；看到合法 claim 才显示“已开始”；收到合法 submit 并通过门槛后才显示“已交付”。
5. 重复通知由原子 claim 防止重复领取。供应商未承诺启动幂等时，不宣称它只会启动一个计费 run；控制重复通知也关系到成本。
6. 明确未送达可按 Retry-After 等规则限次重试。接收结果不明先检查原 run 与 Hub 的领取记录，不换通道重新派发。
7. 超时先对同一个 run 做有限次数的后台复查，保留已完成步骤；确认无法自动恢复才给出一个明确处理动作。不得把“重新读取结果”实现为“重新执行任务”。
8. 每次唤醒只处理指派给该成员的工作，空队列直接结束。默认使用事件触发；定时轮询只给没有即时入口的平台，界面注明延迟，不宣传成实时。

成员能力登记至少包含：原生启动、结果关联、后台执行、工具批准、进度查询、取消能力、会话保持、共享资源范围及最后验证时间。取消只上报该通道实际能确认的程度。多个同类成员不被锁定为 Grok/Muse 两个品牌；同账号共享云电脑或文件时按实际资源限制并发。

## 7. 新通道替换旧通道：不长期维护两个

- 先用独立的接入验证任务测试新通道，不能把运行中的业务任务同时交给新旧通道。
- 验证保留原 Agent 的工具、记忆和已连接应用；只得到一段模型回答不能通过。
- 当前业务步骤结束并确认没有不明派发后，原子切换成员的 active transport；账号 ID、成员 ID、历史成果和本地资料绑定保持。
- 新通道以原生授权和实际 MCP 往返确认可用性，不继续为被替换的 Grok 网页增加 DOM 登录检测；迁移前的资料保护仍保留。
- 切换后不再启动该成员的旧专用浏览器。删除同平台网页发送/抓取执行分支及相关自动 fallback；旧实现只保留在 Git 历史。
- 故障时恢复新通道的原任务，不能背地里换旧通道再做一遍。新通道确实不可用则明确显示暂停或需要处理。
- Muse 的原生通道若尚未达标，该成员的迁移不能标完成。不得为满足“三次跨平台”偷偷改用浏览器、换成 Muse Code 或普通模型后仍写原生 Muse。

## 8. 一份完整交付的验收

下表是完成条件，开发按依赖顺序推进，不把其中某一步当成完整交付。

N1 先做组合验证：Hub 创建就绪的独立验证步骤 → webhook 唤醒指定 Routine → Routine 真实调用同一个自定义 MCP 的 `hello → list_my_work → claim → submit` → Hub 校验本次身份和成果。只看到 webhook 200、普通聊天能用工具，或者只运行 hello，都不能通过。随后原生路径连续三次才完成 N1。验证投入先设半个工作日上限，属于工作量预算，不能当成“半天一定通过”的承诺；有平台授权阻塞时列明具体入口与缺少的权限，不空转等待。

| 编号 | 必须拿出的实际结果 |
|---|---|
| B1 | 挂起 60 秒的隔离回归；无全局锁；超时与迟到响应均不重复派发；文稿编辑不被影响 |
| B2 | 真实账号授权/完成登录后自动核验。30 秒内给出准确阶段反馈；平台任务若更久，继续显示真实进度，不强行在 30 秒内声称可用 |
| N1 | Grok 经原生 webhook 唤醒，通过 MCP 领取、读取、提交，连续三次；全过程不经过网页发送或页面抓取 |
| C1–C2 | **Grok Bot ↔ Muse** 自动接力、共同成果及定向修改，纳入 Dots 事件订阅/原生交付和 Perplexity Computer 官方任务/资产出口；按第 11 节十个目标与故障场景验收，保存实际输入、会话/run 关联、耗时、人工介入与完整产物。四家原生联测均不能由网页或 CLI 模型回答替代 |
| C3–C4 | 执行前换成员、增加确认关卡真实生效；@ 指定成员只改目标段落；原有人工稿与无关成果保留 |
| C5–C6 | 注入一步超时或断网，恢复原 run 后继续下游；单成员工作也通过；重复 webhook、旧版本回执和成员离线有明确行为 |
| U1 | Grok、Muse、Dots、Perplexity 各自原生交付和跨产品接力通过；正文、文件、原工具执行与后续修改均有真实证据；连续三次只是基本可重复门槛 |
| U2 | 已完成平台授权、支持既定远程 MCP 和唤醒契约的新成员，仅配置即可接入；5 分钟从授权就绪后计，不把第三方审批算成已完成 |
| U3–U4 | 原生通道通过后成为唯一生效通道；同平台旧网页执行停用并从新发行移除；单成员故障不锁住其他成员 |
| 发行 | 工程检查及真实平台验收分开记录；本机实际启用、完整退出重开后的资料/文稿保留通过；代码 PR 审阅后合并，文档与 Issue 对齐 |

连续三次是基本可重复验收，不是长期稳定率的统计证明。记录创建、唤醒受理、领取、提交、下游开始时间，并列出需人工处理的次数；不能只给“成功”截图。

## 9. 执行顺序与交付记录

依赖顺序：先验证首版四家的原生完整契约，再完成统一领取、持久通知与文件交接、B 版共同成果与定向修改、确认关卡和恢复。B1/B2/O3 的可控修复不依赖真实账号验证；格式化单独提交。完整交付以第 11 节为准，不将中间接通当成产品完成。

任何原生组合失败都保留具体证据，不回退网页或替换产品来凑成功；同一平台只有一个生效执行通道。当前账号、身份与历史资料不动。编程 CLI/A2A 保留协议兼容，不占首版主要开发资源。

已有 Cloudflare Worker 提供公网 HTTPS MCP，Grok Routine 的 webhook 也是平台提供的地址。这条纯云链路先复用现有入口，不能预设必须新建隧道或暴露用户的本地客户端；本地 CLI 桥接器主动向云端领取和回传即可。

Hub 的排队、唤醒和交接由程序完成，不额外养一个大模型反复轮询。需要拟方案时使用用户已有的牵头 Agent；运行仍会消耗对应平台的额度，不能宣传成零成本。按模型/API 计费的其他产品不能套用为 Grok 订阅包含的额度。

只改文档直接提交 `product-docs`；代码改动走 PR。后续在 Issue 用 B/C/U 编号、提交号和真实结果汇报，未通过的项目保持未完成。本文仅提交方案，本轮不更改运行中账号、代理或客户端。

## 11. 最终取舍：Personal Agent 协作，先拆实现，再确定竞争办法

### 11.1 定位与范围已经确定

**产品：用户已经在用的个人 Agent，在保留各自的模型、工具、授权和运行环境的情况下，共同完成一件工作。** Hub 负责目标、交接、进度、共同成果和人工补充。

目标用户是已经同时使用多家个人助手的个人与小团队。先服务研究、写作、文档/文件和网页成果等工作，不限定为内容运营，也不为一般用户强行增加多个 Agent。用户可指定成员；需要拟分工时交给一位真实牵头 Agent。单成员能完成的任务可以直接完成。成员绑定仍只填备注，不增加岗位配置。

技术层继续按接入契约扩展，Codex 等可作为已有执行成员兼容；市场与首版开发资源聚焦个人助手。编程 CLI 和企业 A2A 不作为首版覆盖数量目标，也不依赖 VPS Claude 或新的替代模型 API 才能继续研究/开发本主线。

首版原生适配目标固定为四种实际个人产品：

| 产品 | 确定采用的接入方法 | 发布前须完成的实际验证 |
|---|---|---|
| Grok Bot | 在原 Bot 授权 Hub MCP，配置专用 Routine；Hub 持久化任务后调用 webhook，由原 Bot 领取、执行、提交 | 当前账号的 Routine 必须能调用该连接器；保存 Bot/run 关联；原工具执行、完整成果和后续修改都真实往返 |
| Muse | 在原 Muse 中创建 REST connector；hook 读取轻量待办信号，有任务才唤醒原 Muse；平台只具备定时时，显示真实等待，接入时选定一种消费入口 | Mac 消费产品中的连接器、hook/定时、正文与文件真实往返；不能用自建模型 consumer 或 Muse Code 替代；同一资料版本可继续修改 |
| ChatGPT Dots | 用户连接 Hub 插件，Dot 订阅指定成员的待办事件；Hub 经 MCP Events 签名回调通知，Dot 使用原权限调用 Hub 工具领取、执行、提交 | 实际账号开放 Dots/插件/事件权限；订阅、通知、后台工具、正文/文件、补充、重启续订与去重完整往返；不以 webhook 2xx 或普通聊天回复代替 |
| Perplexity Computer | Hub 作为官方 Computer MCP 的客户端，经用户 OAuth 委派任务；保留 thread_id，以官方读取/附件/确认工具继续原任务 | 原已连接应用、进度、正文/文件、提问/确认和同 thread 补充；timeout 后读取原任务，不重发新消息 |

Grok、Dots 和 Perplexity 路线有正式文档；Muse 路线有具体开源实现及作者实测。**四者本项目原生联测均未完成。研究决定采用路线，不提前宣称产品接通。** Dots 此前放在扩展表是收窄范围的选择，不是能力不足；现按所有者要求纳入首版完整交付。

| 参考对象 | 已核查到的实现 | 本项目取舍 |
|---|---|---|
| [botline](https://github.com/sabotage-dev/botline) | Worker/D1 邮箱；REST 与 MCP 共用 store；通知与消息分离；门铃原子 lease、忙碌合并、退避和持久重试；Muse 轻量信号 hook | 采用原 Agent 自接入、先持久化后唤醒、廉价探测和忙碌合并。复用设计/许可允许的部件，不再部署第二套邮箱与任务数据库；保留 Hub 自己唯一的任务真相 |
| [Agents Slack Bridge](https://github.com/Ares-X/Agents-Slack-Bridge) | Socket Mode → 持久队列 → 原 hook/side chat → 持久发送/ACK；区分未发送、发送不确定、已发送未确认；已演示讨论、修订、共同成果 | 采用发送状态与恢复语义；不强制用户再注册 Slack、创建 App 或维护 Python 桥；不将其默认 echo consumer 当作原 Agent 接入 |

### 11.3 实现选择：一个协作内核，原环境执行

```text
用户目标/补充 → 真实牵头 Agent 或用户分工 → 版本化任务与交付标准
    → 原子记录步骤 + 待通知记录 → 平台适配器通知/调用原 Agent
    → 原 Agent 领取/执行 → 回传进度、正文与文件 → 验证本轮身份与版本
    → 下游接力 → 可编辑共同成果 → 补充回到关联的原任务
```

- **控制面：** 复用现有 Cloudflare Worker、D1 与业务状态规则，增加任务通知 outbox；真实文件进入 R2。桌面仍是用户的本地工作入口，云端负责已授权的纯云 Agent 交接。涉及本地执行/文件时明确等待本机上线。
- **存储：** `cloud/store.ts` 当前每次重写完整 workspace JSON，且有 1.5 MB 容量限制；完整产品要将任务、尝试、通知、成果索引拆成独立记录，正文与文件按实际大小存储。保留现有 reducer 的身份、领取与版本约束，迁移保留账号 ID、任务与全部历史；不能只在旧 JSON 中无限加事件。
- **任务与通知分开：** 已通知、已领取、执行中、待本人处理、已交付分开。门铃 HTTP 200、已读和 ACK 都不是任务完成。读取后崩溃须保留未完成的 attempt，按原 run 查询/恢复，不能靠未读邮箱再次碰运气。
- **单一执行通道：** 每位成员只有一个 active transport；Muse hook/定时是同一原环境消费规则的能力选择，不双开重复执行；故障不切浏览器重发。旧网页登录资料原样保留，原生通过后停用同平台网页执行。
- **会话与记忆：** 保存平台实际支持的 Bot/thread/session/run 关联。原 Agent 保留原记忆与授权；Hub 共享指定任务的材料，不复制全部私人记忆。平台若每次通知开新 run，则传入当前任务全文与成果版本，不能把它假称为续接原聊天。
- **正文和文件：** 必须取回真实字节、来源与版本；只拿临时链接、文件名或“已生成”不能完成交付。MCP 小文件、REST/官方资产工具按平台支持选择；Muse 的文件能力尚需实测，不能因为 botline 服务端有上传端点就判已支持。
- **修改和确认：** 保留 B 版对话＋成果空间。右侧人工改稿生成 revision，补充携带该版本；旧结果不得覆盖新稿。现有 `shared/workspace.mjs` 把确认关卡写成 false，必须一并修复；平台强制本人确认时在同任务接续，不伪装通过。
- **配置体验：** 每个平台生成适配指令，由原 Agent 配置连接器/任务/技能；用户仅处理真实授权与安全凭证输入。Hub 自动测试实际领取、读取和提交，不让用户逐个手工确认内部状态。平台没有安装 API 时不能承诺零点击授权。
- **成本：** 排队、探测、去重和版本校验用程序；空队列不反复启动模型。规划与写作沿用用户选定的原 Agent，Hub 不强制额外配置一套模型 API；原平台运行仍计入自己的额度。

### 11.4 怎么胜过他们：确定竞争目标，不预先伪造领先

**竞争定位：把现有个人助手的协作能力做成普通用户能持续使用的完整工作产品。** 新意不足以独占市场，争取以接入、任务完成、修改和恢复的实际完成度胜出。

| 竞争目标 | 具体产品实现 | 比较办法 |
|---|---|---|
| 接入更省事 | 平台预设、生成配置指令、安全授权入口、自动真实往返核验 | 同一测试者接同一组 Agent，记录手填配置项、人工操作数、授权与首个成果的用时；对比 botline/crosswalk 的真实流程，不预设其步骤更多 |
| 更少当中间人 | 同目标自动交接，提问集中，停在具体阻塞，必要时一键继续 | 统计搬材料、催进度、重新分配、重复说明的次数；平台必要的授权/确认另计，不假装能消除 |
| 成果能继续用 | 正文、来源、真实文件、人工稿、修订与定向补充关联 | 检验最终文件可打开，来源对应，人工修改保留，下一位读到正确版本；不能只比较聊天是否热闹 |
| 失败后能继续 | 持久任务、outbox、幂等提交、原 run 查询、发送不确定核对 | 检验领取后中断、重复通知、临时断网和旧回执；不丢成果，不重复做有副作用的操作 |
| 不浪费额度 | 轻量 signal、忙碌合并、限次通知、任务结束停机 | 同 Agent/模型/输入条件下，记录空模型运行、通知次数、重复运行和可取得的实际用量；没有用量接口就标不可得，不虚构费用 |

比较使用同一组实际账号、任务和输入，按产品推荐方式正常配置；记录版本、人工协助和差异。基础集合固定为 10 个目标：资料研究 3 个、文稿/文件交付 3 个、已有成果定向修改 3 个、自由组合 1 个。另单列故障场景。单个 Agent 可完成的任务也保留为基线，不强制为了演示协作增加席位。

“更好”的最低证据：在至少一个核心目标上有可复现优势，且交付正确性、授权边界和原能力没有退步；按任务逐项公布记录，不用十个样本声称市场胜率或长期 99% 稳定。本轮没有执行上述比较，**尚不能宣称已经胜过竞品**。

### 11.5 对现有项目的明确处理

1. 保留：成员身份、原子领取/CAS、attempt/lease/版本、前序成果、右侧可编辑工作稿，以及已有账号与浏览器持久资料。
2. 替换：以受控浏览器登录/DOM 抓取作为主要执行方式；本地 runner 先 claim 后触发、而 Agent 又要领任务的双责任设计。每个适配器指定一个领取方。
3. 补齐：原生安装/配置核验、持久通知与忙碌重试、真实文件、原平台会话关联、确认关卡、版本化修改、可恢复的跨平台接力。
4. 停止扩张：为凑 18 个平台继续写适配、通用企业编排、强制 Slack、新养一个模型充当轮询调度器，以及无真实证据的 ready 状态。
5. 执行按依赖关系安排，交付是一份完整产品；首版四家均须按真实能力验收，不用双 CLI 成功替代 Personal Agent 验收。代码走 PR，所有者已排除的云端 Claude 实例不触碰。

**研究结论：定位与实现取舍已经可以收口，按上述方向继续。** 文档/源码研究与方案选择已完成；独立复现、改造与同任务胜出证据属于后续实际工作，当前没有冒充完成。

### 11.6 Dots 纳入首版：采用官方插件事件路线

官方 [MCP Events](https://developers.openai.com/plugins/build/mcp-events) 明确适用于 dots；[Dots 产品说明](https://learn.chatgpt.com/docs/dots) 说明原插件、后台任务与云电脑的能力。现有 Hub 有工具读写，但尚无本项目的事件订阅/发送实现，需补齐：

1. Hub 插件同一 MCP 端点公布待办事件及成员过滤，用户让 Dot 订阅；采用 MCP 2.0/2026-07-28 的事件发现、订阅、取消与刷新。
2. D1 持久化订阅归属、过滤、回调、到期时间及受保护的签名信息；完成官方要求的回调验证。订阅与事件不替代任务本身。
3. 任务/outbox 提交后发送匹配事件，固定事件 ID 用于重试；2xx 仅记通知受理。原 Dot 通过 Hub 工具实际领取和交付，走统一的 attempt/版本/成果校验。
4. 通知不载入完整私密材料，由工具读取任务；后台权限和必要批准仍由原平台执行。取消/过期/撤权后停发；刷新、密钥轮换、重复/乱序与重启恢复进入验收。
5. 不要求用户额外建立 Slack，不使用 GPT 模型 API 代替 Dot，也不自动切网页或其他渠道重发。Dot 回传正文、真实文件和补充修改均须本项目联测。

技术架构与四个平台的接法均已确定，下一步是实现和真实验收；不再因 Dots 需要事件适配就将其排除首版。此次只更新文档，没有创建 Dot、订阅事件或启动用户任务。
