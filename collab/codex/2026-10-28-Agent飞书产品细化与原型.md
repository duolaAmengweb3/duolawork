依据：[Claude 与所有者确认的新方向](../claude/2026-10-28-产品方向-Agent的飞书.md)、[Issue 最新设计](https://github.com/duolaAmengweb3/agent-hub/issues/1#issuecomment-6470702377)、当前 AGENTS.md 顶部新规则。

**本次采用全新的“配方 → 项目群 → 组织积累”方案。旧 B 版布局、单 Agent 工作台和旧成员配置限制不再作为设计依据。原账号资料、测试范围和真实验收要求继续有效。**

## 1. 产品与首日体验

用户打开后，先选“每日 X 内容包”，用已经在用的个人 Agent 组建一个项目群。群里能看到每位成员交了什么、交给了谁；成果在同一群中编辑、退回和反馈。跑过几轮后，采纳记录与经批准的知识使下一轮有依据地改善。

首版只提供一个可用配方，不做一堆空模板。主题可以是 AI、Web3 或用户自己的领域；默认示例为 AI 工具与实践，不把产品定位锁成 AI 博主工具。

第一次使用顺序：
1. 从配方预览看懂成品：5 个候选选题、3 条成稿，每条有出处。
2. 选择现有成员承担发现、查证、写稿。平台是预设，职责属于本项目的分工；一个具备能力的 Agent 可以兼任，不强迫用户买齐多个订阅。
3. 缺少权限时只引导处理该连接；内部配置与验证由产品完成。没有通过真实能力验证的成员不能开始任务。
4. 确认主题、成员和首次试跑。先创建项目群再运行，重复点击只创建一次。
5. 在群内看交接；发现方向不对时发消息或 @指定成员补充。
6. 在成果区改稿、让原成员继续改，最后标记怎么使用了原稿。默认不发布到 X。
7. 满意后可开启每天自动运行。每个项目独立保存时区与节奏；原型示例为北京时间 08:00。

用户无需先建公司、填 OKR、给每个 Agent 设永久职位，也不需要先学 MCP。首版兼容目标仍为 Grok Bot、Muse、Dots、Perplexity Computer；每个配方使用其中适合的成员，而不是强制四家同场。

2026-10-29 按所有者“主要就是不好看”的反馈重做视觉：暖灰底、白色工作面、克制的深绿强调；全局导航和项目列表合为同一侧栏。中间群聊、右侧纸张式成果面板，统一字号与间距，交接卡片收紧。专注审核时用稿件目录替换群聊，宽幅正文居中；窄屏切换资料/聊天。React/Tiptap 与示例数据持久化逻辑保留，仍明确标记设计预览，未把示例接入云端冒充真实任务。

导航不重复堆放项目入口，进度只保留必要交接状态。成员名称与平台身份明确；原型图形为示意标识。未实现的完整 OKR 不放空入口。

## 3. 配方怎么变成可运行项目

配方是一份有版本的工作定义：输入、能力需求、步骤依赖、交付标准、触发节奏、初始项目知识。角色称谓可以存在，但成员仍是原产品的真实个人 Agent，不凭空创建新的“研究员分身”。

“每日 X 内容包”默认流程：
- 发现：收集 5 个有理由、有链接的选题，标出原发布/更新与发现时间。
- 查证：读取原始资料，标出能支持、存疑或缺失的事实；不能把同一篇转述当多个独立来源。
- 写稿：交付 3 条不同切角的成稿，关联选题与核验来源，附可编辑正文。
- 审核：用户改稿、补充要求并反馈。成果交付与用户审核是不同状态。

输入只要求“想关注什么”和可用成员；受众、文风与禁区有默认模板，可以在群里逐步补充。优先选择已验证并有相关权限的现有成员；缺了某家平台先考虑现有成员能否承担，不以品牌强制订阅。缺少必要数据访问能力则明确停在该授权步骤。

创建后的群保存配方快照。以后升级配方不能静默改已有群；用户批准后才升级并保留旧版本。首次试跑与开启每日任务分开确认，避免点击一次就产生长期后台消耗。

时间与频次以实际时区保存。热点模板默认优先最近 48 小时，旧资料有新变化时标明变化时间；无足够素材时交付数量缺口及原因，不把旧内容改日期补满。图中的资讯与出处只是排版示例，不是本轮新闻推荐。

## 4. 项目群：对话可见，执行由系统推进

群消息有五种：用户要求、Agent 工作摘要、系统交接、提问/授权请求、成果卡片。每条保留作者和所属本次运行；不把系统消息伪装成 Agent 发言，不展示虚构思考。

- 交接消息明确“谁 → 谁、交了什么、哪份版本”，可展开读材料；通知成功与下一位实际领取分开。
- @某位成员形成定向工作；一般补充由本项目牵头成员理解并提出影响范围。不能每条群消息都广播给所有 Agent。
- 用户在执行中补充时，记录到原运行；在安全边界消费，不取消已领取工作、重复启动或丢失补充。
- 重做一条稿件只重做依赖步骤，不默认全配方再跑。全量“再运行”创建新的运行记录，先展示影响与确认。
- 资料不足、等待平台本人操作、原成员忙碌分别给出明确下一步；所有项目不因一个按钮挂起而全局锁死。
- 运行中的分工修改在本次安全边界或下一次运行生效，界面说明生效时点。

统一状态：待开始 → 已通知 → 已领取 → 执行中 → 已交付/需要你处理/失败。用户侧可简化显示，但后台证据不能混。群内的交接状态按实际回执推进，不在三处重复同一进度。没有实测依据不显示预计分钟数。

## 5. 成果：原交付、人工稿与补充相连

“内容包”包含单独的选题、单独的 3 条稿件和来源索引。每份可评价的成稿都有稳定 ID、作者、步骤、原交付版本、用户工作稿和修订记录；不是把整包当一个采纳样本。

用户直接修改工作稿时自动保存。Agent 后续交付不能覆盖更新的人工稿；要求修改时送出用户选定的稿件、当前版本、项目规则和补充。发生冲突保留两个版本并让用户合并。

- 点击来源能打开真实原文；正文引用与来源对应，长文本不能悄悄截断。
- 文件交付必须拿到可打开的实际文件及来源关联；文件名或临时链接不能冒充完成。
- “交给 Agent 继续改”先展示目标成员、目标稿与改动范围；按实际能力继续原会话或关联任务。
- 复制、导出是取用信号，不自动等于发布或原稿采纳。发布不在首版默认行为中。
- 本地保存与已交回云端分别有回执，不能用一个“已保存”掩盖尚未同步。

## 6. 采纳率：先把事件与分母做准

成果底部简化为“采用 / 弃用”，再次点击当前选择可撤销评价。系统根据用户事件计算，不读取 Agent 自报满意度。

本版“采用率”＝采用稿件数 ÷ 已反馈稿件数；未反馈单列。改选只更新同一稿件，不重复计数。三条成稿分别评价，复制和导出不改变评价。

这与上一版“直接使用/小改才算原稿采纳”的口径不同，不能把两个指标混成同一历史曲线。当前二选一能证明用户愿意使用成果，不能证明原稿无需大改。原稿与工作稿差异、交回次数另行保留；可辅助显示修改量，但不能只凭字数变化自动断言质量。未来若需要“原稿质量”指标，需补充有依据且允许用户修正的判定，本版不虚报。

- 项目采纳率反映最终成稿；成员指标只归属实际交付相应成果的成员。
- 不能因最终文风不合适，就给提供了正确来源的研究 Agent 记不采纳。素材是否被下游选用另算，不与成稿采纳率混成排行榜。
- 按时率按开始前承诺的截止时间计算，等待本人授权另显示；没设置截止时间不编按时率。
- 成本只显示可取得的实际用量；拿不到的标“未知”，可以另列确认的执行次数。
- 所有比例旁边有样本数、时间范围与口径。样本不足时显示“样本不足”，不据此建议换人。
- 首版记录返工、失败及各阶段时间，为后续建议留证据，不让 Agent 决定自己的评分。

## 7. 项目知识与组织积累

各原 Agent 已有记忆与环境，产品不会假设每次都从零开始。共享知识负责跨 Agent 对齐，不替代原记忆，也不自动共享用户所有私人上下文。

知识分三类：
1. 用户资料：用户写入或上传，按全局/项目选择范围。
2. 成果归档：交付与来源自动归档，标注作者和时间；归档不等于变成必须遵守的规则。
3. 候选规则：从改稿差异提出建议，附具体差异和来源。用户批准后才加入项目规则；升级为全局规则需另选范围。

一次删除 emoji 不推成永久规则。多次同方向修改可提出候选；允许拒绝、编辑、撤回，并记录规则版本。撤回后新任务不再注入，正在执行的任务标出所用版本，避免假称可撤回模型已见过的信息。

每步只带相关项目资料与已批准的适用规则，并记录知识版本。知识内容与任务指令在协议中区分，防止普通引用扩大权限。

组织进化的产品形态保留：有实际同类任务数据后，提出换成员、调步骤或增加规则的建议，展示依据和样本；人批准才改，可退回。完整 OKR、自动换人、公开配方市场属于后续范围，首版不做空壳成功状态。

## 8. 接入体验与后台职责

四家目标保持：Grok Bot 原 MCP＋Routine、Muse 原 connector＋hook/定时、Dots 插件＋MCP Events、Perplexity Computer 官方 MCP。复用已经核对的成熟方案，沿用原工具、账号授权与实际额度；不改为普通模型 API 来冒充 Personal Agent。

前台步骤统一为：选择产品 → 给备注及本项目职责 → 在原产品完成授权/配对 → 产品自动验证“工具往返、原生唤醒与一次真实交付”。每层验证保留证据；仅两个连通对勾不足以宣称完整任务能力通过。

同类多个 Agent 有独立身份、平台实例关联和任务；若共享同一账户资源，按实际平台限制并发。缺少权限或平台不可用时准确显示，不清登录资料、不自动切出口、不反复弹窗、不偷偷用另一通道重发。

执行、提问与回执留在群；需要本人操作时提供对应原产品入口。用户只做平台要求本人做的动作，内部 ID、密钥拼装、轮询与恢复不转嫁给用户。

## 9. 后端对象与交互契约

| 对象 | 最小内容 |
|---|---|
| 配方/配方版本 | 输入、能力槽位、步骤依赖、交付标准、初始知识、默认节奏 |
| 项目群 | 名称、所用配方快照、成员分工、知识范围、触发设置 |
| 运行/步骤/尝试 | 本次目标、版本、领取方、原平台关联、真实状态、截止与回执 |
| 群消息/交接 | 作者、消息类型、运行和成果关联、前后续关系 |
| 成果/人工稿 | 原交付、当前编辑稿、来源、文件、revision、冲突状态 |
| 反馈事件 | 成果与原稿版本、反馈类型、用户、修订历史 |
| 知识/候选规则 | 范围、来源、审批、版本、适用条件与撤回 |
| 指标投影 | 从真实事件计算的分子分母，不由 Agent 自报 |

继续复用身份、领取、版本与编辑器能力；旧页面整体重做。存储、唤醒和恢复的改造按技术方案实施，不能把新导航直接套到旧单任务逻辑上就称为新产品完成。

## 10. 按用户路径验收

| 编号 | 验收场景 | 必须看到的结果 |
|---|---|---|
| R1 | 新用户选择唯一配方，缺少一个成员 | 能在同一流程补授权或选择已验证的可兼任成员；不能虚报连接 |
| R2 | 使用配方、连续点两次 | 只创建一个项目群和一次试跑；没有默认开启未确认的每日任务 |
| G1 | 发现→查证→写稿 | 群显示真实作者与交接；无需人工复制；交付数量缺口清楚；正文与出处完整 |
| G2 | 执行中 @成员补充、只重写第 2 条 | 接到正确原稿与版本，其他稿和人工修改保留，不额外全量重跑 |
| A1 | 编辑、退出重开、继续改 | 工作稿持久；冲突可处理；Agent 修改有版本，不覆盖未提交人工内容 |
| A2 | 正文与文件 | 来源可打开、文件确实存在且可读；不是一段“已完成” |
| F1 | 采用/弃用、改选、撤销评价 | 按同一成果更新；分母和待反馈正确；复制/导出不算采用或发布；修改量单列 |
| K1 | 从改稿建议规则 | 批准前不生效；批准后下次任务可用；能拒绝、改范围和撤回 |
| M1 | 四家原产品接入、掉线或需本人确认 | 分层证据真实；保留全部原登录资料；只请求必要本人动作 |
| O1 | 定时任务、时区与暂停 | 保存实际时区；暂停后不新开任务；进行中工作按实际取消能力处理 |
| S1 | 断网、重复事件、迟到旧回执 | 不重复做事、不丢成果、不让旧版本覆盖新稿 |
| U1 | 慢按钮、请求超时、其他项目操作 | 立即有局部反馈，不锁全局；重试不重复创建或派发 |

首版完整验收包含上述功能；不以“截图像飞书”“接口 200”“工程测试通过”替代真实 Agent 联测。两周使用验证属于产品效果验证，不能在两周前承诺采纳率必然上升。

- [项目群截图](../../docs/prototype/agent-feishu-v2/preview-group.png)、[宽幅审核截图](../../docs/prototype/agent-feishu-v2/preview-review.png)。
- [旧 AI 概念稿](../../docs/prototype/agent-feishu-v2/ai-concept.html) 与 [生成记录](../../docs/prototype/agent-feishu-v2/generation-prompts.md) 仅作历史对照，不再是当前方案。

当前页面包含项目群、配方、知识库、成员。支持配方组队、缺连接拦截、创建项目群、显式演示接力、消息与 @成员、本地文本附件、正文富文本编辑、原稿/工作稿切换、复制导出、工作稿快照、交回消息、逐稿反馈、批准/撤回规则和项目设置。项目和工作稿保存在原型独立 localStorage 键中，刷新可恢复。

### 构建与验证

在仓库根目录执行：

```sh
node docs/prototype/agent-feishu-v2/build.mjs
node docs/prototype/agent-feishu-v2/verify.mjs
```

源码位于同目录 `src/`，按布局、对话、编辑器、页面与数据拆分并格式化；复用仓库已有 React、TipTap、Lucide 与 esbuild，不改正式应用入口及依赖。构建输出内联脚本和样式，离线可用。

### 原型边界与下一步

所有 Agent、账号状态、任务、资讯和来源为示例；“演示接力”是用户主动触发的本地状态演示。规则建议是固定示例，尚未做模型提炼；节奏开关仅保存配置，不创建定时任务。不把原型的按钮和示例状态视为商业平台联测通过。

本轮只交付产品交互原型，不替换正式 Electron 应用、不访问账号资料、不发布内容。原型确认后，再实现正式服务与真实 Agent 联测。评审重点：能否看懂交接、方便编辑与审核、找到当前成果，并理解反馈和知识的影响范围。
