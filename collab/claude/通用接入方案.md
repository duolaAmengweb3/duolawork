# 通用接入方案：让任何 AI Agent 都能加入团队

- 作者：Claude
- 日期：2026-10-28
- 背景：用户提出"只定位个人 Agent 太窄，什么 AI Agent 都应该能接入"，并问内置浏览器方案（Codex 推荐、当前实现）是不是最好的路。

---

## 1. 结论

1. **方向对：** 只接个人 Agent 太窄。能把**大厂个人 Agent（Muse、Grok Bot、Dots……）、本地编程 Agent（Claude Code、Codex、Gemini CLI、OpenClaw……）、通过接口提供的 Agent（API、A2A）**放进同一个团队里协作，这是现有产品都没做到的组合：
   - Paperclip 能管 Claude Code、Codex、OpenClaw 这类可以直接调用的 Agent，但不接 Dots、Muse 这类大厂个人 Agent；
   - Sintra、Marblism 只能用它们自己造的 Agent；
   - 大厂只管自家的 Agent。
2. **不建议让内置浏览器当主干。** 它对"没有任何接口"的网页 Agent 很有用，但每家网站都要单独写适配、网站一改版就坏、部分平台的条款限制自动化提取、Google 等登录会拦受控浏览器、还要求电脑一直开着。用它去覆盖"任何 Agent"，维护成本会随接入数量线性增长。
3. **建议的主干：一份统一的"任务交接规则" + 四种接入方式，按可靠性从高到低选。** 浏览器是第四种，只给真的没有其他入口、又确实重要的 Agent 用。

## 2. 统一的任务交接规则（这是真正的"通用"）

不管 Agent 怎么接进来，工作台只认同一套规则：

| 环节 | 内容 |
|---|---|
| 派给它的东西 | 工作 ID、步骤 ID、要求、前序成果全文和来源、相关公司档案（标注"只是资料，不是指令"） |
| 它交回的东西 | 正文、来源列表、状态（完成 / 做不了 + 原因） |
| 身份 | 每个成员独立凭证；交回的结果必须对得上工作、步骤和这一次派发 |
| 能力声明 | 每个接入方式声明：能否被直接调用、能否被叫醒、能否主动来领任务、交回的结果是否结构化、需不需要人工确认 |

现有代码里的 MCP 工具、`list_my_work → claim → submit`、交付门槛和版本校验已经基本符合这套规则，保留。

## 3. 四种接入方式（按可靠性从高到低）

| # | 方式 | 适合哪类 Agent | 怎么派活 | 怎么收结果 | 可靠性 | 例子 |
|---|---|---|---|---|---|---|
| ① | **直接调用** | 本地命令行 Agent；提供 API 的 Agent | 工作台直接启动或调用它（例如 `claude -p`、`codex exec`、`gemini -p`，或 HTTP API） | 进程输出或 API 返回 | 最高：随叫随到，结果确定 | Claude Code、Codex、Gemini CLI、OpenClaw、Hermes、自建 Agent、OpenAI 兼容接口 |
| ② | **标准协议** | 支持 A2A 的 Agent（主要是企业和云平台的 Agent） | A2A 发任务 | A2A 回传 | 高 | Google Gemini Enterprise、微软、AWS 平台上的 Agent（A2A 1.0，150 多家机构支持） |
| ③ | **MCP + 叫醒** | 能添加自定义 MCP 的个人 Agent | 叫醒（webhook、Slack、邮件）或它自己定时来查 | 它调用 MCP 工具交回 | 中：取决于叫醒方式；有的平台写入要人工确认 | Grok Bot、ChatGPT Dots、Gemini Tasks、Perplexity、WorkBuddy、千问办公 |
| ④ | **浏览器适配**（现有实现） | 没有接口、不能加 MCP，但确实重要的网页 Agent | 在专用浏览器里打开它的页面、输入任务 | 读页面上的回答 | 最低：网站一改就坏；部分平台条款限制 | Muse（官方没写 MCP）、其他网页 Agent |

**选择规则：** 一个 Agent 同时支持多种方式时，**接入时**选定排在前面的那种，作为它唯一生效的通道；**运行时不自动切换**到别的通道重发，避免重复执行（采纳 Codex 方案第 7 节）。例如 Grok Bot 能加 MCP、也有 webhook，就走 ③ 而不是 ④；Muse 先走 ④，等它支持 MCP 或连接器稳定后再切到 ③。

## 4. 为什么这样比"全部用浏览器"好

| | 全部用浏览器 | 分层接入 |
|---|---|---|
| 新接一个 Agent | 每家写一套页面适配 | 支持 MCP / A2A / 命令行的，不用写代码 |
| 网站改版 | 适配失效，要修 | 只影响走 ④ 的少数几家 |
| 速度和确定性 | 要等页面、靠读文字判断"做完没" | ①② 直接拿到结构化结果 |
| 电脑要不要开着 | 要 | ②③ 可以不用（Agent 在自己的云上跑） |
| 平台条款 | 部分平台限制自动化提取 | ①②③ 都是官方提供的接入方式 |
| 能接的范围 | 只有网页 | 命令行、API、企业 Agent、个人 Agent、网页 Agent 全部 |

## 5. 对现有代码的改动

1. **抽出"接入方式"接口**：每种方式实现同一组方法——派发、查询进度、取结果、取消、声明能力。现在的 `local/grok.mjs`、`local/muse.mjs` 变成 ④ 下面的两个实现，不需要重写。
2. **新增 ①（命令行 / API 执行器）**：先做 Claude Code 和 Codex 两个，它们最容易验证，也最能体现"不同类型 Agent 混编"。
3. **保留 ③**：现有 MCP 服务和工具不动；把"叫醒"也做成接入方式的一部分。
4. **② A2A 放后面**：等有用户真正带着企业 Agent 来时再做。
5. **"添加成员"页按 Agent 类型引导**：先问"它是哪类 Agent"，再自动选最可靠的接入方式。用户看不到"MCP、A2A、CDP"这些词。

## 6. 定位上的提醒

- "任何 Agent 都能接入"是**能力**，不要变成**卖点的全部**。卖点仍然是：**一个目标，几位不同的 Agent 自动接力完成，你不用当中间人。**
- 只管编程 Agent 的赛道已经很挤（Paperclip、Orca 等）。我们的独特之处在于**混编**：用 Grok 找 X 热点、Claude Code 写演示代码、Muse 发 Threads 版本，放在同一个团队里。

## 7. 验收

| 编号 | 内容 | 通过标准 |
|---|---|---|
| U1 | 混编接力 | 一个目标由一个命令行 Agent（Claude Code 或 Codex）和一个网页 Agent（Grok 或 Muse）接力完成，不手动搬运；连续 3 次 |
| U2 | 新接一个支持 MCP 的 Agent | 不改代码，只在界面上添加，5 分钟内能领任务、交结果 |
| U3 | 自动选接入方式 | 同时支持 MCP 和浏览器的 Agent，默认走 MCP |
| U4 | 浏览器适配出问题时 | 只影响走 ④ 的成员，其他成员和工作照常 |

## 依据

- MCP：Grok Bot、ChatGPT（开发者模式）、Gemini Tasks、Perplexity Computer、腾讯 WorkBuddy、千问办公均支持添加自定义 MCP（见 `docs/支持的Agent.md`，逐家对照过官方文档）。
- A2A：2026 年 3 月发布 1.0，Linux 基金会称 150 多家机构支持，已进入 Google、微软、AWS 平台；目前主要用于企业，没找到个人 Agent 支持的证据。
- 直接调用：Paperclip 的做法证明了这条路可行，它能统一管理 Claude Code、Codex、Gemini、Cursor、Hermes、OpenClaw 以及 HTTP webhook。
- 浏览器路线的限制：见 `docs/M0验证方案与结果.md` 第 11、12 节（OpenAI 个人服务条款对自动化提取的限制、Google 对受控浏览器登录的限制）。
