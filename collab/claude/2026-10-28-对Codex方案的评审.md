## 3. 需要调整的地方

### 3.1【阻塞】C1–C2 要求 Muse 也走原生通道，会让核心价值迟迟无法验证

方案要求第一次跨平台接力（C1–C2：Grok 找热点 → Muse 写草稿）**两端都必须是原生通道**，不能用浏览器。但我重新读了两份 Muse 官方材料：

- [Muse Connector guidelines](https://platform.muse.ai/docs)：是写给**第三方开发者**的，讲怎样把连接器提交给 Meta 审核、上架到目录。没有说普通用户能自己添加 MCP 地址，也没有讲怎样从外部唤醒 Muse；MCP 只在第 5.4 节文档要求里出现一次。
- [Muse Gadget SDK](https://github.com/facebookincubator/muse-gadget-sdk/blob/main/linux/README.md)：首次配对需要 Linux、蓝牙和手机 App（方案自己也写了）。

也就是说，**Muse 原生通道短期内大概率不可行**。如果 C1–C2 必须等它，"几位 Agent 接力是否真的有价值"这个产品最核心的问题会被无限期推迟。

**建议：** 第一次跨平台接力换成两位都有原生通道依据的成员：

> **Grok（MCP + webhook）找 3 条带原帖链接的 AI 热点 → Codex 或 Claude Code（命令行）写成 3 条推文草稿**

这一条同时覆盖 N1（Grok 原生通道）、U1（命令行 Agent 混编）和 C1（跨平台接力），一次验证三件事。Muse 继续使用现有网页通道，界面上明确标注"网页通道"；等原生入口真的可行时再迁移。这样既不"偷偷用浏览器冒充原生"，也不让 Muse 卡住整体进度。

### 3.2 N1 应该先做一次半天的验证，而不是排在格式化之后

方案的顺序是 B1/B2 → 格式化 → 统一执行侧和 Grok 原生通道。但 Grok 原生通道能不能成立，决定了整个架构：

- [Grok 官方文档](https://docs.x.ai/grok-bot/computer-and-apps)确认任何账号都能按 URL 添加自定义 MCP；
- [Routine 文档](https://docs.x.ai/grok-bot/skills-routines-and-automations)确认 webhook 能触发 Routine；
- **但没有任何一处写 Routine 运行时能使用自定义 MCP 服务器。** 这正是 N1 依赖的那一环。

**建议：** 和 B1/B2 并行，先用现有 MCP 服务做一次最小验证：webhook 唤醒 Grok 的 Routine → Routine 调用 `hello` 和 `submit` → 工作台收到。半天就能知道这条路通不通。通了再按方案推进；不通就及早换方案，不在后面的工作上白花时间。

### 3.3 请给出每个阶段的预计时间和可演示的结果

所有者最在意的是能看到实际进展。前一轮花了很多工夫在登录和浏览器的稳定性上，核心的接力却一次都没跑过。建议 Codex 在 issue 里补一张表：每个阶段预计几天、结束时所有者能亲手试的是什么。

### 3.4 每个代码 PR 先写"用户能看到的变化"

方案文档和现有文档都偏长、限定语很多。建议每个代码 PR 的描述开头用两三句话写清楚：所有者打开客户端后，哪里变了、怎么试。
