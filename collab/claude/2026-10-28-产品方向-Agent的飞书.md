# 产品方向：管 Agent 的飞书——配方、项目群、组织进化

- 作者：Claude
- 日期：2026-10-28
- 起因：所有者认可"配方"这个概念（解决用户不知道拿 Agent 干什么）；并要求从产品角度再往前想一步：**把 Agent 当成人来管理。飞书、钉钉管人，我们管 Agent。一个群就是一个项目组。** 再往上是协作、组织进化，以及 KPI、OKR、知识库。
- 依据：
  - [竞品实现拆解](2026-10-28-竞品实现拆解与复用清单.md)：已经能连上 Agent 的竞品不少，接入正在变得不稀缺；
  - Paperclip 官方说明：它已有组织架构、目标对齐、预算、Agent 绩效评估和技能库；
  - 所有者的实际使用：x-daily-drafts，Grok 每天往里推内容。
- 状态：**所有者 2026-10-28 明确要求按这个新方案来，旧的产品方案已判断有问题，不再沿用。** 新方案还没有经过真实用户验证，验证办法见第 5 节。

---

## 1. 一句话

**用户已经在用的那些 Agent（Grok、Dot、Muse、Perplexity……），在这里像一个团队一样被组织起来：按项目分群、有目标、有共享资料、有绩效，而且越用越好。用户从一个"配方"开始，不用先想清楚怎么搭。**

飞书解决的是"一群人怎么一起把事做成"。我们解决的是"一群 Agent 加上我，怎么一起把事做成，并且越做越好"。

---

## 2. 为什么类比飞书是对的，又有哪些地方不能照搬

**对的地方：**
- 中文用户都懂飞书的结构：群、@某人、文档、知识库、OKR、审批。
- 用户不用重新学一套概念。看到"项目群"就知道该怎么用，这本身就降低了"不知道怎么搭"的门槛。

**不能照搬的地方：** Agent 和人在几个关键点上相反，管理工具必须针对这些差异来设计。

| | 人 | Agent | 所以管理工具要做的 |
|---|---|---|---|
| 精力 | 有限，要排期 | 不会累，但每跑一次都花额度 | 管**额度和成本**，不管工时 |
| 记忆 | 记得项目背景 | 每次运行几乎从零开始，不同 Agent 之间也不共享记忆 | **知识库是刚需**，不是可有可无：每次干活前自动带上项目资料 |
| 可靠性 | 答应的事基本会做 | 会忘了确认、会超时、会理解错 | 系统自动检查和记录，不依赖 Agent 自己汇报"做完了" |
| 动机 | 需要激励，KPI 用来考核人 | 不需要激励 | **KPI 不是用来考核的，是用来决定"下次这一步交给谁"** |
| 成长 | 靠培训、靠经验 | 靠更好的指令、更好的资料、换更合适的 Agent | "组织进化" = 系统根据数据提出改进，人来批准 |
| 各自擅长 | 看个人能力 | 看所在的生态：Grok 有 X，Muse 有 Meta 系应用，Dot 有 ChatGPT 连着的应用，Perplexity 擅长查证 | 分工按"谁手里有这个生态"来分 |

## 3. 产品结构：三层

```text
第 3 层  组织    —— 目标（OKR）、绩效（KPI）、组织进化建议、全局知识库
第 2 层  项目群  —— 成员（Agent + 我）、对话与交接、共同成果、项目知识库
第 1 层  配方    —— 入口：选一个现成的配方，一键建出一个配好的项目群
```

**用户的成长路径：** 先用一个配方（一个群）→ 跑顺了再加第二个、第三个群 → 群多了以后，自然需要目标、绩效和全局知识库。

**第一天只需要第 1、2 层。第 3 层随着使用自然出现，不要求用户一开始就配置。** 这一点和 Paperclip 相反：Paperclip 一上来就要你"建公司、定目标、招 CEO"。

### 3.1 配方：入口，解决"不知道干啥"

一个配方包含以下内容：
- 要哪几类成员，比如"一个能读 X 的 Agent + 一个能查证的 Agent + 一个写稿的 Agent"；
- 每一步谁做、交接给谁；
- 成果的格式，比如"每日 X 内容包：5 条选题 + 3 条成稿 + 出处"；
- 节奏：每天早上 8 点，或者手动触发；
- 一份初始的项目知识，比如风格指南的模板。

选了配方以后：
1. 系统检查你已经接了哪些 Agent，缺哪个就带你去接，接入沿用竞品验证过的流程；
2. 自动建出一个项目群；
3. 第一次运行时你就能看到成品。

举例（第一批，从所有者自己的需要出发）：
- **每日 X 内容包**：Grok 抓热点 → Perplexity 查证 → 写成稿。这和所有者现在的 x-daily-drafts 是同一件事。
- **竞品周报**：Perplexity 调研 → Grok 看 X 上的讨论 → 汇总成一页。
- **活动 / 出行筹备**：Dot 查邮件和日历 → Muse 在 Meta 系应用里联系、比价 → 汇总成清单。

### 3.2 项目群：协作发生的地方

- **成员：** 几个 Agent 加上你。每个成员有头像、名字和状态（空闲 / 正在做 / 等你确认 / 连不上）。
- **对话：** 你在群里说目标、@ 某个 Agent 补充要求；Agent 之间的交接也以消息的形式出现在群里。你能看到"谁把什么交给了谁"，但**交接由系统自动推进，不需要你转述**。
- **成果：** 群里有共同成果，即文稿和文件，类似飞书群里的"文档"标签页。你直接在上面改，改完可以交回某个 Agent 继续做。
- **项目知识库：** 这个群专用的资料，比如风格指南、往期成果、你的修改意见。每次有成员干活，系统自动把相关资料带给它。

### 3.3 组织：进化的地方

**知识库（全局 + 项目）**
- 来源有三个：你手动写的；Agent 交付的成果（自动归档）；**你每次改稿的差异**（系统总结后提议加入知识库，由你批准）。
- 例子：你连续三次把成稿里的 emoji 删掉，系统就提议在风格指南里加一条"不用 emoji"，你点同意以后，所有成员都会遵守。
- 这是"Agent 越用越懂你"的来源，而且**不依赖任何一家 Agent 自带的记忆**。各家的记忆互不相通；我们的知识库是它们共用的那一份。

**KPI（系统自动算，不让 Agent 自己报）**

| 指标 | 怎么算 | 用来做什么 |
|---|---|---|
| **采纳率**（核心） | 成果被你直接用了，或者只做了小改，算采纳；大改或作废，算不采纳 | 判断配方和成员值不值得留 |
| 按时率 | 在约定时间内交付 | 决定是否要换叫醒方式或换人 |
| 返工次数 | 被你退回重做的次数 | 找出容易出错的那一步 |
| 成本 | 跑了几次、用了多少额度（平台能提供的才显示，拿不到就标"未知"，不估算） | 控制开销 |
| 失败 | 超时、连不上、没回应 | 提醒你重新授权或检查 |

**OKR（把群和目标连起来）**
- 你写一个目标，比如"本季度 X 粉丝 +1000"；关键结果是"每天发 3 条""每周 1 条长文"。
- 每个项目群挂在某个关键结果下面；成员干活时会看到"这件事是为了什么"。
- 每周由牵头 Agent 生成一份周报：每个关键结果的进度、哪些群在拖后腿、建议怎么调整。

**组织进化（系统提建议，人来批准）**
- "这一步 Grok 的采纳率只有 40%，Perplexity 试过的 3 次都是 90%，要不要换？"
- "这个配方每次都卡在 Muse 那一步（等了 15 分钟），要不要改成 Dot？"
- "你最近一个月改稿最多的是标题，要不要加一步'标题由 Grok 出 3 个让你选'？"
- 所有调整都要你点同意；系统保留修改记录，可以退回。

## 4. 怎么赢：差异在哪里，护城河在哪里

**先承认事实：** OKR、绩效、知识库这些概念本身，Paperclip 已经有了（目标对齐、Agent 绩效评估、技能库、预算）。光说"管 Agent 像管人"不构成差异。

| | Paperclip | crosswalk | **我们** |
|---|---|---|---|
| 管的是谁 | 编程和命令行 Agent 为主，个人 Agent 还是实验功能 | 什么都能连，但只是"连上" | **你已经在用的个人 Agent**，每家都带着自己的生态 |
| 给谁用 | 开发者：自己部署服务器，开一家"AI 公司" | 愿意自己摸索的人 | **普通个人和一人公司**，界面像飞书一样熟悉，桌面端打开就用 |
| 从哪开始 | 先建公司、定目标、招人 | 先建留言板 | **先选一个配方，第一次运行就看到成品** |
| 怎么衡量 | 任务完成、花费 | 不衡量 | **你采纳了多少成品**，并据此持续改进 |

**护城河（长期能做大的部分）：**
1. **数据回路：** 每次改稿 → 知识库和采纳率 → 组织进化建议 → 下一次更好。竞品要么不管成果（crosswalk、botline），要么管的是代码（Paperclip），拿不到"个人用户对成品满不满意"这份数据。用得越久，越换不走。
2. **配方市场：** 用户把跑顺的项目群（成员搭配 + 步骤 + 知识库模板）发布成配方，别人一键使用。这是网络效应，相当于飞书的模板中心、钉钉的应用市场。配方越多，新用户越容易上手。
3. **接入用别人的成熟代码：** 不在管道上和竞品拼，把力气放在上面两条。

**最大的风险：** Paperclip 把个人 Agent 功能正式打开，并且做了简化版界面。应对办法是先把第 1、2 层做出来，并让真实用户用起来。数据回路和配方要靠积累，越早开始越占优。

## 5. 分阶段（长期做大，但第一版要能用）

| 阶段 | 做什么 | 怎么算成功 |
|---|---|---|
| **第一版** | 1 个配方（每日 X 内容包）+ 项目群（成员、交接、共同成果）+ 项目知识库（手动写 + 自动归档）+ 自动算的采纳率和按时率 | 所有者连续用 2 周，替代了现在的流程；采纳率逐周上升 |
| 第二版 | 3～5 个配方；改稿自动提议加入知识库；周报；简单的 OKR | 3～5 个真实外部用户每周都在用 |
| 第三版 | 多个群组成的组织视图；组织进化建议；配方发布和复用 | 有用户发布的配方被别人用 |

第一版的接入范围按 Codex 已定的：Grok Bot、Muse、Perplexity Computer、Dots。B1、B2、O3 等修 bug 的工作照常进行。

## 5.1 前端重做（所有者要求："前端甚至也要改……现在前端简直垃圾"）

**现在的前端整体废弃，按新方案重做，不在旧界面上修补。**
- 旧界面是为"给单个 Agent 下任务"设计的，信息结构本身就不对。
- 旧代码 `ui/src.jsx` 约 45KB 却只有 116 行，几乎无法维护。

旧前端里只保留两样东西：后端接口，以及可编辑文稿用的 TipTap 编辑器。

**新的界面结构（参照飞书，用户一看就懂）：**

```text
左侧导航            中间                                  右侧（可收起）
────────            ──────────────────────────           ─────────────
消息 / 项目群   →   群对话：你、各 Agent、交接消息          群信息标签页：
配方广场            （@ 某个 Agent 补充要求；               · 成果（可编辑文稿、文件）
知识库              每条交接显示"谁 → 谁、交了什么"）       · 成员（状态、采纳率）
目标（OKR）                                                · 项目知识
成员（我的 Agent）   顶部：群名、所属目标、本次运行进度       · 设置（节奏、配方步骤）
```

| 页面 | 用户在这里做什么 | 第一版是否要做 |
|---|---|---|
| **配方广场** | 浏览配方 → 点"使用" → 引导接上缺少的 Agent → 自动建群并跑第一次 | 要（只放 1 个配方） |
| **项目群** | 看进度、@ 某个 Agent、改成果、交回修改 | 要 |
| **成员（我的 Agent）** | 接入新 Agent（沿用竞品验证过的流程：复制一句话 → 授权 → 自动测试两个对勾）；查看每个 Agent 的状态和各项指标 | 要 |
| **知识库** | 看和改全局资料、项目资料；批准系统提议的新条目 | 要（简单版） |
| **目标（OKR）** | 写目标和关键结果、把群挂上去、看周报 | 第二版 |
| **组织视图** | 所有群和成员的全景，以及组织进化建议 | 第三版 |

**前端质量要求：**
- 代码按页面和组件拆分文件，用正常格式，不压缩成一行。
- 每个按钮点了都要立即有反馈；慢操作放到后台，不锁死整个界面。旧版"按钮点不动"的根源，就是全局只有一个"忙碌"状态，并且请求没有超时。
- 状态以服务端为准，分开显示：已连接、正在做、等你确认、连不上、已交付。不把"设置页显示已连接"当成"已接通"。
- 动手前先出一版可点击的原型给所有者看，确认后再写正式代码。之前就是没对原型先开发，结果做出来的东西不是所有者想要的。

## 6. 不做的事

- 不做真人员工管理，不和飞书、钉钉抢人。
- 不在接入数量上和竞品比。
- 不让 Agent 自己报绩效、自己说"做完了"就算数。
- 系统不在背后自动改组织：所有调整都由人批准，并且可以退回。
- 不在第一版做完整的 OKR 和绩效系统。先把采纳率这一个指标做准。

## 7. 和旧方案的关系（所有者已决定）

所有者 2026-10-28 原话："不要管以前的记录，我们现在是新的思路，新的产品方案""明确要求按照新的来，老的说实话，我们已经判断有问题了"。

**作废，以本方案为准：** 旧的产品设计条款，包括：
- "成员绑定只收备注、不设岗位或职责、不自动按岗位分配"；
- "固定 B 版左对话右成果、不改成团队群聊"；
- "会话工作台是默认入口"；
- 以及其他按"给单个 Agent 下任务"思路定的界面和流程。

新方案里成员可以有职责，项目群就是群聊。系统可以建议分工和换人，**是否需要人确认，由本方案的"组织进化"规则决定**：所有调整由人批准，可以退回。

**继续有效（安全和测试约束，与产品方案无关）：**
- 登录资料与凭证保护；
- 云端 VPS 的订阅 Claude Code 不参加测试；
- 凭证不进 Git、安装包和测试证据；
- 交付必须有"已生效"的验证，不虚报接通或完成。

这些是保护所有者账号和数据的规定，所有者没有要求改，保持不变。
