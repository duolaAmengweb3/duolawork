# 协作优先的工作台设计

- 作者：Claude
- 日期：2026-10-28
- 背景：用户反馈"现在的工作台不是为协作设计的，像是给每个 Agent 单独下任务"。见审计 D1。
- 遵守已有决定（`AGENTS.md`）：保留 **B 版"左侧对话＋右侧成果"**；成员只有备注名，**不加岗位**；**方案必须来自真实 Agent**，不用静态模板冒充；未就绪成员不能派发。

---

## 1. 一句话

**用户交代的是一个目标，不是给某个 Agent 的一条指令。工作台把目标拆给几位成员，按顺序自动交接，用户在一个对话里看到全过程，在右侧拿到大家共同的成果。**

## 2. 现在和应该的对比

| | 现在 | 应该 |
|---|---|---|
| 输入框 | 先选**一个**成员，再写要求 | 默认"交给团队"，写目标就行；需要时可以 @ 某位成员 |
| 谁来干 | 用户选的那一个 | 先出一份**分工方案**：哪几步、每步谁做、为什么是它 |
| 对话里看到什么 | 我和这一个 Agent 的来回 | 团队对话：每位成员的发言、**交接卡片**（"Grok 把 3 条来源交给了 Muse"）、需要我确认的地方 |
| 补充要求 | 发给同一个成员 | 发给团队；可以 @ 某位成员只改他那部分 |
| 右侧成果 | 某一次交付 | 这项工作的共同成果，每一部分标明是谁做的、用了哪些来源 |
| 单个 Agent 做事 | 唯一方式 | 只是一种特例（分工方案只有一步） |

## 3. 核心对象

- **工作**：用户的一个目标，例如"本周 AI 选题周报"。一个工作包含一份分工方案、多次交接、一份共同成果。
- **分工方案**：有序步骤，每步写明：做什么、交给哪位成员、为什么是它（例如"Grok 能直接看 X 上的实时内容"）、要交出什么、是否需要我确认。
- **交接**：上一步的完整成果 + 来源，自动作为下一步的输入。交接本身在对话里显示为一张卡片。
- **共同成果**：右侧文稿。每一步交付的内容按段落归档，标注成员和来源；用户的修改保留，再次派发时全文带上（沿用现有逻辑）。

## 4. 主流程（以"每日 X 内容包"为例）

1. **写目标**：用户在左侧输入"做今天的 X 内容包：3 条 AI 热点，带原帖链接，写成推文草稿"。默认"交给团队"。
2. **出分工方案**：由一位**牵头成员**（用户指定，或默认最近用过的、可以接任务的成员）根据团队里有哪些成员，拟一份方案。牵头成员是真实 Agent，符合"方案必须来自真实 Agent"。
   - 方案示例：① Grok：找 3 条 X 上的 AI 热点，附原帖链接（它能直接看 X）→ ② Muse：按公司档案的语气写成 3 条推文草稿 → ③ 我确认。
   - 方案显示在右侧，用户可以改步骤、换成员、加确认关卡；未就绪的成员不能被选中，并提示原因。
3. **确认后自动接力**：
   - 对话里依次出现："已交给 Grok"→ Grok 的结果摘要 → **交接卡片**"Grok → Muse：3 条热点和来源"→ Muse 的结果摘要。
   - 用户不需要复制粘贴，也不需要逐个去催。
4. **成果汇总**：右侧文稿里第 1 部分是热点和来源（Grok），第 2 部分是草稿（Muse）。
5. **补充**：用户说"第 2 条换个角度"，默认交给负责那部分的成员（Muse）；也可以 @Grok 让它再找一条替换。
6. **出错时**：某一步失败或超时，对话里显示是哪位成员、卡在哪，按钮"重试 / 换成员 / 我来补"；不影响已经完成的步骤。

## 5. 页面调整（在 B 版上改，不推翻）

### 5.1 左侧：团队对话

- 顶部显示这项工作的参与成员头像和当前在做的是谁。
- 消息类型：我、成员发言（摘要，可展开全文）、**交接卡片**、**需要你确认**、系统提示（失败、超时、重试）。
- 输入框：默认"交给团队"；`@` 可以选具体成员；"先给我方案"保留，且默认勾选（第一次使用时）。

### 5.2 右侧：成果 / 分工 / 执行记录

- **成果**（原"文稿"）：按步骤分段，标注成员和来源；保留现有的编辑、复制、导出、"原始交付与工作稿分开"。
- **分工**（新增，原"方案"）：当前分工方案，执行中显示每步的进度。
- **执行记录**、**素材**：保留。

### 5.3 团队页（合并"我的团队"和"成员与账号"）

- 每位成员一张卡片：备注名、平台、**一个状态 + 一个下一步按钮**（见审计 B2）。
- 卡片上显示"它能直接用什么"（由平台决定，例如"X 实时内容""Gmail、Google 文档""Instagram、Threads"），帮助牵头成员和用户安排分工。这是平台能力说明，**不是岗位**，用户不需要配置。
- 账号、浏览器、网络等技术细节收进"详情"。

## 6. 数据和接口改动（给实现方的提示）

- `task` 增加 `leadMemberId`（牵头成员）和 `mode: 'team' | 'single'`；现有多步 `steps` 结构基本可复用。
- 交接事件：步骤完成时写一条 `handoff` 事件（from、to、成果 ID、来源数量），对话里渲染成卡片。
- 发送接口：目标 + 可选 `@成员` 列表；未指定成员时走"牵头成员拟方案"。
- 补充接口：带上目标步骤或成员；没指定时由最近完成的相关步骤的成员接手。

## 7. 验收

| 编号 | 验收内容 | 通过标准 |
|---|---|---|
| C1 | 一个目标由两位真实成员（Grok、Muse）接力完成 | 不手动搬运正文；交接卡片显示在对话里；右侧成果分段标注成员和来源 |
| C2 | 连续 3 次 C1 | 3 次都成功；记录每一步实际耗时 |
| C3 | 方案可改 | 用户换掉一步的成员、加一个确认关卡后执行，按修改后的方案走 |
| C4 | 补充定向 | "@Grok 再找一条"只派给 Grok，结果替换到对应段落，Muse 的部分不被覆盖 |
| C5 | 出错可恢复 | 人为让第 1 步超时，对话里出现"重试 / 换成员 / 我来补"，重试成功后自动继续第 2 步 |
| C6 | 单人工作仍可用 | 分工只有一步时，体验和现在一样顺畅 |

**C1、C2 是产品价值的第一道门槛**：之后再对比"只让一个 Agent 全做"，看接力是否真的更好。
