## 0. 结论

1. **基础能跑**：49 项单元测试、类型检查（先运行 `npm run hub:types`）、构建、协议集成测试都通过；界面打开没有 JS 报错。
2. **用户反馈的两个 bug 在代码里能找到直接原因**：按钮点不动 → 全局 `busy` 锁 + 请求没有超时（B1）；登录完成后状态不变 → 登录判断条件过严，而且"登录"和"能接任务"之间还隔着一次真实任务验证，界面没有讲清楚（B2）。
3. **最大的问题是产品设计**：工作台的基本单位是"给一个成员下任务"，不是"一个目标由几位成员协作完成"（D1）。这和产品定位直接冲突。设计建议见 [协作优先的工作台设计.md](协作优先的工作台设计.md)。
4. **跨平台接力从未测试过**：所有真实测试记录都写着 `crossPlatformCollaborationTested: false`，真实任务只是读取健康检查接口这类最小任务。

## 1. 产品 bug

依据等级：**已确认** = 代码里直接能看到；**推断** = 和用户反馈吻合但我没法在真实账号上复现。

### B1【高】按钮点不动：全局 busy 锁，请求没有超时（已确认）

**现象（用户反馈）：** 按钮点了没反应。

**原因：**
- `ui/src.jsx` 第 24 行的 `run()`：任何操作开始时 `setBusy(true)`，结束时在 `finally` 里复位。界面上绝大多数按钮都是 `disabled={busy}`。**一个操作没结束，所有按钮一起变灰。**
- `ui/src.jsx` 第 8 行的 `api()`：直接 `fetch`，**没有超时、没有 AbortController**。后端只要有一个请求不返回，`busy` 就一直是 true。
- 最容易卡住的是 `local/server.mjs` 第 133 行的 `/api/account/open`：依次 `await cloud.state()`（访问 Cloudflare）→ `connections.enable()` → `browsers.open()`（启动 Chrome）。任何一步慢或卡住，整个界面都锁住。
- `run()` 里还 `await refresh()`，刷新慢也会拖长锁定时间。
- `api()` 里 `await r.json()`：后端返回非 JSON（比如 502 页面）时，报出的错误用户看不懂。

**修法：**
1. 去掉全局 `busy`，改成**每个按钮自己的进行中状态**（例如 `pending[actionKey]`），一个操作卡住不影响别的按钮。
2. `api()` 加超时（建议 15 秒，打开浏览器这类可放宽到 30 秒），超时给出明确提示："××没有响应，可以重试"。
3. 打开登录窗口、启动浏览器这类慢操作，后端**立即返回**一个"已开始"，进度通过 `/api/state` 轮询体现，不让前端干等。
4. `run()` 里的 `refresh()` 不要 await（或者放到 finally 之后）。
5. 非 JSON 响应给出友好的错误文案。

**验收：** 人为让 `/api/account/open` 卡住 60 秒（测试里 mock），期间其他按钮仍可点击；15～30 秒后该按钮显示超时提示并可重试。

### B2【高】登录完成后状态不变（推断，和代码吻合）

**现象（用户反馈）：** 在平台上登录完了，工作台里的状态没变。

**原因，可能是以下几条叠加：**
1. **判断条件过严**（`local/login-status.mjs`）：
   - Grok（第 37 行附近）：必须同时看到"账号菜单"和"输入框或 Bot 列表"才算 `authenticated`；
   - Muse（第 40 行附近）：必须同时看到输入框、设置、资料库、目标四个元素且没有密码框；
   - 其他任何情况都返回 `unknown`，界面显示"登录待确认"。页面改版、语言不同、元素加载慢都会落到 `unknown`。
2. **只在专用窗口打开时检测**：窗口关掉后，如果之前从没判定为 `authenticated`，状态就停在 `unknown`（第 90 行附近）。用户登录后很快关窗，就会一直不变。
3. **检测有 15 秒缓存**（第 47 行 `interval=15000`），加上界面 5 秒轮询，用户登录后最多要等约 20 秒才可能看到变化，期间没有任何"正在检查"的提示。
4. **"已登录"不等于"可以接任务"**：README 写明登录成功后还要跑通一次真实任务，成员才显示"可以接任务"。如果这一步没有自动开始、或者界面没说明，用户看到的就是"登录完了还是不能用"。

**修法：**
1. 账号卡片只给用户看**一个**状态和**一个**下一步动作：
   - 未登录 → 按钮"去登录"；
   - 正在检查 → 显示"正在确认登录…"和转圈；
   - 已登录、正在做接入测试 → "已登录，正在测试能否接任务（约 1 分钟）"；
   - 可以接任务 → 绿色"可以用了"；
   - 需要你处理 → 写清楚是什么、按钮直达。
2. 登录窗口里加"我登录好了"按钮（或工作台上），点了立即强制检测（`force`），不受 15 秒缓存限制。
3. 判断条件放宽成"有输入框且没有登录表单/密码框"即可视为已登录，其余信号只作为加分；同时**把每次检测看到的信号记到日志**，方便定位"为什么判成 unknown"。
4. 判定已登录后**自动开始**接入测试，不需要用户再点。

**验收：** 用一个真实账号：打开登录窗口 → 登录 → 关窗，30 秒内卡片从"去登录"依次变到"可以用了"，全程不需要刷新页面或重启客户端。

## 2. 设计问题

### D1【最高】工作台是"给单个 Agent 下任务"，不是"协作"（已确认）

**代码依据：**
- `ui/workbench.jsx` 第 14 行：`memberId=draft.memberId||…`，输入框一次只选**一个**成员；
- 第 72 行：发送按钮的条件是这一个成员 `canDispatch`；
- 后续补充要求也发给同一个成员；
- 对话里没有成员之间的交接，不能 @ 其他成员；
- "先给我方案"可以拆步骤、每步选成员，但入口和心智模型仍是"让某一个 Agent 做事"。

**为什么最重要：** 产品的价值是"跨生态的几家 Agent 接力完成一件事，用户不用当中间人"。现在的界面让用户做的事，和直接打开 Muse 或 Grok 聊天几乎一样，只是多了一层。

**怎么改：** 见 [协作优先的工作台设计.md](协作优先的工作台设计.md)。核心是：用户交代一个目标 → 默认交给团队 → 生成"谁做哪一步、为什么"的分工 → 确认后自动接力 → 对话里能看到每次交接 → 右侧是大家共同产出的成果。

### D2【高】跨平台接力从未验证

所有真实测试记录（`evidence/grok-real.json`、`muse-real.json`、`studio-real.json`、`workbench-real.json`）都写着 `crossPlatformCollaborationTested: false`；真实任务内容是"读取健康检查接口、报时间"这类最小任务。

**建议的第一个真实验收：** Grok 找 3 条带原帖链接的 AI 热点 → 自动交给 Muse 写成 3 条推文草稿 → 结果出现在右侧文稿。不手动搬运；连续成功 3 次；记录每一步实际耗时。

## 4. 建议的顺序

1. **B1、B2**（按钮和登录状态）——用户每天都会碰到。
2. **O3** 格式化代码——单独一次提交，后面修改更安全。
3. **D1** 按设计文档改造工作台，同时完成 **D2** 的第一个真实接力验收。
4. B3、O1、O2、O4～O6。
