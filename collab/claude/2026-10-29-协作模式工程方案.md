## 0. 一句话

**用"步骤依赖图"替换"按顺序一个接一个"，在它上面搭出三种协作方式；双盲靠"领取和读取时只给该给的材料"来实现；比对由用户已有的 Agent 按固定格式交回，程序只做确定性检查；分歧变成正文里的决策卡；改稿由已有的 Agent 归纳成规则，用户就地一键确认。**

Hub 不新增自己的大模型调用，不让用户多付一份 API 费用。

## 1. 现在的代码为什么做不到

| 问题 | 位置 | 后果 |
|---|---|---|
| 只能顺序推进 | `engine.mjs` 的 `advance()`：找第一个"前面都已完成"的 waiting 步骤 | 无法让多个成员同时开工 |
| 领取时拿到前面所有成果 | `step.claim` 返回 `predecessorDocumentIds = 所有 position 更小且已完成的步骤的文档` | 做不到双盲 |
| 读取只检查"是不是项目成员" | `api.mjs:190`（read_document）、`files.mjs:66`（下载附件） | 成员可以直接读到其他成员的底稿 |
| 提交只有标题、正文、来源 | `submit_work` 的 `items` | 程序无法比对"谁说了什么"，也无法检查汇总有没有漏掉分歧 |
| 分工写死成三个槽位 | `shared/recipes.mjs` 的 discover / verify / write，以及 `project.slots` | 无法按目标选择协作方式 |

## 2. 数据改动（都在 `hub_v2_records` 上新增字段或类型，不另建数据库）

### 2.1 步骤（step）新增字段

| 字段 | 取值 | 作用 |
|---|---|---|
| `dependsOn` | stepId 数组 | 取代按 position 排序推进；position 只用于显示 |
| `role` | `explore` / `integrate` / `blue` / `red` / `verify` / `solo` / `revise` / `distill` | 决定提交格式和检查规则 |
| `visibility` | `blind` / `deps` | `blind`：只能看共同材料；`deps`：可以看依赖步骤的成果 |
| `optional` | true / false | 可选分支到截止时间还没交，汇合照常进行 |
| `stance` | 文本，可选 | 红蓝对抗时的立场说明，由系统模板生成 |

### 2.2 运行（run）新增字段

`mode`（`race` / `redblue` / `solo`）、`members`、`integratorId`、`maxVerifyRounds`（默认 1）、`joinDeadlineAt`。

### 2.3 新增记录类型

| 类型 | 内容 |
|---|---|
| `claim` | 成员提交的单条论断：`{runId, stepId, memberId, text, sources:[{url, canonical}]}`，从提交内容拆出，便于比对和引用 |
| `disagreement` | `{runId, documentId, topic, type: fact/reasoning/preference/constraint, positions:[{memberId, claimId, text}], round, status: open/verifying/resolved_by_evidence/pending_owner/decided, decision, decidedAt}` |
| `read_log` | `{memberId, objectId, allowed, at}`，用来证明隔离确实生效 |
| `edit_signal` | `{documentId, fromVersionId, toVersionId, diffStat}`，改稿归纳规则的原料 |

规则仍然用现有的 `knowledge` 记录（已有范围、版本、批准和撤回），只新增 `origin: {documentId, versions}` 和 `status: suggested`。

## 3. 引擎改动

### 3.1 推进：依赖图取代顺序

`advance()` 改为：**所有依赖都已完成（或可选依赖已超过截止时间）的 waiting 步骤，在同一个事务里全部变为 ready。** 多个步骤可以同时就绪，这就是并行。

创建运行时做校验：无环、每个步骤只有一位责任成员、依赖都存在。旧配方映射为一条直线依赖（`dependsOn = [上一步]`），行为和现在完全一样。

### 3.2 三种方式编译成步骤图（新文件 `shared/modes.mjs`，取代 `recipes.mjs` 的固定槽位）

**赛马互证（研究类默认）**

```text
explore(A) ─┐
explore(B) ─┼─► integrate(I) ─► [按需] verify(V) ─► 交付
explore(C) ─┘
```

- explore 步骤 `visibility: blind`，没有依赖，同时就绪。
- **比对和汇总合并成一步**（integrate），由整合成员 I 一次完成，少叫醒一次。I 可以是参与 explore 的成员之一，也可以另选。
- 事实类分歧需要补证时，才追加 verify 步骤（见 3.5）。

**红蓝对抗**

```text
blue(B) ─► red(R) ─► blue 修订(B) ─► 交付（仍未解决的质疑变成决策卡）
```

- red 能看到 blue 的成果和原始来源，带有"挑出缺乏依据的地方"的立场。
- 默认只对抗 1 轮。Liang et al. 2023 指出对抗要适度；用户可以调到最多 3 轮。

**单兵直通**：一个 solo 步骤，直接交付。

**依赖自动接力**：目标里如果既要研究又要成稿，系统在 integrate 后面自动接一个 revise/write 步骤，不让用户自己去选"接力"。

### 3.3 双盲：所有读取路径只给"该给的"

新增一个统一的可见性函数 `canRead(tx, memberId, object)`。下面三种情况为允许，其余一律拒绝：

1. 自己提交的成果；
2. 当前分配给该成员的步骤，其**依赖链上游**的成果，而且该步骤是 `visibility: deps`；
3. 项目共同材料：用户上传的资料、已批准的知识。

在三个地方使用它：
- `step.claim`：`predecessorDocumentIds` 改为"依赖链上游的成果"。explore 步骤没有依赖，所以什么都拿不到。
- `read_document`（`api.mjs:190`）：用 `canRead` 替换 `requireProjectAccess`。
- 附件下载（`files.mjs:66`）：同上。

拒绝时返回 404，不泄露标题；每次读取都写一条 `read_log`。

叫醒消息只带编号，不带任务内容（botline、Paperclip 都是这样做的）。界面文案用"Hub 输入已隔离"，不写"完全独立"，因为原平台自己的记忆不在 Hub 的控制范围内。

### 3.4 提交格式：加上"论断"和"比对"

**explore 和 solo**：`items[].claims: [{text, sources:[url]}]`。研究类必须填，写作类可以不填。

**integrate**：除了成稿，还必须交 `comparison`：

```json
{
  "agreements": [{ "claimIds": ["clm_a1", "clm_b3"], "text": "…" }],
  "disagreements": [{ "topic": "…", "type": "fact|reasoning|preference|constraint",
                      "positions": [{ "claimId": "clm_a2", "text": "…" }, { "claimId": "clm_b1", "text": "…" }],
                      "recommendation": "…" }],
  "omitted": [{ "claimId": "clm_c4", "reason": "与目标无关" }]
}
```

**程序检查（确定性，不调用模型）：**
- **覆盖检查：** 每条 explore 论断都必须出现在 agreements、disagreements 或 omitted 中的某一处。有遗漏时，步骤进入 `needs_review`，提示"有 N 条论断未处理"。这一条专门对付"大乱炖"里悄悄丢掉分歧的情况。
- **来源独立性：** URL 先规范化（统一大小写，去掉 utm 等跟踪参数和 `#` 片段，去掉 `www`，统一结尾斜杠）。只有**至少两位成员、各自至少有一个不同的规范化来源**的一致项，才标为"已互证"；所有来源都相同时，标为"同一来源"。这一条专门对付"互相点头"。
- 引用的 claimId 必须真实存在，并且属于本次运行。

**red**：`objections: [{target: claimId 或段落引用, problem, evidence: {url | quote | check}}]`，或者 `noneFound: {checkedScope}`。没有 evidence 的质疑**不被接受**（进入 needs_review）；`noneFound` 是合格结果。系统**不统计**质疑条数。

**blue 修订**：对每条质疑回复 `accept` 或 `reject` 并附理由；被拒绝、但 red 仍坚持的质疑变成分歧。

### 3.5 分歧的处理

integrate 提交后，为每条分歧建一条 `disagreement` 记录：

| 类型 | 处理方式 |
|---|---|
| 事实 | 自动追加 1 个 verify 步骤，交给不是分歧双方的成员（没有的话交给整合者），**只给这条分歧的论断和原始来源**。补证成功则标为 `resolved_by_evidence`，否则转为 `pending_owner` |
| 推理 | 同上；补证后仍有分歧，转为 `pending_owner` |
| 偏好、约束 | 直接转为 `pending_owner` |

- 轮次由程序计算，上限是 `maxVerifyRounds`（默认 1）。没有新证据就不再追加。
- **有待决分歧时，成果照样交付**，稿件标"待你决定 N 项"，不冻结整个运行。

### 3.6 决策卡（浅色主题）

- integrate 的成稿里，在分歧位置写占位符 `{{decision:序号}}`。引擎把它替换成 Tiptap 自定义节点 `<hub-decision id="dis_x">`。
- 新命令 `decision.choose {disagreementId, revision, choice, requestId}`，只有所有者能调用。choice 可以是：选某一方、两种都保留（写成条件结论），或者自己写。
  - 服务端校验 revision 后，生成新的工作稿版本：把节点替换成所选内容；同时更新分歧状态，在群里记一条消息。
  - 稿件已经被改过、revision 对不上时，返回 409，前端显示对比，不自动合并。
- 卡片上有一个可选的勾选框："同类问题以后都这样选"，勾上后生成一条规则建议（走 3.7 的确认流程）。
- 视觉：浅色底 `#FFF8EB`、琥珀色细边框，并排显示双方的头像、主张、来源，两个"采纳"按钮。选完后折叠成一行"已按你的选择：…（可撤回）"。

### 3.7 改稿即训练（不调用 Hub 自己的模型）

1. 用户保存稿件（`document.edit`）时，服务端算出文本差异。改动明显时（删除或替换了整句、整段），记一条 `edit_signal`。
2. 用户停止编辑 10 分钟后，同一份稿件合并成**一个** distill 步骤，交给这个项目的整合成员（用户已有的 Agent），让它根据改动前后的差异归纳出**最多 1 条**规则建议。也可以选择"没有可归纳的规律"。
3. 归纳出的规则以 `knowledge(status: suggested)` 的形式，出现在**稿件页边**："Dot 从你的修改中总结：『开头先讲实操场景』 [以后都这样] [只这次]"。
   - 点"以后都这样"，就是现有的 `knowledge.review → approved`，默认只在本项目生效；
   - 规则列表里可以改成全局，也可以一键撤回。
4. 下一次运行开始时，规则自动进入 `run.knowledge` 快照（现有机制）。交付物记录当时用了哪些规则版本。
5. **是否起效：** 在某条规则生效后产出的稿件上，用户如果又做了同类修改，这条规则标为"可能未起效"，**只提示一次**，不自动生成新提案。

**限制（防止死循环）：**
- 每个项目同时最多 1 个进行中的 distill 步骤；
- 最多 3 条待确认的规则建议，超出的排队；
- 规则正文只能是文字。需要"程序执行"的规则，只能从固定的检查器目录里选（去重、必填字段、版本一致、来源独立），不能生成新代码；
- 规则建议显示来源（基于哪次改稿）。外部材料里的原话不能直接成为规则。

现有的 `style_signal`（emoji 判断，`engine.mjs:811`）并入这一套，不再单独处理。

### 3.8 安全边界：默认开启，不用配置

- 新成员默认"只准备成果"，接入时**不出现**任何授权表单。
- Hub 本身不替成员执行对外动作。如果成员的提交里带了对外动作的请求（发布、发送、付款），生成一张决策卡："Dot 想发布到 X：[允许这一次] [拒绝]"。
- 成员页只放一行说明："Hub 只能约束经过 Hub 的操作"。

## 5. 界面（浅色，延续 #6 的结论）

- **新建项目：** 输入目标 → 系统推荐一种方式（三张小卡，每张一句话说明，研究类默认"赛马互证"）→ 勾选成员（显示信源标签）→ 开始。不出现岗位下拉框。
- **群聊：** 每个阶段一行紧凑进度条，例如"独立研究完成 · 8 项一致（5 项已互证）· 2 项分歧待你决定 [查看依据]"。
- **审阅：** 决策卡就嵌在正文里；规则建议在页边；"待我决定"页面只汇总所有决策卡的入口。

## 6. 实施顺序和测试（每一步都有确定性测试，最后才上真实平台）

| 顺序 | 内容 | 必须通过的测试 |
|---|---|---|
| 1 | 先修 #9 的三个阻塞：分页、锁的范围、规则上限 | 150 篇稿件时能看到最新的；4 个成员并行加上用户持续编辑时，没有保存失败 |
| 2 | 依赖图引擎和三种方式 | 3 个成员赛马：3 个 explore 同时就绪，integrate 等齐（或等到截止时间）才就绪；旧配方行为不变 |
| 3 | 双盲隔离 | A 用自己的凭证读 B 的 explore 成果（文档和附件）→ 404，并有 read_log；整合者能读；叫醒消息不含正文 |
| 4 | 提交格式和程序检查 | 两位成员引用同一个 URL（一个带 utm）→ 标"同一来源"；integrate 漏掉一条论断 → needs_review |
| 5 | 分歧和决策卡 | 事实分歧只追加 1 次补证；偏好分歧直接进决策卡；选择后生成新版本；revision 冲突返回 409 |
| 6 | 红蓝对抗 | 没有证据的质疑被拒；`noneFound` 合格；被拒绝且仍坚持的质疑变成决策卡 |
| 7 | 改稿即训练 | 连续编辑只生成 1 个 distill；确认后下一轮快照包含这条规则；同类修改再出现时只提示一次 |
| 8 | 真实平台 | 用两家不同平台（例如 Grok + Perplexity）跑一次赛马互证，按所有者现有研究组织的目标，从头到尾实际走通 |

## 7. 成本说明

赛马互证每轮要叫醒"参与成员数 + 1"次（整合），加上必要的补证。比对和汇总合并成一步，就是为了少叫醒一次。没有新证据时不追加步骤。项目设置里显示"每轮大约叫醒 N 次"，取不到的费用标"未知"。
