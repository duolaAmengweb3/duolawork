# 消息接收状态误报修复

## 真实问题

2026-11-06，ATEL 群的“你在线吗”于北京时间 19:35:20 发送。Gemini2VPS 接收端于 19:35:24 开始处理此消息，19:35:55 在 Hub 领取，19:37:38 回群完成。用户在 19:35:48 截图时，界面显示“1 条消息排队中”，并用固定说明声称它在等待正在处理的工作。

核对时，其他独立会话没有占用这条消息的执行队列。错误来自展示：未领取消息默认被叫作排队，原生接收端的 `working` 回执又没有进入展示判断。回复耗时约 2 分 18 秒是真实的；本次展示修复不宣称缩短了模型响应耗时。

## 修复范围

聊天底部、消息进度和成员状态使用同一份判断：

- 未收到对应消息的实际接收证据：等待接收。
- 对应原对话已开始接收此消息，尚未领取：正在接收。
- 原生端确认已投递，尚未领取：已送达，等待接收。
- 原生端明确报告此消息排队，或当前绑定的同一原对话仍在处理已确认的前一条消息：排队中。能定位前一条消息时提供查看入口。
- Hub 领取后：处理中，优先展示 Agent 的实际进度。
- 回群完成后：清除待处理提示，不被滞后的原生状态改回排队。

只按精确消息和原生对话判断，不按整个账号的忙碌状态推断。进度卡片显示各接收者各自的原因，移除通用的“正在处理时收到的补充会排队”说明。
