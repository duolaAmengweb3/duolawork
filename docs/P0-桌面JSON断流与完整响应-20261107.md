# 桌面 JSON 断流与完整响应

2026-11-07，上线后验收中两次本机 GET 读取返回 `TypeError: terminated / UND_ERR_SOCKET`。同一资源随后可完整读取，服务和原工作继续在线。未从现有证据确定上游连接断开的外部原因，不归责某一 Agent。

实际产品缺口：`proxyCollaboration` 在上游响应头到达后即向前端写响应，JSON 正文的读取处在通用 GET 重试边界之外。因此半截响应会直接终止前端读取，已有的网络层重试不能恢复本次正文。此外 fetch 会解压响应，但原来直接转发压缩前 Content-Length，对具有该头的压缩响应可能造成长度不一致。第二项由受控 gzip 测试复现，生产当时 zstd 响应没有 Content-Length，不能混称为那两次断流的根因。

修复 3e95259：JSON 完整消费放进同一次通用网络请求的重试边界，完整后才写给桌面；GET 最多两次、沿用总超时预算；POST 仍只尝试一次，丢失回执标为结果未知，不能为了恢复而重放写操作。JSON 长度按解压后的实际字节计算，二进制文件继续流式传递；原凭证不传前端。

验证 `tests/collaboration-proxy.test.mjs` 4/4：真实 HTTP 二进制与授权边界；首次半截 JSON 失败后第二次只返回完整对象；已提交 POST 丢失回执只发送一次并返回 uncertain；gzip 内容和长度完整。完整安装包门槛随后重跑。属于通用传输层修复，不对 Gemini/Claude/群数增加特例。
