# Agent Hub v1 开发与验收对照

Codex · 2026-10-30。本文只细化执行和证据，不另立产品方案。

**唯一产品依据：** [Claude《v1 产品方案（定稿）》be1e76c](https://github.com/duolaAmengweb3/agent-hub/blob/be1e76c4e9c08f646932ea258045ec4417c321c6/docs/v1%E4%BA%A7%E5%93%81%E6%96%B9%E6%A1%88%EF%BC%88%E5%AE%9A%E7%A8%BF%EF%BC%89.md)。执行与差异在 [#16](https://github.com/duolaAmengweb3/agent-hub/issues/16)；原型和复审在 [#17](https://github.com/duolaAmengweb3/agent-hub/issues/17)、[PR #18](https://github.com/duolaAmengweb3/agent-hub/pull/18)。与本文冲突时，以定稿为准。

## 1. 做出的产品

用户已有的 Grok Bot、Dot 接入后，交代一次目标，成员真实领取、分工、交接、补证、自查，交回可编辑成果。默认一份最终成果，用户明确选择时才并排独立提交。修改、取舍和经用户确认的规则能在下一轮沿用。

- 不新增 Hub 的模型调用。汇总、语义检查、补证、归纳规则由原 Agent 做，程序负责依赖、访问控制、结构校验、版本、调度和计数。
- 不用浏览器点聊天伪装后台协作。第一批按定稿接 Grok 的 MCP + Routine、Dot 的 MCP + Events；具体协议、授权、订阅和回执条件先做技术核对。
- 接口、协议或 SDK 实际不满足时，记录原始证据和影响，回 #16 提出差异。未经所有者确认不换成网页脚本、轮询或另一家 Agent 当成完成。
- Muse 第二批；不顺便加入组织架构、排名、OKR 或其他平台。开发顺序只是依赖安排，交付范围仍是完整 v1。

## 3. E0–E12 逐项完成条件

所有项由 Codex 实现并提供证据，Claude 按定稿复核。每个 PR 写明 E 编号、定稿条款、测试场景、证据和剩余问题。

| 项 | 必须交付 | 必须验证什么 |
|---|---|---|
| E0 | 分页、项目级并发控制与带抖动重试、规则上限 | 150 篇稿件仍取到最新；4 位模拟成员并发写、用户持续编辑无丢稿/保存失败；每项目最多 1 条试行、3 条待确认，直接 API 也不能绕过 |
| E1 | 安排编译依赖图；旧配方可兼容 | 独立研究可并发，汇总等依赖齐全；重复领取/提交不重复推进；三种协作方式与并排模式分别按定稿编译 |
| E2 | 领取、读文档、读附件统一权限判定与读取日志 | 用成员 A 的凭证读成员 B 独立阶段成果/附件返回 404；自己、合法上游和公共资料可读；换 ID 不能绕过 |
| E3 | claims 与全部去向记录、检查意见证据 | 漏去向退回补交一次，仍缺失明确标注；“不开放原始数据”等无数字但影响可行性的论断即使被丢弃仍能让审阅者看见；无证据的质疑不冒充有据纠错 |
| E4 | 自查、内部修订上限、部分达标状态 | 默认内部修订 1 次，可配 0–3；仍不达标交付并列缺口，不显示完成；用户修改只保留历史自查说明，主动复查才唤醒，并绑定提交版本 |
| E5 | 事实补证与取舍决策分开 | 事实冲突每项最多补证 1 次，中性输入不带成员名/多数意见；取舍直接进入正文决策卡；决定可撤回，正文与计数同步 |
| E6 | 本轮记录由真实提交与来源关系计算 | 每项能追到论断、原始来源、核查者；同 URL 的 utm 变体去重，同域两篇论文不合并；未经核查不升级独立互证；额外贡献连续三轮为零只建议单人，不自动切换 |
| E7 | 改稿归纳、页边便签、规则确认/撤回/运行快照 | 连续改稿不生成便签风暴；只在用户确认后生效；下一轮带具体版本；“已带入”与“结果已符合”证据分开；临时要求优先，不静默覆盖长期规则 |
| E8 | 独立并排交付 | 不创建整合步骤；各自自查；采用段落保留原文与出处；工作稿可继续编辑，重复采用不重复插入 |
| E9 | Grok 四步、Dot 三步真实接入，投递/订阅/回复分开 | 先核对协议、SDK、签名与平台实际行为；双平台均有授权、工具调用、任务领取和结果回收证据；Grok 忙碌按 90 秒/3 分钟/6 分钟重试；Dot 工具可见但不可调用、事件迟到不能误标成功；重投同一事件不重复建任务 |
| E10 | 按原型与定稿第 4 节制作正式界面 | 1440×900 与 1280×800 实际操作和截图；跨页面计数一致；采纳/撤回不跳阅读位置；失败有三操作；已连接/可接任务等状态来自真实证据；所有者确认观感 |
| E11 | 前端接真实服务；快照加增量事件 | 正式数据不以 localStorage 示例为来源；真实状态能更新；断线重连恢复且不重复事件；服务/页面重启后项目、稿件、决定和规则保留；保存失败明确提示 |
| E12 | 成员归属人 | 每位成员有归属人，v1 都是所有者；读取和派发不能串到其他账号；不提前实现跨主体组织功能 |

## 4. 真实账号验收：同一目标的六条主线

使用 Grok + Dot 的真实账号，保留同一目标，另建可追踪的运行记录。正常路径必须由真实成员完成；失败或未达标场景可以人为设置受控条件，但要写明注入条件，不能用模拟回复冒充真实返回。

| 场景 | 必须看到的结果 | 对应证据 |
|---|---|---|
| 正常 | 两位领取并提交 → 汇总 → 自查 → 一份成果；计数逐条可点开 | 双平台任务/提交标识、Hub 步骤事件、最终文档版本、截图/录屏 |
| 来源冲突 | 定向补证一次，有据纠错或未确认；路线取舍出现决策卡 | 原论断、来源、补证任务与返回、决策原位和处理后计数 |
| 成员失败 | 收到 1/2，提供重试缺失成员、用已有结果成稿、终止；部分成稿明确缺口 | 受控失败条件、重试记录、剩余交付和部分标记；重复操作不重复任务 |
| 人工修改冲突 | 交回修改后继续改，候选不覆盖，三方对比后由用户应用 | 原稿/派发基准/当前人工稿/候选版本；提交时间与操作录屏 |
| 不达标 | 一条故意无法满足的标准 → 内部修订一次 → 部分达标且列缺口 | 真实成员自查与修订结果、次数、未达标项；不能只测字段非空 |
| 规则复用 | 人工改稿 → Agent 归纳 → 便签 → 用户确认 → 下一轮带入 | 修改差异、归纳任务、用户确认记录、下一轮规则版本快照；结果符合另需段落或程序校验 |

“成果可用”单独核对：最终稿覆盖用户目标和合格标准；重要论断有去向；不把不同偏好拼成矛盾的大杂烩；事实与未确认内容分开；没有内容证据的“都同意”不算协作价值。做不到的标准应诚实部分达标，不能靠更改标准把验收变绿。

## 5. 四类证据与状态不能混用

验收汇总只放在 #16，一行一个场景，记录方案条款、E 编号、构建/提交、运行/步骤/文档版本、预期、实际、证据链接、状态、复验者。截图和机器记录放现有 evidence 目录，不另开分散的过程文档。

| 证据类 | 能证明 | 不能替代 |
|---|---|---|
| 模拟交互 | 流程、异常控制与 UI 行为 | 真实平台接入 |
| 字段与确定性校验 | 权限、结构、版本、并发、计数和来源归一化规则 | 语义正确、事实独立或文稿可用 |
| 真实往返 | 授权、通知、领取、工具调用、完成与结果回收 | 成果满足目标 |
| 成果可用 | 真实目标、正文、来源和验收标准逐项核对 | 稳定性、隔离和异常恢复 |

统一状态：未验证 → 开发中 → 自测通过/待复验 → 复验通过；未通过记失败与复验步骤。平台条件不满足记明具体阻塞，保留证据。不能把 UI 25 项通过改写成 E0–E12 已完成。

## 6. 最后交付门槛

1. E0–E12 全部可逐项对账；六条真实主线有证据；四类证据分列。
2. 修复必须增加能重现该问题的检查，补测相邻状态（例如选择、撤回、刷新；复查期间继续编辑）。代码和证据使用同一构建，复验失败不删除历史记录。
3. 界面逐条对照定稿第 4 节和本轮审计，不只检查截图无溢出；点击后的结果、错误与恢复也要验证。
4. 按 AGENTS.md 在正式发布时运行 `verify:session` 和 `deliver:local`，核对实际桌面、服务与构建一致。不得为升级清空账号、换资料目录或强制重新登录；有运行任务先交接。
5. Claude 复核实现与证据，所有者确认视觉与操作体验。发现影响范围/定位的差异，先回 #16；不自行降级，也不把待复验称作完成。

不能承诺软件永远没有新问题；可执行的“不偏”保证是：固定条款、逐项对应、真实目标验收、失败留痕和独立复验，任一门槛不满足就不交付成“已完成”。

## 7. 所有者需要配合的事

现在保留现有 Grok、Dot 登录，不需要重新登录或提供密码。Codex 先准备好可用的正式接入入口、可达服务和可核对的测试流程，再请所有者在原平台完成本人授权/配对。只有平台实际要求本人操作时才打断所有者；不把内部状态确认或开发自测转交给所有者。登录、授权、工具连通、通知送达、任务领取、成果回收分别记录，不能一项代替另一项。
