## 1. 一句话

**把你已经在用的几个 Agent（Grok、Dot……）组成一个团队：你交代一次目标，它们自己分工、交接、互相纠错，达标后交回一份能直接用的成果；只有真正需要你取舍的事才交给你；你的修改和决定会被记住，下一次自动带上。**

产品围绕所有者的三件事：

| | 用户得到什么 | v1 做什么 |
|---|---|---|
| **接上** | 自己的 Agent 能被叫醒、领任务、交成果 | Grok Bot、Dot 真实接通；成员页显示真实状态 |
| **有用** | 协作比一个 Agent 好，而且看得出好在哪 | 先独立后整合、冲突时补证、达标后才提交、"本轮记录" |
| **沉淀** | 成果和经验留下来，下次用得上 | 成果页、知识库（规则和资料）、决定存档、规则自动带入下一轮 |

## 2. 两个核心原则

1. **用户只关心结果。** 几个 Agent 怎么分工是系统内部的事。默认只交给用户**一份达标的最终结果**；用户明确要求时，才把各成员的成果并排给他对比。
2. **一个 Agent 能做好的事，就交给一个。** 需要别人的信源，或者需要纠错时，才叫别人。产品是否成功，不看参与人数。

## 3. 完整使用流程（以"研究智能戒指的产品机会"为例）

| 步骤 | 用户做什么 | 系统和成员做什么 |
|---|---|---|
| ① 接入 | 在"成员"页添加 Grok、Dot（第 6 节） | 完成真实往返测试后，状态变为「可接任务」 |
| ② 新建 | 点「+ 新建项目」，说目标 | 三步向导（4.2） |
| ③ 安排 | 看安排卡，可修改；点「开始」 | 按目标给出默认安排；交付形式默认「一份最终结果」 |
| ④ 执行 | 不用管 | 派发任务；独立阶段互不可见；出现冲突时定向补证；整合；**对照合格标准自查**，不达标就内部修订 1 次 |
| ⑤ 成果 | 打开审阅 | 一份成果，加一行「本轮记录」；需要取舍的地方以决策卡出现在正文原位 |
| ⑥ 改与定 | 改稿；在决策卡上选择；在页边便签上点「以后都这样」或「只这次」 | 版本受保护，Agent 返回的稿子不覆盖人的修改；确认的规则进入知识库 |
| ⑦ 下一次 | 在项目里直接说新任务 | 沿用安排和规则；依据里显示规则「本轮已带入」 |

## 4. 页面规格（逐条实现）

**通用视觉：**
- 浅色主题，白色内容区，浅灰导航，一个蓝色强调色。
- 字号：界面文字 14px、正文 16px、辅助信息不小于 12px。
- **琥珀色只用于"需要你决定"，绿色只用于"可接任务 / 已完成"，红色只用于"需要处理 / 有缺口"。**
- 以 PR #13 的界面为基础修改，不重做。

### 4.1 导航

左侧窄栏，从上到下依次是：**项目、成果、待我决定、知识库、成员**；底部是设置和头像。

- 「待我决定」有未处理项时，显示数字徽标。
- **不要做成：** ✗ 再加一套"团队"入口 ✗ 把"成员"放进设置里。

### 4.2 新建项目（三步）

| 步骤 | 确切内容 |
|---|---|
| 第 1 步 | 一个大输入框，提示文字：「你想让团队做成什么？例如：研究智能戒指有没有适合个人开发者的机会」。下方可以「添加资料」（文件或链接）。按钮：「下一步」 |
| 第 2 步：安排卡 | 见 4.3 |
| 第 3 步：节奏 | 单选：「只做一次」（默认）/「定期做」。选定期时，出现时间点（可多个）和时区。按钮：「开始」 |

- ~~已有项目里发起新任务时，不走向导：直接在项目输入框里说，沿用该项目的安排卡~~（**2026-10-30 更正：** 这条导致"有人在线吗"被当成任务，是方案的逻辑错误）。**群聊默认是聊天：** 闲聊和打招呼由系统用状态回复，或由牵头成员用一句话回复，不创建运行；问进展由系统直接回答；明确的工作要求，由牵头成员先回复「要我按『{当前安排}』开始吗？」，附「开始」「只是聊聊」两个按钮，**用户点了「开始」才创建运行**；分不清是聊天还是工作时，按聊天处理。审阅页、决策卡上的按钮本来就是明确动作，不需要再确认。输入框旁边保留「调整安排」文字按钮。
- **不要做成：** ✗ 岗位下拉框 ✗ 填写流程节点 ✗ 开头就设置权限 ✗ 弹出长篇说明。

### 4.3 安排卡（新建第 2 步，以及项目里的「工作安排」）

```text
交付形式   ● 一份最终结果（推荐）   ○ 各自提交，并排对比
怎么做     ● 各自研究，再由一位汇总   ○ 一位做，另一位检查   ○ 一位直接完成
参与成员   ☑ Grok（X 实时讨论）  ☑ Dot（ChatGPT 应用、邮箱）  ☐ Muse（未连接）
汇总/检查  [Dot ▾]
合格标准   · 每条结论附来源  · 缺少的信息写明缺口  · {从目标里提取的要求}   [+ 添加]
           [让团队安排]                                           [开始]
```

- **默认值来自固定规则，不调用模型：**
  - 目标中含有"研究、调研、找、对比、评估"→ 默认「各自研究，再由一位汇总」；
  - 含有"方案、计划、决定、评审"→ 默认「一位做，另一位检查」；
  - 其他情况 → 默认「一位直接完成」。

  安排卡上用小字注明「按目标类型给出的默认安排，可以修改」，**不能写成"AI 已分析"**。
- **「交付形式」：**
  - 「一份最终结果」：用户只收到一份结果（见 5.4）；
  - 「各自提交，并排对比」：每位勾选的成员独立完成、互不可见，**没有汇总步骤**；「怎么做」这一行隐藏，「汇总/检查」也隐藏。
- **「合格标准」：** 预填两条通用标准，再从目标里提取要求（例如"附实测数据"）。用户可以增删。这是成员自查和整合检查的依据（5.4）。
- **「让团队安排」：** 由已勾选成员中的**一位**（默认是汇总者）拟一份安排草案，按钮旁小字写「会额外叫醒 {成员名} 一次，费用以平台为准」。
  - 等待时显示「等待 {成员名} 领取 / 正在拟定」；
  - 用户随时可以直接点「开始」用当前安排。草案晚到的话，以「稍后建议」显示，**不自动替换、不自动开跑**。
- **多样性提示：** 勾选的成员中有两位以上来自同一平台时，在成员行下方用浅灰小字显示：「这几位来自同一平台；是否互补，可参考过去的成果。」**不阻止开始。**
- **搭配记录：** 同一组成员在同类项目中满 3 轮后，在成员行下方显示一行事实，例如：「Grok + Dot · 5 轮 · 有据纠错 3 · 独立互证 12（样本 5 轮）」。不排名，不打分。
- **不要做成：** ✗ 「赛马」「红蓝」这类术语 ✗ 必须先选方式才能开始 ✗ 草案自动开跑 ✗ 编造时间或费用（"约 300 Token"之类）。

### 4.4 项目页（群聊状态）

布局：左边是项目列表，中间是群聊，右边是可收起的侧栏，有「成果 / 资料 / 本群成员 / 依据」四个标签。

**顶部一行（高 56px）：** 项目名 · 成员头像 · 状态，加上「工作安排」「暂停」两个按钮。状态示例：
- 「各自研究中 · 互不可见 · Grok 已交付 · Dot 研究中」
- 「汇总中」
- 「本轮已交付 · 1 项待你决定」

**群聊里的消息类型：**

| 类型 | 样子 |
|---|---|
| 用户消息、成员的正常消息 | 聊天气泡 |
| 交接 | **一行**，无边框：「G → D　Grok 的研究已交给 Dot 汇总 · 查看」。**有缺口时**，这一行末尾显示红色「有缺口」，并默认展开缺口说明 |
| 补证 | 一行：「因 2 处数据冲突，请 Grok 补证 1 次」 |
| 成员掉线 | 浅黄色提示条：「收到 1/2：Grok 已交付，Dot 未响应（已等待 {时长}）」，三个按钮：「只重试 Dot」「用已有结果成稿（标明缺口）」「终止本次」 |
| 成果卡 | 标题、份数，加一行「本轮记录」（5.6），按钮「审阅」；有待决项时，显示「{n} 项待你决定」 |

- 状态以真实回执为准：「等待领取」和「已领取」分开显示。
- **不要做成：** ✗ "正在思考…"假动画 ✗ 每次交接一张大卡片 ✗ 没有回执时显示预计用时。

### 4.5 审阅

- **进入方式：** 点成果卡上的「审阅」，或点项目列表里的「审阅成果」。**点项目本身，总是进入群聊。**
- **布局：** 正文占主要区域（可视区域至少占面板高度的 65%）。顶部一行依次是：稿件标签（01 / 02）、「版本 {n} ▾」（原稿也在这个下拉里）、「出处」「…」（复制、导出）；右端用小字显示「已保存」。
- **自查结果（2026-10-30 补充，因 #17 评审发现遗漏）：** 正文标题下方，「本轮记录」那一行的前面，显示「合格标准 3/3 符合」，点击展开逐条自查结果，包括每条的检查者和对应段落。有不符合项时，改为红色「部分达标 · 1 项未达标」，展开后显示未达标项和缺口。并排对比模式下，每一栏顶部各自显示自己的自查结果。
- **用户自己修改之后（2026-10-30 补充，PR #18 审计）：** 自查是检查**成员交付**的，用户自己的修改或在决策卡上的选择，**不会触发重新自查**，也不显示"待重新自查"这种没有人负责的状态。显示改为灰色的「自查基于版本 {n} · 之后有你的修改」。如果用户想要复查，点旁边的「让 {成员名} 按标准再查一次」，这会明确叫醒一次该成员。
- **格式工具栏：** 选中文字时才浮出。
- **底部一行：** 「采用成果」「弃用」「让 {成员名} 改」。写「采用成果」，是为了和决策卡上的「采纳此方案」区分开（#17 评审）。
- **「让 {成员名} 改」：** 在稿件旁展开一个输入框，可选择接收的成员，输入框是空的，不预填内容。发送时附上完整工作稿和基准版本。发送后**停在原稿件**；返回的结果作为「候选版本」，用户可以对比后应用，**不自动覆盖**。
- **并排对比模式**（交付形式选了"各自提交"）：各成员的成果按相同的小节左右并排，每节有「采用这段」，采用的内容放进下方的「我的工作稿」。
- **不要做成：** ✗ 发送后跳回群聊 ✗ 返回稿自动覆盖 ✗ 弹窗里预填一段示例要求。

### 4.6 决策卡（正文原位）

- **只用于取舍**，例如"用现成的 SDK 两周出 Demo"还是"自研算法多两个月但形成壁垒"。**事实问题不能做成决策卡**：有证据的事实走"有据纠错"，查不清的标"未确认"。
- **样子：** 浅色底 `#FFF8EB`，琥珀色细边框，宽度与正文一致。
  - 标题「待你决定：{主题}」；
  - 两栏并排，每栏有头像、成员名、主张（最多 3 行，可以展开）、来源链接和「采纳此方案」按钮；
  - 底部是整合者的建议，以及「两种都保留」「我自己写」两个按钮，外加一个勾选框「同类问题以后都这样选」（默认不勾）。
- **点击后：** 卡片原地变成选中的内容，变化的部分淡黄色高亮 3 秒，段末出现「已按你的选择 · 撤回」。**页面不跳动，滚动位置不变。**
- **不要做成：** ✗ 弹窗 ✗ 单独的决策页 ✗ 系统替用户选 ✗ 只显示结论、不显示来源。

### 4.7 页边便签（改稿即训练）

- **出现时机：** 用户停止编辑 10 分钟后，后台由汇总成员归纳；结果返回时出现在被修改段落的右侧页边。用户不在这篇稿子上时，项目列表上显示一个小圆点。
- **内容：** 「{成员名} 从你的修改里总结：『{规则，最多 40 字}』」，范围选择默认「本项目」（可选「同类项目」「全部项目」），三个操作：「以后都这样」「只这次」「改措辞」。
- 一篇稿子同时最多一张便签；整个项目最多 3 条待确认的规则。
- **不要做成：** ✗ 不经确认就生效 ✗ 默认对全部项目生效 ✗ 弹窗打断编辑 ✗ 宣称"模型已训练""永不再犯"。

### 4.8 成果页（新增）

- **紧凑列表，** 每行显示：标题、所属项目、交付成员、日期、状态（「待审阅」「已采用」「已弃用」「部分交付」）、版本数。
- **顶部：** 搜索框（搜标题和正文），筛选项目、状态、时间。
- **点一行：** 打开该稿件的审阅界面，左上角有「← 返回所属项目」。
- 数据复用现有的 document 和 version，**不另存副本**。
- **不要做成：** ✗ 卡片墙 ✗ 在列表里显示大段正文预览。

### 4.9 待我决定

- 两个标签：「待处理」「已决定」。
- 「待处理」里是所有未决的决策卡和对外动作请求，按项目分组；点击后跳到稿件中的对应位置。
- 「已决定」里每条显示问题、你的选择、日期，以及由此生成的规则（如果勾选了「以后都这样选」）。

### 4.10 知识库

- 两个标签：「规则」「资料」。
- **规则是紧凑列表，** 每行显示：状态（「待确认」「生效中」「已撤回」）、正文（最多 2 行）、范围、来源（「来自你在 {稿件} 的修改」/「来自决定」/「手动添加」）、「已用于 {n} 轮」、最近一次回执状态（5.7），以及「撤回」「修订」。
- 待确认的规则置顶，**并展开全文**。
- **冲突提示：** 本次任务的要求与某条规则冲突时，按本次要求执行，并在稿件页边提示：「本次要求与规则『{规则}』冲突，已按本次要求执行。」后面跟两个按钮：「保留原规则」「为这类情况另建规则」。
- **事实类资料**显示「来源时间 / 采集时间」，不设统一的过期时间。

### 4.11 成员页

- **每位成员一张卡片：** 头像、备注名、平台、信源标签、唤醒方式（「主动叫醒」/「定时检查」），以及状态：

| 状态 | 颜色 | 下方小字 |
|---|---|---|
| 未连接 | 灰 | 「连接」按钮 |
| 连接中 | 灰 | 当前进行到第几步 |
| 待验证 | 黄 | 「发送测试」按钮 |
| 可接任务 | 绿 | 「最近一次真实任务成功：{时间}」 |
| 需要处理 | 红 | 具体原因（如「授权已撤销」），以及「修复」按钮 |

- **很久没有真实任务时，** 只在小字里显示「状态较久未确认」，**不自动降级，也不要求重新登录**。派发任务前，先做一次平台允许的低成本检查；没有低成本检查的平台，以本次任务的领取回执为准。
- **搭配记录**放在页面底部（规则同 4.3）。
- **一行说明：** 「Agent Hub 只能约束经过 Hub 的操作；成员在自己平台上的工具和权限不受影响。」
- **不要做成：** ✗ 只有配置、没有真实往返就显示绿色 ✗ "示例成员"出现在正式界面。

## 5. 协作机制（后台怎样保证"有用"）

### 5.1 三种做法，编译成步骤

| 安排 | 步骤 |
|---|---|
| 各自研究，再由一位汇总 | 各成员 `explore`（互不可见）→ 汇总者 `integrate` →（有冲突时）`verify` 补证 → 自查 → 交付 |
| 一位做，另一位检查 | 执行者 `draft` → 检查者 `review` → 执行者 `revise` → 交付 |
| 一位直接完成 | `solo` → 自查 → 交付 |
| 各自提交，并排对比 | 各成员 `explore`（互不可见）→ 分别自查 → **并排交付，不整合** |

步骤之间按依赖推进：各成员的 explore 同时开始，integrate 等必要的输入都齐了才开始。

### 5.2 互不可见（独立阶段）

- 成员领取 explore 任务时，**拿不到**其他成员的成果；读文档、读附件也同样受限。
- 允许读取的只有三类：自己的成果、依赖链上游的成果、项目共同资料。
- 无权读取时返回 404，并记录读取日志。
- 界面上只说「互不可见」，悬停提示：「Hub 不会把其他成员的结论发给它；成员自己平台上的记忆不在 Hub 控制范围内。」**不写"完全独立"。**

### 5.3 结构化提交

- 研究类提交，要把结论拆成一条条论断（`claims`）：每条有正文和来源。提出者可以把某条标为「风险」。
- 汇总者提交时，**所有论断都要有去向**：
  - 采用的：列出编号；
  - 没采用的：按「背景重复」「与目标无关」「证据不足」分组列编号，每组一句话；
  - **影响目标、存在冲突、带有风险**的论断，必须逐条写明处理方式：「采用 / 有证据反驳 / 不适用（说明条件）/ 保留疑问」。
- 缺少去向时，程序退回补交一次；补交后仍然缺少，成果标「有未处理依据」，并在依据标签里列出。
- 检查者（「一位做，另一位检查」中的检查方）每条质疑都要附证据；「未发现问题」是合格结果。系统不统计质疑条数。

### 5.4 达标后才提交（所有者决定）

- 交付前，由**汇总者或检查者**对照安排卡上的「合格标准」逐条自查；"一位直接完成"时，由完成者本人自查。自查结果（每条「符合 / 不符合 + 原因」）随成果一起提交。
- 程序先检查能自动检查的部分：每条是否附来源、是否有缺口说明、是否有未处理的论断。
- 有不符合项时，自动在内部修订 **1 次**（项目设置里可以改为 0～3 次），用户看不到这个过程。
- 修订后仍不符合，照样交付，但成果卡标红色「部分达标」，并列出未达标的项和缺口。**不能显示"已完成"。**
- 并排对比模式下，每份成果各自自查、各自标注。

### 5.5 冲突时的定向补证

- 汇总时发现**事实冲突**，自动给一位非冲突方的成员（没有的话给汇总者）派一次补证，**只发给它冲突的论断和原始来源**。论断以中性格式列出，不写成员名，不写"多数人认为"。
- 每个冲突**最多补证 1 次**。补证成功，标「有据纠错」；仍然不清楚，标「未确认」。
- 属于**取舍**的冲突（路线、成本、偏好），不补证，直接做成决策卡。
- 「全员交叉检查一轮」作为可选开关，放在「工作安排」里，默认关闭；开关旁小字写「开启后，成员会互相核对彼此的论断，每轮多叫醒 {n} 次」。
- 改口规则：成员在看到别人的论断后推翻自己原来的论断，必须写明依据；没写的照样接受，但标「改口 · 未说明理由」，第一轮的原始论断保留。

### 5.6 本轮记录（"有用"怎么看得见）

成果卡上一行：「本轮记录：独有发现 {a} · 独立互证 {b}（多处引用 {c}）· 有据纠错 {d} · 待你决定 {e}」。点任意一个数字，打开「依据」标签中对应的列表。

| 数字 | 怎么算 |
|---|---|
| 独有发现 | 被采用、并且只有一位成员提出的论断数 |
| 独立互证 | 由成员核查过原始来源关系、确认相互独立的一致项数，注明核查者 |
| 多处引用 | 程序发现的、多个来源的一致项。程序**只往下降级**：同一规范化页面或 canonical 相同的，算同一页面；引用同一份公告的，**只有出自该公告的那条论断**算共享来源；**根域名相同不合并** |
| 有据纠错 | 同时具备原论断、反证、适用条件和核查者的修正数。证据有争议时，只算「处理过的质疑」，不计入 |
| 待你决定 | 进入决策卡的取舍数 |

- 四项（独有发现、独立互证、有据纠错、待你决定）都为 0 时，这一行换成：「本轮没有记录到额外贡献 · 查看依据」。
- 连续 3 轮如此，在成果卡下方提示：「最近 3 轮协作没有记录到额外贡献，要不要改为一位完成？」后面两个按钮：「改为一位完成」「保持现状」。**不自动切换。**
- **不要做成：** ✗ 综合评分 ✗ 成员排名 ✗ 宣称"优于单个 Agent"。

### 5.7 规则怎样进入下一次

- 运行开始时，把**生效中**的规则冻结成快照，随任务下发；记录每条规则的版本。
- 依据标签里，每条规则显示三种状态之一：
  - 「本轮已带入」：有派发记录；
  - 「结果已符合」：程序检查通过，或审阅成员给出了对应段落；
  - 「未确认 / 发现偏离」。
- 在某条规则生效后产出的稿件上，用户又做了同类修改时，便签提示：「『{规则}』好像没有起作用，要改一下吗？」，两个按钮：「改措辞」「删除这条」。**每条规则只提示一次。**

### 5.8 追加成员的规则

| 情况 | 谁决定 | 安排卡或群聊里显示的原因 |
|---|---|---|
| 需要某位成员**账号里实际可用**的信源 | 程序根据成员登记的能力建议；能力未知就标"未知" | 「建议加 Grok：需要 X 上的讨论」 |
| 出现事实冲突 | 程序在本项目已有的成员和调用上限内自动补证 | 「因 2 处数据冲突，请 Grok 补证 1 次」 |
| 用户把任务标为「重要」 | 用户 | 「你标了重要：加一位检查」 |
| 成员主动建议加人 | 成员提议，用户确认 | 「Dot 建议加 Muse 查 Instagram：[同意] [不用]」 |

## 6. 接入 Grok 和 Dot（第一批，所有者决定）

**通用：** 向导按平台显示**真实步骤数**和当前进度；所有密钥、配对码只在 Hub 页面里复制，**不出现在发给 Agent 的话里**；全部步骤完成，才变为「可接任务」。

### 6.1 Grok Bot（4 步，参照 Paperclip 已上线的接入向导）

| 步骤 | 用户看到和做的 | 完成条件 |
|---|---|---|
| 1. 命名 | 填备注名（默认「Grok」） | — |
| 2. 连接 | 「复制下面这段话，发给你的 Grok Bot」，以及一个一次性配对码（15 分钟有效，只在 Hub 页面显示）。Grok 会添加 Hub 的 MCP 插件，并打开授权页，用户在授权页里输入配对码 | Hub 收到授权，并且 Grok 成功调用了一次工具 |
| 3. 接收任务 | 「复制下面这段话，发给 Grok，让它创建一个『只由 webhook 触发』的 Routine」。然后在 Grok 的 Routine 面板里复制 **Webhook URL 和密钥**，粘贴回 Hub | 两项都已填写 |
| 4. 测试 | 「发送测试」：两个对勾「已送达」「已回复」。只是测试，不创建任务 | 两个对勾都亮 → 「可接任务」 |

- 页面要提示：「Grok 的插件对你的整个账号有效，其他 Bot 也能使用。」
- Grok 的 Routine 正在运行时，再触发会返回 400 或超时（botline 实测）。这种情况按「正忙」处理：在 90 秒、3 分钟、6 分钟后各重试一次，**不算失败**。
- 如果 Routine 无法调用插件，用 REST（`/tools/*`）做诊断，分清是插件的问题还是叫醒的问题。

### 6.2 Dot（3 步，参照 Paperclip 已上线的 Dot 接入；OpenAI 官方 MCP Events）

| 步骤 | 用户看到和做的 | 完成条件 |
|---|---|---|
| 1. 命名 | 填备注名（默认「Dot」） | — |
| 2. 连接 | 「复制下面这段话，发给你的 Dot」。Dot 会添加私有 MCP 插件，并在它自己的浏览器里打开 Hub 的连接页，输入配对码（15 分钟，一次性）。用户在 Hub 页面上看到「已连接」 | 授权完成 |
| 3. 测试 | 三个检查项：「已连接」「任务通知已开启」（事件订阅成功）「测试事件已确认」 | 三项都通过 → 「可接任务」 |

- 前提：Hub 的 MCP 支持 `2026-07-28` 版协议，实现 `events/list`、`events/subscribe`、`events/unsubscribe`，并向回调地址推送签名事件。请先核对 `@modelcontextprotocol/server` 2.3.1 是否已经支持。
- Paperclip 的复盘里记录过：事件可能很晚才到达（有一次晚了约 32 分钟）；设置里能看到工具，不代表 Dot 能调用（需要重启 Dot）。**这两点都要写进验收。**

### 6.3 Muse（第二批）

自定义连接器（REST）+ 定时检查（可以加 hook 检测）。成员卡的唤醒方式写「定时检查」，状态里显示「下次检查：{时间}」，**不承诺立即响应**。必须提示用户在 Muse 里选「始终允许此网站」，否则每次都会卡住。

## 9. 验收

**真实联测（必须是 Grok + Dot 的真实账号）：** 同一个真实目标，例如所有者自己研究组织的任务，至少跑通下面 6 种情况，每种都要有截图或录屏，以及数据记录：

| 情况 | 通过标准 |
|---|---|
| 正常 | 两位领取并交付 → 汇总 → 自查 → 一份成果；本轮记录的数字可以逐条点开核对 |
| 来源冲突 | 自动补证 1 次；结果标「有据纠错」或「未确认」；取舍类冲突出现决策卡 |
| 成员失败 | 出现「收到 1/2」和三个按钮；选择用已有结果成稿后，标「部分交付」 |
| 人工修改冲突 | 交回修改后继续编辑；候选版本不覆盖当前稿；能看到三方对比 |
| 不达标 | 故意设一条做不到的合格标准 → 内部修订 1 次 → 标「部分达标」，并列出未达标项 |
| 规则复用 | 改稿 → 便签 → 「以后都这样」→ 下一轮依据里显示「本轮已带入」 |

**确定性测试（不用真实账号）：**
- 互不可见：成员用自己的凭证读取另一位成员 explore 阶段的文档和附件 → 404。
- 去向检查：漏掉一条论断 → 退回。另外必须测试 Codex 提出的反例：一条不含数字、未标风险、没有分歧，却决定项目能否做下去的论断（例如"不开放原始数据"），被归入「与目标无关」后，审阅者或用户必须能看到它。
- 来源降级：同一页面带 utm 参数 → 算同一页面；arxiv 上两篇不同的论文 → **不合并**。
- 便签：连续编辑只生成 1 张；同一个项目最多 3 条待确认规则。
- 分页：150 篇稿件时，项目页显示的是最新的；4 位成员并行工作的同时用户持续编辑，不出现保存失败。

**界面验收：** 1440×900、1280×800 两种尺寸截图，逐条对照第 4 节；所有者确认观感。

**证据分开列：** 模拟交互、字段校验、真实往返、成果可用，这四类证据分别列出，**不能互相替代**。

## 10. v1 不做什么

- Perplexity（所有者没有账号）、Hermes 等可换模型的成员：放到以后。
- 跨主体协作（加入别人的 Agent）：只预留"归属人"字段。
- OKR 层级、组织架构图、配方市场、预算系统。
- 深色主题。
- Hub 自己的大模型调用。
- 自动执行对外动作（发布、发送、付款）。成员请求对外动作时，只生成决策卡「{成员名} 想{动作}：[允许这一次] [拒绝]」。

**安全约束（继续有效）：** 不碰云端 VPS 上的订阅版 Claude Code；登录资料和凭证不进 Git、安装包和证据；交付必须有"已生效"的验证；不虚报接通或完成。
