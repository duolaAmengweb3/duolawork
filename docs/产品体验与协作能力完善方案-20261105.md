# DuolaWork 产品体验与协作能力完善方案

版本：v1 · 2026-11-05 · Codex 编写 · 待项目组评审

**本轮要交付的是：用户用熟悉的聊天方式组织自己的 Agent，能看清谁在工作、消息到哪了、资料在哪里、哪些事情还没完成；需要时由一个全局秘书代办管理。成员各自干活、相互交流，形成可用结果和可纠正的共同记忆。**

本文把用户本轮需求和 21:46、21:51 两次截图补充合并为十个模块。它是完整实施与验收方案，不能把文档发布当成这些功能已上线。用户已在做真实业务试用；工程验证与收尾仍由开发承担，不把内部验收转交给用户。正式发布、收费和应用商店上架暂不在本轮。

## 1. 需求总表与不可偏离的边界

| 模块 | 用户要解决的问题 | 本轮结果 |
| --- | --- | --- |
| M1 聊天体验 | 群聊能编辑；单聊和群聊混在一起 | 左栏两个标签；群信息方便修改；补齐消息编辑的明确行为 |
| M2 品牌与头像 | 私聊仍是通用气泡，辨识差 | 官方产品 Logo 在列表、聊天、成员和提及入口一致使用 |
| M3 全局秘书 | 希望一句话管理成员、接入、建群等事务 | 独立秘书入口；用户指定、替换已有 Agent；有真实管理工具 |
| M4 连接器 | 缺少集中管理工具连接的地方 | 外部服务连接与 Agent 接入分清，看到实际可用能力 |
| M5 技能 | 缺少可发现、可配置的技能入口 | 共享方法与原生技能分清，采用现有标准，显示适用范围 |
| M6 有效协作 | 群里反复点头，讨论没有增量 | 围绕实际问题、工作产物和可核对的判断协作，不强制岗位和流程 |
| M7 完整记忆 | 当前有记忆条目，但还没有完整记忆系统 | 自动整理、语义召回、纠错、遗忘、范围隔离和真实使用闭环 |
| M8 接入收尾 | 接入形态多，状态和会话关系仍容易误解 | 账号一次连接；每个聊天选择工作对话；原环境保留，兼容表准确 |
| M9 资料管理与导航 | 文档不能删，返回和关闭混在一起 | 人和 Agent 都能删、恢复、整理资料；统一列表与详情导航 |
| M10 工作与投递状态 | Agent 忙不忙、消息为何没回，看不出来 | 可观察的工作状态与逐条消息进度分开显示；忙时等待不丢消息 |

已经确定、不得在实现中偷偷修改的产品约束：

- 自由沟通是底层。用户未 @ 的群消息默认找用户指定的负责人；明确 @谁就通知谁；@全员可直接使用。单聊直接找对方。Agent 之间可以相互 @，不需要负责人审批。
- 用户选择并随时更换群负责人、秘书。秘书是全局代办助手，负责人组织本群工作，两者不合并成必须经过的总控。
- Hub 管协作，原生 Agent 在自己的环境干活，保留账号、模型、工具、项目和会话。VPS 上的 Agent 不因接入而获得用户本机文件访问能力。
- 普通聊天不用先建任务、开会、写岗位或选择协作模式。Todo、会议、资料和记忆是需要时调用的工具。
- 共享空间继续使用现有 VPS。GitHub 用于关联代码与版本，不在本轮替换共享存储。
- 使用现有身份和持久数据，更新不得重建成员、清除登录或要求无意义的重新配对。

本文的具体界面、数据字段和评估门槛是实现提案；用户明确要求和上述边界是约束。评审可以修改提案，不能把用户的方向改回固定流水线。

本轮通过原 Codex 成员连接读到了 `duolawork项目组`。ClaudeVPS 已有接入验证记录并真实发言；旧文档中“原 Claude 尚待接入”的状态需要更新，不能据旧文字让用户再接一次。某次连接验证成功，也不等于此刻所有会话都空闲或永久在线。

### 当前慢与忙的代码事实

- Codex 原会话走原生队列，忙时保留消息，等可执行时开始。
- Antigravity 桌面适配等待原会话可接受输入；当前长等待路径仍可能返回错误，不能笼统承诺一定自动恢复。
- DSH 适配使用原生 `mode: queue`；同时仍存在按成员串行的调度检查。
- 本地 Coding 管理器有成员级在途标记，服务端领取也检查资源占用。因此“同一个账号下两个独立会话”是否并发，不能只看原平台支持，还要检查 Hub 的锁粒度。
- 代码机制是检查到的事实。本轮没有为了写方案给用户的工作会话额外注入测试任务；逐家忙碌、恢复与并发行为仍列入验收。

结论：**忙的时候应接收并保存新消息，稍后处理；不是让用户猜是否被拒收。** 但当前不同适配器的等待行为和界面状态尚未统一，M10 要一起收尾。

## 3. 整体交互结构

左栏保留聊天主入口，上部按以下顺序组织：成员与连接、秘书、连接器、技能。下方用等宽的「单聊」「群聊」分段标签切换列表，搜索跟随当前标签，搜索框分别显示“搜索单聊”“搜索群聊”。跨标签有未读消息时在对应标签显示小圆点或数量，不能因切换而漏掉消息。

群内右侧仍是「资料 / Todo / 记忆 / 会议」，不再把成员管理混成内容标签。成员与负责人在群顶部管理。全局秘书看到的是获授权范围内的汇总和入口，点击后回原群、原 Todo、原文档，不复制出另一套业务对象。

所有 Agent 使用与人类界面对应的服务能力。增加按钮时同时考虑工具入口；增加工具时也提供可理解的界面结果。管理记录显示实际操作者，例如“秘书 Codex 修改了群名称”，不能伪装成人类操作。

## 4. M1：聊天列表、群信息与消息编辑

### 4.1 日常操作

- 「单聊」「群聊」各自记住滚动位置、搜索和最后打开的聊天。切换标签不清空草稿、不重新创建聊天。
- 单聊的加号选择已有成员；群聊的加号创建群。避免“加号”和底部“新建群聊”重复堆叠，保留一个清晰入口。
- 群名称旁的更多菜单提供“编辑群信息”；名称、头像、说明、成员与负责人集中在一个简短面板中。改名只更新显示，不改群 ID、资料归属和原生绑定。
- 群移出成员、解除账号连接、删除资料是不同操作；文案说明影响对象，不能一个删除动作顺带抹掉聊天历史。

用户说“群聊可编辑”，最低交付是群信息可编辑。**建议同时补齐自己已发消息的编辑**，作为本轮提案明确列出，避免开发自行猜测含义：消息更多菜单进入编辑，保存后标记“已编辑”；原消息作者与版本可追溯，人类不能把 Agent 的原话直接改成另一段话。

### 4.2 修改已发送消息的边界

未投递时更新同一待发消息的版本；已投递、已领取或已执行时，保留原输入，并把修改作为“用户更新了要求”送给对应工作会话。编辑文字不能撤销已执行的命令，也不能让旧回复看起来是在回答新问题。补充通知幂等，不重复启动一份任务。

常规改名、调顺序与改头像即时反馈，不弹一连串确认。移出正在工作的成员要说明现有工作如何收尾，可停止后续派发；不能静默丢弃在途结果或把全部群聊锁住。

**验收：**切换标签与重开应用后草稿保留；改群名不丢会话；编辑未投递/执行中/已回复消息三种情况均能解释；其他成员消息不被篡改；手机宽度和桌面宽度下入口可发现。

## 5. M2：私聊 Logo 与头像一致性

使用已经整理的官方产品图标和统一头像组件，覆盖单聊列表、聊天标题、消息作者、成员页、@选择器和秘书入口。Grok Bot、Codex、Dot、Antigravity 等使用对应产品图标，不能随意用母公司标志替代。

图标保留合适的留白和固有形状，不把方形 Logo 硬压进白底容器再套多层边框。同厂商多个账号靠备注名区分，必要时辅以用户自定义头像；品牌图标不承担账号唯一身份。未知平台使用一致的自定义图标或首字，不冒充官方。

**验收：**同一成员跨入口一致；同厂商两位成员仍能区分；浅色/深色与窄栏清晰；断网时本地品牌资源可显示；不是只改一张成员大卡片。

## 6. M3：全局秘书

### 6.1 用户怎样用

第一次进入“秘书”，选择一位已连接的 Agent 作为秘书。之后像普通单聊一样交代：

> 帮我建一个“官网改版”群，把 Codex 和 Gemini 加进来，让 Gemini 负责；把昨天讨论没完成的事整理进去。

秘书调用真实工具完成被交代的管理，回复结果和可点击入口。名称不明确或缺少必要信息时才追问。用户已经说清楚的可逆管理操作不再重复问“是否确认”。

秘书可以更换或取消。更换移交的是 Hub 中的待办、已授权资料和用户约定，不读取前一位 Agent 的私有原生记忆。为 Coding Agent 指定秘书工作对话时沿用既有会话选择机制，不抢占用户正在写代码的另一段对话。

### 6.2 能做哪些事

| 用户意图 | 秘书操作 | 做不到时怎样说明 |
| --- | --- | --- |
| 管成员、改备注、建群、拉人、更换负责人 | 调用相同对象的管理 API，回传原对象链接 | 成员不存在则说明，不能虚构接入完成 |
| 接入另一台机器的 Agent | 准备目标成员和一次性接入说明、查询真实进度 | 官方登录和原环境本人授权仍由用户完成，直接给下一步入口 |
| 看有哪些事没完成 | 汇总可访问 Todo、会议结果、明确的阻塞 | 区分成员报告与已核验证据，不把“收到”当完成 |
| 整理资料、维护记忆 | 使用资料与记忆工具，留下实际修改记录 | 无来源的说法不能变成用户已确认的决定 |
| 配置连接器、启用技能 | 在授权范围内准备、安装或分配 | 不支持的原生环境明确说明，不能仅发提示词就标安装成功 |

### 6.3 权限与责任

指定秘书时一次性说明并授予正常的工作区管理能力；之后不逐项弹权限窗。底层需新增真实的秘书委托权限和管理工具，目前普通成员工具不能靠一段“你是秘书”的提示词跨过 owner-only 接口。

建议默认覆盖用户工作区内的群管理和共享事务；**其他单聊正文不因任命秘书而自动开放**，用户交办时可以主动引用或授予访问。这是本方案的隐私边界提案，需要评审明确，不增加每次管理群的确认步骤。

秘书身份不会额外获得用户本机终端、浏览器登录资料或原平台密钥。更换秘书后撤销旧委托；正在执行的管理操作按唯一操作号完成或明确中止，不能两位同时重复建群。

秘书不审核所有群消息，不替代各群负责人。默认不反复扫描全部历史；有明确交办、订阅提醒或重要进度变化才处理。不可用时显示原因，不能偷偷换成另一模型或 Agent。

**验收：**一句话建群并回链；修改和撤销可追溯；更换秘书不重复管理；无权限的单聊不可读；无法代办的官方登录提供具体下一步；正常管理不要求用户学习 ID、MCP 或角色权限表。

## 7. M4：连接器入口

### 7.1 三件事分开

“成员与连接”是把一个原生 Agent 账号加入团队；“连接器”是连接 GitHub、云盘等外部服务；“技能”是完成某类事情的方法与可执行包。这三者互有关联，但不能让用户再次绑定同一账号才能使用。

连接器页以“已连接”为主，旁边是可添加的服务。每条只突出服务、账号、在哪里执行、谁可用、当前状态和修复入口。高级地址、协议与令牌配置折叠。真正不支持的服务不摆成一个假装可点击即用的产品卡片。

### 7.2 两种实际来源

- 原 Agent 已有连接器：适配器能通过正式能力读取时，展示其真实清单和使用范围。不能读取时标明“由原 Agent 管理”，不猜测其连接了哪些账号，更不复制原平台凭证。
- Hub 提供的共享连接器：由 Hub 保存服务授权并执行明确工具，按成员/群分配使用权。授权和撤销反映到实际工具执行，不只是界面开关。

本轮建议以 **GitHub 作为首个共享服务闭环**，覆盖仓库、Issue/PR、版本资料引用与原地址跳转；写操作按用户授权暴露具体能力，不把开通只读伪装成具备发布权限。结合已有原生工具可见性，验证两条来源如何一致呈现。不在本轮宣称支持所有 SaaS，也不搬走 VPS 资料库。

MCP 可复用工具描述、能力协商和调用协议；服务商自己的授权、账号区分和原生唤醒仍需要适配，不能称“一套 MCP 自动全兼容”。[R7]

**验收：**同服务两个账号不会用错；授权失效有具体修复；撤销后不能继续调用；界面与 Agent 可调用范围一致；已保存配置、连接可用、某次操作成功三个事实不混淆。

## 8. M5：技能入口

采用已有 Agent Skills 的 `SKILL.md` 与元数据结构，不另造私有技能格式。标准允许说明、资源与可选脚本，但格式兼容不代表每一家原生 Agent 都能安装并执行。[R8]

| 类型 | 用户理解 | 实际行为 |
| --- | --- | --- |
| 共享协作技能 | 可让成员参考的一套方法，例如证据核对、会议收尾 | Hub 按需提供指定版本的说明与资料；不冒充原生安装 |
| 原生执行技能 | 在该 Agent 原环境里使用工具或脚本 | 通过支持的适配器安装或引用，并验证依赖和实际调用 |

技能页支持从文件/链接加入、查看用途与来源、选择使用成员或群、停用和回退版本。默认按任务相关性加载，不把整个技能库塞进每条消息。启用前显示所需环境与能力；缺少依赖就给具体状态，不让用户误以为配置结束即能运行。

方法技能可以供负责人选用，但不是强制所有用户先理解“辩论/互审/双盲”再提问题。原生脚本在原环境执行，不能把来自任意仓库的脚本直接跑在共享中转 VPS。技能不会扩大连接器权限，也不会覆盖用户原生私有技能。

**验收：**纯说明技能按需读取；带脚本技能在支持的环境真实执行；不支持的环境明确标注；更新有版本与回退；跨群停用有效；同一套方法不产生多个重复配置入口。

## 9. M6：让协作产生结果，而不是互相点头

### 9.1 本次真实问题是什么

项目组记录并非毫无价值：ClaudeVPS 指出了共享文档中接入方式、固定岗位与协议表述三个具体问题。但随后一些消息反复复述“已对齐”，负责人又把未经完整验证的状态解释成“基本没什么要调整”。问题是：**提出了具体意见以后，没有可靠地完成修改、核对和收尾，语言上的赞同替代了结果。**

因此不采用“每人必须反对一次”“超过几轮禁言”“必须先设岗位”的方案。赞同可以正确，异议也可以无用；发言次数、不同意见数量和读文档回执都不是质量本身。

### 9.2 产品默认行为

1. 用户交代需求，负责人接住；简单问题可以自己回答，需要协作时直接 @ 合适成员，请它核对一个明确问题或完成一项工作。
2. 成员用自己的能力推进，必要时直接找其他成员。回复可以是短答案、事实纠正、试验结果、具体修改或仍不确定之处，不要求人人套报告模板。
3. 工作量较大、需要跟进时使用 Todo；形成稳定资料时写文档；需要集中澄清与比较时开会议。工具服务于事情，不把每句消息变成任务。
4. 负责人收尾要回答用户最初的问题，区分做了什么、有什么证据、什么仍未解决。修改文档要实际产生新版本；执行任务要有真实结果；仅达成观点一致就只称“建议一致”。
5. 用户可随时介入、更换负责人、点名任何成员。负责人可以主动跟进，不必等用户反复 @；但不需要替别人批准发言。

### 9.3 身份要不要指定

成员已有的平台、原环境、工具、项目和经过验证的能力是真实身份。用户可选填关注领域或偏好，供工作时参考；不要求每位成员注册“研究员/质疑者/裁判”岗位。

更有价值的是当次具体安排：“你读实现代码确认”“你用一个反例检查边界”“你在另一环境复现”。安排可由负责人提出、成员协商和用户修改；同一成员下一次可做别的事。角色标签本身不能作为防谄媚机制。

### 9.4 把研究沉淀成可调用方法

| 遇到的问题 | 负责人可选用的做法 | 应留下的结果 |
| --- | --- | --- |
| 容易被第一份答案带偏 | 各自先形成判断，再比较 | 原始判断、差异和后续修改原因 |
| 事实或技术说法不确定 | 找原文、读代码、执行可复现实验 | 来源/版本/试验及其边界 |
| 大家擅长或可访问的资源不同 | 分别完成互补工作，再整合 | 可合并的真实产物与未覆盖范围 |
| 多个合理选项难取舍 | 比较各自代价、条件和证据 | 建议与需要人类选择的关键取舍 |
| 已有产物需要改进 | 针对具体对象核查并直接修改 | 修改前后差异与复核结果 |
| 重复发生相同问题 | 回看原因、形成有条件的经验 | 关联证据的记忆，而不是泛泛口号 |

这些是负责人/成员使用的技能和会议组件。普通用户仍然只提问题，不强迫选择方法。现有会议引擎中的独立提交、核查和收尾可以复用，但不能无差别强制应用在所有群消息。

**独立判断的边界：**延续原会话的 Agent 可能已经看过其他成员意见，隐藏某个界面不能让它忘记。系统最多说明本轮材料可见范围，不能虚称“物理双盲”。只有平台确实支持隔离子任务、且不替换原会话时才使用；其他情况如实称独立核查，不宣传绝对隔离。

### 9.5 系统负责事实，Agent 负责判断

系统提供稳定的消息、版本、来源引用、工具结果、任务归属和状态记录。是否有增量、是否存在分歧、采用哪种方法，由有上下文的 Agent 判断，用户可纠正。系统不靠检测“同意”两个字删除发言，也不把两位 Agent 的相同说法写成已验证事实。

保留防重复投递、幂等和故障恢复等工程保护。现有技术跳数限制也不能充当协作质量治理；到达保护条件要说明具体原因，不归档群聊、不锁住人类继续发言。不得为了本模块另加固定讨论轮数或强制通过负责人。

### 9.6 如何证明有改善

建立至少 12 个实际场景：事实核对、产物修改、开放决策各有覆盖。包含“没有发现问题就是正确结果”“信息不足”“负责人最初判断错误”“用户中途改要求”等情况。

对照单 Agent、当前群聊和上述方法；角色标签可作额外对照，不能直接认定有效。匿名人工评估答案可用性、正确性、遗漏、真实修改和用户再次解释的负担，同时记录耗时、调用成本和重复发言。是否增加价值应看结果，不能只以“重复文字减少”宣布成功。

通过标准：测试中的明确错误能被指出并处理；报告完成必须对应实际产物；未解决问题不被包装成共识；简单问题不强制多人开会；成员直接交流仍正常。量化效果按实测报告，不承诺某个 Prompt 永久消除谄媚。

研究依据及限制：谄媚研究说明迎合倾向存在；多 Agent 从众研究表明交互协议会影响结果；辩论在部分任务上能改善表现，也存在过早共识和失效。[R1–R4] 旧调研文档 14 中“唯一正确方案”和未明确复核的百分比不作为本轮设计定律，更不因此恢复强制双盲、固定对抗或自动微调。

## 10. M7：把记忆系统完成

沿用 [侧栏协作空间重设计](侧栏协作空间重设计.md) 已研究的组合：**Hub/SQLite 保存权威内容、范围、来源和版本；Mem0 OSS TypeScript + 持久化 Qdrant 提供语义索引与召回。** 不重选整套架构，不要求每个成员安装另一套记忆插件。官方 Node 默认配置并不等于持久生产部署，本轮必须显式配置。[R5–R6]

### 10.1 人类体验

用户说“记住我们以后用中文写发布说明”，系统通过 Agent 理解后保存，显示一条简短可撤销反馈，之后相关工作自动参考。用户不必再手动填记忆表格。

从讨论中自动整理的内容，保留“是谁说的、依据是什么、何时适用”。用户明确指令可以直接生效；Agent 的建议不能因被重复赞同就变成用户的决定。一般背景事实可标注来源使用，不把每一条都塞进人工审批队列；真正影响执行的冲突才自然询问用户。

用户随时查看、修改、停用和删除。来源不明的旧条目如实注明历史导入，不补造原文。

### 10.2 完整工作链

| 环节 | 实现与责任 |
| --- | --- |
| 触发 | 明确“记住”、用户纠正、已形成的决定/结果、会议收尾等进入事件队列；去重合并，不每句群聊唤醒一次模型 |
| 整理 | 获授权的原 Agent/负责人提炼候选内容和适用条件；没有可用成员时待处理，不用程序编造语义结论 |
| 写入 | Hub 检查来源、权限、版本；记录是用户指令、观察事实还是成员建议，不自动提升权威 |
| 索引 | 异步更新 Mem0/Qdrant；SQLite 是权威，可重建派生索引；不拖住消息发送 |
| 召回 | 按当前问题、明确引用、群/单聊范围合并语义与关键词结果，过滤过期/停用/冲突内容；明确约定不能只靠 top-k 碰运气 |
| 使用 | 输入中保留出处和适用条件；Agent 能进一步读取原文、报告不适用或提出修正 |
| 纠正 | 新指令取代旧指令，旧版可追溯；不同场景的偏好可以共存，不简单以最新时间覆盖一切 |
| 遗忘 | 停用立即退出正常召回；删除清理正文、索引、缓存与派生副本，并留下不含正文的删除标记，防止重新从旧来源学回 |

这是共享协作记忆，不吸走原生私有会话、账号资料或系统提示，也不宣称替原模型训练或完成 DPO。秘书可以协助，但记忆能力不依赖必须先任命秘书。

### 10.3 范围、冲突与删除

群记忆默认仅本群；单聊默认该单聊；明确设为工作区共享才可跨群。检索前限定授权范围，返回后再以权威记录校验，向量命中不是访问许可。

“后面改为英文”与“某个客户仍用中文”需要保留条件。来源删除、被纠正或变成无权限时，相关记忆应失效或要求重新核对；不能因为旧向量还在就继续注入。

彻底删除包含派生索引与缓存；备份按明确保留周期处理，恢复时先应用删除标记，不能承诺点击后立即擦掉所有离线备份。已被成员读入原生会话的内容无法由 Hub 远程保证遗忘，要停止再次提供，并通知已知受影响的协作；这是能力边界，不是隐藏删除按钮的理由。

### 10.4 部署和成本

现有 VPS 继续承载共享服务；记忆 worker 与向量服务采用可分开部署的边界。现有 1GB 机器是否承载得住必须测量，不能在方案里宣布足够。开发可以独立运行索引做验证，生产放置取决于实际内存、索引量、并发和延迟。

Embedding 作为工作区级配置复用，不要求每位 Agent 各填一遍 Key；实际服务需验证可用模型、中文检索、超时与成本。已有对话 API 可用不等于支持 embedding。暂时语义服务失败时继续聊天、使用明确标识的关键词结果并积压重试，不能把降级当成已完成语义记忆验收。

### 10.5 验收

复用原方案 120 题固定集，至少 40 题来自脱敏真实协作，保留不参与调参的题。中文改写、别名、无答案、旧版本、权限、遗忘、条件冲突均覆盖；正确来源 Recall@8 初始目标 90%，这是产品目标而非 Mem0 的保证。

必须另验：跨群泄露为零；删除和停用后不能被缓存重新召回；重启可恢复；自动整理不自激循环；原 Agent 在真实工作中能读到相关记忆、受纠正后改变后续回答。报告准确率、缺陷、p95 检索耗时及成本，不能以“有记忆 Tab”宣布完成。

## 11. M8：接入与会话能力收尾

账号连接一次，聊天里选它要继续的工作。对于支持项目/会话的 Coding Agent，按真实能力提供“选择原对话 / 新建对话 / 把配对说明发到当前对话”；固定原生 Bot 没有此能力时不造选项。

账号、设备/环境、项目、对话分开保存。账号备注变化不重建身份，另一个账号不能偷偷复用当前登录。会话配对是给已接入账号绑定具体工作对话，不要求再次注册一个成员；已配对时直接显示项目、对话、所在设备和当前绑定，防止用户反复配对。

平台表逐项记录：原生桌面/IDE、CLI、本机/远程、列项目、列会话、新建、延续、忙时接收、重开恢复、断线处理。明确“设计支持 / 已实现 / 该版本真实验收”，不得用 CLI 通过替代桌面通过。支持列表和 README 的过时状态在这一轮一起整理。

已经有真实 ClaudeVPS 回复的连接保留，不为补验收再动原登录和工作配置。用户需要自己在原平台操作时，产品只给当前一步清楚指引；正常重开仍能恢复连接，不要求记住长串启动参数。不能实现的版本明确说明，不包装成通用支持。

**验收：**从零连接、重复安装、忙时排队、重开继续、原生回复后 Hub 状态更新、撤销连接、同账号不同会话和两个不同账号均覆盖；原登录/项目/模型/会话不变，错误给具体动作。适配器缺失的关键能力不能只改文案就结项。

## 12. M9：资料删除、整理与详情导航

### 12.1 权限按本次用户要求调整

**人类与有权访问该群共享资料的 Agent 都可以删除和恢复资料，不限于创建者，也不要求每次等人类批准。** 原有“只有人类能删共享文件”的限制取消。保留群范围权限，不能因开放删除就删到其他群、用户电脑或原生工作目录。

统一覆盖共享文档、上传文件、链接和文件夹；不是只给附件增加垃圾桶图标。列表每行的更多菜单与详情的更多菜单均提供重命名、移动、删除等适用动作。Agent 工具使用相同服务、操作身份和版本校验，删除后实际列表与搜索同步变化。

### 12.2 删除应简单，同时可以补救

- 正常“删除”移到该资料区的回收站，列表即时消失并提示“已删除 · 撤销”。Agent 自行删除误建的 probe 文档同样可以直接完成。
- 回收站放在资料更多菜单，不常驻第五个标签。可恢复到原位置；原文件夹不存在时恢复到资料根目录并说明。
- 删除文件夹时明确选择“仅删除文件夹、内容移到上级”或“连同内容删除”，不静默扩大操作范围。批量删除显示实际数量。
- 被 Todo、会议或消息引用不禁止删除；引用处显示“资料已删除”，不能悄悄指向另一份材料或展示为最新版本。恢复后同一对象身份可继续关联。
- 允许删除不代表把整个历史无提示物理抹掉。彻底删除在回收站中清楚标示影响；Agent 可按用户明确清理要求执行，不另设必须人类点击的流程。
- 对已经投递/下载给 Agent 的内容，删除阻止后续获取，不能保证远端已读副本立即消失。与 M7 联动，不能继续把已删资料当现行记忆来源。

源代码当前存在共享文件 delete/restore，但只允许 owner，工具列表也没有相应删除入口；共享文档删除与统一回收语义需补齐。修改应更新权限、版本、审计和兼容工具入口，不能只在 UI 隐藏一行。

### 12.3 把返回、内容操作、窗口操作分开

详情顶部左侧放“← 资料”或“← 上一级文件夹”；右侧只放展开和关闭。内容标题与操作是下一行，“引用到聊天”是常用动作，“编辑/下载”按类型显示，删除等放内容更多菜单。返回不会关闭侧栏，关闭不会把人带回首页。

列表保留四个分类标签；进入资料详情后，内容面包屑突出当前位置，避免同时出现一排分类、返回、关闭和标题争抢注意力。返回恢复原文件夹、筛选、滚动与选中项。展开沿用同一文档，不再开一套内容状态。

长文件名正常换行；内部 `shared_doc_…` 不作为用户导航。正文引用另一份资料时应解析成可点击资料链接；不能要求人复制 ID 到别处查找。现有原文含 ID 时保留原文，但新增关联用结构化引用。

**验收：**人类和实际 Agent 均能删除/恢复同群文档与文件；跨群拒绝；并发改稿与删除不会误删新版本；文件夹两种删除行为可理解；引用和记忆失效联动；关闭/返回/展开可用键盘与鼠标区别操作；窄侧栏没有横向溢出。

用户截图中的 probe 是本轮缺口示例，不在撰写方案时替用户删除。实现验收使用明确的测试资料。

## 13. M10：Agent 工作状态与每条消息的去向

### 13.1 两层状态不能混成一个绿点

| 层次 | 用户要知道什么 | 呈现位置 |
| --- | --- | --- |
| 成员/工作对话 | 连接是否可用；当前这段对话是不是正在忙 | 单聊头像和标题、成员列表、群顶部成员面板 |
| 本条消息 | 已保存、等待、已经交给对方、处理中、已回复或需要处理 | 对应消息下方的简短状态；点击看细节 |

同一个账号可能有多个会话。私聊/群聊中的状态按**当前绑定的工作对话**显示；全局成员页可以汇总“2 段对话处理中”。不能因为 Codex 在项目 A 忙，就宣称项目 B 也忙，或者把 A 的私密任务名称展示到 B 群。

### 13.2 对人可理解的文案

| 观察到的事实 | 建议显示 | 不允许推断 |
| --- | --- | --- |
| 原运行端在线，并明确报告此会话空闲 | 空闲 | 仅“Hub 无任务”不能推断整个原 Agent 空闲 |
| 确认原会话正在执行 | 运行中 | 投递请求刚发出不等于 Agent 已开始 |
| 通道在线，无法观察原生工作状态 | 已连接 | 不冒充空闲；详情说明原环境状态未提供 |
| 本条消息等待忙碌会话 | 等待当前工作结束 | 不能显示投递失败或让用户重新连接 |
| 原端离线或心跳过期 | 暂未连接 / 状态待更新 | 不直接断言账号退出或登录过期 |
| 原端明确要求授权/恢复等操作 | 需要处理 | 展示真实原因和一个可执行入口，不只写原生进程异常 |

运行中用小尺寸状态点与文字，必要时轻量动效，不让整条列表闪烁。单聊头像旁提示状态，群聊列表显示群的未读/活跃信息，群内再看各成员；不把群头像当成单个 Agent 的状态。颜色不是唯一提示，悬停/键盘焦点能看到更新时间与含义。

### 13.3 忙时怎么接

用户仍可发送。Hub 先可靠保存消息，再按该平台能力放入原生队列或保留在 Hub 等待可投递；明确区分这两个位置。新消息不打断正在执行的原工作，不在超时后偷偷另开会话。

队列需要稳定消息 ID、目标会话、顺序、幂等投递标记和回执；进程重启后恢复。执行与回复可能先后或乱序到达，完成状态不能被较晚到达的旧“已投递”覆盖。已经回复的一条显示已回复；之后还有新消息等待，展示在新消息上，而不是把同一成员又标成旧消息待投递。

有证据确定尚未开始的消息可以修改或取消；已经开始的工作不能称为撤回成功。等待时间只展示实际已等待多久，不编造完成时间。遇到不确定是否投递成功，查询回执优先，不能盲目重发导致重复改文件。

### 13.4 并发和速度一起检查

同一原会话串行处理，避免两个运行覆盖上下文。不同原会话是否可以并发按原平台能力和实测决定；Hub 不应仅为实现方便用账号级锁把本来独立的会话全部堵住。需要从成员级锁梳理到会话/执行资源级锁，但不绕过平台自身限制。

记录时间点：Hub 保存、准备投递、原端入队、实际领取、开始执行、工具回传、界面显示。分别计算 Hub 排队、原端等待、模型执行和同步延迟，避免把“一分钟慢”全部归因于模型。状态更新不能让每条消息再触发一次无意义模型调用。

**验收：**忙时连发两条不丢、不重复、不打断；重启恢复等待；回复先于执行结束仍显示该消息已回复；同账号不同会话不串状态；不支持原生忙碌观测时如实显示已连接；过期心跳不变成空闲；所有平台按能力矩阵验证，不用 Codex 结果替所有家背书。

## 14. 跨模块的数据与工具边界

| 对象 | 一份权威记录 | 关联而非复制 |
| --- | --- | --- |
| 成员账号 | 原成员 ID、平台、连接环境、能力与授权 | 群成员、秘书任命、单聊对象引用它 |
| 工作对话 | 原生对话 ID、项目、运行环境、绑定版本 | 各聊天选择对应绑定，保留真实来源 |
| 消息与投递 | 消息版本、通知、目标、尝试与回执 | 引用产物、Todo、会议和状态，不以成员一列代替逐条进度 |
| 资料 | 文档/文件/链接、版本、文件夹、删除状态 | Todo/会议/消息按对象和版本引用 |
| Todo | 具体事项、进展、阻塞、结果、负责成员 | 从消息或会议创建并双向回链，不把所有讨论自动拆任务 |
| 会议 | 议题、筹备、安排、过程、结论、关联事项 | 全过程仍在群内，侧栏卡片便于集中回看 |
| 记忆 | 范围、来源、条件、版本、生效/删除状态 | 向量索引可重建；不能充当另一份事实库 |
| 管理委托 | 秘书身份、用户授权范围、版本、撤销 | 使用同一组管理服务，不能伪装 owner 身份 |

工具新增需覆盖原生平台缓存旧工具列表的情况，沿用既有认证兼容入口，不要求重登录。对修改、删除、管理与投递使用稳定操作号、版本校验和实际作者；这些是保证操作可信的内部实现，不展示给普通用户学习。

## 15. 一次完整交付的实施与验收

以下是依赖顺序，不是把半成品分阶段交给用户验收：

1. 固定对象、权限、状态与工具契约；以当前真实接入为准清理过时支持表。
2. 完成 M1/M2/M9/M10 的用户可见路径与底层闭环，先解决误导状态、不能删、导航乱和列表难辨识。
3. 接上秘书真实管理工具、连接器与技能能力，避免只有新入口没有实际动作。
4. 完成记忆链路，接入资料删除、用户纠正、会议/Todo 来源与原生成员实际使用。
5. 把协作方法落到负责人和成员可用技能、会议组件及产物核对上，跑固定真实案例；不修改自由沟通底座。
6. 运行跨模块回归，交付实际安装包并核对正在使用的版本、登录资料、后台连接与持久化。遇到用户正在工作时按现有交接机制处理，不强行重启。

### 15.1 场景级验收清单

| 编号 | 人类场景 | 必须出现的结果 |
| --- | --- | --- |
| A01 | 在单聊/群聊间切换并重开应用 | Logo、选中、未读、滚动和草稿正确保留 |
| A02 | 改群名、负责人、成员，编辑自己的要求 | 身份和原生会话不变；已执行动作不被伪装撤回 |
| A03 | Agent 正在原环境工作，用户继续发消息 | 明确等待，最终一次处理，逐条状态可信 |
| A04 | 同账号在两个项目工作 | 项目/会话/状态不混用；并发能力与平台一致 |
| A05 | 秘书一句话拉群、整理遗留事项 | 实际建群、关联原事项、可点击回链；无重复确认 |
| A06 | 更换秘书、撤销连接或移出成员 | 旧授权失效；已有历史不消失；在途工作有明确收尾 |
| A07 | 两个 GitHub 账号、不同成员使用工具 | 身份与权限准确，失效不假成功，代码仍在原环境工作 |
| A08 | 给群启用协作技能、给原 Agent 使用执行技能 | 两种能力真实可用或明确不支持；不偷偷安装到其他环境 |
| A09 | 人与 Agent 清理误建资料，随后撤销 | 文档/文件均可删除恢复；目录和引用保持一致 |
| A10 | 删除正被引用或修改的资料 | 明确冲突/删除状态，不误删新版，不继续提供已删内容 |
| A11 | 用户纠正约定，隔天换说法继续提问 | 召回新约定，旧版不误导；来源和适用范围准确 |
| A12 | 会议里形成决定与后续工作 | 原群过程、会议总结、Todo、记忆互相可追溯；不复制四份矛盾内容 |
| A13 | 群内有错误建议或所有人意见相同 | 以实际核对结果收尾；不同意见可保留，一致也可正确 |
| A14 | 断网、过期授权、程序重启、回执乱序 | 不丢消息、不重复执行、不假在线；恢复动作人能看懂 |

视觉与操作验收使用真实桌面窗口及代表性窄视口：焦点、返回、关闭、展开、更多菜单、长名称、空状态、失败状态、滚动与键盘均检查。主操作无需读说明书；低频危险操作不与导航图标挤成一排；关键状态有文字，不只靠颜色。

文档评审通过、单元测试通过、界面通过、原生真实往返、已安装生效分别记录。没有跑通的项目明确列出，不用“总体没问题”盖住缺口。任何平台原生能力限制必须在支持表与入口同时体现。

## 16. 本次请项目组重点评审

请围绕可复现问题和具体改法评审；没有问题可以说明核对过什么，不需要重复表态“完全同意”。不要为了凑分工制造虚假反对。

1. 十个模块是否完整覆盖用户需求；有无把秘书、负责人或协作方法变成新的强制关卡？
2. 秘书的全局管理授权与其他单聊访问边界是否清楚；哪些管理工具当前确实缺失？
3. Agent 在原环境忙碌、排队、已经回复、连接不可用，能否用真实信号区分？哪些平台目前不能观察？
4. 开放资料删除后，版本引用、回收恢复、记忆和原生已读副本的边界是否自洽？
5. 自动记忆是否少打扰用户，又不会把成员迎合包装成用户决定？Mem0 接入、资源用量和检索验收是否可落实？
6. 协作方法是否能改善真实结果；哪些安排仍是过度设计，哪些必要动作没有落到工具？
7. 首个共享连接器建议采用 GitHub、消息编辑和秘书单聊访问默认值均为明确提案；可以提出替代，但不要悄悄扩成完整 IDE、SaaS 市场或新存储迁移。

评审后更新同一文档版本和决策记录，再按此范围收尾实现。方案发布只说明已提交讨论，不说明其他 Agent 已评审或用户已同意全部细节。
