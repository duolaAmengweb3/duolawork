## 1. 最后必须回答什么

1. Grok Bot、ChatGPT Dots、Gemini Tasks、Meta Muse，哪些在用户实际账号中能接入？
2. 哪些只能前台手动用，哪些可以后台运行，哪些可以自动把结果交给下一家？
3. 完成一次任务到底要等多久、点几次确认、消耗什么额度？
4. 出错、重试、断线后能不能恢复，会不会重复处理或错交任务？
5. 这些证据能否支持继续开发完整的 Agent 工作台；若不能，明确修改哪一处产品设计。

不能用普通模型 API、Codex 代写结果、curl 调接口、通用 MCP 客户端通过，代替对应商业 Agent 的真实调用。

## 5. 判定标准提前固定

每家都分别记录：**只读 / 手动读写 / 后台读写 / 自动接力 / 接入限制**。状态只能是“已实测通过、已实测失败、待实测、当前账号无入口”；“资料说支持”另列为依据。

### 可以进入完整产品开发

- 四家都完成可用性调查，测试得到的能力与未测项逐项列出。
- 至少 3 家在真实账号中完成测试资料读取和持久化写回；每家基本操作连续 3 次通过。
- 至少 2 家能在不逐轮催促、不人工搬运正文的情况下完成后台任务，并有一组两家接力连续 3 次成功。
- 所有必要人工确认都有准确位置和恢复方式；有确认的平台不能计入“全自动回写”的通过数。
- 独立测试定时至少观察 3 个实际轮次。服务自己发出提醒不算平台已启动。
- 重复提交、并发领取、失败重试、撤销与跨成员访问检查通过，且有可读证据。
- 本地版还须通过 V16—V19；V20—V25 覆盖参数化多成员/账号/混合组合，V26—V30 覆盖真实入口、交付、共享资源、停止和安装维护；模拟机制与真实平台记录分开，用户示例不是固定验收组合。

浏览器路线按端到端读取任务、完成工作、保存结果验收；若由适配器领取/回传，必须记录执行端身份、原平台来源、对话与版本。它可以证明浏览器路线完成任务，但不能算成“Agent 原生 MCP 读写已通过”。每家台账分别列原生/浏览器两栏，不用混合计数掩盖能力差异。

### 需要修改定位再继续

- 只能前台手动调用：可以说明存在“人工发起的共享工作台”能力，但不算自动接力产品通过。
- 主要成员每步都要人工确认：必须修改其岗位或流程位置，不能承诺无人值守。
- 两家及以上无法完成真实接入/读写，或没有两家能完成自动交接：本轮整体不通过，具体记录受限平台、接口或账户条件，不继续照旧方案开发全套 UI。
- 接得上但不减少人工搬运或改善结果：技术验证通过、产品价值未通过，两者分开结论。

## 6. 证据与交付

代码放在一个最小验证目录；只维护本文和一份结构化验证结果，不按每个小步骤堆一份文档。

每条结果至少保存：测试编号、平台、实际执行时间、试验轮次、任务/步骤/调用 ID、预期/实际结果、计划/开始/完成时间、确认次数、结果来源、失败原因与证据路径。模型自己说“已完成”不能成为唯一证据；必须能和服务端事件及持久化结果相互核对。

最终交付：

1. 四家能力对照表：谁可全自动、谁半自动、谁当前不能用。
2. 一条真实接力任务的完整时间线、成果和服务端证据。
3. 实际耗时、人工介入、可见额度与接入步骤。
4. 是否继续开发，以及原方案必须修订的条目。
5. 所有失败与待测项，不能因为后面重试成功就抹掉失败。

涉及定时、续期和恢复的验证按真实时间观察，不能压缩等待后宣称已验证长时间稳定。不会把“测试服务上线”当成本轮全部验收完成。

## 9. 用户补充：主动唤醒优先于定时自查

用户关心的是上一家完成后，下一家能否立刻收到工作并开始，而不需要用户逐家去聊天。共同档案和岗位规则只配置一次，后续触发携带任务 ID 与版本，Agent 从工作台读取本次要求与上下文；不要求用户每次重新说明工作。

触发路径按以下顺序验证：

1. **官方 API / webhook**：优先；[Grok Routine 官方说明](https://cursor.com/help/grok-bot/routines)提供 webhook，文档区分接收/启动与任务完成。[OpenAI Workspace Agents 官方说明](https://help.openai.com/en/articles/20001143-chatgpt-workspace-agents-for-enterprise-and-business)及[触发接口](https://developers.openai.com/workspace-agents/trigger-runs)已描述 API channel 和队列触发，但指向 Business/Enterprise 的 Workspace Agents，不能直接当成个人 Dots 账号也开放。原方案“各家全部不能外部触发”的笼统说法不作为已确认前提。
2. **专用完整浏览器适配器**：没有适用官方入口时，先核对允许接入方式，再在客户端管理的对应账号环境进入指定 Agent/会话派发、记录开工与完整交付。能操作网页不能代替平台资格确认；个人 ChatGPT 网页自动提取已发现明确限制，不作为默认回传。必要人工确认如实保留。
3. **定时自查**：保底路径，单独标识由轮询间隔带来的延迟，不宣传即时协作。

浏览器路线还要分开验证两种结果回传：Agent 通过 MCP/API 自己提交；或浏览器适配器读取 Agent 已完成的输出、核对任务标识和版本后回传。后者必须标注为“浏览器采集回传”，不能伪装成该平台的原生写工具通过。不得采集半成品、把聊天里的“我完成了”当结果、把某个旧会话回答贴进新任务。

工作台负责状态、上下文、交接、重试和证据；已选择的本地客户端负责账号隔离、专用完整浏览器和允许范围内的网页交互。后续再增加托管，不预设普通 Worker 自己长期运行 Chrome，不先购买云浏览器服务。

V15 是本轮优先验证项：每条路线报告真实触发延迟与排队延迟，支持时至少连续触发 3 次。快速投递、模型开始、执行完成是三个不同指标；官方 HTTP 接收成功或浏览器发出消息，都不能直接算“实时协作通过”。

## 10. 本地先行的验收边界

执行形态经历扩展路线核查（第 11 节）、专用浏览器补查（第 12 节），用户最终在第 13 节选择了客户端管理专用完整浏览器。历史候选用于保留依据，不代表同时开发两套默认安装路径。

账号会话由专用浏览器保存，用户首次在官方网站登录，无需导出 Cookie 或交平台密码；同账号原生多个 Bot 复用该账号会话。必要登录/验证/批准由本人处理。客户端/电脑退出时本地步骤暂停，关闭日常 Chrome 不应影响专用环境；资源占用需实测。

以后托管复用任务协议、步骤状态、平台适配器和证据格式；不自动上传本机 Cookie/资料，托管需主动启用并重新登录，平台访问条件与长期稳定性另验。

## 11. 产品方案层面的验证结论（v0.4 历史核查，2026-10-26）

本节保留当时扩展路线的核查依据；执行形态已由第 13 节的用户决定更新，平台限制和输入/交付区分仍然适用。

### 11.1 结论与范围

**“Chrome 扩展复用已有登录 + 云端工作台保存任务、协调交接”有可用的通用机制与现成产品依据，值得实施最小集成验证。原方案“四家个人 Agent 登录后均可在后台全自动派发、收取结果，之后直接搬到云端”不成立为已确认承诺，必须按平台能力修正。**

这次完成的是文档、公开产品与架构核查。未安装扩展、未启动商业 Agent 测试任务、未访问或导出用户 Cookie、未改变现有浏览器/VPN，也没有本项目长期稳定性实测数据。原有市场统计没有在本次重新调查，不能计作需求已验证。

### 11.2 哪些能现在判断

“机制有依据”指官方接口具备对应能力；“设计可处理”指已有具体处理路径，尚未以代码证明；“前提不成立”指当前方案不能据此承诺，不表示所有替代路径都失败。

| P08 | 网页能操作，就能统一自动抽取四家的回答 | **不能这样承诺。** OpenAI 个人服务公开条款明确限制自动/程序化提取数据或输出 [S10]；其他平台也不能从浏览器通用能力推定授权 | 个人 ChatGPT 网页自动采集不作为默认产品路线；优先适用的正式 Agent/连接器回传。这里是依据条款作出的产品决定，不推断必然封号 |

| P12 | 第三方开源浏览器工具已证明本项目稳定 | **没有。** 现成工具证明类别可做；工具用途、权限和控制方式不同，不能拿其通用任务结果代替四家接力 [S8][S9][S11] | 参考已有实现，独立验收本项目，不给无依据的成功率 |

Grok 的正式触发使“基本全部必须靠云浏览器”并非必要前提；OpenAI 的接口结果限制使“有 API 就闭环”也不成立。必须分别设计输入、实际执行和交付，浏览器只解决适用的交互环节。

### 11.4 修订后的完整用户路径

1. 用户在工作台选择要完成的事情，选已有的 Agent；不先问协议名称，不要求用户配服务器或开发者终端。
2. 安装扩展，按连接的平台申请网站权限；扩展确认账号和目标 Agent/会话。已有登录直接用；缺登录、验证码和平台正式授权才由用户处理。公开发行的安装体验仍需商店审核验证，未打包加载只用于开发验证。
3. 产品根据已确认能力推荐分工、建立任务上下文和必要正式连接器。开发者负责自动配置能配置的部分；平台强制本人批准的步骤明确标出，不让用户每天复制提示词。
4. 派发后区分“等待平台开始”“运行中”“结果已收到”“等你确认”。收到完整且可归属的成果才开启下一步，不以页面文字或平台 completed 单独作交付凭证。
5. 用户在普通页面继续工作。只有登录失效、必须批准或结果确需决策时合并通知；目标工作页被用户接管则暂停，不争夺页面输入。
6. 断连/休眠后对账恢复；可确定没发出才重发，已发出未确定完成先查原会话。不做无限重试，不清零失败记录。

**用户日常负担的设计目标：一次连接与规则设置，日常只交需求、看结果和处理必要确认。** Chrome/本机在线仅是依赖浏览器步骤的运行条件。首次安装耗时、每轮介入次数和实际可用性必须实测，当前没有“20 分钟一定完成”或“永远不用管”的证据。

### 11.5 哪些由开发者现在做，哪些确实需要账号实测

- **本轮已完成：** 通用浏览器机制和现成实现核查、平台触发/结果区别、已发现的账号资格和访问方式限制、用户路径与故障处理设计；已经同步 v0.4。
- **开发者可以独立继续：** 实现最小扩展和任务服务；在自有测试页面验证消息发送/收取、后台休眠、断连、页面关闭、重复交付、权限范围及不抢焦点。它们只能证明本产品机制，不能替商业 Agent 过关。
- **商业账号里才能确认，但测试仍由开发者执行：** 指定 Agent 实际派发、正确工具权限、完整交付、是否卡批准、实际配额/等待以及至少两家自动交接。只有登录、验证码和平台强制本人批准时请用户介入，不要求用户自己排查或自行做验收。
- **本轮不能定为通过：** 四家自动协作、实际长期稳定、用户愿意使用/付费、云端托管条件。不能拿本次方案审查替代这些证据。

**继续判断：按修订方案进入最小集成验证；原版“四家网页统一全自动”不能直接进入完整开发或对外承诺。** 仍保持原 M0 的三家真实集成、两家后台交接等要求，不以换成普通模型 API、只做一页聚合聊天或悄悄降低通过数量代替目标。

## 12. 多端登录与专用浏览器补查（2026-10-26）

用户进一步提出内部浏览器，担心新增登录与原有使用相互影响。本节核查本人多端登录、网页登录兼容性与产品安装负担；它是新的方案比较，未启动任何浏览器、未登录用户账号，也未将新候选冒充已实现功能。

### 12.1 多端登录不是所有平台都能一概保证

| 对象 | 查到的官方依据 | 本次能下的结论 | 不能推出的结论 |
| --- | --- | --- | --- |
| ChatGPT | [OpenAI 账号政策](https://help.openai.com/en/articles/10471989-openai-account-sharing-policy)明确允许本人多设备使用；[跨设备订阅说明](https://help.openai.com/en/articles/20001056-troubleshooting-subscriptions-linked-to-another-chatgpt-account)确认同一购买账号在另一设备仍可使用订阅 | 不需要因为多一个浏览器就另买 ChatGPT 订阅；不必按单设备账号设计 | 不保证永不重验、不保证无限并发，也不证明个人 Dots 有工作区 API 权限；额度仍按原账号/套餐规则 |
| Google / Gemini 的登录账号 | [Google 登录会话说明](https://support.google.com/accounts/answer/3067630?hl=en)明确同一设备多个会话正常，新浏览器或 App 会创建独立会话 | Google 账号可在原浏览器和新的独立环境保有会话，不能把重新登录等同重新注册账号 | 不能据此确认 Gemini Tasks 的多任务并发、任何嵌入式浏览器都可登录或账号验证永不过期 |
| Grok Bot | [官方 FAQ](https://docs.x.ai/grok-bot/faq)确认桌面与移动端的同一 Bot/会话跨已登录设备同步 | 原有桌面/手机使用与新增受支持入口不必互斥 | 该说明不是第三方浏览器入口承诺；[Grok FAQ](https://docs.x.ai/grok/faq)区分 Grok Bot 与 grok.com 普通聊天，不能拿普通 Grok 网页替 Bot 接入过关 |
| Meta Muse | 本轮查到官方产品有 App/WhatsApp 等使用方式，但没有找到 Muse 专门的同时登录上限、不挤掉原会话或第三方浏览器支持承诺 | **本项仍未确认，不能写“四家都官方保证多端不互踢”** | 普通 Meta 账号设备列表、其他 Meta App 的政策及第三方报道，不能代替 Muse 的明确规则或本账号实测 |

多端登录、多个任务同时执行、第三方程序自动操作，是三个不同问题。前者通常不要求换账号；后两者仍取决于具体产品能力与访问规则，不能凭多端政策直接验收。

### 12.2 “内部浏览器”必须区分两种实现

1. **App 里嵌 WebView/CEF/Electron 网页窗口。** 不把它选作通用登录底座：[Google 帮助页](https://support.google.com/accounts/answer/7675428?hl=en)明确可能阻止嵌入其他应用或受自动化控制的浏览器；[Google OAuth 政策](https://developers.google.com/identity/protocols/oauth2/policies)也限制在开发者控制的嵌入式用户代理里发起授权。Google 账号能多端登录并不能解决这一限制。
2. **客户端管理独立的完整 Chrome 和持久资料目录。** 可以作为替代扩展路线的更可控候选。Chromium 官方[资料目录说明](https://chromium.googlesource.com/chromium/src/+/main/docs/user_data_dir.md)支持自定义目录；这让任务浏览器与用户平时的 Chrome 分开，而不是复用正在被占用的资料目录。使用完整 Chrome 仍不能保证 Google 一定接受自动化环境，也不消除平台网页和配额限制。

“用系统浏览器给我们的 App 做 Google OAuth 登录”只得到本 App 的相应授权，不会自动把 Gemini、ChatGPT 等网站的登录 Cookie 搬到另一浏览器；不能用这个办法承诺免登录。新独立目录应由用户在对应官方网站正常登录，之后保存这套会话，不偷偷复制原浏览器资料。

Chrome 官方[远程调试说明](https://developer.chrome.com/blog/remote-debugging-port)也建议将自动化/调试环境和真实日常资料目录分离。不要为了实现专用浏览器去开启用户默认资料的全局远程控制；本机控制通道不能暴露到公网。

### 12.3 从用户角度要做什么

- **扩展路线：** 安装扩展，批准指定网站权限，确认当前账号；通常可复用已有网页登录，不额外安装浏览器。但需正确处理工作标签页、用户关页及页面休眠。
- **专用完整浏览器路线：** 安装我们的客户端；客户端检测可用的完整浏览器并管理专用运行目录，缺依赖时由产品提供清晰的安装流程。每家首次登录、验证码和平台授权仍由本人完成；用户无需自己配置 CDP、目录或常驻脚本。当前还未完成打包、登录与安装实测，不能称作已开箱即用。
- **之后使用：** 保留专用会话，失效时只重连对应平台；任务在产品自己的环境中运行，不操作日常 Chrome 的会话。移除绑定时可清理本产品的专用目录，不能清理用户原浏览器。
- **同一账号的订阅与额度：** 新浏览器不等于新订阅或新额度。能否使用某个 Agent 功能仍由原套餐和授权决定，不能把“同账号已付费”推成任意企业功能免费可用。

### 12.4 补查时的建议与剩余验证

以下是比较时的建议，用户随后已采纳专用完整浏览器路线，最新确定方案见第 13 节。

**建议将“客户端 + 专用完整 Chrome”作为优先比较的执行环境，而不是简单在 App 内嵌网页。** 它的优势是独立管理任务窗口、资料和进程，减少用户日常操作影响；这是工程可控性的判断，不是已经取得更高成功率的实测结论。

v0.4 的任务状态、正式触发和原生结果回传仍可复用；不因切换浏览器形式重做协作逻辑，也不通过切换形式抹掉平台资格限制。开发前先比较两条路线的正常登录与自动任务闭环，再固定发行形态，不能仅凭“内部”二字选择。

新增必须验证：原 Chrome 与专用环境保持同账号会话时是否互相失效；新环境登录是否被拒；目标是真正的 Agent 入口而非普通聊天；同一账号并发是否冲突；会话重启后是否保留；必要批准是否能接管；移除产品能否只清理专用资料。测试由开发者执行，仅本人登录/验证/批准时需要用户参与。没有实测前不承诺“登录一次永久有效”或“内部浏览器一定稳定”。

## 13. 用户确定的方案与同类多成员要求（v0.5，2026-10-26）

### 13.1 已确定的产品形态

**用户已选择：本地客户端管理专用完整浏览器 + 云端任务工作台，之后再做云端托管。** 不再把现有 Chrome 扩展作为默认形态，也不同时开发两种默认安装流程。平台支持的正式触发/连接器继续优先使用，浏览器仅承担适用的交互与登录环节。

用户安装我们的客户端；浏览器依赖、专用目录、进程和任务恢复由产品管理，用户只在各家官方页面完成首次账号登录与必要验证/批准。普通 WebView 不是通用登录底座，日常 Chrome 的资料不复制、不覆盖，不因关闭用户日常浏览器而退出专用执行环境。

当前只完成方案修改，没有安装客户端或验证任何新登录；不把用户选择写成技术验收通过。

### 13.2 所有已适配平台的同类多成员、多账号都是 P0

用户澄清：**Grok、Muse 和“10+10”都是举例，不能写成只支持两家、固定测试门槛或数量上限。** 通用模型面向所有已适配平台，支持单平台重复添加、多个账号以及跨平台混合团队；新增平台通过能力声明与专门适配接入，不只改名称就宣称支持。可用规模和并发按资源及实测报告，不承诺无限容量。

专用浏览器采用普通完整浏览器的持久资料目录来保存并隔离账号；这与指纹浏览器的设备指纹伪装不是同一件事。当前不要求采购指纹服务，不以指纹伪装作为登录或稳定性的解决方法。

支持以下结构，不以平台名称作为唯一成员：

| 结构 | 产品怎么支持 | 当前依据和限制 |
| --- | --- | --- |
| 同账号多个原生 Bot | 一个账号连接/登录环境，绑定多个不同原生 Bot ID，各自有名称、岗位、任务和结果 | Grok 官方[创建 Bot](https://docs.x.ai/grok-bot/bots)和[FAQ](https://docs.x.ai/grok-bot/faq)有多 Bot 依据，具体数量、套餐和本项目接入仍需验；同账号 Bot 共享平台云电脑及部分资源，不承诺底层隔离 |
| 多个独立账号 | 每个账号独立持久资料目录和身份；一个账号可再绑定其支持的原生 Agent | 可管理同平台多账号；实际登录必须使用对应已有账号，10 个独立 Muse 不靠开 10 个标签页伪造 |
| 同一个原生助理的多个任务/角色上下文 | 作为同一成员的不同会话/职责记录，显示共同账号和原生身份 | 不冒充多个独立原生 Agent，不声称获得独立订阅配额；Muse 单账号原生分身能力未核实 |

数据模型固定区分平台、账号连接、Agent 成员、会话/执行。`account_connection_id` 和 `member_id` 独立，任务和成果带上对应原生 Agent、会话和尝试版本；仅“都是 Muse”不足以匹配身份。

### 13.3 管理、调度和故障处理

- 成员列表按平台/账号/岗位/状态筛选，显示账号别名和具体成员；允许继续添加同类，不覆盖上一名成员。
- 用户可以明确指定成员，或指定岗位由可用候选成员接手；单任务默认选择一个，不对 10 个同类成员全部广播。需要多人分别出结果时显式创建独立任务。
- 同账号多个原生 Bot 共享登录环境但分开锁定会话和任务；不同账号不共享 Cookie、下载目录或平台授权。发现当前账号身份与绑定不符，暂停并显示原因，不向错误账号派活。
- 成员配置与登录资料保留，活动浏览器按需启动；账号、会话和设备资源各有并发约束。默认先一个活动浏览器任务，按实测资源与平台能力调节；原生接口另计。
- 设备在线、账号连接、成员就绪、执行和排队分别显示；成员列表不以示例数字封顶，也不能把配置数量宣传为同等并发执行，不让所有账号的浏览器始终常驻。
- 账号配额按实际平台范围计算，不把同账号的 10 个 Bot 当作 10 份额度。达到上限或失效只暂停关联成员，其他账号继续；不自动充值、不静默更换付费身份。
- 成员停用与账号断开分别处理。删除账号须明确影响哪些成员/任务，只清理产品专用资料；保留历史结果与来源，改派记录新尝试，不覆盖旧身份。

### 13.4 验收与缺少账号时的记录方法

V20—V25 覆盖可配置平台/数量的同类多成员、跨账号隔离、原生多 Bot、混合团队、结果归属、故障范围和容量；原 V01—V19 的真实接入、接力、批准、恢复和不打扰要求不变，不因用户示例取消其他平台适配能力。

分开交付两类证据：

1. **产品机制与容量：** 可先用明确标记的测试数据和测试适配器验证可配置规模的成员管理、队列、身份校验、故障隔离及新增平台注册；只能记为本产品机制通过。
2. **真实平台能力：** 每个实测平台、账号和原生成员提供身份、登录、派发与交付记录。没有账号、缺原生多 Bot 能力或未验证的条目标为待测/受限，不能用标签页、模拟回答或普通模型 API 填充真实成功数量。

报告具体测试平台、账号数、成员数、执行并发、通过/失败和资源边界。不能从少量平台样本推断所有平台兼容，也不能把用户的示例重新变成平台白名单或固定规模承诺。当前尚未开始本轮真实连接及容量测试。

## 16. Magpie 参考结论（源码核查，2026-10-26）

[Magpie](https://github.com/yetone/magpie) 的核心是本地模型网关和编程工具模型配置管理，既支持 API Key/本地模型，也读取已有订阅的登录凭证，不是只有付费 API 接入。[账户源码](https://github.com/yetone/magpie/blob/main/internal/provider/account.go) 明确读取 CLI 保存的登录或系统钥匙串；[路由源码](https://github.com/yetone/magpie/blob/main/internal/agent/route.go) 负责把模型选择映射到本地网关。

我们的核心是已有原生 Agent 的唤醒、能力/账号绑定、任务交接和完整成果验收。Magpie 的网关不能直接证明 Grok Bot/Muse 等的原生能力能被调度。但账号生命周期、配置原子修改/恢复、路由故障和本地诊断的做法有参考价值。本轮只阅读公开代码，没有安装 Magpie、读取其订阅凭证或改变任何现有模型配置。


## 17. 日常操作回归与钥匙串弹窗处理（2026-10-27）

本轮新增实际回归，非商业 Agent 联测：

- **重复打开连接设置：** 先实际复现失败，已验证成员被退回 unverified。修复后查看配置保留验证；显式轮换凭证才撤销验证，并使旧 nonce/回执失效。`tests/setup-stability.mjs` 与新增单测通过。
- **原生桌面重开：** Electron 窗口内创建账号、成员与公司档案；刷新、退出、再启动后读回相同任务版本、成员、档案和加密测试凭证。`evidence/desktop.json`。此测试使用 mock keychain，不冒充正式钥匙串验证。
- **钥匙串弹窗：** 初次原生桌面重开测试错误地访问了 `Agent Hub Safe Storage` 的真实钥匙串条目，触发用户截图的授权框；测试超时退出。已停该测试进程，改成临时独立 Electron 资料目录与官方 `use-mock-keychain` 测试后端；随后重开测试通过。测试模式强制校验临时目录，正式客户端仍保留原有加密，不启用 mock 后端；没有要求用户输入密码或修改系统钥匙串权限。
- **剩余事实：** 正式版仍是本机签名而非稳定 Developer ID 签名，不能承诺正式客户端换构建后的系统首次授权永不出现。Electron 官方说明这类签名变化可能再次请求钥匙串授权；本轮解决的是测试访问正式钥匙串导致的反复弹窗，没有绕过 macOS 权限。

参考：[Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)、[Electron 官方测试隔离修复](https://releases.electronjs.org/pr/53790)。目前 12 项单测及连接设置/桌面重开回归通过；真实商业平台仍待接入，不能宣布全产品验收完成。


## 18. 更新不得丢失登录资料（2026-10-27）

用户明确要求后续更新、修复不能让其重新登录。本轮把它写进 PRD 4.5 和根目录 `AGENTS.md`，并落实为程序保护与构建前置验收。

**实际复现与修复：** 之前测试只检查长期 Cookie。增加会话 Cookie 后，真实完整 Chrome 关闭重开断言实际失败（得到 undefined，预期 session-a）；增加 `--restore-last-session` 后通过。没有读取或导出用户的真实 Cookie，没有启动 Electron 或访问其钥匙串。

| 保护项 | 实现和本轮结果 |
| --- | --- |
| 程序与登录资料分离 | 固定 `.config/agent-hub/profiles/<account_id>`，独立账号目录索引。打包器检查输出路径，禁止与持久数据或其父/子目录和软链接重叠；不把登录资料打包 |
| 原账号资料不见时 | 已登记目录缺失或移动即停止，不新建空白环境。真实 Chrome 测试把临时账号目录移走，打开被拒绝且没有生成替代目录；恢复原目录后继续读回 |
| 浏览器身份固定 | 保存原浏览器路径、产品和最高使用主版本；缺浏览器、换产品和降级被拦截，不自动换 Chromium 或清空旧资料 |
| 关闭/更新后保留 | 长期 Cookie、会话 Cookie、LocalStorage、IndexedDB 关闭重开后全部读回；从另一程序安装目录加载替换代码后，仍复用相同外部 profile 并读回全部四种标记 |
| 用户主动退出 | 测试主动删除会话 Cookie，再关闭重开仍保持退出，不拿旧快照恢复用户已撤销的会话 |
| 回归和打包门槛 | 15 项单测通过；完整 Chrome 回归通过，结果在 `evidence/browser.json`。`package:mac` 前置运行 `verify:session`，失败中止打包 |

这是登录资料留存机制的工程验证，不是商业 Agent 已登录验收。网站主动失效会话、用户退出或平台要求验证码，仍需按平台要求处理。没有承诺平台永远认可同一会话。

实现依据：[Chromium 会话恢复处理](https://chromium.googlesource.com/chromium/src/+/354945de1fb564ef04c07cf8bfedf434d2d81747/chrome/browser/sessions/restore_on_startup_policy_handler.cc)；本轮结论以安装的完整 Chrome 实测为准。
