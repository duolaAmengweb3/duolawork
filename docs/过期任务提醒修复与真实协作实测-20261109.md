# 过期任务提醒修复与真实协作实测 · 2026-11-09

本记录区分两项工作：过期 Todo 通知的代码修复与部署；用户身份发起的右侧协作空间讨论实测。后者只讨论方案，本轮没有修改侧边栏、资源权限或执行任何业务任务。

## 已确认的通知缺陷

受控验收 A 被取消后，旧 `check` 跟进通知仍是 ready。旧的显式 claim 在事务里抛出 task_not_ready，事务回滚，不能清掉旧 turn/outbox。旧 inbox、合并领取和本机缓存还可能继续投递它。

修复提交 `8199cc8`；原生分发包 `30d2520`。服务端在任务变更、inbox、显式/批量领取、运行状态读取、接收回执、投递/重试、日常维护统一核对当前任务状态。取消、换执行人、成果/约定换版、已结束父任务的旧子项跟进会原子收尾：turn removed、outbox canceled、followup superseded。临时前置不满足保留等待，条件恢复后可接续。根任务最终核对结果仍可送达。

不会自动完成真实工作，也不会释放已有领取的执行租约。正常人类消息与仍有效的合并通知保留；失效门铃后面的正常消息会恢复投递。晚到 HTTP 结果、缓存的旧成功回执不能把失效通知复活。四种原生接收入口在启动/排队前尊重 applied:false；Codex 只清除本连接器自己排入的已完成/合并/移除提醒。

测试另发现：任务明确解除接受状态后，以相同成果重新核对，旧幂等判断会直接返回 blocked 记录。已调整为只有状态和接受结果仍相同才复用旧核对；重新确认产生新的核对并恢复后续依赖。

## 实测发现的协作问题

1. 需求不明确时直接扩展为左右栏整体重做；纠正后能回到右侧，但前面的过大方案已带偏第一轮讨论。
2. 未核实就写“90%/85% 高频”“缺上传入口”“没展示交付核对”等判断。需读取实际界面和当前版本，事实、推测、设计建议分开。
3. 相同 1672 字方案在 #605/#606/#607 用三个不同 requestId 连发；第三次才触发重复提醒保护。这不是全员数限制，是同一请求重复提交与反复唤醒问题，正常长讨论不能因此设固定轮次上限。
4. #614 声称“已闭环”，但 #612 的默认关闭连接器和投票放行等相反口径仍在原方案里；#620 又在 Dot 尚未领取时称“全体成员意见已收敛”。需要实际合并产物与参与状态，不以“已采纳”替代。
5. 对同样能力的成员强贴专业标签、默认只找两位没有依据；本次用户明确要求全组讨论，应统一通知，独立贡献、允许反对/无补充；负责人负责综合，普通沟通仍按用户设置路由。
6. #624 虽已合并 Dot 意见，仍把等待 4分22秒直接称为“正常表现”、把综合意见称为“全员达成一致”。前者没有等待时间验收依据，后者没有逐人同意证据。合并建议可以交给用户，不需要为了措辞再唤醒一轮；不能因此声称整个协作机制已经完善。

## 右侧协作空间方案的当前边界

本群工作以现有资料、Todo/成果、记忆、会议为基础，统一资料列表并保留文件夹；类型作为可选筛选，条目显示可编辑、上传附件、外部链接的能力差异。任务直达实际核对过的具体版本，不凭最新更新时间猜产物，编辑从预览明确转到当前工作稿。

本群资源引用全局连接器、具体账号、配置与技能版本，区分本群可用、用户明确受限、本次已选用、本次实际调用；使用记录关联会议/Todo，显示最近结果和来源。沿用默认开放、后置管理；只把用户指定的 ATEL 飞书连接限制到 ATEL，不改成所有群逐个审批。Hub 只保证自身连接器路径的群范围校验；成员原环境的私有工具另行标明，不承诺虚假的全局隔离。会议结束不删全局连接、不改变群默认。

投票是意见与分歧记录，不以模型票数代替事实核对或用户执行决定。任务沿用当前 Todo，外部任务同步需确定唯一权威状态源。自动化作为触发层，说明时区、执行身份、目标群、下一次触发、停用、重试和结果，不另造一套任务系统。
