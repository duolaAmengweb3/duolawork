## 1. 一句话

**一人公司的 AI 团队：把你已经在用的大厂 Agent（Grok Bot、ChatGPT Dots、Gemini、Meta Muse 等）按岗位组成一个团队，跨生态接力干活。工作台先帮你把团队搭起来，再帮你派活、盯进度、收结果。**

## 2. 要解决的问题

**问题一（最大的）：打开这些 Agent，不知道怎么搭。**
订阅不是障碍（Dots 包含在 ChatGPT 套餐里，Muse 送了一大批），难的是：该让哪家干什么、在它的设置里点哪里、跟它说什么它才会照做。证据：龙虾代装被打到二三十元，但"装完帮你搭好怎么用"的服务从 300 元涨到 1000 元，卖家原话是"大家买的根本不是安装，而是跨越那道鸿沟的能力"（x-daily-drafts 仓库报告）。

**问题二：一件事跨了好几家，你只能自己当中间人。**
各家 Agent 最大的区别是"手里握着哪个生态"：X 在 Grok 手里，Gmail 和 Google 文档在 Gemini 手里，Instagram、WhatsApp 在 Muse 手里，飞书在豆包手里，企业微信在 WorkBuddy 手里。一件事跨了生态，就得你来回复制粘贴、盯着谁做完了没有。

**背景：** 一人公司在国内有政策推动（截至 2026 年 5 月全国 426 个 OPC 社区、106 项专项政策），创业者的痛点是"一个人什么都得干"；海外 63% 的 solo 创业者在用 AI，只有 8% 能用到全流程（见 `docs/需求场景.md`）。

## 3. 定位和对比

| | 我们 | "AI 员工"产品（Sintra、Marblism） | Paperclip（开源，约 10.7 万星） |
|---|---|---|---|
| Agent 从哪来 | 用户已有的大厂 Agent | 自己造的 | 用户自己部署的（Claude Code、OpenClaw 等） |
| 能力和生态 | 最强模型，天生连着用户自己的账号 | 取决于自己做得多好；能接的工具有限 | 取决于用户怎么配 |
| 要不要懂技术 | 不要 | 不要 | 要 |
| 怎么派活 | 账号可用的官方触发优先；否则用本地后台浏览器发送任务；实际接力待验 | 能 | 能 |

**我们的弱点（要正视）：** 控制权在大厂手里；网页、登录及账号权限可能变化；本地执行依赖电脑在线。护城河要靠可靠交接、公司档案、模板和接入体验积累，不能仅靠浏览器代点。

## 4. 目标用户

- **第一批：做内容的一人公司**，手上有两个以上个人 Agent。第一个用户是你自己（你现在就在用 Grok 每天往 x-daily-drafts 推内容）。
- **第二批：服务型一人公司**（独立顾问、接单的人），用来做获客和线索跟进。
- **适合的事：** 跨生态、重复发生、可以后台执行的任务。下一步就绪后主动派发，不人为等几个小时；实际开始及完成耗时待测。
- **第一版本地要求：** 电脑在线；各平台必要的登录、验证码和人工批准仍需处理。不承诺无人确认的所有平台、所有操作都可全自动。

### 4.1 执行方式：本地客户端管理专用完整浏览器，后云端托管

- 用户已确定采用此形态：客户端 + 专用完整 Chrome/受支持完整浏览器 + 云端任务工作台。Chrome 扩展不再是默认安装项；浏览器依赖由产品准备与维护，不让用户自己配置目录、远程调试或常驻脚本。普通 WebView 不作为通用登录底座。
- 专用浏览器使用普通浏览器的独立资料目录与进程管理，不等于指纹浏览器，不把购买指纹服务或伪装设备身份作为产品前提。
- 每个独立平台账号有专用持久资料目录，与日常 Chrome 分开；首次用户在官方网站正常登录，不复制日常资料、不要求导出 Cookie、不代收平台密码。同一账号下多个原生 Bot 可复用该账号的登录环境。
- 默认不抢窗口、不动系统鼠标键盘和剪贴板。用户主动查看、登录或批准时显示对应专用窗口；必须前台的步骤等待接管，不偷切日常窗口。无窗口和可见运行模式的兼容性分别验证。
- 首页分开显示客户端在线、账号连接、成员就绪、任务实际执行、等待登录/批准和结果验收，不能把“客户端有心跳”当作所有成员正在工作。通知按受影响账号/任务合并。
- 工作台保存任务版本和执行记录，客户端恢复前先核对原会话；断线、浏览器进程退出、页面变化、休眠都要恢复或明确报错，不能盲目重复派发。
- 成员数量和同时执行数量分开管理。支持可配置的平台组合与多成员规模，测试覆盖单平台多成员、多个账号与跨平台团队；“10 Muse + 10 Grok Bot”只是举例，不是固定验收或上限。活动浏览器按任务启停，资源、吞吐和容量按实测报告。
- Cookie/网站会话留在本地专用目录；设备密钥按系统安全存储保管，云端只存连接标识和必要任务/结果。任务内容仍会送到所选平台，不能宣传所有数据都只在本机。
- 官方触发、平台执行和结果回传分别检查；内部浏览器不会自动获得企业 API、绕过登录限制或让网页采集符合平台规则。正式入口适用时继续优先使用。
- 用户关闭日常 Chrome 不应影响专用运行环境；电脑睡眠、断网或退出客户端执行端时本地步骤暂停，官方云端运行另行追踪。以后托管复用协议和适配逻辑，需单独验证登录和运行环境。

### 4.2 协作不等于强制四家串行

一个任务按所需的实际能力分配成员，模板不强制每次经过四家，也不要求用户同时购买四家订阅。比如内容包可由有来源能力的成员研究，再由另一成员形成稿件；无新增信息的重复改写不增加步骤。部分成员受限时，先显示可完成的工作和确切阻塞项，不能假装已经替它执行，也不暗中换成通用模型 API。

产品价值先看是否免除用户逐家派活和搬运、是否保留来源与可交付成果；“四家出现在同一页”不能算价值验证通过。原始统计与市场判断仍需实际使用证据，不能以架构审查代替用户需求验证。

### 4.3 同类多个 Agent、多个账号（P0）

**平台不是成员的唯一键。** 第一版对所有已适配平台支持多个成员、多账号及跨平台混合团队。用户举的“10 个 Muse + 10 个 Grok Bot”仅说明同类可重复添加，不限定品牌、固定比例或数量上限；实际可用容量由资源、平台约束和实测决定。

平台列表通过适配器注册扩展。每个适配器声明登录、账号/原生 Agent 识别、触发、结果交付、多 Agent 和并发能力；只有通过对应验证的能力才向用户提供。可扩展不等于所有网站无需适配就能接入。

| 对象 | 是什么 | 示例与规则 |
| --- | --- | --- |
| 平台 | 产品类别及其接入能力 | Muse、Grok Bot，不等于一个固定成员 |
| 账号连接 | 用户实际授权并确认身份的平台账号 | Muse 工作账号 A/B；各账号的登录资料、状态和额度分别保存 |
| Agent 成员 | 绑定账号及真实 Agent 身份的工作成员 | 同账号多个原生 Grok Bot，或不同账号各自的 Muse；有独立名称、岗位、任务和结果 |
| 会话/执行 | 某个成员的一次任务和对话 | 新聊天或新标签页不自动算成新 Agent，不从会话数量夸大成员数量 |

- 支持“同一账号下多个原生 Agent”和“多个独立账号下各自的 Agent”两种结构。平台没有原生多 Agent 能力时，多个岗位/会话要如实显示为同一 Agent 的任务上下文；需要 10 个独立 Muse 时接入对应的真实账号，不假装复制出了原生分身。
- 每个成员显示名称、平台、所属账号别名、岗位、连接状态、任务数及最近成果；支持按平台/账号/岗位/状态筛选、暂停、恢复、改名和解绑。
- 可以固定派给某个成员，也可以交给指定岗位的候选成员队列，由系统选择有能力且可用的一个。一次任务是否让多名成员各做一份须显式指定，不向所有同类成员默认广播。
- 不同账号的 Cookie、会话、文件下载和授权环境必须隔离；同账号原生 Bot 的产品内任务分开记录，但不承诺平台底层资源互相隔离。Grok 官方说明同账号 Bot 共享其云电脑、文件和登录状态。
- 配额属于账号或平台实际定义的范围；10 个成员不等于 10 份订阅额度。账号失效只暂停关联成员，单个成员失败不应导致其他账号全部停工。
- 解绑成员默认保留历史交付与出处；删除整个账号连接需显示受影响成员、暂停未完成任务，并仅清理本产品对应的专用登录资料。

### 4.4 成果、上下文和操作责任（P0）

- 每个任务指定最终交付负责人和交付清单：需要什么正文/文件、来源、格式、必填项和截止要求。成员完成推理或回复“好了”不等于用户已收到交付；进入结果验收后才允许下一步使用。
- 交接必须携带本次目标、规则、相关资料版本、前序成果和反馈；不要把整个历史聊天和全部账号资料无差别发给每个成员。事实、推断与待核实项分开，程序格式校验不能冒充事实或文稿质量保证。
- 同一任务用固定输入版本；用户改要求或前序结果更新后生成新版本，标记哪些后续结果需要重做，不静默用旧稿继续。
- 多名成员操作同一文档、日历或目标时必须协调写入；同账号多个 Bot 的平台共享资源也计入冲突范围。任务队列去重不能替代第三方实际动作核对。
- 暂停、取消、接管有清楚含义：停止后续派发、请求平台停止、平台已停止分别显示。平台没有取消入口时如实显示仍可能运行，不以关闭本地窗口伪装远端停止；已发邮件/发布内容不承诺能撤销。
- 发出请求后状态不明的动作进入待核对，不盲目重试写入、发送或购买。用户已设置的常驻授权按其明确范围执行；平台必须本人批准的要求仍保留。
- 浏览器/适配器更新不重置账号登录与任务记录；失败适配器可停用或回滚兼容版本。安装依赖、网络失败、更新、退出和卸载只操作产品自身资料，不改全局 VPN 或关闭其他应用。
- 账号登录态只在本机；任务中允许交给哪些成员、哪些资料可跨平台发送须可见。支持导出交付、解除账号和删除产品数据；解绑不等于第三方平台历史同时被删。

### 4.5 更新不得丢失登录资料（用户硬要求，2026-10-27）

正常更新、修复、替换安装包、程序回滚和账号别名修改，不得让用户因本产品重建浏览器环境而重新登录。程序目录与持久资料目录必须分离；已有账号固定复用自己的资料目录及浏览器产品。默认不删除 Cookie、LocalStorage、IndexedDB、会话记录、Local State、账号配置或密钥。

- 保留长期与会话 Cookie，正常退出等待落盘，重开恢复会话。
- 资料目录缺失/损坏/被占用、原浏览器缺失或检测到浏览器降级，停止并保留现场；不能自动换浏览器、重新生成账号或建空目录要求重新登录。
- 更新前置验收覆盖资料路径保护、同账号复用、替换程序代码后 Cookie/LocalStorage/IndexedDB 留存、账号隔离，以及主动退出登录不会被恢复。
- 平台主动使会话过期、撤销授权、强制验证和用户主动退出由平台决定；不能承诺所有平台永久免登录。商业平台真实联测仍是单独验收项。

当前已实现对应目录与浏览器绑定保护、会话恢复和自动化发布门槛；工程证据见 M0 最新第 18 节。后续维护规则已写入根目录 `AGENTS.md`。

## 5. 产品结构：三层

借鉴 Sintra、Marblism、Lindy、Paperclip 已经验证过的设计（见 `docs/复用的设计逻辑.md`）：

```
公司档案   你的业务、客户、品牌语气、目标、禁区。讲一次，所有 Agent 都知道
    ↓
团队       按岗位组织：社媒经理、行政助理、获客、内容……
           每个岗位交给握着对应生态的大厂 Agent（"成员"）
    ↓
工作       例行工作：某个岗位每天 / 每周自己做的事
           接力任务：跨岗位、跨成员的多步任务
```

## 6. 名词表

| 名词 | 意思 | 例子 |
|---|---|---|
| **公司档案** | 所有成员都知道的背景，几栏固定内容 + 自由笔记 | 品牌语气：大白话；禁区：不荐币 |
| **岗位** | 团队里的一个角色，写清职责、由谁来干、例行工作 | 社媒经理 |
| **账号连接** | 一份真实平台账号的授权和专用登录环境 | Muse 工作账号 A |
| **成员** | 绑定某账号下真实 Agent 身份的一个工作成员；同平台可有多个 | Grok Bot · 行业研究员、Grok Bot · 内容编辑 |
| **例行工作** | 岗位按时间自己做的事 | 每天 08:00 出 X 内容包 |
| **接力任务** | 由几步组成的一件事，每步交给一个成员 | 「10 月 27 日 X 内容包」 |
| **步骤** | 接力任务里的一步 | 第 1 步：Grok 抓 X 热点 |
| **叫醒** | 工作台通知成员"轮到你了" | 调用 Grok Bot 的 webhook |
| **确认关卡** | 交了结果后要你点头才继续 | 发布前要你确认 |
| **模板** | 预先设计好的岗位或接力任务，可重复用 | 「每日 X 内容包」 |
| **时间线** | 所有动作的记录 | 08:02 Grok Bot 领取第 1 步 |

## 7. 功能

优先级：**P0** = 第一版必须有；**P1** = 第一版后尽快做；**P2** = 以后。每一节对应原型里的一页。

### 7.1 首次使用向导（原型：0 首次使用向导）——最重要

设计目标（尚未实测）：打开就知道怎么搭，**20 分钟内跑通第一个任务**。用户不需要懂 MCP、webhook 这些词。

| 步骤 | 内容 | 优先级 |
|---|---|---|
| 1 讲讲你的生意 | 填公司档案；可以粘贴已有介绍，自动拆成几栏 | P0 |
| 2 想让团队做什么 | 选场景或岗位：每日内容包 / 社媒经理 / 行政助理 / 获客 / 自己定 | P0 |
| 3 你有哪些 Agent | 可多次添加同类平台、选择已有账号或新增账号；推荐岗位和具体成员，不把一个平台当成一个人 | P0 |
| 4 一个一个连上 | 客户端准备专用浏览器，用户首次在官方网站登录各账号；选择该账号下的原生 Agent。同账号后续添加原生 Bot 复用登录。产品验证身份、派发与回传，正式授权按需引导 | P0 |
| 5 定规则 | 哪些事先问你（对外发布、发邮件、花钱默认要问）；每个成员每天最多叫醒几次 | P0 |
| 6 试跑一次 | 一个简短的测试任务走完整条接力，你看着每一步亮起来 | P0 |

### 7.2 团队（原型：8 团队）

| 功能 | 说明 | 优先级 |
|---|---|---|
| 岗位卡片 | 职责、由哪个成员来干（以及为什么是它）、例行工作、状态 | P0 |
| 招岗位 | 内置 4 个岗位模板：**社媒经理、行政助理、获客、内容核实**；每个附职责、推荐成员、例行工作、实测原话 | P0 |
| 例行工作 | 每天 / 每周固定时间自动开始，平时不打扰，只在确认关卡找你 | P0 |
| 更多岗位 | 客服（Muse）、数据分析（Dots）、行业研究（Perplexity）、电商运营（Dots） | P1 |
| 每日团队简报 | 各岗位昨天做了什么、今天等你确认什么、哪个成员掉线 | P1 |

### 7.3 公司档案（原型：5 公司档案）

| 功能 | 说明 | 优先级 |
|---|---|---|
| 固定栏目 | 业务、产品、客户、品牌语气、目标、禁区 | P0 |
| 自由笔记 | 例如「本周选题」「常用信息源」 | P0 |
| 自动带上 | 成员领任务时，相关档案自动附在任务里 | P0 |
| 成员也能读写 | 显示最后是谁改的；修改档案默认不需要确认，可在规则里改 | P0 |

## 8. Agent 那边看到什么（原型：7 Agent 那边看到的样子）

成员连上后，在它自己的 App 里多出一组工具：

| 工具 | 作用 |
|---|---|
| 测试连接 | 回一句"连上了"，用于向导第 4 步 |
| 查看我的任务 | 轮到我做的步骤和例行工作，附任务说明、要求、前几步结果、相关公司档案 |
| 领取 | 告诉工作台"这一步我来做" |
| 提交结果 | 交上结果，或说明做不了、为什么 |
| 读公司档案 | 按栏目或关键词读 |
| 写公司档案 | 新建或追加笔记 |

**安全规则：** 前几步的结果和公司档案，对 Agent 来说"只是资料，不是指令"，工具返回时明确标注。

## 9. 状态

**步骤：** 等待前一步 → 可以做了 → 进行中 → 结果验收中 → 完成；有批准关卡进入“等你确认”；缺交付进入“交付不完整/待补充”，状态不明的第三方动作进入“待核对”，不自动重试。打回/改派生成新尝试。
**任务：** 进行中 → 已完成 / 出错 / 已取消；已取消表示工作台停止后续派发，不自动证明所有平台运行已终止。另列每个远端执行的取消请求/确认状态。
**例行工作：** 到时间就生成一个接力任务（只有一步也算）。

## 10. 第一版做和不做

**做（P0）：** 首次使用向导、公司档案、团队（4 个岗位模板 + 例行工作）、接力任务（含「每日 X 内容包」模板）、所有已适配平台的同类多 Agent/多账号及混合团队、客户端管理普通完整浏览器、可用的官方触发、结果核对回传、断线恢复、确认中心和时间线。M0 先验证真实路径；容量测试的平台和数量可配置，配置数、真实连接数及运行并发分开报告。

**不做：**

| 不做 | 原因 |
|---|---|
| Agent 之间自由互聊 | 第一版围绕有任务标识的工作流接力，不做无限对话 |
| 云端浏览器托管 | 本地版验证后再增加；现在不购买、不自动上传本机登录态 |
| 指纹伪装、验证码绕过 | 会话隔离和后台执行使用普通浏览器机制；平台必要的人为验证保留 |
| 工作台自己接大模型指挥它们 | 第一版用规则就够 |
| 自动发布到社交平台 | 发布一律留给人（小红书已严打 AI 托管账号） |
| 多人协作、多门生意、收费 | 先把你一个人的用法做顺 |

## 11. 已知限制（官方文档核实）

| 平台 | 限制 |
|---|---|
| Gemini Tasks | 需 Google AI Pro 或 Ultra；不在欧洲、英国、瑞士开放；自定义应用仅美国、英文；**写入必须手动确认**；Gmail 触发时间不精确 |

## 2026-10-27 产品交互修正：以会话发起工作

用户反馈当前只有任务台，不知道怎么用。默认入口改为“工作台”，任务记录成为辅助入口。

- 新工作：选一位已真实接通的成员，用一句话描述目标；默认直接执行，也可选择“先给我方案”。未接通的平台不可选，不要求用户填写岗位、任务编号、MCP 或触发 URL。
- 先给方案：原 Agent 返回结构化方案或必要问题；用户在会话里补充，或在右侧调整步骤、分工后开始执行。程序不使用预设步骤冒充模型规划。
- 工作中：同页展示真实领取/派发/等待/批准/交付状态；补充消息排在当前步骤之后，保留原领取，不伪装成即时打断。暂停只停止后续派发。
- 收到成果：全文与来源进入原会话，可复制、继续提要求或选择另一位已就绪成员接力，前序完整正文自动传递。
- 失败：保留输入，标明具体等待/核对原因；不明回执不自动重发。新任务、补充和执行方案均做幂等处理。
- 验收：默认首页可理解；一句话真实派发；真实方案能调整后执行；继续提要求能取到前序完整成果；同一请求不重复创建；账号切换不丢当前草稿；同页可见成果；支持的入口逐条验收。工程测试与商业 Agent 实测单独记录。

参考（官方材料，2026-10-27 查阅）：[Dust 首页与会话](https://dust.tt/academy/first-steps-on-dust/chapter/discover)采用输入栏、会话历史与 Agent 入口，并支持会话内交接；[Manus 交互与交付](https://help.manus.im/en/articles/14431752-chatting-with-manus-agent-on-slack-channels-dms-and-file-delivery)在原会话确认接收并回传结果。借鉴这些交互逻辑，不引入它们的模型 API，不替换用户原 Agent。


## 2026-10-28 已选定 B：对话＋成果

这是用户明确选定的默认产品形态，替代团队群聊和项目看板的首页尝试。

- 窄导航栏，左侧约三分之一为任务对话，右侧为主要成果空间；不让用户操作复杂状态卡片或先理解任务管理系统。
- 文稿：真实交付自动展开，可直接编辑、格式化、复制和导出 Markdown；原稿与人工工作稿分离，人工修改不伪装成 Agent 原始交付。人工稿自动保存到本机，保留最近版本，旧窗口不能覆盖新版本。
- 继续修改：发送前保存当前文稿，服务器核对稿件归属与版本，再将全文加入本轮原 Agent 输入；不得只改前端显示、仍让 Agent 使用旧稿。
- 素材：汇总本次用户提供与成果引用的链接，区分来源，不编造抓取标题、更新时间或已核验的事实。
- 执行记录：只展示实际领取、派发、等待、本人批准和回传，不捏造内部思考、预计完成百分比或不存在的成员动作。
- 草稿与恢复：工作输入及所选会话重开可恢复；保存失败的文稿在浏览器缓冲保留并可重试。切换成果、素材和记录不丢掉编辑内容。
- 文本资料：支持明确标注的 TXT/MD/CSV/JSON 输入，合计长度提前检查；不以不可用的上传按钮暗示支持任意文件。
- 验收：原 Muse 拟方案、用户确认执行、成果自动进入文稿区、人工编辑保存、原稿不变、编辑全文交回 Muse、最终改稿回到同一工作。另覆盖未就绪成员拦截、原始来源、复制导出、失败恢复、窄屏和登录资料保护。
