## 可复现的根因

1. 官方 DeepSeek 启动时载入旧会话，旧项目目录 realpath 返回 ENOENT；健康会话启动时另遇过云端连接中断。
2. `DshManager.tickHost → syncBindings` 负责后续恢复，但按顺序等待绑定，第一段异常会跳到整个成员的 catch。
3. 旧会话仍在官方会话清单中，已有的“会话 ID 不在目录中则跳过”保护没有覆盖“ID 存在、项目已不存在”。每轮都先失败，健康会话无法自愈。
4. catch 没有清理 sourceReady，状态残留；UI 又只按绑定存在判断绿点。待接收展示未区分恢复故障、离线和真实排队。

这是恢复路径上的缺陷，不是靠重建成员、重新登录或用户重复发消息解决的问题。

## 修复设计

- 后台恢复按唯一原会话并行执行，每段单独记录失败；坏目录和慢绑定不挡住健康会话恢复。接收器仍按原通道投递，不增加模型并发上限或降低上下文。
- 后台恢复失败下轮可重试；显式选择会话时仍返回操作失败，不能伪装绑定成功。
- 缺失目录、临时连接失败、其他恢复错误分别记录原因。健康会话继续工作；故障恢复后清除本段错误。
- 检查原运行端失败时清除 sourceReady，不把“无法联系”武断解释为“用户关闭了软件”。
- 会话标记和待接收摘要共用真实状态。Claude 服务端按群绑定计算是否在线，不能借其他在线会话显示绿色；连接在线只说明接收器在线，不声称原 Agent 空闲。
- 原消息、原会话 ID、工作目录绑定与历史保留。不会自动改变业务群的会话选择、创建替代项目、修改原生登录或权限。
- 日常产品的职责是报告可操作原因、保存消息、自动重试属于我们连接的短暂故障。用户原环境的启动/修复属于另一个操作范围；本次 Claude 恢复依据用户新增的明确指令。

## 追加：已领取工作在原生模型报错后卡住

2026-11-07 15:25 原 DeepSeek 审计会话发生 DeepSeek Messages stream: duplicate message_start（MALFORMED_RESPONSE），此前模型接口多次 HTTP 500。原生 turn/end 明确 error、running=false；Hub #372 已领取但无回复，后续 #383 一直被同会话旧通知占住。模型错误属于原生服务；错误结束后 Hub 仍显示处理并不继续核对，属于我们的接收器遗漏。

修复：即使 signal 没有新的 ready 通知，也定期核对已领取工作。原生 running=true 时延长原领取，不补发；unknown 或查询失败不视为停止。原生明确空闲持续 60 秒且服务端仍 active 时，在同一原会话只补一次回执核对，要求读取已有结果并回传，不再领取、重做操作或重跑全量。补发前持久化，原生 requestId 固定，进程重启不重复。若再次空闲仍无回执，通过既有 conversation-state ended 记录中断并释放资源，后续消息继续；不伪造成功。界面区分正在核对结果/原会话回复中断，按具体 turn 关联，不把旧错误覆盖新的执行。

定向 42/42：包括无新消息仍恢复、重启不重复、原生运行/未知/网络错误不触发重做、恢复失败释放后续、同群精确状态显示。真实原会话恢复及最终构建结果另附。
