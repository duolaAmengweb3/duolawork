# 会议自主组织与点名修复

用户提出会议需求，负责人理解后组织并交付。信息确实不足时才继续追问，不把“请确认开始”当成固定步骤。负责人保存目标、预期交付与安排后可直接调用 start；真实提交 finish 后结束。新补充必须被负责人读取和处理，原讨论与不同意见保留。用户仍可随时停止。系统的时间上限作为异常兜底，不代替负责人的完成判断。

## 本次现场

duolawork 项目组的会议记录一直是 preparing；界面把唯一活动会议自动选作聊天范围。12:51 的负责人回复和 12:54 用户点名被筹备路径接管。该路径未保存 mentions，也未按点名派发，导致用户选了 DeepSeek，实际仍只通知负责人。它们不是成员离线的证据，也不是已经正确结束后单纯 UI 刷新慢。

## 修复边界

- 只有主动发起会议或点击回到会议沟通才选择会议范围。普通进入群聊和查看会议记录不会改变发送范围。
- 筹备、进行、收尾区分显示；真实结束后输入框不再使用旧会议。结束不会清空草稿或点名。
- 先解析和校验点名，再进入会议处理。显式 @ 走普通消息投递，保留会议关联以便回看；不把接收者强制拉入会议调度，不把正常回复变成筹备发言或私有独立意见。
- Agent 文字 @ 的兼容识别与普通群聊相同；显式空 mentions 不误通知，引用和代码中的文字不误通知。
- 已结束会议的旧引用可以继续讨论，产生正常通知，不生成无法领取的过期会议工作。
- 删除固定开始口令与确认引用门槛。负责人处理最新需求后自行开会和提交结果；客户端显示真实动作状态。保留旧 confirmationQuote 参数兼容老客户端，但它不再是开始条件。
- 不自动重发此前丢失点名的历史消息，不虚构成员回复，不根据 Todo 已完成批量结束所有会议。
