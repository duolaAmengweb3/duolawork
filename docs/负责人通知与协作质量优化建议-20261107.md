# 负责人通知与协作质量优化建议

日期：2026-11-07。状态：只读分析与待审方案，尚未修改协作规则。
范围：负责人如何组织协作、通知谁、如何收尾。既有分会话、传输提速工作单独推进；本方案不把减少通知次数当成性能验收。

## 1. 产品结论

有明确的优化空间，属于值得优先处理的协作质量问题；不能仅凭“经常通知全员”就判定所有这些调用都浪费，也没有证据说明全员通知功能本身不应该存在。

观察到的主要问题是：负责人把“提到成员、感谢成员、同步进展”和“需要成员处理”混在了一起。一部分通知确实带来了必要的独立审查；另一些只是给完成通知再加一轮收到和总结。与此同时，负责人多次在汇总中扩大结论或遗漏限定，迫使成员反复纠偏。若只减少 @，可能连这些有价值的纠偏一起消失。

建议让负责人更准确地组织参与、保留公开过程和自主交流。用户不需要选择协作模式、配通知规则或每次审批。

## 3. 具体案例与判断

### 应当保留的全员参与

- **ATEL #46**：用户原话是“你先看下，然后安排大家都看下”。负责人将不同章节和检查方向分给四位成员。这次全员参与有明确授权，也有不同的预期贡献，合理。
- **项目组 #273 后续评审**：用户要求大家讨论提速方案。成员发现了会话绑定、断线重试、归因和产品操作负担上的实质问题。不能为了减少消息取消这类评审。
- **X内容 #147 → #149**：修改稿交给终审者，后者读回实际版本并发现元数据残留。再次通知审阅者是必要交接，不应按“已经讨论过”阻止。

### 明显可以改进的通知

- **X内容 #158**：终审者已在 #157 锁版并交付，负责人再次总结、致谢、表示等待用户查阅，仍通知 Dot 和 grok2。未提出新的审阅对象或待解决问题，属于可以免去的执行唤醒；总结仍可公开发在群里。
- **ATEL #112**：真正下一步是请 grok3 完成章节，但结构化收件人包含 Codex、grok3、ClaudeVPS、Dot 四位。前面几位主要出现在感谢和已完成工作说明里。若需要独立审稿，应明确请谁核对什么，不能靠顺手带全员名字隐式组织。
- **项目组 #254**：给用户解释为何还未验收，结构化收件人包括四位其他成员，而正文主要提及 Codex 和 DeepSeek。说明正文里看见的 @ 与实际通知对象还可能不一致，应让真实通知对象可见。

### 不能简单当作浪费的“来回纠正”

- **项目组 #281 → #283/#286/#290**：负责人把讨论中自己的扩展提议误归给原方案，把待测归因写得过于确定，并把“用户可以选新对话”收窄成“用户必须手动开终端”。其他成员的纠偏保护了产品方向。
- **项目组 #299 → #300/#301**：负责人把“发出到接手 6–20 秒”写成正常响应时长，又遗漏接手后的工作时间。纠正有必要；更好的优化是在汇总时保留测量阶段和证据范围。
- **ATEL #112 → #113/#115/#116**：成员纠正“已全部互审”“预算公式彻底杜绝风险”等过度表述，并核查实际章节衔接。这些回复有价值，不能因含有“收到/同意”字样就屏蔽。

### 已有的正向例子

ATEL #114 用户问“你为啥老是叫全员”；#117 负责人承认进度同步时习惯性带上所有人。此后样本中的六条负责人消息均不再通知全员，两条只通知一位成员，其余不通知其他 Agent；章节更新、校验与交付仍在继续。

这是“可以改进而无需禁止协作”的可行线索，**不是长期不降级的验证**。同一负责人在其他群仍有相似习惯，不能只依赖用户在每个群提醒一次。

## 4. 当前机制与原因边界

核对源码 ea907c2：
- 普通 Agent 消息不会默认广播。显式 mentions 指定收件人；mentionAll=true 才通知其他全部成员。
- 成员完成负责人组织的工作后，相关反馈可以自动回到负责人；不要求所有人再 @ 一遍。
- 旧工具兼容入口可能从未提供结构化 mentions 的正文中识别 @。本次关键样本多为明确提供结构化名单，不能归咎于正文解析器把普通名字误当 @。
- 因此，样本主要支持“负责人选择了过宽的收件人、汇总不够准确”；尚不支持“系统在所有消息里自动广播”或“Gemini 平台独有故障”。

来源：[路由](../shared/chat-routing.mjs)、[消息发布与负责人指引](../cloud/collaboration/conversation.mjs)、[上下文交接](../cloud/collaboration/inbox.mjs)。

已有工具说明与指引包含不广播、独立判断、避免点头等要求，仍然发生上述现象。因此只加一句“少 @ 全员”不算完整方案。需要可核对的例子、真实收件人展示和结果质量验收。

## 5. 建议的最小产品方案

### 5.1 不增加用户操作，由负责人判断谁需要现在参与

负责人每次组织协作时，能说明“这次希望谁补充什么”。这是工作质量要求，不新增必须填写的表单、固定角色或硬性字段。

| 情况 | 建议行为 |
| --- | --- |
| 用户问现有进展、已有材料足够回答 | 负责人直接答复用户；缺少的事实向实际执行者核实 |
| 一个具体问题需要某位成员 | @ 该成员，说明问题或交付物；其他人仍可在群里阅读与发言 |
| 多个独立方向需要不同判断 | 同时 @ 相关成员，保留独立结论与反例，不要求先同意负责人 |
| 用户明确要求全员，或所有人都受重要变更影响 | 正常 @ 全员，不要求人类再点确认 |
| 整理、感谢、同步已完成的结果 | 普通群消息；用姓名或消息/资料引用说明来源，不顺手把贡献者都叫醒 |
| 结果交给下一位处理 | @ 下一位及确实受影响的人；明确使用哪个结果、版本、处理哪一处 |
| 新约束会影响正在执行的工作 | 立即通知实际受影响成员，包括必要时全员；不能以“同步无需唤醒”为由压住纠正或停止要求 |

重要区别：消息保存在群里、稍后可读，不等于所有 Agent 已经读过。紧急纠正、停工、依赖变更等不能只放群里等待下次碰巧看到。

### 5.2 收尾以用户问题为中心，继续保留独立复核

负责人对照本次需求和补充，说明当前结论、依据、未决项以及下一步。直接引用参与者的相关版本和范围，不把“提出建议”写成“已验证”，不把局部通过写成全量通过。

收到一处纠正时，定点核实并更正受影响结论；如果改变了其他人的工作，通知受影响成员。普通更正无需再组织全员赞同。

不能为追求“一次总结结束”掩盖分歧。仍有会影响结果的未决问题就继续组织必要核查；用户仅要求方案时也不能擅自进入开发。

### 5.3 保留公开协作与主动补充

用户的 @、Agent 之间直接 @、成员主动质疑、会议讨论全部保留。负责人不能审批或垄断其他成员交流。

不采用“每轮最多叫两人”“总共只能讨论几轮”“检测到收到就拦截”“负责人决定后其他人不得再说”等硬规则；不靠 stay_silent 包装完成。普通讨论不要新增系统审批。

### 5.4 让通知结果看得见

消息下方用简洁的收件人提示显示实际通知了谁，必要时点开看；姓名来源引用与真正的通知样式可区分。以保存的 recipientIds 为准，避免正文只写两个人，实际叫了四个人而用户不知道。

Agent 发消息的工具结果也返回最终收件人，便于自检。兼容旧工具时仍按既有明确 @ 语义处理，不用后台模型偷偷重写名单。

这只是透明度改善，不能把人工逐条检查收件人变成使用产品的必要步骤。

## 6. 如何验证没有协作降级

用户批准后，先在隔离测试群对同一组任务、同一平台/模型与工具进行对照，再小范围验证真实协作。无需把现有业务群重新拉出来反复开会。

必须覆盖：
1. 一位成员即可解决的问题，直接获得正确答案。
2. 用户要求全员独立评审，全部正确通知，关键反例保留。
3. 新约束、停止和连续补充在执行中到达，不漏传给受影响的人。
4. 负责人总结中故意放入证据范围错误，成员仍能纠正。
5. A 交付给 B，B 能获取正确资料版本并继续，不因减少通知断链。
6. 只需部分审阅者复核的修改，不将其误写成全员通过。
7. 无新事项的最终汇报，不触发要求人人“确认收到”的新一轮。
8. 负责人暂时离线、换负责人或多人共享原会话时，工作状态和未决要求保留，排队原因真实。
9. 原生平台缓存旧工具目录时，真实 @、资料引用与负责人反馈仍兼容。

先看正确性：需求覆盖、关键风险发现、事实与证据一致、交接完成、必要响应没有丢。再看效率：从需求到可用结果耗时、实际模型调用/可获得的 Token、无新信息的往返、人工纠正次数。

不能用“消息少了”判定成功。成本或模型耗时拿不到就标未测，不用通知人数冒充。若必要参与减少、风险漏检或负责人迟迟不推进，先回退负责人指引的变更；保留可观察数据，不扩大强制限制。

## 8. 待用户审阅的决定

建议先实施：**负责人有目的地邀请参与 + 汇总保留证据范围 + 展示真实收件人**，保留自由交流和必要的全员参与。
