## 同时确认并修复的 Hub 缺陷

替换订阅后，旧订阅的回调 accepted 记录仍阻止新订阅接到尚未领取的工作。新消息还会被 coalesce 到这个旧门铃后面。没有订阅时进入 waiting_subscription 的消息，在首个订阅建立后也仍等旧重试时刻。它们是可以隔离复现的产品缺陷，不是模型语义判断问题，也不能反推为初始平台未启动的唯一根因。

修复以当前订阅的真实回执为准：

- subscribe 成功后，仅把匹配成员/通道/当前配置、尚未领取的 accepted 或 waiting_subscription 通知重新纳入派发。原任务已取消、换版或改派的提醒先按现有规则退休；活动领取和已有租约不动，旧的 stalled 历史工作不自动恢复。
- 已经建立新订阅的旧版本状态也兼容：派发新消息时，只有旧门铃对当前所有有效订阅确实有 accepted 回执，才允许新消息合并等待。旧接收者的回执不能替新接收者作证。健康同订阅仍合并，不重复启动。
- 同一个接收订阅的事件 ID 在重试中保持稳定；不同接收订阅各有可追踪回执。只重排通知，不造 Agent 领取或业务完成。
- 状态扫描按页处理，501 条用例覆盖跨页，没有固定会话数；其他成员、不同连接版本和已领取工作受到保护。
- 审计补充：异常遗留的 ready + claimedAt/lease 记录也不能吸收新消息，统一使用真正未领取的判断。
