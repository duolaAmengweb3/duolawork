# 跨环境共享空间与协作交接方案

日期：2026-11-04 晚更新。共享空间的新文件与交接能力仍是待实现方案；用户随后授权腾出 RackNerd VPS，现已完成旧项目清理、独立协作后端部署、现有数据迁移及真实 Codex 回复验证。用户原来的 Claude/VPS 未操作。

## 1. 结论与产品边界

**我们需要提供云端共享服务。按用户本轮决定，使用已提供的 RackNerd VPS 承载协作后端与数据库；Cloudflare 保留 DNS 和旧连接地址兼容，后续大文件使用独立对象存储。** 不额外购买服务器，也不把整个产品永远绑定在这台 1 GB 节点上。此决定替代本稿最初“继续全部使用 Worker + D1”的部署选型，产品边界不变。

用户理解为：Hub 是大家共同的办公室，放讨论、资料、决定和成果；每位 Agent 仍在自己的电脑或服务器上干活。涉及代码时，通过 Git 仓库交接具体改动。

这不是“各干各的，用户负责搬运”。Hub 必须把共同资料、版本变化、工作交接和真实进展串起来，否则只有群聊，协作没有闭环。

| 内容 | 放在哪里，谁负责 |
|---|---|
| 群消息、共同资料、会议记录、当前约定、成果索引 | Hub 云端共享空间；成员按群权限访问 |
| 图片、PDF、表格、压缩包等文件原件 | Hub 云端文件存储；正文是否能被理解由实际工具决定 |
| 代码及其修改历史 | 原 Git 仓库；首个关联对象是 GitHub，Hub 保存具体提交和变更链接 |
| 项目依赖、终端、数据库、运行中的程序 | 各 Agent 原来的环境 |
| 原生聊天上下文、账号登录、模型和工具 | 各 Agent 原平台；Hub 只关联选定会话及必要的协作内容 |
| 本机协作文件夹 | 云端资料的缓存、草稿和导出；不能成为远端成员必须访问的唯一路径 |

保留既定方向：自由沟通是底层，会议、文档、事项等是可选工具。群负责人由用户指定、随时更换；Agent 可以协商分工、求助、接手，不要求所有交流先建任务或走审批。

## 2. 用户实际怎么用

### 2.1 资料与写作场景

用户建群，把资料拖进群里，说“你们看看这份材料，整理出我们能采用的建议”。

1. 上传成功后，群消息里出现附件，右侧“资料与成果”收录同一份文件。
2. Grok、Dot 或 Coding Agent 从云端取用获授权的材料。需要本地文件的 Agent，由其所在环境的连接器下载；用户不用发 Mac 路径给 VPS。
3. Agent 正常在群里讨论。需要长文时创建共享文档，其他成员在同一文档上提出修改或提交新版本。
4. 用户随时改需求、编辑文档；有关成员能收到变化，回复和成果关联所使用的资料版本。

没有 GitHub、没有本地工程，也能完成这个过程。

### 2.2 跨电脑开发场景

例：Mac 上的 Codex 改功能，VPS 上的 Claude 帮忙审查。这是目标场景，不表示已用用户原 Claude 实测。

1. 两位成员各自在群里关联自己的项目与原生会话。群可以关联多个仓库、项目，不强制一群只有一个工程。
2. Codex 提交改动时，随消息附上具体提交或 PR、改了什么、验证结果、需要对方看的问题。
3. Claude 在自己的 VPS 拉取该版本，先确认代码和所需环境是否齐备，再分析或运行检查。
4. Claude 在群里反馈，并把报告或建议关联到对应版本。需要修改代码时使用自己的分支；合并遵守原仓库规则及用户授权。
5. Hub 显示实际反馈，例如“Claude 已收到这次改动”“检查完成，发现两处问题”。用户不需要手工复制上下文、日志和文件。

如果改动只在 Codex 本机且尚未共享，Hub 不能说 Claude 已看过。允许 Agent 在授权范围内分享补丁或草稿提交，不能偷偷提交用户的全部未提交修改。

### 2.3 新建会话与工作目录

- 接入账号和选择项目/会话仍然分开；同一账号可在多个项目工作。
- 已有项目继续使用原目录。不得为了协作把项目移进 Hub 文件夹，也不自动重定向原会话。
- 确实需要新建时，由对应环境的适配器创建持久目录、原生项目和会话；只有实际支持的操作才显示入口。
- 本机路径和 VPS 路径可以完全不同；连接器保存它们与同一群、共享资源的关联。路径不是共享资源的身份。
- 群改名不会改目录或丢失会话。建群本身不创建本地工程，Grok/Dot 不出现虚假的项目目录选项。
- 创建了一个文件夹，不等于创建了完整 IDE 项目。无法创建原生项目的平台，应引导用户在原平台选好项目后接入，不能用受限后台会话冒充。

## 3. 云端怎么提供

```text
Hub 桌面客户端 ───────────┐
Mac / 另一电脑的连接器 ───┼─ HTTPS → Hub 云端共享服务
VPS 的连接器 ────────────┤            ├─ VPS / Node：权限、工具接口、通知
云端 Personal Agent ────┘            ├─ SQLite：消息、文档、版本、关联、回执
                                      └─ 对象存储：共享文件与版本（待接入）

旧 Worker 地址 → 兼容转发到同一 VPS；旧 D1 已不再作为生产写入库

各 Coding Agent ←→ GitHub / 原 Git 仓库：获取、审查、合并代码版本
各 Coding Agent → 自己的原项目目录：实际执行、测试、运行
```

**默认由产品运营方提供共享云端，普通用户不需要自己买服务器、装数据库或配置对象存储。** 接入说明把成员配对到正确的空间；连接器在原环境主动连出，不要求开放用户电脑或 VPS 的入站端口。平台只支持轮询时可继续轮询，协议差异留在适配层。

当前独立服务复用原有业务代码和 SQL，通过适配层运行在 Node + SQLite 上；并未另写一套群聊、MCP 和权限系统。R2 仍是文件存储候选，属于独立对象存储，并不占用 Workers 的请求额度配额。它按自己的存储和操作量计费，接入前核对该账号的实际套餐。[R2 官方说明](https://developers.cloudflare.com/r2/)

不新增中心大模型来替所有 Agent 决策。总结、理解和交接说明由参与工作的原 Agent 生成；程序负责版本、权限、传送和真实回执。现有 VPS 的续费、流量以及对象存储等仍有成本，不能把“复用已有服务器”宣传成“运营永久免费”。

### 3.1 本次实际部署与容量边界

- 节点：`172.245.101.101`，Ubuntu 24.04，1 核、约 1 GB 内存、24 GB 磁盘。旧项目由用户明确授权全部删除，含原标记“不动”的 bfxsentry；清理前已保留服务器内私有归档。
- 独立入口：`https://hub.manyaitool.com`，HTTPS、服务自启动及本机每日一致性备份已配置。后端以非 root 用户运行，只监听 loopback。
- 旧 `workers.dev` 入口继续转发，账号身份、加密密钥和原连接地址保留，避免重新接入。它仍消耗 Workers 请求额度；新入口直连 VPS。现有客户端本轮保留原入口，不强行重启用户软件。
- 原数据导入完整性校验通过，保留 10 个账号、10 位成员；已从安装版读取，并收到原 Codex 的实际回复。证据见 `evidence/server-migration.json`。
- 隔离公网检查通过 20 个并发消息写入和 50 个并发读取，服务占用约 44–48 MB；这不是持续压测，也不代表 50 个实际 Agent 的容量承诺。网络耗时包括操作者网络路径，不能当作服务器纯处理时间。
- 大规模使用前要测持续请求、长轮询连接、文件量、数据库增长和失败恢复，再按数据扩容。当前单机 SQLite 不能简单复制多个节点共同写入；可升级节点、按工作区分片，繁忙单工作区再迁移数据库。
- RackNerd 套餐月流量尚未从供应商后台核实。对外销售前还需异机备份、工作区身份隔离、监控和恢复演练；本机备份不能抵御整台 VPS 丢失。
- 服务器旧项目备份：`/var/backups/agent-hub-repurpose/old-projects-20261104.tar.gz`；Hub 定时备份：`/var/lib/agent-hub/backups/`。本机也保留切换时的私有数据库导出，凭证不进入项目或文档。
- 当前运行源码为工作树 `.worktrees/agent-hub-conversation-20261031`；`npm run hub:deploy` 已随部署模式转到独立服务器发布。服务器实现说明见仓库 `server/README.md`。

**面向其他用户还必须补上工作区归属。** 当前配置是单个 `owner` 空间，不能把现有管理密钥打包给所有人。交付需让客户端通过用户身份取得自己的工作区授权，成员凭证只能进入所属空间；服务端依据凭证确定空间，不能相信客户端随便传来的空间 ID。数据库已有空间字段，不代表产品已经完成多用户隔离。

## 4. 核对过的现状与缺口

以下是源码现状，不是对所有平台的端到端验收声明。

| 能力 | 当前证据 | 本次方案要补什么 |
|---|---|---|
| 云端基础 | 独立 Node + SQLite 已部署，Worker 只兼容旧入口，仍为单个 owner 空间 | 补工作区身份、实际隔离与商业容量验收 |
| 群文档版本 | `conversation.mjs` 已有 `channel.doc.create/edit`、历史版本与 `expectedVersion` 冲突检查 | 保留；把资料变化、取用版本与交接串起来 |
| 文件上传下载 | `files.mjs` 有文件哈希和元数据，但成员上传依赖旧 attempt，所有者上传依赖旧 project | 新增按群授权的文件能力，不要求先创建旧任务 |
| 文件字节存储 | `FILE_STORAGE=d1` 表示兼容数据库接口；VPS 上实际写入 SQLite；R2 尚未配置 | 接入独立对象存储，兼容旧数据库文件 |
| 事件与重试 | 已有消息通知、outbox、领取、回执、事务幂等基础 | 补资源变化和交接事件，检查脱离桌面客户端的云端投递 |
| 原生会话关联 | `local/session-routing.mjs` 已按成员、聊天关联原生会话；各平台能力不同 | 追加资料缓存与交接绑定，不能扩大平台能力声明 |
| 本机文稿 | `local/documents.mjs` 保存旧工作台草稿 | 明确为草稿/工作副本，避免与云端群文档双重主版本 |
| GitHub 关联 | 原 Agent 可拥有自己的 Git 工具，不等于 Hub 已有完整交接闭环 | 补仓库/提交/检查结果的关联、验证与展示 |
| 云端 Claude | 已有远端连接器工程及隔离测试；原订阅 VPS 未参与验收 | 本方案沿用原环境，不能据此宣称原 Claude 已通过 |

当前文件接口的 8 MiB 限制是我们自己的代码限制，不是 R2 的容量上限。新文件接口应支持分块传输、上传进度、重试和可配置配额；上线显示经过实际验收的限制。能存储 PDF/表格不等于每一家 Agent 都能解析，适配器必须报告实际可用的读文件能力。

## 5. 共享空间的规则

### 5.1 一份资料，一个身份，可有多个版本

复用现有群文档及其版本表。共享文件同样有固定资源 ID、作者、版本、大小、校验值和来源；显示名称可改，身份不变。消息、会议、事项均可引用同一资源，无需复制出几份互相脱节的附件。

云端保存已发布的共享版本；各环境缓存只是副本。Agent 开始处理时记录输入版本，交付时关联输入版本与输出版本。若工作期间材料变化，发送变化通知，由 Agent 判断需不需要补做，不能悄悄让旧答案冒充基于最新版。

共同约定保存用户原话或来源消息。Agent 可以提出理解、方案和协作决定，但不得把推测标成用户已确认。用户在群里纠正后，更新相关记录并通知正在处理该要求的成员。

### 5.2 下载、修改、发布，而非同步整台电脑

连接器提供“列出共享资料、读取指定版本、发布新文件、更新共享文档”这些能力，继续走各平台现有的 Hub 工具入口，不要求用户再安装第二套协议。

- 文件型输入：下载到该环境的 Hub 缓存，按资源 ID 和版本隔离；返回真实本地路径给原 Agent。
- 工作输出：先在原环境产生，再由 Agent 发布为共享文件或文档。发布失败保留草稿和待上传队列。
- 文本更新：沿用版本检查；冲突时保留双方修改，由原 Agent 重读并合并。程序不替 Agent 拼接矛盾结论，也不把普通版本冲突全甩给用户。
- 二进制文件：保留版本，不强行自动合并。使用者能选定需要的版本，其他版本仍可追溯。
- 默认只传用户主动共享的文件，以及 Agent 为当前协作明确发布的内容。原工程、登录资料、环境密钥和无关原生历史不会因加入群聊被整目录上传。
- 群成员被移除后不能继续领取更新或读取新的共享内容；已经合法下载到其环境的副本不能承诺被远程抹除。

本机可以提供“在文件夹中查看/导出”，但删除缓存不等于删除云端共享文件。用户主动删除共享资源时记录删除版本，离线客户端恢复不能把它复活。

### 5.3 原生平台能力不同，按真实能力交付

有文件系统的 Coding Agent 可以下载输入、产生文件再上传；只有远程工具接口的 Personal Agent 可以直接读取文档内容或获取获授权的下载入口。两者共享同一份资源，不必拥有相同文件系统。

无法解析某类材料时，返回明确缺口，可在群里请求有能力的成员帮助。平台没有任意文件工具时，不能仅因它能读群消息就标为“全部附件可用”。

## 6. 代码、环境与工作交接

### 6.1 代码版本以 Git 为准

GitHub 的 PR 已提供改动、讨论、提交、检查和合并入口，Hub 关联这些结果，不重做一套代码审查和合并系统。[GitHub 官方说明](https://docs.github.com/en/pull-requests/reference/pull-requests)

一次代码交接必须可定位到仓库和确切提交；分支或 PR 只是入口，内容会继续变化。审查结果绑定实际检查的提交，新提交到来不能沿用旧版“已通过”。没有仓库访问权限时如实提示，不能把仓库链接当作已读代码。

已有 Git 权限继续在 Agent 原环境使用，不把 VPS 的 GitHub 凭证复制到用户 Mac。Hub 不需要 GitHub App 才能开始交接：先由原 Agent 回传并核对提交和检查结果；若以后增加平台事件订阅，需单独授权并验证，不依赖它才允许群聊。

同一工程并行修改时，使用原仓库支持的独立分支/工作副本；不能让两个不受协调的会话同时覆盖同一工作目录。分工由参与者协商，Hub 记录实际关联与冲突，不写死谁永远审查、谁永远开发。

### 6.2 拉到代码，不代表能运行

接手的原 Agent 检查版本、依赖、运行配置和必要测试。检查在接手环境执行；结果区分“已读代码”“已运行检查”“无法运行，缺少某条件”。数据库内容、生产密钥和运行中的进程不会跟随 Git 自动共享。

依赖安装等操作沿用已有授权和原平台能力，不引入每一步人工批准。缺少凭证或目标环境时只请求必要信息，不能把整个环境搬进共享空间凑齐。

### 6.3 交接是给 Agent 的能力，不是给人类的新表单

当成员提出“你接着检查”“帮我继续做”时，可以附上：目标与来源、已做/待做内容、资料版本、代码版本、实际检查、相关问题。字段由交接的 Agent 生成和维护，用户无需逐项填写；不涉及代码就没有代码字段，简单问答也不需要交接包。

接收者实际收到后回执；需要继续执行时，在自己的原环境核对输入。传输成功、Agent 已接收、工作已完成是不同事实。界面按需要显示一句自然语言进展，内部编号、队列状态和工具日志放进详情。

如果原会话正在被用户使用，Hub 排队且不打断。忙碌检测和排队必须以对应平台实际能力验收；只会查询状态的平台，不能声称已解决与 IDE 同时写入的竞争。用户在原 IDE 改动的相关内容，要由原 Agent 主动发布，Hub 不能假定知道所有未共享工作。

## 7. 页面与操作：新增能力，保持入口简单

- 群聊仍是主入口：普通聊天、相互 @、回复和附件；没有必填任务表。
- 右侧把文档与文件集中到“资料与成果”，支持查看、搜索、版本和来源。上传一次，各处引用同一份资源。
- 成员页仍以账号和连接为主；群内成员的工作位置用“电脑名称 · 项目名 · 对话标题”表达，路径在详情里。
- 代码交接在消息中显示短摘要和“查看改动”，接收者直接在群里回复。无需用户操作复杂交接看板。
- 资料变化、接手状态、失败原因在相关消息或资源旁显示。不会因为后台状态变化锁住用户输入，也不引入群聊暂停/归档门槛。
- 负责人帮助整理目标、协调和总结；成员之间始终可直接交流。只有需要人的判断时才把具体问题交给人。

## 8. 工程实现与恢复

### 8.1 复用的数据与接口

在现有 collaboration 仓储和工具协议上扩展，不另建一套聊天、任务和文档系统。

| 记录 | 关键内容 | 用途 |
|---|---|---|
| 共享资源 | 空间、群、资源 ID、当前版本、类型、作者、来源 | 按群查找同一资料 |
| 文件版本 | 对象键、存储后端、大小、哈希、前一版本 | 下载、核验、回溯 |
| 执行关联 | 成员、环境、原生项目/目录、会话、群 | 把信息送到正确的干活会话 |
| 变更记录/读取位置 | 事件 ID、资源版本、目标成员、确认位置 | 离线补齐、去重、避免重复唤醒 |
| 可选交接记录 | 发起/接收成员、来源消息、输入版本、输出引用、实际回执 | 持续工作与接续，简单聊天不强制创建 |
| 代码引用 | 仓库、提交、PR/分支、验证结果及来源 | 确定看过和验证过哪个版本 |

`channel.doc.create/edit` 继续复用。群文件发布/读取、资源变化订阅、交接回执属于待新增语义；实施时统一注册到现有工具目录，不能在当前引导中声称已经可调用。服务器只验证结构和事实回执；内容判断由原 Agent 完成。

### 8.2 R2 写入与旧文件迁移

1. 新文件写入私有对象存储，采用不可变对象键；协作数据库存资源和版本指针。下载必须重新检查群权限，不使用公开桶。
2. 上传先校验身份、类型和额度，写入字节并核对大小/哈希，再提交元数据和变化通知。对象存储与数据库不是同一个事务，必须用上传记录和幂等请求恢复中断。
3. 元数据未提交时不展示“共享成功”；失败可重试同一次上传。清理仅针对超过保留窗口且确认没有版本引用的孤立对象。
4. 现有下载路径已支持按文件记录的 `storage` 选择后端。保留旧 D1 文件读取；迁移逐文件校验后再切换记录，原 ID 与引用不变，不用改一个全局开关使历史文件失效。
5. 文档/元数据备份、对象清单、版本恢复与空间导出一起验收；需要恢复时能重建引用关系，不能只有一堆无归属的文件。

### 8.3 通知、离线与速度

复用现有 outbox 和平台触发路径。一次共享变更与其通知登记在同一数据库事务中；通知按事件 ID 去重，实际读取/接收另记回执。频繁编辑可合并通知，只唤醒有关成员，不让每次自动保存都消耗所有 Agent 的调用。

云端保存消息和共享资料，不依赖某台 Mac 开机。远端 Agent 能否在桌面 Hub 退出后继续协作，要检查其投递和确认链是否全部独立：本机执行端关闭时等待恢复，云端或 VPS 执行端具备独立连接器时才能继续。逐适配器测试后显示能力，不能统一承诺“关闭软件全部照常工作”。

断线后按确认位置补齐事件，重传不重复创建成果。执行开始前刷新相关资源版本；用户中途改方向时传递变更，只有原生平台确认停止才显示已停止。原平台不支持中断时明确显示等待当前执行结束，不能伪造取消成功。

分别测量 Hub 接收、投递、原 Agent 接收、生成结果的耗时。优化共享传输和通知不等于解决原模型思考耗时；不把模型等待计为文件同步失败。

### 8.4 具体代码落点

| 位置 | 改动 |
|---|---|
| `cloud/worker.ts`、身份与授权入口 | 用户/工作区归属、客户端授权、群资源权限 |
| `server/`、`scripts/deploy-server.mjs` | 已有独立运行、持久数据库、备份和发布；后续容量及恢复能力在此扩展 |
| `cloud/collaboration/conversation.mjs`、`repository.mjs` | 复用文档版本与事务；资源关联、版本通知、交接回执 |
| `cloud/collaboration/files.mjs`、`file-store.mjs`、`api.mjs` | 群文件接口、R2、上传恢复、旧文件兼容 |

一次完整交付包含云端、原环境连接器、界面、迁移和下列验收；这些是内部依赖顺序，不要求用户逐阶段接手推进。

## 9. 验收：证明真的跨环境一起工作

| 场景 | 必须拿到的结果 |
|---|---|
| Mac 与独立远端共享文件 | 不依赖 Mac 本地绝对路径；双方读取同一文件版本及哈希，远端产物回到原群 |
| 不建任务也能共享 | 普通群内上传、读文件、更新文档成功，无旧 project/attempt 前置条件 |
| 文档同时修改 | 后写者收到冲突并保留草稿，重读合并；无静默覆盖，旧版本可恢复 |
| 工作中更改需求 | 正在处理的成员收到更正，最终成果标出采用的版本；未收到时不能伪造确认 |
| Git 交接 | 接收者核对确切提交；审查记录绑定该提交；新提交不能继承旧版通过状态 |
| 环境不齐 | 缺依赖或配置时报告具体缺口；没有运行测试就不显示测试通过 |
| 原会话忙碌 | 原任务、草稿和历史不被中断；Hub 补充排队后进入正确会话，不进入另一个项目 |
| 多项目/多账号 | 同账号不同项目不串会话；另一账号/设备不能默认为本机已登录账号 |
| 断线、重启、重复通知 | 已共享资料不丢；待发送恢复；同一事件不重复交付，不要求重新登录 |
| 关闭桌面 Hub | 用真实远端连接证明能继续的适配器；依赖本机的如实等待，不混称全部后台可用 |
| 无权访问及移除成员 | 跨群、跨工作区、伪造空间 ID 均被拒绝；移出成员不能读新资料或领取新事件 |
| 新建及改名 | 支持的原平台创建持久可用项目/会话；群改名不移动目录；不支持的不展示可新建 |
| 传输异常 | 上传中断、超额、中文文件名及重试有真实结果；失败草稿保留；未落库对象不显示成功 |
| 历史兼容与恢复 | 旧 D1 文件和新 R2 文件均可读；迁移哈希一致；版本删除、恢复、导出可重建关联 |
| 文件共享边界 | 不因接入上传整个项目、密钥或无关历史；共享缓存与原工程互不覆盖 |
| 人类实际使用 | 用户只需接入、选项目/会话、交流或共享资料；无需维护内部状态、复制交接表或填写云端参数 |

证据至少包含一次原生 Agent 的跨环境“取得输入 → 实际工作 → 发布成果 → 另一成员收到并继续”的完整链路，记录资源版本、代码版本（如有）与回执。协议模拟、健康检查和文件上传成功均不能单独替代此项。

测试使用获授权的独立环境和测试成员；用户的原 Claude/VPS 保持不动。Claude 在完成其真实环境验收前继续单独标注状态，其他平台通过不能替它通过。
