# 消息异常处理：正常协作继续，异常由负责人收尾

所有者确认日期：2026-11-06。此文替代旧的“最多 8 跳后交给用户恢复”规则。

## 用户体验

用户正常发消息，不需要理解投递日志、跳数或恢复流程。成员忙碌时消息排队，连接恢复后尚未开始的消息自动继续。对同一条原消息的多个接收者合并展示，不把一件事情拆成四项待办。

“消息进度”分为：

- **需要你处理**：只有明确的本人操作或决策。显示哪件事、影响、具体下一步和入口。缺工作对话提供“选择工作对话”，断连提供连接入口。
- **自动处理中**：正常排队、恢复投递、已交给负责人核对；明确无需重复发送。
- **已处理记录**：默认折叠，保留实际回复、收尾理由与依据。

相关需求直接显示摘要，可回到原消息。诊断信息放在“处理详情”，不再让用户面对一排“连续回应已暂停”自行排查。沟通入口引用真实原消息、指向当前负责人，并保留用户未发送草稿。

## 暂缓通知的边界

正常长讨论不按固定跳数停止。后台对同一因果分支内、五分钟中的以下情况暂缓后续自动通知：

1. 同一作者、接收者和引用的相同请求第三次重复出现。
2. 同一分支已有 60 条自动消息，触发容量保护。

第二项只统计消息量，不能证明发生循环；正常且有新证据的密集协作也可能触发。界面必须明确显示“流量保护暂缓通知”及范围，不把它当作已判定空转。当前阈值仍保留；合并通知、限速自动恢复和有效新证据保留策略尚未在本轮实现。第一项只匹配正文、接收者及引用的相同请求，改写/标点变化仍可能绕过，不能称为语义循环识别。用户的新要求和其他分支不受当前暂缓影响。

## 负责人如何收尾

后台将同一原消息（重复循环按分支）归为一件异常，仅发送一次独立核对通知。通知不与普通消息合并，以免核对丢失或吞掉用户补充。负责人通过 `resolve_delivery` 获取原需求、原通知及各成员实际回执，选择：

- `retry`：仅继续未开始的原通知，复用原消息和回执，不另造任务。
- `covered`：引用每位相关成员的真实回复，说明后续结果已覆盖旧通知。只收尾旧通知，不把它标成成功执行。
- `dismiss`：说明为什么无需再通知，例如重复致谢。
- `needs_user`：明确需要用户决定或完成的具体事项。

负责人可以分成员处理。同意、沉默、出现新消息都不能自动证明旧任务完成。引用接口检查同群、作者以及每条通知的时间：依据消息时间必须不早于通知创建时间；内容相关性与原要求是否全部覆盖仍由负责人实际核对，系统不冒充已经理解业务结果。部分完成不能关闭整条要求，不能把时间校验宣称为业务验收。

已开始但结果不明的执行不能直接重放。负责人自身无法接收时，不再重复付费唤醒它诊断自己。负责人只回复“收到”却未处置异常，也不算完成：留在自动处理区，明确显示“负责人核对未完成”、负责人及最近核对时间，不转成人类待办、不无限重试。旧版自动升级为“询问负责人”的记录按此恢复；负责人显式提出的本人决策仍保留。负责人更换后，未完成核对交给当前负责人。

历史记录区分“旧通知已被后续回复覆盖”与“不再通知”，展示原需求、处理人、时间和实际依据消息入口。用户可从“对结果有疑问”引用原需求与负责人沟通，保留未发送草稿；这不是自动重开或重放旧执行。逐项要求与交付版本的结构化映射仍未实现。

## 升级与数据

旧的 `limited`、`stalled`、`unavailable` 记录保留并建立异常关联；升级不会批量重做旧工作。连接恢复只继续未开始且仍适用的通知；过期会议通知不得重启旧会议。相同异常的发现与核对幂等，无状态变化不持续写入维护回执。

所有平台使用同一群消息处理链。平台原生权限、登录、项目、会话和凭证不改变。旧 MCP 目录支持通过现有 `post_message` 工具封装调用新工具，不要求重登录。
