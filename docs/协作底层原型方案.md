# 协作底层原型方案：Agent 自己协作，Hub 提供工具和展示

- **作者：** Claude｜**执行：** Codex｜**日期：** 2026-10-30
- **所有者原话：**
  - "我要的是协作，不是一个固定的程序。"
  - "你这个案例非常适合作为我们的协作底层原型，我们先要实现这个效果，然后做到一些协作工具给 agent 调用，并且配合软件功能的展示。"
- **地位：** 这是新的执行依据。`docs/v1产品方案（定稿）.md` 中由程序编排协作的部分**全部搁置**，包括：安排卡和三种做法、步骤图、论断去向、自查和内部修订、本轮记录、确认按钮式的"聊天/任务判断"。接入、成员、成果展示、知识库等基础设施继续保留。

## 1. 要实现的效果（以 Agents Slack Bridge 的实测为准）

参照对象：[Agents Slack Bridge](https://github.com/Ares-X/Agents-Slack-Bridge)（该仓库**没有许可证**，只借鉴思路，不复制代码）。它在 2026-10-04 的实测中，让 Muse、Grok Bot、Hermes、Dots 四个 Agent 待在同一个 Slack 频道：用户只发一条开放任务，**用户和程序都不规定谁先说、谁做什么**，它们自己提方案、选执笔人、指出彼此的遗漏、修订，6 分 07 秒后交出一份共同的最终版本，之后没有陷入互相回复的死循环。

**我们第一阶段的目标，就是在 Agent Hub 里复现这个效果：** 用户的 Grok 和 Dot（之后加 Muse）作为群成员，像真人同事一样在群里协作。

## 2. 用户看到什么

- **项目就是一个群。** 群里有用户和几位 Agent。
- **用户怎么说话都行。**
  - 说"有人在线吗"，Agent 会像同事一样回应（谁回、回几句，由 Agent 自己判断）。
  - 说"帮我研究一下智能戒指的机会"，Agent 们自己商量怎么分工、谁来汇总、要不要问用户问题。
- **Agent 之间可以 @ 对方。** 被 @ 的 Agent 会被叫醒，回应提问、接手工作或提出异议。
- **用户可以随时插话、纠正、追问。** Agent 读到之后会自己调整。
- **成果和决定由界面展示：** Agent 一起写的文档出现在侧栏；Agent 请用户拍板的事以卡片显示；Agent 记下的团队经验进入知识库。

## 3. 分工：Agent 做什么，Hub 做什么

| Agent 自己决定（Hub 不干预） | Hub 负责（基础设施） |
|---|---|
| 回不回某条消息、怎么回 | 把群里的新消息**送达**每位成员，并按平台能力叫醒它们 |
| 要不要 @ 别人、请谁帮忙 | 被 @ 的成员**一定会被叫醒** |
| 怎么分工、谁执笔、谁复查 | 每位成员回复前都能读到**完整的群聊记录**（可分页） |
| 什么时候算完成 | 提供**协作工具**（第 4 节），Agent 自己决定用不用、什么时候用 |
| 要不要问用户、请用户拍板 | 把工具产生的东西**展示**在界面上（文档、决定卡、知识） |
| 对别人的结论提出异议 | **防止死循环**（第 5 节）；记录谁说了什么、谁改了什么 |

**原则：** Hub 不判断"这句话是聊天还是任务"，不规定协作流程，不替 Agent 选执笔人。

## 4. 协作工具（通过 MCP / REST 提供给 Agent）

第一批工具，每一项都写明了界面上怎么显示：

| 工具 | Agent 用它做什么 | 界面上怎么显示 |
|---|---|---|
| `read_channel` | 读群聊记录（分页，从最新往前） | — |
| `post_message` | 在群里发言；可以 `@成员`；可以回复某条消息 | 群聊气泡；被 @ 的成员名高亮 |
| `stay_silent` | 读过但决定不回复，**写一句原因**（例如"已有人回答，无需补充"） | 默认不显示；在"查看过程"里可以看到 |
| `create_doc` / `read_doc` / `edit_doc` | 创建共享文档；读取；修改某一段（写明修改原因） | 右侧"文档"标签实时显示；每段标出最后修改者；可查看修改历史 |
| `suggest_edit` | 对别人写的段落提修改建议，但不直接改 | 段落旁出现建议，作者或用户可以采纳 |
| `ask_user` | 向用户提一个需要决定的问题，附选项和各自的依据 | 群聊里出现一张决定卡；用户点选后，结果作为一条消息回到群里，所有成员都能读到 |
| `deliver` | 把某份文档标记为"交给用户的成果" | 群里出现一张成果卡；文档进入"成果"页 |
| `remember` | 提议把一条经验记进团队知识（例如"用户不喜欢新闻腔"） | 出现一张小便签，用户点「记住」或「不用」；确认后进入知识库，之后每位成员读群聊时都会带上 |

**写在每位成员接入说明里的协作习惯**（参考 Slack Bridge 的做法，只是建议，不是程序规则）：
- 回复前先读最近的群聊；
- 一条消息最多回一次实质内容；没有新内容就用 `stay_silent`；
- 需要别人行动时才 @ 别人；
- 不同意就直说，并给出依据；同意时不必重复别人的话。

## 5. 防止死循环和浪费（这是 Hub 唯一的"硬规则"）

- **谁会被叫醒（2026-11-02 参考 DeepSeek dsh-superagent 后细化，见第 9 节）：**
  - 用户发言**没有 @ 任何人**：如果用户设了「**负责人**」（只能由用户指定，程序不猜），先叫醒负责人，由它读完群聊后自己判断：回一句、自己动手做，还是 @ 别人；**没设负责人时叫醒全员**，每位自己判断要不要回。负责人不是关卡，见第 9 节 U2。
  - 用户或 Agent **@ 了某位成员** → 叫醒被 @ 的成员。
  - 用户**回复某位成员的某条消息** → 叫醒那位成员，不需要再 @。
  - Agent 普通的发言（没有 @ 任何人）**不叫醒任何人**。
- **同一条用户消息引发的 Agent 互相 @，最多 8 跳**（参考 botline 的跳数上限）。超过后群里提示「讨论已经很长了，需要你看一下吗？」，并停止自动叫醒。
- 同一位成员在 1 分钟内最多被叫醒一次；正在运行时收到的新消息合并处理，不重复叫醒。
- 这三个数字放在项目设置里，可以调整。

## 6. 第一阶段验收：在 Hub 里复现案例

**环境：** 用所有者真实的 Grok 和 Dot（**尽量接所有者原本在用的 Bot，带着它们自己的记忆和工具**；如果只能接新建的自动化账号，必须明确写出来）。

**参照 Slack Bridge 的分层验收，逐层通过：**

| 层 | 测试 | 通过标准 |
|---|---|---|
| 1 送达 | 用户发一条消息 | 两位成员都收到；有送达和叫醒记录 |
| 2 真实 Agent | 用户问"有人在线吗" | 至少一位 Agent 用自然语言回复；**没有创建任何"任务"** |
| 3 双向 | Grok @Dot 提一个问题；Dot @Grok 提一个问题 | 双方都被叫醒，并在群里回答 |
| 4 自然协作 | 用户只发一条开放任务，例如"一起设计一个 3 分钟的纯文字破冰游戏，自己分工、互相挑错，选一位执笔交出最终版" | 用户中途**不插话**；Agent 自己分工、至少出现一次互相指出问题并修订、由一位用 `create_doc`/`edit_doc` 写出最终版并 `deliver`；结束后不再互相回复 |
| 5 工具 | 在任务中让 Agent 遇到需要用户决定的问题 | 出现 `ask_user` 决定卡；用户选择后，Agent 读到并继续 |

每一层都要有真实记录：消息、叫醒日志、截图或录屏。**模拟成员的测试不能代替真实成员。**

## 7. 从现有代码复用什么、搁置什么

- **复用：** Grok、Dot 的真实接入和叫醒（PR #19 已真实跑通）、成员页、文件和文档版本、知识库、成果页、本机构建和登录资料保护。
- **改造：** 叫醒的触发方式，从"派发任务步骤"改为"群里有新消息或被 @"；成员领取的东西，从"一个步骤"改为"群聊的新消息和上下文"。
- **搁置（不删除代码，不再推进）：** 安排卡、三种做法、步骤图、论断去向、自查和内部修订、本轮记录、"聊天还是任务"的程序判断和确认按钮。
- 原来的"决策卡""页边规则便签""成果审阅"界面，改为由 `ask_user`、`remember`、`deliver` 这些工具触发。

## 8. 不要做成

- ✗ 程序判断"这是任务"然后自动派发
- ✗ 规定发言顺序或固定流程
- ✗ 程序替 Agent 选执笔人
- ✗ 每条 Agent 发言都叫醒所有成员
- ✗ 用模拟成员冒充真实协作
- ✗ 把新建的自动化账号说成"用户自己的 Bot"

## 9. 本轮细化提案：以自由沟通为底层，工具辅助 Agent 协作

**补充作者：Codex｜2026-10-31｜状态：方案评审稿，没有修改运行版。**

本节以 Claude 的 `78e21d2` 和 [Issue #20](https://github.com/duolaAmengweb3/agent-hub/issues/20) 为主线，不另立一套产品方向。第1—8节原文保留。下文明确区分所有者已定原则、研究事实和实现建议；细化建议不冒充所有者已经确认。

### 9.1 所有者已明确的原则

| 编号 | 已明确的意思 | 实现时不能换成什么 |
|---|---|---|
| U1 | 正常对话框用于沟通 | 每句话都启动一轮正式任务、生成待审阅成果 |
| U2 | 有负责人，由用户指定 | 程序自动指定，或规定所有对话、交接都必须经过负责人 |
| U3 | 产品提供工具，不规定固定用法 | 必选协作模式、发言顺序、执笔人、汇总流程 |
| U4 | Agent之间的沟通与自主协作是核心 | 多个单人聊天拼在一起，或程序只转交文档却宣称多轮交流 |
| U5 | 不能偷偷换产品逻辑 | 遇到接入限制后，改用新助手或便宜模型，却仍称完整接入原Agent |

所有者提出的进一步方向是：借鉴Slack的自由沟通底层，在其上提供会议、任务看板等协作工具。本稿按这个方向细化；不把Slack的所有功能、收费方案或交互细节一并当成已确认需求。

**产品表述建议：给用户已有的个人Agent一个可以相互沟通、共同做事的工作空间，再提供帮助它们协作的工具。** Hub不充当替所有Agent思考的总控模型。

### 9.2 为什么先借鉴Slack的对象关系

以下是查到的产品事实；后面的取舍是本稿的设计建议。

- Slack用频道承载围绕团队、主题和项目的对话，用线程组织某条消息下的讨论，提及用于引起指定成员注意。[Slack基础概念](https://slack.com/help/articles/56387669632147-Getting-started-for-Frontline-Members)、[频道、私聊、线程与提及](https://slack.com/help/articles/360000411963-Use-Slack-with-a-screen-reader)。借鉴的是通信关系，不是指定谁研究、谁审核。
- Canvas把较长的共享内容放在会话旁，也可以作为频道或私聊标签打开。[Slack Canvas](https://slack.com/help/articles/203950418-Use-a-canvas-in-Slack)。对应Hub的共享文档，不要求每条回答都变成文档。
- Lists支持把消息加入清单、分配事项、在线程中讨论，并切换表格或看板视图。[Slack Lists](https://slack.com/help/articles/27452748828179-Use-lists-in-Slack)。对应可选任务工具，不是聊天开始前的流程配置。
- Huddles把集中讨论、关联线程和会议笔记放在一起。[Slack Huddles](https://slack.com/help/articles/4402059015315-Use-huddles-in-Slack)。Hub可借鉴“围绕一个议题集中协作”，不需要先把Agent做成语音会议参会者。
- 飞书同样将成员管理与具体事务分开，支持从会话消息创建任务。[飞书群成员管理](https://www.feishu.cn/hc/zh-CN/articles/360049068007-话题群群主指南)、[飞书创建任务](https://www.feishu.cn/hc/zh-CN/articles/360741352378-创建任务)。它们提供工具入口，没有要求所有聊天先填好工作安排。

**不原样照搬人类软件的地方：** Agent需要能够通过工具读消息、发消息、提及同伴、共享与修改文档；界面上的“能点”必须对应Agent也能调用的真实能力。给人看的群聊页面，不自动等于Agent之间已经能交流。

### 9.3 两层结构，不是两条强制流程

| 层 | 提供的能力 | 谁决定怎么用 |
|---|---|---|
| 通信底层 | 群聊、私聊、线程、提及、历史、通知、成员管理、身份与回执 | 用户和Agent通过沟通决定如何协作 |
| 协作工具 | 共享文档、会议、任务看板、请用户决定、成果交付、经验记录 | 用户可以操作，Agent可以主动调用，也可以不用 |

负责人是用户授予某位Agent的协调职责，不是唯一发言入口，不是其他成员行动前必须经过的审批关卡。其他成员仍能主动提问、互相@、提出异议、直接找用户、更新获授权的共享材料。用户可直接指定某位做事，也可让它们自行商量。

**这里分开记录“群成员”和“某件事的参与者”，只为避免数据混用，不要求用户逐项配置。** 某件事只有一位执行，不会把其他Agent移出群；负责人变更，也不会自动重写所有历史分工。

### 9.4 界面建议：先把“一个正常的群”做好

本小节是Codex的界面建议，不是新一套已确认原型。继续使用现成浅色组件，先核对操作，再做精细视觉。

```text
会话列表             项目群名称       负责人：用户指定       成员 · 工具
群聊 / 私聊          -------------------------------------------------
                     用户和Agent的真实消息、提及、线程回复
                     文档 / 会议 / 看板只在被使用时出现关联入口
                     -------------------------------------------------
                     输入消息……              @成员   附件   工具   发送
```

- **建群：** 选择成员，群名可后改；不要求先填写目标、项目类型、工作安排、验收标准、日程。负责人由用户设置，未指定时如实显示，不由程序猜，也不因此禁止普通沟通。
- **成员：** 顶部人数或右侧“成员”能直接打开名单，提供“添加成员”“移出本群”“设为负责人”。移出本群不删除账号、不退出平台、不清空登录资料；从软件断开账号是另一项操作。
- **移出后的行为：** 停止该成员的本群新通知和后续工具访问，保留历史。远端正在执行的内容未必能立即停止；迟到回执留在过程记录中，不能因此自动把成员加回。已经交给原平台的信息也不伪称能够收回。
- **私聊：** 在Agent名片点“发消息”就能建立持续对话，不先建立正式项目任务。群内回复可开线程，用户可随时返回主群。
- **普通消息：** 回答直接显示在气泡里。没有文档操作时不出现成果卡；没有请用户决定时不出现待审阅要求。技术投递记录放“查看过程”。
- **工具入口：** 共享文档、会议、看板可以从群顶部或输入框打开；工具使用后的内容可固定为群标签。未使用的工具不占满主界面。
- **去掉旧干预：** 不再展示“三轮没有额外贡献，改为一位完成”；不要求用户从“各自研究/一位检查”等模式中选一种才能说话。

### 9.5 Agent到Agent的消息，是底层必须交付的能力

沿用第3—5节的原则：用户新消息可唤醒群内成员，Agent是否回应由它自己判断；Agent主动提及另一位时，系统为对应成员建立可靠的待处理通知。普通Agent发言不会无差别唤醒全部同伴，但其他成员下次读取群聊时能读到它。

这里“送达”“唤醒”都必须记录实际状态。应当发出通知，不等于外部平台保证立即执行；平台未接受、正在忙或被限流时，显示对应情况，不冒充已经回应。

需要具备的工具行为：

| 能力 | 可预期的行为 | 不替Agent规定的事情 |
|---|---|---|
| 读取群聊 | 按游标读取本群主消息和线程，可查旧消息、引用原文；超长内容可以继续分页 | 不把旧项目要求强行当作每条新消息的任务标准 |
| 群内发言/回复 | 记录真实发送者、原消息、线程、时间；用户和Agent都能直接看到正文 | 不要求回答拆成claims、自查表或正式报告 |
| 提及同伴 | 保存真正的目标成员ID，通知其读取上下文，并让回复回到原线程 | 不规定只能负责人@别人，也不代写对方的回复 |
| 保持安静 | Agent明确选择暂不回复时，记为已处理；不生成“同意”“收到”等占位气泡 | 不要求所有成员对每条消息表态 |
| 读取成员 | 返回本群真实成员、负责人和接入信息；连接信息不假冒实时在线状态 | 不再把全软件的成员名单塞给所有项目 |

发送者由该Agent已经认证的连接绑定，不能传一个名字就冒充另一个成员。文字里提到Grok、引用Dot的观点，不会自动生成它们的发言气泡或响应回执。新增成员也不会自动把全软件的私人资料共享到群里。

消息之间保留原始关联：谁问了谁、哪条消息引起提及、对方是否收到、回复了什么。用户能看到Agent实际互相交流，而不只是看到几张“各自完成”的卡片。

**例子只展示一种可能，不是默认剧本：** Grok找到一条产品讨论后，主动@Dot核对文档；Dot指出限制并反问适用场景；Grok补充依据；任一位可整理共享文档。这条协作也可以由Dot发起，或者双方判断不需要分工。程序不得规定角色、故意安排错误或强迫出现分歧。

### 9.6 在底层之上增加的工具建议

第4节已有共享文档、决定卡、交付与知识工具。本轮重点增加下面两类工具，补足所有者提出的协作空间；**两类都可由用户或Agent发起，不是所有事情必经的环节。**

**集中讨论 / 会议**

- 可以从一句话或现有线程发起，围绕一个议题聚合讨论。议题和参与者可调整，不要求用户先填完整议程。
- 参与者能相互追问、补充、引用消息、查看共同资料；负责人不自动成为每次会议的唯一主持或执笔人。
- 头脑风暴、评审、复盘等可作为可选提示或模板，用户/Agent可修改，不作为程序固定发言顺序或投票规则。
- 保留讨论原文、分歧和待办；需要时由Agent用文档或任务工具整理，不能用“多数同意”自动证明事实正确。
- 会议发起、加入、读取、结束及关联记录要有对应工具，不能只给用户一个会议页面。实现用文字线程即可，不把语音/视频接入当成这项能力的前提。

**任务清单 / 看板**

- 把需要持续跟踪的事项存下来。可以从消息创建，也可由Agent主动创建；用户不必先填完分工表才得到帮助。
- 支持负责人/参与者、状态、说明、关联消息/文档和截止时间；非必要字段可留空。提供可修改的常用状态，不强迫每项工作走同一套流程。
- 用户拖动或修改事项，Agent通过工具创建、查询、更新事项，两边读写同一份数据。
- 一个任务可以请多位协助，成员可以商量调整；记录变更者和原因，不自动把任务参与者当作群成员名单。
- 任务进行中仍可正常沟通；新问题不被“等整轮结束”的全局锁挡住。外部平台同一执行器正忙时，真实排队并告知，不伪装已插话成功。

会议和看板之间可以互相引用，文档和决定也可关联它们，但不强制“先会议、再任务、再文档、最后审核”。

**可配置的协作方法**可以在以后沉淀为工具预设、Skill或模板；不得把某一套管理学方法重新写成所有群都必须服从的底层程序。

### 9.8 唤醒、防循环与原Agent身份：必须如实说明

**原生响应是异步的。** Grok文档明确：202表示受理，后台才异步执行。[Grok Webhook Triggers](https://docs.x.ai/grok/automations/webhooks)。OpenAI文档也把回调确认与后续异步处理分开，要求处理乱序、重复和订阅刷新；改工具后需要重新扫描清单。[OpenAI MCP Events](https://developers.openai.com/plugins/build/mcp-events)。因此可以做会话交互，不能把“UI像聊天”包装成外部Agent必然秒回、任意可中断。

**第5节的8跳/1分钟是Claude提出的可调整防循环参数，不是用户指定的协作方法。** 细化建议：记录触发链和消息游标；去重、合并密集通知，达到限额保留未处理消息并提示可继续，不删除消息，不把“受限暂停”说成“达成共识”。节流不能让对方的回复永久丢失。需要在Issue #20复核这些参数的实际效果，不能为了过验收悄悄缩短讨论。

**现有接入与目标身份仍有差距。** 目前验证的是专用Grok账号自动化和ChatGPT Work事件会话，旧Bot/Dot的专属记忆与工具完整继承没有证实。Slack Bridge的说明依赖实际的Agent唤醒接收器或账号支持的事件能力，并非一个通用模型API就能替代。[桥接项目说明](https://github.com/Ares-X/Agents-Slack-Bridge)。此仓库未声明许可证，本项目只借鉴接口思路，不复制代码。

实现前要逐个确认：用户指定的是哪个原Agent、事件是否确实送入该Agent、它已有工具是否实际可用。拿不到证据就标“账号自动化/接入会话”，不能把接入名改成Grok或Dot后宣布完整继承。若平台限制导致接不回指定原Agent，应带具体证据回Issue #20讨论，不静默换新会话、换模型或重新让用户登录。

### 9.9 验收按用户能看懂的场景补齐

第6节五层真实验收继续有效。下表补充用户指出的产品缺口和上层工具。**表中均为待验项，原版104项工程测试及六条任务联测不算这些新交互已经通过。**

| 场景 | 必须看到 | 不能冒充通过的做法 |
|---|---|---|
| 普通问答 | “在吗”在群里直接得到真实Agent正文，无任务、成果、验收表 | 把回答藏在待审阅文档里 |
| 成员管理 | 群中可添加/移出成员、用户设负责人；刷新后相同；移出不退出账号 | 通过改执行模式来缩减群名单 |
| 非负责人发言 | 用户直接@另一位，该成员实际收到并回复 | 强制经过负责人代理回答 |
| 双向Agent沟通 | A主动@B，B用自己的连接回复并可追问，A继续处理；消息关联可核对 | 一个模型把双方台词都写出来，或人工逐条转发 |
| 自主协作 | 一条开放需求后，Agent自己交流和调整，完成有实际意义的共同产物；用户不代搬消息 | 预先分配研究/审核/执笔角色，或强迫制造争论 |
| 保持安静/结束 | 无需补充可不发言；交付后观察有无自动循环，保留观察时长和实际唤醒数 | 预定轮数结束后自动宣布已达共识 |
| 中途沟通 | 做事时用户可补充，其他空闲Agent可回复；同一忙碌执行器的等待状态真实可见 | 所有消息等整轮完成后再开始处理 |
| 共享文档 | 两位Agent实际读写同一文档，能核对修改者、版本与建议；人工编辑不被覆盖 | 只传一段“已修改”的说明，没有版本变化 |
| 会议工具 | 围绕同一议题保留多轮真实交流，允许临时改变安排，笔记和原文有关联 | 预置一段圆桌台词或强制每人一票 |
| 看板工具 | Agent创建/更新事项，界面同步；用户调整后Agent能读取；变更留来源 | 静态看板或每句聊天都自动建卡 |
| 用户决定 | 真实问题由Agent发起，用户选择变成群消息，对应Agent读到后能继续 | 只有卡片动画，Agent不知道用户选了什么 |
| 名单与身份 | 群名单、Agent读取名单、提及对象一致；未接入成员清楚显示 | 全软件名单混进本群，提到名字就当成已参与 |
| 重复/乱序与限流 | 不重复发言或建卡，未处理内容仍可读，恢复后沿原线程继续 | 清空队列、丢消息或重登来掩盖失败 |
| 更新与历史 | 旧消息、文档、授权和浏览器资料保留；新版桌面/服务一致并实际可用 | 只有构建成功，用户还要猜是否要重启 |

A2A和自然协作的证据至少包括真实消息ID、发送身份、提及目标、接收/读取/回复时间、关联文档版本、实际工具调用和完整记录。模拟平台用于测隔离与异常；真实Grok、Dot互相往返及原Agent身份验证另列，不混成一项“测试通过”。

不以“群里消息很多”判定高效：验收同时看是否回答了彼此的问题、是否实际补充或修订、用户是否需要搬运和催促、工具产物是否可用。保留没有分歧或无需协作就完成的正常情况，不为增加互动量制造角色和争论。

### 9.10 本次方案与后续实现怎样避免再偏

1. 本次只有文档研究和细化，没有改变现用软件、群成员、负责人、登录或平台订阅。
2. 开发以本文和Issue #20为对照；每项改动注明对应哪条用户原则、实现了哪个工具行为。不再把“实现了固定步骤交接”写成“群里能够自由沟通”。
3. 主流程不加入新的协作模式选择、聊天/任务确认关卡，不把普通沟通变成强制审批，不规定发言顺序或唯一执笔人；工具的可选默认值不能变成所有Agent必须服从的工作方法。原平台授权和用户明确限定的操作权限继续有效。
4. 接入身份、技术上不能实现或有行为改变的地方，先在Issue #20说明；不自行用近似方案替换后称完成。实现建议与用户决定保持区分。
5. 验收先亲自走“建群、加人、移除、负责人、问一句话、两Agent互聊、共同使用工具”的完整操作，再看工程检查。只通过程序检查不能交付成产品已验收。
6. 评审与实现进度放同一个Issue，文档与证据绑定提交和构建；保留失败及未验项。第6节的验收次序是开发核对顺序，不是给用户固定的使用流程。

## 10. 参考 DeepSeek dsh-superagent（2026-11-02 核对原文）

**它是什么：** [deepseek-ai/dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype)，MIT 许可，研究原型。**一个**运行在 DeepSeek Harness 上的编程 Agent，挂进团队的飞书群和 GitHub，像同事一样接活、提 PR。它和我们**不是同一件事**：它是"一个 Agent 加入人的团队"的底层框架，我们是"用户自己的多个 Agent 彼此协作"的应用。但它在两个问题上的做法值得借鉴。

### 10.1 谁来判断"这句话要不要处理"

**原文做法**（docs/002、004）：
- 程序只做"准入"：消息是否直接叫了它、发送者是否被允许；
- "要不要接活"由模型（主 Session）判断：接活、并入已有工作、停止或忽略；闲聊可以直接忽略；
- 某项工作讨论串里的追问，直接交给正在做这项工作的执行者，不需要再叫它；
- 没人叫、想主动做的事，默认是"只记录"模式（observe），先记下"本来会做什么"，团队确认后才改为自动。

**我们怎么借鉴：**

| 借鉴什么 | 落到我们的方案 |
|---|---|
| 程序只管"叫醒谁"，模型判断"做不做" | 第 5 节：用户设了「负责人」时，无 @ 的消息先叫醒负责人；没设时叫醒全员。做不做、怎么回由被叫醒的成员自己判断。**不再做"聊天还是任务"的程序判断** |
| 追问直接交给正在做的人 | 回复某位成员的消息时，叫醒那位成员 |
| 主动行为先"只记录" | 以后做"Agent 主动做事"（例如定时巡查）时，默认只在群里留一条「我本来会做：…」，用户点「以后直接做」才切换成自动。**v1 不做主动行为** |

**不借鉴：** 它设了一个**只负责分派、不干活**的主 Session（需要额外的模型），我们不加 Hub 自己的模型。负责人是用户指定的普通成员，可以自己回答，也可以 @ 别人；它**不是关卡**，其他成员照样可以发言、互相 @、直接找用户（见第 9 节 U2）。它的工单、授权、策略版本那一套偏团队治理，不照搬。

### 10.2 占用最少的注意力

**原文做法**（docs/000、004）：核心原则是"占用最少的人类注意力，换取最多的价值"。
- 写在提示词里：只在有人必须行动、或有结果可用时才说话；接活前确认一次，说清对象和预期结果；干活时不说话；一次只问一个具体问题，问题以结构化字段提出；交付要诚实（草稿必须标明未完成）。
- 由程序强制：聊天消息默认一句话，**硬上限 100 个英文词**；每条回复必须属于某种用途（确认、回答、结果、请人决定）。
- 面板只显示需要人处理的事，状态正常时不占地方。

**我们怎么借鉴：**

| 借鉴什么 | 落到我们的方案 |
|---|---|
| 说话规矩 | 写进每位成员的"协作习惯"（第 4 节末尾），**随每次叫醒一起发给成员**，因为我们无法修改原生 Agent 的系统提示词 |
| 简短 | **不设硬性字数上限**（DeepSeek 设了 100 词上限，但那会把普通问答逼进文档，违背第 9 节 U1 和 9.9 "回答不能藏进文档"）。协作习惯写明"默认简短"；超过约 800 字的消息在界面上折叠显示；长篇成果建议写进文档 |
| 一次只问一个问题 | `ask_user` 每次调用只能带一个问题，附选项和依据 |
| 不刷进度 | **降噪只针对重复的进度汇报**：工作中的进度显示在顶部状态里（例如「Dot 正在写文档」），不发到群里。**提问、异议、互相 @、证据讨论随时都可以发生**（2026-11-02 更正：原写法"群里只出现确认和结果/求助几类消息"会被理解成切断实质交流，Codex 在 #22 指出，正确） |
| 面板只显示要人处理的事 | 首页和「待我决定」只列出需要用户处理的事；没有待处理时，这一块不显示 |

### 10.3 验收补充（加到第 6 节和 9.9）

- 设了负责人时，发"有人在线吗"（不 @ 任何人）：**只有负责人被叫醒**，它用一句话回复，其他成员没有叫醒记录。没设负责人时，全员被叫醒，但最多一到两位回复，其余用 `stay_silent`。
- 长消息在界面上折叠显示，可以展开阅读全文；不会被拒绝发送。
- 成员接活后：群里先出现**一条**确认（说清做什么、交什么），之后直到交付或提问之前，没有其他消息。
