# DuolaWork Todo 节点检查与协作推进优化方案

日期：2026年11月9日。版本：v0.4。状态：待评审产品方案；已补充结构化交付及三项已知风险的轻量处理。

本项在现有 Todo 上补齐按任务组织的成果提交、完成检查、必要依赖和后续推进，让负责人既能分配工作，也能按步骤把事情带到实际交付。它是协作的一项优化，沿用现有「任务 → Todo」两层结构，具体过程由负责人根据任务安排。

## 1 要解决的问题

此前的分工主要说明「谁做什么」，成员接到工作后容易各自直接做到最终结果。中间需要先形成的共同依据、阶段成果或决定没有被明确接住；即使讨论完成，也可能停在「收到」，没人推进下一步。

这次补充的是「做到什么程度，才能继续哪件事」。主要目标是减少抢跑、遗漏和无人跟进，让用户看到真实进度。节点检查不能代替任务本身的质量判断，也不解决原生会话排队、消息丢失或连接故障；这些稳定性问题需要单独修复。

## 2 沿用任务和 Todo

| 对象 | 产品含义 | 维护方式 |
|---|---|---|
| 任务 | 要完成的一件事，记录目标、负责人和最终交付 | 创建者先归组，负责人维护整体安排 |
| Todo | 为完成这件事需要做的具体工作，可以是执行、讨论、核对或等待用户决定 | 执行者反馈，负责人安排接续 |
| 节点 | 对后续推进有影响的一条 Todo 及其完成检查 | 使用同一条 Todo，不新增第三层对象 |

需要多人贡献后才能汇总时，可以建立若干并行 Todo，再由同一任务下的一条汇总 Todo 接续。共同复核也作为同层 Todo，避免继续嵌套子任务。

小事可以保持一条独立任务，普通问答直接回答。有明确跟进需要时才使用 Todo；已有事项的补充和会议继续关联原任务，不因每次聊天或开会再建一份清单。

## 3 负责人怎样安排过程

### 3.1 先对齐需求

需求确认沿用正常对话：有影响结果的歧义就问清楚，明确的要求直接采用。复杂事项可简短说明理解和准备交付的结果，便于用户纠正；不设置固定的需求确认关卡。

任务保留相关用户原话及最新补充的引用，执行者与核对者可直接读取，负责人的复述不能成为唯一依据。负责人推断出的目标或条件要与用户明确要求分清。核对者发现完成条件本身偏离原要求时，可以指出原文依据并退回修订，不必先接受负责人的标准；不因此给所有任务增加一轮人类确认。

### 3.2 按当前任务拆 Todo

负责人选择本次实际需要的步骤和成员，不预设统一的阅读、讨论、合稿、审计顺序。安排可以边做边调整；普通排程由负责人处理，涉及目标或执行范围的改变再交用户决定。

每条 Todo 用简短内容说明要做什么、交回什么、怎样算完成。需要先完成其他工作时才设置前置依赖；需要他人复核时才指定核对人。资料、原讨论和实际结果直接关联现有对象。

| 信息 | 要求 |
|---|---|
| 工作与完成条件 | 默认写清楚，一句话能说清就不扩成表单 |
| 执行者 | 谁交回这项结果；可以是负责人本人 |
| 前置 Todo | 可选，只记录确实影响开始的依赖 |
| 核对人 | 可选，用于关键节点；普通小项由执行者自检 |
| 成果安排 | 本次要回答哪些问题、提交什么；成员可以按任务自行组织内容 |
| 结果 | 关联具体成果、必要依据与遗留问题；提交与检查通过分别记录 |

这些内容主要由 Agent 维护，用户可以直接在聊天中调整。

普通小项默认只需要简短成果和必要依据，复用本任务已有安排，不逐项重新设计结构，也不额外叫一位成员审阅。任务关联、版本与操作者由系统处理；多人比较或复杂产物确实需要时，再约定相应结构。提交与自检合并保存，避免仅为维护记录增加往返。

### 3.3 顺序与依赖分开

列表先后只表达安排顺序，不自动把所有 Todo 串行化。没有依赖的工作可以同时进行，成员仍可相互提问、质疑和求助。

配置了前置依赖的 Todo，在所需前项完成后才能启动。可选意见不设为必要依赖；确实缺少关键结果时，负责人补查、恢复或改派，不能因其他人已交付就跳过它。取消前项不等于完成，负责人应明确后续工作怎样改接。

依赖限定在同一任务的 Todo 之间，不允许自依赖和循环依赖。跨任务的成果可以引用；复杂的跨任务调度不纳入本项首版。

### 3.4 成果结构按任务安排

讨论保持自由，到阶段交付时再把必要内容整理成便于检查和接续的成果。结构化不要求统一 JSON 或同一张表；有清楚章节的说明、对照表、图稿、代码补丁和验证记录，都可以按任务需要提交。简单结果可以很短，重要的是与对应 Todo 和完成条件明确关联。

多人结果需要比较或合并时，负责人约定共同要回答的问题、必要产物与完成条件。成员可以用不同结构表达，但必须能对上这些共同问题。独立工作由执行 Agent 自行组织成果；负责人不逐项审批它采用什么标题或表格。

内容结构可以随发现调整。改变表达方式不等于改变完成要求；不能在结果不达标后自行降低约定标准。有实质变化时，负责人接住调整，保留原依据及未满足部分。

### 3.5 业务内容可变 交付关联稳定

成果的业务结构按任务确定，系统稳定保存它属于哪个 Todo、依据哪版要求、是谁提交的，以及具体内容或产物版本。检查记录再指向这份成果及本次完成条件，不凭标题或聊天位置猜关联。

短成果可直接保存于 Todo 的交付记录；长文档、文件和代码继续使用现有资料或仓库原件，固定引用相应版本。提交不要求每次新建一份共享文档，也不把多种格式压成一篇大摘要。

## 4 成果提交与检查通过分开

普通 Todo 可以由执行者自检；影响后续方向、重要产物或最终交付的节点，由负责人或指定成员核对。要求独立审阅时，提交者不能代替审阅者给出结论。核对责任按本项安排，不增加永久岗位或发言审批。

成员提交一份阶段成果，说明约定内容对应在哪里、有哪些缺口以及必要依据。仍有缺口的成果可以保留，不能伪装为全部满足。自由发言、阶段成果和已经核对的结果分别表达，不要求每条聊天整理成提交件。

检查记录明确关联本次成果、完成条件及核对者，并保存通过或需要补充的结论、具体问题和必要依据。格式完整只是可检查的前提，不能直接证明内容正确、有用或已被独立审计。

核对既看完成条件，也看它是否仍对应原始要求。即使清单逐项满足，核对者发现遗漏用户目标或引入错误前提，仍可提出需补充或修订；不能由程序看到勾选齐全就自动接受。

需要他人核对的成果提交后显示「待核对」。通过后完成 Todo；需补充时带着具体问题继续处理。普通自检可以把提交和自检记录在一次动作中保存，用户不需要为此增加操作。

检查力度随工作需要变化。整理资料可以核对范围和实际可读性；内容、设计或实现工作按约定用途、事实与必要验证核对。不要求证明 Agent 完全理解，不要求每项独立审计，也不要求全员一致。

「收到」「已读」「我做完了」、字段填齐和无人反对均不自动通过。提交与核对通过以实际保存的动作和结果为准；人工直接核对也保留真实身份，不冒充其他成员的独立意见。

负责人归总时，围绕共同问题整合各成员的提交成果，保留重要依据、分歧及处理去向，形成综合成果。可以继续讨论、追问和求助，不能只拼接文字或把多数同意写成事实核验。

只对影响结论、关键事实或执行安排的重要发现说明处理去向：采纳后体现在哪里，暂不采纳依据什么，或还需查什么。普通措辞建议不逐条做表。已有的最终核对直接检查综合产物是否实际保留或修正了相关内容，不能仅凭负责人写“已采纳”通过，也不为此再增加一层审计。

成果、要求或输入发生变化时，旧核对仍属于原版本。系统提示受影响的关联，负责人判断并补充必要复核；确认变动无影响时可简短说明，不要求所有人重新审阅。普通进度更新、任务改名和归组不应导致内容检查失效。

## 5 结果返回以后继续推进

Todo 的有效成果通过约定检查后，系统根据保存的依赖关系识别可以接续的工作，通过现有通知与跟进能力交给对应成员。负责人接住结果并安排下一步，不需要用户再发一句「继续」。有明确任务负责人时由其跟进，未指定时沿用群负责人；换人不能丢失待核对与待接续事项。

这次结果应导向明确的后续动作：继续已就绪 Todo、补充当前工作、呈报需要用户决定的问题，或核对整件事的交付。成员间可以直接交接；在接手方实际接住之前，原负责人继续跟进。

系统维护记录、依赖和待接续状态，Agent 负责内容判断与实际组织。可派发、已通知、已接收、进行中和完成不能混为一谈。刷新或重启后，尚未完成的接续仍需保留，重复反馈不应重新启动已经执行过的工作。

全部 Todo 结束后，沿用现有「待核对交付」处理：负责人核对最终结果、说明未决项后再结束任务。不能仅凭子项全部打勾就宣布整件事已交付。

## 6 协作与执行怎样衔接

阅读、讨论、整理候选稿和约定范围内的验证可以在协作中正常推进。涉及采用哪份方案并改变正式目标时，按用户要求保留执行确认。

需要确认时，用原任务中的一条 Todo 呈现：准备采用什么结果、实际改哪里、主要影响以及怎样验收。用户可以在原聊天说「按这版执行」，也可在任务中点击「确认执行」；两者对应同一份提案，不要求重复确认。

用户已明确授权的执行直接沿用相应确认。确认覆盖约定的一批动作，范围内的执行细节、纠错和复验继续自主处理。目标或关键范围改变时，只呈报需要重新决定的差异。账号和工具的默认权限保持独立，不增加逐次工具审批。

确认后，执行 Todo 接续原任务，由负责人或指定的事项负责人跟进。执行人交回真实结果后，继续验收或修正；若执行暴露了需要重新讨论的问题，就带着结果返回相关 Todo，保留仍然有效的工作。

执行反馈未知时先核对实际状态，不将超时等同于失败，也不直接重试可能已发生的外部操作。用户明确暂停时停止后续相关工作，保留已发生操作的真实记录。

## 7 会议使用同一份 Todo

会议用于集中推进某些 Todo，议程与对应任务关联。负责人在需要交叉讨论、共同核对或作出选择时组织会议；分工和全员参与本身不强制开会。

会议产生的结论、产物和新工作回写原 Todo，不另造一套会议进度。会议总结可以作为阶段成果，不能代替各项实际核对，也不能自动把关联 Todo 全部标为通过。会议结束时说明哪些工作已完成、还缺什么、接下来谁做。待用户确认或待执行的任务可以继续保留，会议正常结束，普通群聊继续。

## 8 用户怎样看到进度

沿用现有 Todo 入口及按任务分组的列表。任务收起时显示目标、负责人和当前关键进展；展开后查看具体 Todo、执行者、结果和阻塞。并行工作可以同时显示，不强行压成唯一当前步骤。

默认突出用户关心的三件事：现在做到哪里、还缺什么、接下来谁处理。需要用户决定时，直接展示具体问题或执行提案；正常内部接续不制造待用户处理提示。

点开 Todo 可查看本次要求、当前成果、检查结论与剩余问题。负责人可以调整交付安排，成员和人类都可以在已有编辑入口提交或核对；不增加必须学习的模板编辑器。

Todo 的等待原因用人话说明，例如「等待资料返回」「已提交，待负责人核对」「等待你确认这版方案」。前置依赖和详细记录按需展开，用户不用配置流程图或学习新模式。

完成项数量只表示 Todo 记录，不能当作产物质量或实际工作量百分比。任务完成仍以实际交付为准。

## 9 不同任务使用同一机制

以下只是负责人可能采用的安排，用来检验通用性，不作为系统固定模板。

| 任务情况 | 可以怎样安排 | 检查与接续重点 |
|---|---|---|
| 信息已足够回答一个问题 | 负责人直接回答，必要时补一项核实 | 不为简单问答创建多步流程 |
| 比较多个选择 | 相关成员并行调查，汇总差异，再处理关键取舍 | 核对比较依据与遗漏，不以赞同人数代替判断 |
| 修复故障 | 定位问题，形成修复，验证结果，按授权安排发布 | 修复和验证对应实际版本，结果回来后继续收尾 |
| 执行已批准的运营事项 | 直接执行约定动作，再核对结果 | 复用已有授权，不重复调研和确认 |

同一任务进行到一半发现缺少依据，可以补一条 Todo；某个步骤不再需要，可以说明原因后取消并调整后续依赖。步骤数量和参与人数由任务需要决定。

## 10 合理性与取舍

这项优化适合需要分步推进、多人接续或持续跟进的工作。它把关键安排从聊天里的口头承诺变成可查看、可恢复的 Todo 关系，减少成员越过必要前提和负责人收完结果后停下的情况。

代价是增加少量整理和核对。通过可选依赖、按需复核和直接复用原任务控制开销；简单工作保持简单。负责人仍可能拆错步骤或判断错误，用户和成员可以纠正，计划随实际情况调整。

首版重点验证三件事：必要前提未满足时是否避免抢跑，结果返回后是否真正接续，以及最终交付是否符合要求。还要观察返工、总耗时和用户纠偏负担，避免为了进度记录增加大量无效往返。

结构化主要减少错关联、漏交和版本混用，内容质量仍需要任务相关的核查。成员找不到充分依据时可以交回未知或缺口；不为凑结构编结论，不用字段数量、引用数量或采纳率给贡献打分。

上述三项已知风险先通过原话直达、普通事项轻量默认和重要发现的产物核对处理，再验证效果。开发验收预先加入错误完成条件、简单事项、正确少数意见与错误质疑等情景，核对真实产物及调用开销。运行中的记录用于判断残余问题、额外成本和质量变化，不能代替这些处理和发布前验证。

自由交流、成员直接协作、多人并行和按任务选择参与者继续保留。本项不增加固定轮次、统一岗位、默认全员审计，也不将所有工作改造成串行审批。

## 11 验收标准

| 情景 | 预期表现 |
|---|---|
| 普通问答或一步能完成的小事 | 直接处理，不强制建立多步 Todo |
| 同一任务拆出多个独立 Todo | 可以并行，列表排序不会误变成依赖 |
| 后项确实依赖前项 | 前项达到完成条件后接续；需要复核的前项未通过时不抢跑 |
| 成员只回复收到或已读 | 消息正常保留，不自动完成 Todo |
| 普通小项与关键节点 | 前者可以自检完成；后者按指定责任完成核对，不统一升级成审计 |
| 一项检查未通过或必要成员未返回 | 显示具体缺口，负责人补查或改派，其余无依赖工作继续 |
| 收到结果、刷新或重启 | 待接续工作仍保留并继续推进，不靠用户再说继续；重复结果不重复执行 |
| 前项取消、调整依赖或出现循环 | 取消不冒充完成；调整有明确去向；循环和自依赖被拒绝 |
| 用户已有明确执行授权 | 直接沿用，范围内不重复确认 |
| 需要新的执行决定 | 呈现具体方案；人类确认后执行；讨论完成不冒充授权 |
| 用户补充、暂停或产物发生实质变化 | 处理受影响工作和检查，保留有效成果，不静默丢掉新要求 |
| 会议结束、执行尚未结束 | 会议正常结束，原任务继续跟进，不残留正在会议状态 |
| 执行完成、失败或结果未知 | 负责人接住后验收、修正或核实，不停在收到，也不盲目重试 |
| 子项全部结束 | 主任务待核对交付，实际核对后才结束，不自动宣布全量交付 |
| 成员自行设计成果结构 | 能组织适合本次工作的内容；多人结果对齐共同问题即可，不要求模板完全相同 |
| 成果字段齐全但存在实质错误 | 仍可核对不通过；形式校验不冒充内容正确 |
| 成果不完整或找不到充分证据 | 保存已有结果和明确缺口，必要项未满足时不通过 |
| 成员提交新成果或完成条件改变 | 旧检查不能覆盖新对象；普通进度更新不会使检查失效 |
| 旧工具或界面尝试直接标记完成 | 对采用本机制的 Todo 走同一提交与检查逻辑，真实返回实际状态，不绕过检查或要求重登录 |
| 任务负责人不同于群负责人 | 指定核对与接续责任有效，不把所有结果只发给群负责人 |
| 自由发言、明确 @ 或普通问答 | 正常沟通，不因成果结构不齐被拦截 |
| 负责人拟定的条件遗漏或误解用户要求 | 执行者或核对者能据原话提出修订，不因满足错误清单就通过 |
| 普通事项启用结构化提交 | 不增加额外核对成员或专门模型调用，提交与自检可合并 |
| 负责人报告已采纳关键纠正 | 最终产物确实体现对应纠正；只写处理记录仍不能通过 |
| 成员提出错误质疑或没有发现问题 | 正确内容可以保留，不为显示协作价值强制改稿或制造反对 |

验证至少覆盖简单事项、多人并行和有依赖的连续工作，不能只用写文档一种场景判断适用性。质量、返工、耗时和用户负担需要通过真实任务比较，节点数量不作为优化成功指标。
