# 自然聊天与协作任务可视化产品方案

版本：v0.4，2026-11-10。

**状态：当前产品共识已记录，可继续补充；没有额外等待用户确认的主流程卡点。本轮仅更新文档，尚未实施。**

本文件集中保存本轮已达成的产品原则和拟议交互。后续补充继续更新本文件，不为每轮聊天另建一份方案。当前客户端已经存在的任务、Todo、提交、check 和负责人跟进能力属于基线；本文的新交互与流程不能据此标为已实现或已上线。

## 1. 产品边界

保持像现有大模型产品一样的自然聊天。Agent 理解用户意图、关联工作、组织协作并自动推进；产品将这些过程可视化，让用户能看见、补充和纠正。

产品负责保存原始表达、关联关系、状态、回传和接续。意图理解与内容判断由 Agent 承担，不能承诺通过任务结构消除模型理解错误，也不把防止所有误解的成本转给用户。

用户日常使用不需要先填需求表、选择流程模板、整理任务清单或逐项确认。用户可以展开内部过程，但任务管理不是继续对话的前置条件。

沿用既有授权范围。生成卡片、建任务和普通推进不增加确认关卡；用户明确要求先讨论、先准备或另行确认的执行事项，继续遵守原要求。

## 2. 用户已明确的原则

| 编号 | 已确认原则 | 产品含义 |
|---|---|---|
| D01 | 用户可以直接在群里发需求 | 对应 Agent 理解、关联工作并输出卡片，随后自动推进 |
| D02 | 未 @ 默认负责人，有 @ 由对应成员处理 | 保持现有群消息路由；负责人不是所有成员直接协作的审批入口 |
| D03 | 意图由 Agent 按复杂度结构化输出 | 不统一要求所有需求填写同一套业务字段 |
| D04 | 用户可以修改，但任务无需确认才开始 | 卡片承担回显和纠正作用，不变成审批单 |
| D05 | 需求确实不明确时，Agent 可以先问 | 先解决影响行动的歧义，再组织意图和推进，遵循正常聊天习惯 |
| D06 | 任务主要用于 Agent 协作管理 | 数量按工作需要决定；不把减少任务数量当作产品目标 |
| D07 | 关键是同一任务的合并和推进 | 补充、成果、讨论和内部工作归回同一目标，并能持续接续 |
| D08 | 任务侧栏也是需求输入入口 | 可在查看任务时补充要求，也有“添加到会话”入口 |
| D09 | 侧栏补充回到聊天中形成关联卡片 | 任务记录和群聊记录关联同一次输入，按 @ 规则交给对应成员推进 |
| D10 | 任务内容应对群内协作成员共享 | 共享最新要求与进展；实际通知谁处理、谁需要同步变更分别管理 |
| D11 | 不额外增加用户的质量管理负担 | 内部结构化、提交和节点 check 由 Agent 维护；不统一增加人工验收表 |
| D12 | 负责人主动总结 | 过程可视化后仍须向用户交付阶段进展和最终结果，不能只更新后台状态 |
| D13 | 需求补充后继续推进 | 补充、询问和纠正进入当前任务，不自动触发整件事暂停 |
| D14 | 节点可以随需求变化 | 调整受影响的工作、依赖和预期结果，保留仍有效的成果与进展 |

卡片布局、按钮文案和编辑方式由设计落实，不增加独立的用户确认步骤，见第 12 节。用户后续问题继续记录到本文件。

## 3. 用户动线

### 3.1 从群聊提出需求

1. 用户照常发送消息，可选 @ 成员。
2. 接收 Agent 理解本次需求及相关上下文；有影响行动的歧义时先正常追问。
3. Agent 判断关联已有任务、更新已有意图，或创建新的工作事项。
4. 聊天中显示轻量关联卡片，让用户看到关联哪件事、Agent 怎样理解、由谁处理、现在准备做什么。
5. 无需用户点击确认，Agent 在授权范围内继续组织工作。
6. 用户发现理解或关联有误，可直接回复纠正，也可修改卡片或从侧栏补充。

普通问答可以直接回答。已在任务中的进度询问、补充或纠正沿用其关联；不因为每条消息、每个工具动作都重复创建一份主任务。

### 3.2 从任务侧栏补充

任务详情增加一个直接输入区，支持普通文本和现有 @ 操作。进入输入区时已经绑定正在查看的任务，不要求用户再选择一遍。

用户发送后：

- 保存原始补充，并关联当前任务。
- 群聊出现同一次补充的任务卡片与正文。
- 按明确提及或默认负责人规则通知对应 Agent。
- 接收 Agent 整理本次补充对意图、任务和推进安排的影响，然后继续工作。
- 任务侧栏和聊天展示同一条补充的关联状态，不形成两份彼此独立的需求。

原始补充送达与 Agent 完成理解是不同事件。界面不能在用户刚发送时，伪称所有成员已经理解并调整完毕。

### 3.3 添加到会话

任务详情提供“添加到会话”入口，携带当前任务引用，便于用户继续围绕该任务发消息。

设计落实：点击后将引用放入主聊天输入框，用户继续输入、@ 后再发送。侧栏的直接输入区则可以当场发送，无需绕回主输入框。这是入口交互的设计选择，不增加一轮用户审批。

### 3.4 修改和纠正

用户可以继续用自然语言说明“关联错了”“我指的是另一件事”“改成这个目标”。Agent 更新对应工作关系并保留修改来源；可视化修改入口提供同等能力。

修改不新增普遍适用的确认步骤。确实影响执行方向且无法明确判断的部分，沿用正常对话澄清。

### 3.5 简单问答、临时交流与任务怎样区分

由接收 Agent 根据用户本次表达和当前上下文判断，用户不选择消息类型。程序不靠消息长短、固定关键词、是否带问号或是否 @ 人来判定要不要建任务。

需要分开处理两件事：这条消息关联哪项工作，以及它是否产生新的工作。消息可以关联任务但不新建任务，例如询问进度、追问依据或讨论一个结论。

| 用户表达示例 | 处理方式 |
|---|---|
| “你在线吗”“谢谢” | 正常交流，不额外启动协作任务 |
| “这个 GitHub 准备到哪一步了” | 读取并回答已有任务状态，沿用关联，不重新建立一份准备任务 |
| “这个结论的依据是什么” | 在原事项下回答或核查；若需要后续调查，由 Agent 安排原任务内的具体工作 |
| “这份方案还要覆盖周末” | 补充原意图并调整相关工作，不另建一份相同主任务 |
| “另外给另一个产品整理一份发布方案” | 新交付目标，新建独立任务，可保留业务关联 |
| “先帮我研究一下，再给出完整方案” | 有持续推进与交付责任，创建或接续相应任务 |

示例用于说明上下文判断，不变成关键词匹配规则。一开始可以直接答完的问题，随着后续讨论产生跟进工作时，可以转为任务并保留前面的消息来源；误建或重复建立的轻任务可以归并。判定偏差由同一套可视化关联和自然语言纠正机制处理，不为了分类增加一轮人类审批。

卡片展示实际关联、意图和进展，不要求为每句闲聊显示“非任务”等分类标签。

## 4. 意图卡与进展展示

### 4.1 意图结构按需求复杂度生成

简单需求可以只显示一句理解与关联事项。复杂需求可按需展开目标、当前范围、关键约束、预期结果或待澄清内容。

这些是可能出现的内容，不是所有任务必须填满的固定表单。卡片应保存用户原话及相关补充的来源，使负责人复述不成为唯一依据。

卡片的展示不表示用户逐项批准了 Agent 的理解、建议或推断。用户看到偏差可以纠正；没有点击修改也不等于另行授权扩大执行范围。

### 4.2 拟议卡片示例

以下只是本轮需求的展示示例，不是全产品的固定业务模板：

```text
关联事项：X 每日运营准备
当前理解：核查 GitHub，形成每天发的内容方案
本轮范围：先讨论和准备，发布另行决定
当前推进：核查仓库情况、整理参考内容

查看任务 · 补充要求 · 修改关联
```

侧栏输入产生的群聊卡片应同时展示用户补充原文、关联任务和通知对象，用户无需翻历史才能知道这条补充去了哪里。

### 4.3 面向人类的聚合视图

用户默认看到目标、整体进展、当前阻碍和结论。内部可以有多项执行、讨论、核查及核对工作，具体数量由 Agent 按需要组织，按需展开查看。

进展发生实质变化和阶段交付时，负责人在聊天里明确回应；不能只悄悄修改旧卡片。普通内部动作不要求每次单独刷一张卡。

## 5. 同一任务的关联、合并与变更

### 5.1 按交付目标组织

同一目标的讨论、补充与成果持续关联原主任务。重复建立的工作可以归并，具体子项可继续并行。新目标可以新建任务，并保留与原事项的关联，不把整群永久锁定在一件事上。

Agent 负责判断关联，程序稳定保存对象编号、来源、版本和合并关系。任务或群名称只用于显示，不依赖中文标题作为后续关联键。

### 5.2 合并时保留现场

合并应保留原始需求、各自的成果、重要分歧和正在执行的状态。旧引用仍能定位到相应工作，不因合并重新执行已经完成的操作。

不同成员为同一目标提供的独立判断可以同时保留。归集到同一任务不表示把不同意见压成一个结论。

### 5.3 用户补充持续生效

例如，用户补充“每天都要发”，更新原任务的要求及相关安排。成员建议“当天有素材才发”保留为建议；未经用户改变原要求，不直接替代用户目标。

复用现有需求来源、版本和依赖关系，识别需要调整或复核的部分，保留仍有效的工作。旧要求下迟到的成果不能直接宣称完成新要求。

### 5.4 相同任务的判断与归并操作

Agent 先读取用户明确指定或正在回复的关联，再结合相关任务的当前目标、预期交付、范围和原始要求作判断。明确转换目标时可以创建新任务；同一项目、同一个参与者或相似标题，本身都不足以证明是同一任务。

关联与合并按以下规则落地：

1. 已有任务的新要求、新材料、修订和进度询问，关联原任务。
2. 同一预期交付被重复建立时，选择一个主任务作为统一推进入口，并保存归并关系。
3. 属于同一业务但有独立交付结果的工作，分别保留任务，必要时关联资料或前置成果。归入同一业务不强制合并所有工作。
4. 为同一目标提供的不同观点、独立核查或不同子项，保留各自成果与责任；不因为内容看起来相近就抹掉独立贡献。
5. 已结束事项产生新的修订时，按是否仍属于原交付选择重新打开并形成新版本，或建立关联的新任务；旧完成记录不被覆盖。

合并的结果必须是明确的任务关系变化，不能只在聊天里说“已经合并”。旧任务引用仍能找到归并后的工作，原始补充、成果和变更记录可追溯、可纠正。

已有执行保持其实际状态和结果归属，不能因合并重复派发、伪造完成或强制终止原生 Agent。对重叠执行，由负责人决定复用哪份结果及如何调整剩余工作。

### 5.5 多任务并行管理

同一群允许多个主任务同时存在，每项分别保存当前意图、要求版本、负责关系、子项、成果、依赖、等待原因和下一步。结果和后续通知使用任务关联，不依靠“群里最近在聊哪一件事”判断归属。

一个任务等待成员、补资料或等待用户决定，不自动暂停其他任务。负责人分别维护各任务的可推进工作和待解决事项；无依赖的子项可以并行，明确依赖前项结果的工作再等待。

任务管理上的并行与原生运行端的执行并发分别展示。多个任务可以同时跟进；实际同时执行需要可用的独立 Agent 或原生会话。共用同一不可并发会话时，该运行端按真实情况排队，其他可执行工作继续。不要求每个任务都另建原生会话，不因任务变多静默替换用户原会话，不把建立多份任务显示为实际并发成功。

用户默认看各主任务的整体进展和当前动作，需要时展开内部工作。新结果与需求变更回到各自任务，由相应负责人接续并汇总，避免串任务或让用户逐个协调队列。

### 5.6 运行中的任务接住需求变化

任务是一份可以持续更新的工作计划。任务关联持续保留，当前意图、节点安排和具体执行可以演进。系统不能把用户每次发消息当成停止当前目标，也不能把一次原生调用结束当成主任务结束。

每次相关补充形成一条变更记录：保留用户原文，Agent 给出对当前工作的理解和影响范围，更新卡片并继续接续。影响范围可以很小，也可以涉及整项任务；用户已经明确改变要求时直接执行调整，不重新索要同一决定。

| 变化 | 工作计划怎样调整 | 继续推进的方式 |
|---|---|---|
| 询问进度、追问依据或补充说明 | 记录关联，回答问题；无需改变的节点保持原安排 | 问答结束后原工作继续 |
| 新增一项要求 | 增加或调整对应节点，检查所需依赖 | 已有有效工作继续，新项进入可执行队列 |
| 修改已有要求 | 更新受影响节点的交付约定与必要依赖 | 只复核或重做受影响部分，其他工作继续 |
| 新材料推翻已有依据 | 保存新来源，重开使用该依据的相关节点及下游检查 | 其他成果保留；负责人明确需要补查的部分 |
| 改变顺序、优先级或处理成员 | 调整排程、责任和必要交接 | 原执行保持真实记录，在可接续点转交或切换 |
| 用户明确改变整体目标 | 更新当前意图，重新判断哪些工作仍可复用 | 保留历史成果，收起已不需要的工作，按新目标接续 |
| 用户明确停止或取消 | 停止该事项后续推进，处理关联的未开始工作和待通知 | 其他独立任务继续，保留已发生的操作与结果 |

需求版本变化需要传给相关参与者，但不能直接等同于所有节点成果失效。Agent 负责判断影响范围；程序按明确的节点关系记录调整、复用及复核。普通进度变更不改变交付要求，未受影响的核对结论可以继续使用。

正在执行的成员收到相关变更，接续时按最新版工作；原调用稍后返回的成果先保存其依据和版本，再判断哪些可用、哪些需要调整。不能把这些实际产物直接丢弃，也不能不看变化就将旧结果标成最新要求已完成。

需要澄清时，只让依赖该答案的工作等待。其他可独立进行的节点继续；如果整项任务确实都依赖同一答案，显示具体待答问题，由负责人接住用户答复后自动继续。

## 6. 接收对象、共享内容与同步

### 6.1 接收规则

- 群聊中用户没有 @：默认由群负责人处理。
- 用户明确 @ 某位或多位成员：由指定成员处理，不要求先经负责人批准。
- 用户明确 @全员：按全员通知语义处理。
- 任务侧栏补充回到所在群，沿用同一群消息规则：没有 @ 交给群负责人，明确 @ 交给指定成员；保留当前任务关联。具体 Todo 执行者不因此替换群消息的默认接收者。
- 明确提及某人不会自动更换主任务负责人。

成员的实际结果归回其关联任务，负责人可以据此统筹和总结。正常 Agent 之间交流继续保留。

### 6.2 内容群内共享

群成员可以查看同一份任务、补充、成果和进展。共享仍遵守用户已设置的访问范围，不将任务内容复制到无关群或其他私有工作空间。

群聊卡片可见与原生 Agent 实际读过、理解过分别处理。不能把“发到群里”当作所有成员已经同步记忆的证据。

### 6.3 接续时使用最新要求

成员接手或继续关联工作时，取得当前意图、有关原始补充、已收结果和影响本次工作的变更。正在做受影响工作的成员收到变更提醒，并在接续时调整。

内容共享不要求每次补充都唤醒全群或让人人回复“收到”。实际接收和运行仍受各原生平台能力影响，按真实状态显示，不声称可以即时撤销已经发生的外部动作。

## 7. 任务流与状态推进

继续使用现有任务、Todo、成果提交、节点 check 和负责人跟进能力。具体节点、成员、前置依赖及交付内容由 Agent 按任务安排，不预设固定人数、轮次或统一业务步骤。

Agent 发起协作、成员回传、结果核对、依赖解除、用户修订和明确阻碍，都应更新同一事项，并产生必要的接续。不能因为普通消息被填成某个隐藏类型，就静默丢掉已建立的跟进责任。

实现时需统一聊天关联、任务更新和通知接续的入口，避免“任务有新补充、聊天没有卡片”“结果已提交、负责人没有接续”“重试产生重复任务”等不一致。结构化内容如何按既有能力落地，留待技术细化，本文不宣称现有接口已经支持全部交互。

状态应反映真实动作：建议、通知、实际接手、成果提交、核对通过和整体交付分别有依据。负责人不能仅凭自己的话术把建议写成已执行，把未生成的截图写成准备好了。

必需成果与征求意见按本次安排区分。有阻碍或尚缺结果时，负责人汇总当前已知结果、缺口与下一步，不一直等待，也不把部分结果称为全员通过。

### 7.1 完整任务生命周期的处理规则

持续交付需求形成主任务，由 Agent 按当前需要拆分节点。每个节点说明要形成什么结果、由谁处理以及确实需要的前置条件。随着信息补齐可以增加、合并、重排或取消节点，不要求第一轮把全部路径规划完。

| 发生的事情 | 系统与 Agent 的接续 | 用户看到的进展 |
|---|---|---|
| 新需求明确 | 建立或关联任务，输出意图卡，开始当前可做节点 | 理解的目标、关联事项与当前动作 |
| 新需求有关键歧义 | Agent 提问；已明确且独立的工作可以先进行 | 具体问题及仍在进行的工作 |
| 工作期间收到用户补充 | 写入同一事项，按影响调整节点；保留未受影响执行 | 这次补充关联哪里、调整了什么、接着做什么 |
| 多位成员并行处理 | 各自接手与回传，成果归回对应节点 | 各分支实际处理中、排队或已交回的状态 |
| 一个成员迟回、离线或执行失败 | 保留请求和已交成果；负责人恢复、补查、调整安排或报告所需支持 | 卡在哪个节点、其他部分进展及下一步 |
| 阶段结果到达 | 保存成果及当前版本，完成适当核对后激活可接续工作 | 已形成的结果与接下来推进的节点 |
| 出现不同意见 | 负责人比较依据、补查或形成待决事项；独立分支继续 | 重要分歧与如何处理，不刷逐个点头 |
| 用户提出另一项独立需求 | 创建独立任务并分别管理进展 | 两项工作的独立关联与状态 |
| 重复任务被合并 | 统一跟进入口，保留原成果、引用和在执行工作 | 一个聚合进展，历史可追溯 |
| 工作完成，或重要阶段需要汇报 | 负责人对当前用户要求核对结果并在群里交付总结 | 得到什么、遗留问题、需要决定的具体事项 |
| 已交付后用户继续修订 | 关联原成果，按范围重开相关工作或建立后续任务 | 原结果保留，新一轮修订有独立进展 |
| 用户暂停、停止或随后要求继续 | 明确记录控制动作；按有效要求和已完成结果恢复 | 哪些暂停、哪些恢复、当前从哪里接着做 |
| 任务要求长期重复运行 | 区分持续运营安排与每次交付，复用素材及要求，按实际排程建立各次执行 | 每次实际执行和结果，不用一个永久进行中的状态代替运行 |

任务主线持续存在。一次消息得到回复、一次工具返回、一个 Agent 的原生调用结束，都只更新它们对应的工作；剩余节点、未处理变更和待汇总事项仍需接续。存在可推进工作时，系统应调度相应处理者；需要外部条件时，记录清楚等待对象并在条件满足后继续。

### 7.2 进度如何保持一致

主任务的进度由当前节点、实际接手、成果和核对记录形成。节点数量可以随工作演进，不以一个容易失真的完成百分比作为唯一反馈。用户应看清当前在哪一步、已经得到什么、还缺什么以及谁在接续。

负责人组织和总结，各成员反馈自己的执行事实，程序维护关联与状态的一致性。不能由一个成员的一句“全部完成”覆盖其他未完成节点；也不能因新增一个节点就把已完成工作显示为全部重新开始。

已知实现调整：现有需求变更逻辑会统一使该协调关系下的关联任务成果通过状态失效。本方案将其改为按影响范围调整，并区分用户要求更新、节点内容变化和普通进度变化，避免一次补充把无关工作也带入返工。

### 7.3 连续变化的工作示例

“X 每日运营准备”最初可以并行核查 GitHub、整理参考内容和确认发布能力，再汇总准备方案。

- 用户补充“周末也要发”：更新日更要求及内容储备安排，仓库核查继续。
- 用户补充“先别公开仓库”：调整对外范围，继续整理公开前需要的资料和内容方案。
- 用户问“现在做到哪了”：回答当前任务状态，原工作保持推进。
- 用户再要求“同时整理公众号方案”：判断为独立交付目标，创建另一任务并行跟进，复用适用素材。
- 参考材料返回后：负责人接住结果、处理差异并形成准备方案；没有让用户再说一次“继续”。

这一示例展示同一机制处理补充、范围变化、状态问答、多任务和结果接续；业务内容由 Agent 组织，状态推进不写死为该内容场景专用规则。

## 8. 负责人收敛与总结

负责人负责维护当前理解、组织协作、处理分歧和推进下一步。其他成员仍可以直接交流、求助和提交结果。

阶段结果形成、出现影响推进的阻碍、用户追加要求或用户询问进度时，负责人应接续处理并给出可理解的回应。回复了一条通知不等于整个任务已经结束。

阶段总结按本任务需要组织，不强制同一篇长模板；应让用户能看清当前结论、实际完成、尚缺什么及下一步。必要取舍交给用户，正常内部推进由 Agent 自行完成。

当用户要求“先准备”，负责人先交付准备情况；发布、公开仓库等后续动作按用户实际授权推进，不能因产出候选稿就提前要求用户选择发哪一篇。

任务整体结束应有对应结果；不能以所有人已读、无人反对、消息已回复或子项数量推断交付完成。

## 9. 质量核对与用户负担

成果结构化与已有节点 check 继续用于 Agent 协作。普通事项可以简短提交并自检，确有需要时安排其他成员复核；不为所有任务统一增加独立审计、人类验收表或逐项批准。

程序可以检查关联、结构、版本、实际操作者及状态一致性；内容是否有用、依据是否充分及理解是否正确，仍需要 Agent 判断和真实效果评估。本文不将“有提交、有 check”写成自动保证结果正确。

用户只需继续聊天、查看需要的进展，并在发现偏差或需要自己决定时介入。

## 10. 对已有设计的衔接

| 已有设计 | 本轮衔接方式 |
|---|---|
| 群聊与 @ 路由 | 保留默认负责人、明确提及优先及成员直接交流 |
| 任务 → Todo | 继续组织工作，不新增强制第三层用户对象 |
| 成果 submit / check | 复用 Agent 内部提交与核对能力，按任务需要使用 |
| 需求来源与版本 | 保留原话、补充和有效版本，避免旧结果覆盖新要求 |
| 负责人协调记录与接续 | 与聊天卡片、任务动作衔接，明确持续跟进责任 |
| 右侧协作空间 | 任务详情增加补充入口与关联操作，默认聚合展示 |
| 原生 Agent 接入 | 保留原身份、模型、工具、工作环境和历史，不改成模型 API 托管 |

本轮不重做整个聊天产品，不创建通用审批系统，也不把所有普通聊天改造成固定工作流。周期性运营的调度能力与一次性的准备任务需要区分，具体排程方案尚未在本轮定稿。

当前代码已有任务分组、需求版本和结果核对等基础；本方案要求的自动关联卡片、双输入入口、明确的重复任务归并，以及完整的多任务接续，仍属于本轮产品设计与后续实现范围。不能将既有父子分组当成全部合并逻辑已经实现，或将运行端会话绑定当成每个任务都能真实并发。

## 11. 拟议验收场景

这些是后续验收目标，本轮只整理文档，未执行开发或验收。

| 场景 | 应有表现 |
|---|---|
| 群聊直接提出明确需求 | 对应 Agent 输出关联与理解卡片，自动推进，无须先确认任务 |
| 确有影响行动的歧义 | Agent 在正常聊天中澄清，然后整理意图和推进 |
| 用户纠正理解或关联 | 原始补充保留，可见地更新相关任务并继续接续 |
| 用户在侧栏补充并 @ 一位成员 | 当前任务已关联，群里出现同次输入的卡片，由指定成员处理 |
| 用户在侧栏补充而不 @ | 沿用所在群的默认负责人规则，不向全群广播执行通知 |
| 同一目标多次补充或重复建任务 | 归并到正确事项，保留历史及成果，不重复执行 |
| 同一业务里出现不同交付目标 | 分别保存任务及其成果，需要时建立关联，不因主题相近错误合并 |
| 结果在归并后迟到 | 正确归回原工作及当前主任务，旧引用仍可追溯，不重复执行 |
| 同群有多个并行目标 | 各自进展与成果正确归属，不因名称相似混合任务 |
| 一个任务等待或阻塞 | 其他无依赖任务继续推进，不形成全群暂停 |
| 多个任务共用不可并发原生会话 | 明确显示运行端排队，不伪装实际并发；其他可用执行者继续工作 |
| 普通问答后来产生持续工作 | 保留原消息来源，接续已有任务或转为新任务，无需用户先选择消息类型 |
| 用户在成员执行期间修改要求 | 受影响工作获得变更，旧成果不冒充完成新要求，有效工作保留 |
| 用户连续补充多次要求 | 全部补充归入当前有效意图，只调整受影响节点，不将任务自动暂停或清空已有进度 |
| 用户询问状态或插入普通问答 | 正常回答，任务继续，不将一次对话回应当作任务暂停或结束 |
| 某项补充需要用户澄清 | 只等待依赖答案的工作，其他独立工作继续；答复后自动接续 |
| 需求变化时旧执行稍后回传 | 保存真实成果和依据，复用有效部分、调整受影响部分，避免丢成果或误报新版完成 |
| 必要成员迟回或离线 | 保留真实等待与工作状态，负责人报告阶段结果和缺口 |
| 意见冲突 | 保留差异与依据，由负责人处理或提出具体待决问题，不把未反对写成一致 |
| 准备阶段形成结果 | 主动总结准备是否完成及下一步，不提前把用户推到发布选择 |
| 通知或网络重试 | 同一次补充、关联卡片和接续不重复产生业务工作 |

内容、研究、开发等不同任务均应覆盖；评估目标遗漏、错误关联、无依据完成、需要用户催促的次数，以及新增流程带来的实际耗时。协议测试、界面测试和原生 Agent 的真实协作效果分别记录。
