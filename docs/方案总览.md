## 一、怎么走到这个方案的

| 阶段 | 结论 |
|---|---|
| 找方向（Xduola 文档 1～22） | 试过编程 Agent 配套、多 Agent 管理工具、视频、GEO、获客等，按"能长期做大"的标准都不理想 |
| 你的想法 | 各家都在做个人 Agent，能不能聚合到一个工作台，让它们协作 |
| 可行性（文档 23，已修订） | MCP 提供工具入口，不代表会主动开工。优先验证账号实际可用的官方触发；没有入口时用本地浏览器代发任务、收取结果；真实接力尚待验证 |
| 扩展（`支持的Agent.md`） | 标准 MCP 可复用，但权限、后台能力和浏览器页面需逐家实测；浏览器路线需要各平台适配器。Claude Duet 你决定不做 |
| 需求（`需求场景.md`） | 一人公司是真潮流；各家的区别是"握着哪个生态"；跨生态的事天然要接力 |
| 你的两个纠正 | 订阅不是障碍；**最大的问题是"打开了不知道怎么搭"** |
| 复用（`复用的设计逻辑.md`） | 借鉴 Sintra、Marblism、Lindy、Paperclip：按岗位组织、公司档案、分步上手、例行工作 |

## 二、方案一句话

**一人公司的 AI 团队：把你已经在用的大厂 Agent 按岗位组成团队，跨生态接力干活。工作台先帮你把团队搭起来，再帮你派活、盯进度、收结果。**

## 三、解决什么问题

1. **不知道怎么搭**（最大的）：该让哪家干什么、在哪里设置、跟它说什么。→ 首次使用向导，目标 20 分钟内搭好，实际耗时尚未测得。
2. **跨生态只能自己当中间人**：X 在 Grok 手里、Gmail 在 Gemini 手里、Instagram 在 Muse 手里。→ 工作台当中间人，它们接力。

## 四、用户拿到什么

| 东西 | 是什么 |
|---|---|
| 首次使用向导 | 安装客户端 → 选要做的事 → 在专用浏览器连接已有账号 → 选择该账号下的 Agent/岗位 → 定规则 → 试跑；无需用户搭浏览器、手配 MCP 或搬运结果 |
| 公司档案 | 业务、客户、语气、目标、禁区，讲一次，所有 Agent 都知道 |
| 团队 | 4 个岗位：社媒经理、行政助理、获客、内容核实；每个岗位交给握着对应生态的 Agent |
| 同类多成员 | 所有已适配平台都可重复添加成员及账号，跨平台混合组织；成员各有名称、岗位、任务与结果归属。同账号多原生 Bot 按平台能力支持，不将重复网页冒充 Agent |
| 例行工作 | 比如每天 08:00 出一份 X 内容包；平时不打扰，只在要你确认时找你 |
| 接力任务 | 跨岗位、跨 Agent 的多步任务，例如：Grok 抓热点 → Dots 核实 → Gemini 写稿 → Muse 改 Threads 版 → 你确认 |
| 确认中心、时间线 | 所有要你点头的事在一处；每一步谁做的、交了什么都有记录 |

**适合：** 跨生态、重复发生、可以后台执行的事。任务就绪后主动触发，实际开始和完成耗时由实测确定；不承诺即时完成。

## 五、怎么实现

- 工作台、任务队列和接力状态按 Cloudflare Workers + D1 设计；费用随实际调用与存储核算。
- 第一版固定本地客户端管理专用完整 Chrome/受支持完整浏览器，由产品准备依赖并管理工作窗口、账号资料目录和恢复。用户安装客户端后首次登录各家账号；不默认采用普通 WebView，也不要求用户自己配置 Chrome 扩展、CDP 或目录。
- “专用”指普通完整浏览器的独立账号资料和产品管理，不等于指纹浏览器；无需购买指纹浏览器服务，指纹伪装不属于当前方案。
- 登录按账号隔离：10 个独立 Muse 账号对应 10 份互不串用的登录资料；一个 Grok 账号下的多个原生 Bot 可以共享该账号登录，每个成员仍绑定自己的 Bot/会话身份。平台若不支持同账号多个原生 Agent，就走多个已有账号，不伪造分身能力。
- 官方 API/webhook 在当前账号可用时优先；派发和结果回传分别检查。没有适用入口的平台，只有确认访问方式可用于该产品且适配通过后，才启用扩展操作专用会话。定时自查单独标记。
- 原生连接使用标准 MCP 或平台自定义连接器；浏览器采集回传单独标记，不冒充原生工具写回。
- 会话凭证留在本机；工作台会接收任务和结果，不能宣传“所有数据都不离开电脑”。登录态、验证码与平台必要批准仍需本人处理。
- 专用浏览器只在用户主动查看、登录或必要批准时展示，不抢日常 Chrome 或系统输入。后台模式、页面休眠与恢复仍需验，不承诺永不暂停。
- 平台通过可扩展的适配器注册；平台列表不是 Grok/Muse 的硬编码分支。新增平台需要登录/身份、触发、交付和能力验证，不能只改名称就宣称兼容。
- 已连接成员数与执行并发分开：成员和账号数量可扩展，测试数量/平台组合可配置；浏览器按任务启停并限并发，不让所有已连接账号的浏览器始终常驻。实际可用容量与并发根据资源和实测报告。
- 同账号额度、配额错误按账号统一管理；一个账号失效只暂停关联成员。已有任务保留身份与结果，不能偷偷换账号、串单或自动增加付费。
- 本机睡眠、断网或客户端执行端退出时，本地步骤暂停；用户关闭平时的 Chrome 不应关闭产品的专用执行环境。官方云端任务另外追踪，恢复后先核对原任务再重试。
- 平台接入门槛已发现实质差异：OpenAI 官方触发 API 暂不返回回答正文；公开个人服务条款限制自动提取输出，不能默认用抓网页替代原生回传。详见验证文档第 11 节，不把四家网页一律自动化作为已成立方案。

## 七、竞争和定位

| | 我们 | AI 员工产品（Sintra、Marblism） | Paperclip |
|---|---|---|---|
| Agent | 用户已有的大厂 Agent | 自己造的 | 用户自己部署的 |
| 优势 | 最强能力，天生连着用户的账号；不用懂技术 | 开箱即用 | 能直接调用，控制力强 |
| 弱点 | 控制权在大厂；网页与登录可能变化；本地执行依赖电脑在线；护城河要自己积累 | 能力和能接的工具有限；额度和退款被诟病 | 要懂技术、自己部署 |

## 八、风险（按大小）

1. **接力是不是真的比"一个 Agent 全做"好**：决定产品有没有价值。第 1 周对比。
2. **各家实际能不能接上、叫醒能不能用**：M0 实测。
3. **20 分钟能不能搭好**：决定读者会不会半路放弃。
4. **Agent 会不会照做**：靠实测过的接入原话 + 时间线兜底。
5. **大厂改规则、Paperclip 跟进**：差异放配置里；靠档案、模板、接入体验积累壁垒。

本轮补充的关键产品要求（细则见 PRD 4.4、开发文档 1.4、验证文档第 14 节）：真实 Agent 入口与能力分开核验；成果按清单验收；上下文与反馈有版本；共享资源避免并发覆盖；暂停/取消必须反映平台实际状态；登录/额度按账号局部处理；安装更新不破坏会话；用户可看清资料发送范围、导出成果并删除产品数据。上述均是设计要求，尚未实现或实测通过。

## 十、需要你做的

1. 使用时说明想完成的工作、时间及需要确认的动作；分工由模板和已验证能力推荐，不要求先理解每家接口。
2. 安装客户端，在产品的专用完整浏览器里首次登录每个需要接入的账号；同账号下多个原生 Bot 不要求重复登录。已有日常 Chrome 登录资料不偷偷复制过来。
3. 本地步骤运行时保持客户端执行端和电脑在线，必要时处理验证码、平台批准。方案审查、适配、测试和维护由开发者完成，不交给用户自行排查。
4. Cloudflare 已有授权，不重复索取；云端托管以后另行启用。
