# 自由沟通改版：交付与验收记录

执行依据是 `协作底层原型方案.md`，不再把普通消息转成旧 run/step。原有账号、登录、文档和历史没有重建。

## 用户规则

- 负责人是通用产品中的群设置：由用户选择、随时可换，也可暂不指定。
- 更换负责人不更换账号、不清聊天、不作废正在回应的通知。原负责人及其他成员仍可发言、互相 @。
- 群成员独立增删。移出群不删除账号或登录；执行中移出会明确提示等待当前回应完成。
- 群聊是默认入口。文档、事项、会议、决定、知识是按需使用的工具，不规定发言顺序、岗位或执笔人。
- 旧工作区通过只读历史入口回看；继续沟通可创建新群，不重跑旧编排。

## 已实现

独立频道与持久消息、分页历史、回复引用、@ 选择、私聊、用户管理群成员和负责人；真实成员身份写入，非群成员不能读写。

投递有持久未读、平台受理、真实领取和真实回传之分。忙时合并未读而不丢消息；同一账号仍受资源锁约束。普通 Agent 发言不广播唤醒所有人，需要行动才定向 @；达到可调跳数限额保留消息并允许继续。

共享 Markdown 文档有版本、作者和乐观锁冲突检查，可编辑、复制、导出、建议修改和交付固定版本。用户决定返回群消息并再次唤醒提问者；等待用户时释放当前通知，防止原租约阻挡后续回答。知识经用户批准后才带入成员上下文。会议和事项与工具读写同一份数据。

Grok 现有回传工具可将明确的 `@本群唯一备注名` 解析为通知；不匹配群外、重名、代码和引用。结构化工具可显式传空 mentions 避免通知。记录保留 `mentionsFromText`，不把兼容路径冒充新工具调用。

## 2026-11-02：专用浏览器退出与主动关闭

修复位于通用运行层，不按用户、账号或机器写特例。启动失败会等待已归属 Chrome 退出；软件退出和账号关闭会等待正在启动的实例，拒绝迟到的打开请求；CDP 断开仍保留进程归属，并优先请求 Chrome 保存退出。单个手动窗口退出失败不阻止其他窗口回收。发信号前重新核对 PID、绑定的浏览器可执行文件、专用资料目录和调试标记，不关闭日常 Chrome 或未知进程。

用户主动点击“关闭专用窗口”后，自动恢复暂停并持久保存；普通轮询、软件重开不会重新拉起，明确打开或连接才恢复。正在执行或验证的账号拒绝关闭，以免打断任务。登录资料、成员绑定和原生 MCP 授权保留。后台会话确有需要时仍可存在；无窗口不等于进程卡死。

验收：`npm run deliver:local` 包含 124 项单元检查、`tests/browser-lifecycle.mjs` 和既有登录保护门槛，再打包并启用真实安装包。新增真实 Chrome 隔离测试覆盖失败启动、单账号关闭/整体退出与启动竞态、断开后回收及连续 3 轮会话 Cookie 保留；暂停状态覆盖重启持久化、多账号隔离和轮询竞态。证据见 `evidence/browser-lifecycle.json` 与 `evidence/activation.json`。这些是工程和隔离登录标记验证，不代表商业平台永不过期。

开发用 Codex Chrome 调试配置是本机配置，和上述产品源码修复分开；不能将本机设置当成产品通用交付。

## 2026-11-02：普通消息时延修复与原生唤醒限制

长期协作方案已发布到 Issue #22。共同现状、变化关注和交接等新增管理能力仍是方案，不以本轮时延修复冒充实现。

已修复三处 Hub 调度问题：用户消息不再等待 Agent 自动连续唤醒的 60 秒间隔；同成员已有待领取通知时合并未读，避免重复启动原平台运行；忙碌成员跳过投递不再占用本轮实际投递名额。保留 Agent 自动连续唤醒设置、账号资源锁、平台重试要求和全部登录资料。界面区分等待投递、等待平台唤醒、正在处理，等待状态只关联本次仍待领取的通知。

工程回归：新增 4 个调度回归案例，全量 128 项检查通过；真实安装包经过资料保护、退出重开和启用校验。Worker 已部署版本 `689e57a1-f289-4045-9c94-26c57414d23d`。证据见 `evidence/conversation-latency.json`、`evidence/activation.json` 和 `tests/conversation-latency.test.mjs`。

真实原生联测尚未通过即时沟通验收。历史样本 Dot 用时 60.599 秒（发消息到领取 49.891 秒、领取后回传 10.708 秒）；本轮 Dot 用时 54.229 秒（领取前 42.225 秒、领取后 12.004 秒）。同轮 Grok 接受唤醒后约 117 秒仍未领取，测试群超时归档，未发第二轮消息。Grok 自动化运行记录可见对应 webhook 运行，并返回 list_work 无待领取工作；页面仅显示分钟级时间，不能据此断定它是在测试归档前还是归档后查询。

Hub 的 sendingAt 是开始投递时记录的逻辑时间，不能视为平台实际受理完成时间；dueAt 还会改写为后续重试时间，不能用投递后的值计算最初排队耗时。平台内部调度、初始化和工具调用各占多少尚未查明。不同时间的少量样本不能计算提速比例，也不能承诺稳定秒回。

本轮结论：Hub 人为等待和名额阻塞已修复并启用；原生平台唤醒到领取的长等待仍是未解决缺陷。未改用其他模型、网页自动代发或轮询用户登录来掩盖它。
