# DuolaWork 全局体验与会话调度审查

日期：2026-11-06。范围：当前 conversation-first 实现、桌面连接器、VPS 原生接收器、聊天和侧栏。正式发布不在本轮范围。

## 产品原则

一个账号可以同时处理多段原生工作对话。Hub 群绑定到哪段原生对话，就把工作送到那段对话；不以账号为单位给所有群排一个队，也不凭空替用户新建或改绑对话。多个群主动复用同一段对话时，仍然顺序处理。

消息发送结果、连接可用、原对话是否忙、Hub 工作是否完成，是不同事实。界面只显示实际观察到的状态，不能用“已连接”冒充“空闲”，不能把排队显示成离线，也不能把负责人尚未跟进显示成自动修复中。

## 已定位并修改的缺陷

| 问题 | 实际原因 | 本轮处理 | 验证 |
|---|---|---|---|
| 发送后消息消失，几秒后再出现 | 发送前开始的 GET 晚到，覆盖 POST 成功后的画面 | 成功回执保留到列表确认；拒绝倒序读取结果 | 修复前浏览器复现失败，修复后持续可见且无重复；MessageSnapshots 单测 |
| 秘书也可能吞掉刚交办的内容 | 已有轮询时 load 直接返回，发送端却移除临时记录 | 收到真实列表记录前保留发送成功的回执 | 实际浏览器延迟旧轮询、断网和重开重试 |
| 同账号只能并行两段对话 | 连接器写死 capacity=2，无平台能力依据 | 删除固定两段上限；保留同一原生会话互斥 | 三段独立会话同时进入执行；第四个群共享其中一段，不重复启动 |
| 某些旧连接仍按账号串行 | 原界面回复在后续 tick 才结算，未进入按会话调度 | 已完成验证的连接在派发前迁移，现有在途工作先核对 | 原互动接收器已验证/未验证两种路径 |
| 首次长任务或项目读取慢时显示离线 | 运行端心跳 await 原生执行或目录读取 | 心跳、目录读取、长任务分开；关闭时仍等已有任务结束 | 真实 HTTP + 挂起原生执行和目录读取的隔离测试 |
| 已排进原对话却被显示离线 | 远端心跳状态白名单漏了 syncing | 保留排队状态，不降成 offline | 远端状态 API 回归 |
| 多会话的投递状态不准确 | 前端只读账号根状态；远端未上报分会话执行 | 按准确 turn 读取绑定对话的回执；远端上报绑定范围内状态 | 精确 turn 匹配、跨群不误匹配、完成后清理状态 |
| 多会话下 CLI 权限/接收器识别不一致 | Hook 只查看账号根记录，漏掉 executions | 同时识别各原生执行；仍只授权当前 Hub 工作 | 原生 Hook 作用域、后续人类工作不继承权限、已管理对话不重复挂接 |
| 一个桌面对话找不到，整个账号所有群都显示离线 | DeepSeek/Antigravity 桌面管理器以任一缺失判整个成员失败 | 缺失定位到该对话，其他对话继续；不创建替代对话 | 可用与缺失两段并存、恢复后原地可用 |
| 负责人无法更新其他人的进行中 Todo | 所有 doing 更新都被当成 accept | 进度编辑不变更执行人和首次接手时间；接手仍按执行人校验 | 负责人/执行人更新与越权接手回归 |
| 桌面更新后误以为 VPS 也更新了 | 没有远端版本回执或更新入口 | 程序内容版本随心跳上报；连接页可直接通知 Agent 自行更新，复制说明作为离线备用，收到新版回执才消失 | 旧版本提示、新版本消失、不新增配对码、不重登录 |
| 负责人核对已停下仍在“自动处理中” | review_incomplete 仍被归到自动处理区 | 单独显示“待负责人跟进” | 状态来源及界面检查；不伪造后台继续执行 |

## 其余模块核查结论

| 模块 | 当前规则及审查判断 |
|---|---|
| 路由与 @ | 用户未 @ 发给指定负责人；显式 @ 优先；普通聊天不自动继承会议。继续保留。会议状态与 @ 另有专项回归。 |
| 会议 | 负责人通过真实工具发起/结束；人类可随时停止。不会从“完成了”之类话术推断会议结束。 |
| 工作项目与对话 | 先选可辨识项目，再选已有/新建对话；能配对当前对话的形态展示配对入口。新群不偷偷继承全局旧会话。 |
| 原环境忙时更换绑定 | 不能把执行中的同一对话改指向另一个项目。原工作完成后可更换；不应阻挡其他独立对话执行。 |
| 资料 | 文件夹、文档/文件/链接、版本引用、删除和回收的边界保留；删除不应悄悄令历史版本引用变成另一份内容。 |
| Todo | 指派、接手、进度、阻碍、结果与会议关联仍有价值；不把“已指派”当作“已完成”，不以消息数量算完成率。 |
| 记忆 | 共享记忆的来源、批准、修改、停用和检索范围要有实际记录；它不等于每家 Agent 原生私有记忆。现有单测可验证权限/版本，不能替代实际长期使用效果评估。 |
| 秘书 | 全局委托独立于某一个群负责人；可以汇总跨群情况，不能拿缺少记录的项目推断成已完成。 |
| 连接与升级 | 账号登录、Hub 授权、对话绑定、运行端版本分别保留；升级不清凭证、项目或会话，不伪造新成员。 |
| 重试 | 发送使用同一 requestId 去重；执行结果不明时先核对，不批量重放可能已经执行过的任务。 |
| 执行环境 | 本机 Agent 继续在本机，VPS Agent 继续在 VPS；共享资料走 Hub，不因为入群获得另一台机器的本地环境。 |

## 保留的边界及仍需改进之处

1. **同一原生对话顺序处理有必要。** 不同群可选择不同对话并行，但如果刻意选择同一段，不能承诺并行。平台实际限流和机器资源不足仍可能造成等待；本轮没有伪造模型的并行能力。
2. **绑定变更期间仍有短暂调度锁。** 用于避免用户选新对话时工作误送到旧对话。已收窄到正在变更的聊天及所涉及的原生对话，其他原生对话继续派发。服务器准备/提交期间也禁止该聊天领取，提交时原子更新绑定，迟到的旧绑定同步不能覆盖新选择。
3. **自动消息流量保护仍是粗粒度判断。** 取消了 5 分钟累计 60 条就交给负责人处理的规则。现在只有同一分支在 10 秒内密集发送超过 20 条定向自动消息时，超出部分进入持久队列，短暂等待后分批自动投递，不进入人类待办或异常复核；用户新消息独立。第三次完全相同的请求仍交负责人核对，防止重复执行副作用。旧暂停记录没有被批量重放。流量判断只用于技术退避，不判断讨论有无价值。
4. **负责人是否理解完整需求是行为问题。** 路由正确、消息不丢、讨论能继续只是基础；必须通过实际需求对齐与交付验证。不能把本轮调度测试算成“所有负责人不再漏需求”。
5. **远端升级有实际边界。** 新版接收器包部署到 Hub，不会自动改写用户 VPS 的程序。连接页“让 Agent 更新”通过已有工作对话发送维护要求，复用授权，等待当前工作结束后切换；只有远端报出新版版本，才算该连接已升级。原环境离线无法收取通知时，仍可复制说明在原 Agent 中执行。Claude 独立连接器本轮未操作。

## 验收与交付口径

- `tests/message-refresh-ui.mjs`、`tests/secretary-desk-ui.mjs`：真实浏览器 + 隔离 HTTP 服务。
- `tests/experience-ui.mjs`：模拟发送接口延迟 2 秒，验证输入即时反馈、切群草稿、阅读位置及无重复。一次与其他浏览器测试并跑时 p95=234ms 未通过；独立复测 p95=16.2ms。两个结果均保留，不把本机空载结果当线上 SLA。
- `tests/coding-session-concurrency.test.mjs`、`tests/chat-sessions.test.mjs`：调度器与后台协议验证，不冒充三个真实模型并行完成。
- `tests/remote-runtime.test.mjs`：原授权复用、版本回执、会话状态、心跳独立于长任务，隔离协议验证。
- `tests/antigravity-cli-bridge.test.mjs`、`tests/dsh-manager.test.mjs`：原生适配器作用域和故障隔离。
- 打包与启用仍须通过 `npm run deliver:local` 的登录资料保留门槛；上线证据单独记录。仅编译或单测通过不能称为实际已生效。

当前生产 Gemini2VPS 的只读绑定检查显示：项目组、X内容、ATEL 对应不同原生会话；单聊与项目组共享一段。这是现有绑定事实，不是模型执行验收。本轮没有擅自修改这些绑定。

## 远端更新与原生执行补验

随后将更新入口简化为“让 Agent 更新”：通过该成员已有的工作对话发送版本明确的更新说明，运行端复用原授权安装并等待当前工作结束后切换。服务端按更新版本去重；必须收到实际新版心跳，界面才移除更新提示。离线环境保留复制说明入口，不能把无法收到的通知标成完成。当前普通聊天中的一句“更新”仍由原 Agent 理解执行，不做关键词强制拦截。

真实 Gemini2VPS 验证发现两处仅靠模拟测试没有暴露的问题：

1. 更新时在途工作保存在分会话记录中，启动逻辑却只检查账号根记录，造成错误地重新连接并进入重启循环。已修复为保留、核对各原生会话的真实回执。第一次遇到此错误时由维护者仅修复 Gemini 接收器；不能把这次人工修复写成自更新成功。
2. Antigravity CLI 的前台请求结束不代表它的后台命令结束。三段原生会话的实际 25 秒命令同时执行，但接收器过早撤掉回传上下文，导致后续原生回复被拒绝。已改为保留原进程、原会话与领取，等待真实 Hub 回执；不另起模型轮次，不重跑已完成命令。异常结束后的新用户消息可以继续同一对话，不自动重放旧失败任务。
