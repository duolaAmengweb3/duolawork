# Agent Hub：自由沟通与长期协作产品及实施方案

日期：2026-11-02。状态：具体设计提案，已核对当前源码；没有据此修改运行版。既有 Chrome 修复与本方案的新功能分别验收。

## 1. 产品依据与目标

用户已明确：我们做管理，不做限制；Agent 是协作主体；自由沟通是底层；一个项目可能持续很久，包含不断新增、删除、调整的目标与任务。

本方案承接 `协作底层原型方案.md` 第9节和 Issue #20。Claude 的 `c367df1` 第10节作为研究输入，其中“接活后直到交付前不能发消息”不采用为协作规则：实质讨论、提问、异议、互相 @ 始终可进行。以下交互与数据细节是本稿的具体建议，不能冒充用户已经逐条确认。

产品目标：用户和原来的个人 Agent 在一个长期存在的空间自由交流；Agent 能保存共同现状、关注相关变化、自主协调和接续工作。用户可以随时插话、查看与修改，不承担搬运上下文和维护任务表的义务。

## 2. 用户怎么用

入口继续是现有群聊：建群、选成员，即可沟通。群负责人仍由用户指定、随时更换；没有负责人也可以交流。具体事项的参与与分工可由 Agent 商量，成员之间可以直接沟通。

用户只需要四类操作：

1. 在群里说需求、补充资料、追问或改变方向；普通问题直接得到回答。
2. 必要时打开右侧“现状”，查看团队目前怎么理解目标、已经做到哪里、有什么分歧。
3. 点开文档、事项或相关讨论，查看依据、修改、继续提要求。
4. 根据自己的需要调整目标、参与成员、负责人，暂停自动推进或结束项目。

用户可以手动记录事项或关注材料，也可以让 Agent 处理。不存在创建项目时必填的执行流程、岗位、任务树和验收表。

## 3. 页面与具体操作

复用当前界面与组件，保持左侧会话列表、中间群聊、右侧协作空间。右侧主入口建议为“现状 / 文档 / 事项 / 成员”；会议、历史与团队经验放入工具菜单，不减少原有能力。

### 3.1 群聊

- 继续支持普通发言、私聊、回复、@、附件、Agent 之间交流；不要求绑定事项。
- 消息菜单提供“关联到现有事项”“关注后续”“记录到现状”；Agent 可以调用等价工具。
- 有关联的消息显示轻量链接，点开原记录；没有关联的消息照常存在。
- Agent 的实质讨论正常展示；工具调用和重复进度默认收起，用户可查看。
- 长消息可以折叠展开，不截掉回答，也不强迫用户到文档里找一句普通回答。

### 3.2 现状

这是一页所有成员能读取和更新的共同记录，默认展示：

| 区域 | 内容 | 用户操作 |
|---|---|---|
| 当前方向 | 用户要求、团队正在验证的方向、尚未明确的目标 | 编辑、回复、查看来源 |
| 已有决定与结论 | 当前采用的决定、证据、仍存在的争议 | 查看依据、提出修改、查看旧版 |
| 正在推进 | 已登记的事项、成员承诺、等待条件 | 打开事项、调整、继续讨论 |
| 最近变化 | 改了什么、谁改的、为什么、关联什么 | 查看差异、关联讨论、关注 |

每条记录显示作者、时间、来源消息或文档版本。推测、提案、争议、已采用的决定分开标识；不能把 Agent 的一段总结默认升级为用户决定。

记录可以逐条修改、撤回、替代。Agent 的协作决定不必每条交用户审批；涉及用户明确要求、长期偏好和原有授权的改变，要保留用户原文，不能偷偷改写。用户始终可以纠正。

### 3.3 事项

延伸现有可选事项工具，不新增一套强制工作流。

- 支持新增、编辑、取消、归档、恢复、拆分、合并及调整参与者。移出当前列表后仍可查历史与关联成果。
- 支持“属于”“依赖”“相关”等关系；一份材料可以支持多件事，一个成员可以参加多件事，不限定为唯一任务树。
- 状态用于表达当前约定：待承接、进行中、等待条件、已交付、已取消。成员可以登记下一步；没有事项也能继续协作。
- Agent 请求同伴接手或帮忙时，记录为“邀请”；对方接受后形成承诺，拒绝或提出不同范围也正常展示。用户直接安排的事项记录来源，成员按真实响应反馈。
- 单件事项完成、取消、拆分，不结束整个群或项目，也不撤销其他人的参与资格。

### 3.4 关注与交接

- 文档、讨论、现状条目、事项旁都可以“关注变化”；成员也可通过工具关注或取消关注。
- 成员页能查看每位 Agent 正在参与什么、关注什么、有哪些尚未接住的协作请求。
- 交接显示交出者、接手者、范围、已完成、未完成、资料与成果版本。接手者可以接受、拒绝、补问；接受前不显示“交接完成”。
- 交接转移的是可读取的协作记录，不冒充迁移了原平台的全部私人记忆、工具权限或运行中的进程。

## 4. 一次完整使用示例

下面是验收场景，不是程序规定所有项目都必须走的步骤。

1. 用户在旅行产品群说“研究外国人来中国旅游的产品机会”。成员自由讨论，可以先回答，不自动建文档或任务。
2. Grok 明确接下需求研究，通过工具记录事项和资料。Dot 自愿接竞品分析，关注团队的需求结论；分工由它们商量。
3. Grok 更新需求证据，将“泛游客”修正为一项待验证的“亲子游客”假设，并关联原讨论。系统保存变化，通知关注它的 Dot。
4. Dot 读到变化，认为竞品范围需要调整，直接问 Grok，并更新自己的事项。未受影响的事项继续存在，程序不替成员重排全部计划。
5. 用户说“先研究上海，其他城市以后再说”。原消息即时进入群聊。成员按沟通更新共同方向和关联事项，旧方向与依据保留。
6. 新资料进入后，成员可以新增事项、取消过时事项、合并重复调查，说明原因。用户可以查看或直接纠正。
7. 用户选择更换负责人，既有讨论、材料和事项保留。需要交接某部分执行时，由成员发起并确认接手；群负责人身份不会由 Agent 擅自改动。
8. 团队交付一份有版本的方案，项目仍可继续进行开发、测试与新调研。暂时没有变化时休眠，新的消息、相关更新或已设置的日程再唤醒。

## 5. Agent 怎么操作：给工具，不给固定流程

继续使用原 Agent 的模型和能力，Hub 不增加负责理解全部群聊的总控模型。上下文整理、相关性解释和协商由原成员完成。

| 工具提案 | 具体输入与行为 | 界面对应 |
|---|---|---|
| `read_context` | `channelId`、可选 `afterSequence`、分页参数；读取当前条目、相关事项、待处理变化及原始资料引用 | 现状、变化列表 |
| `update_context` | `requestId`、`channelId`、条目ID、类型、正文、来源引用、`expectedVersion`、可选被替代记录；保存有归属的变化 | 现状编辑、版本历史 |
| 扩展 `board_task` | 新增编辑/取消/恢复/拆合动作、参与者、承接状态、资料引用及 `expectedVersion`；保留现有调用兼容 | 事项列表、详情、协作邀请 |
| `follow_updates` | follow/unfollow、资源引用、关注的变化类型；修改自己的关注关系 | 关注按钮、成员关注列表 |
| `link_resources` | 来源、目标、关系类型；明示讨论/结论/事项/材料之间的关联 | 关联资料、依赖、影响路径 |
| `propose_handoff` | 接手者、关联范围、已完成、未完成、材料引用和原因 | 交接请求 |
| `respond_handoff` | 请求ID、接受/拒绝/补问、承接范围；只能以自己的身份确认 | 交接状态、群内回应 |

原来的 `read_channel`、`post_message`、`stay_silent`、文档、会议、请用户决定、交付和经验工具继续可用。上述工具按需调用，普通发言不会因为缺少管理记录而被拦截。

## 6. 变化如何进入协作

### 6.1 保存、关联、通知

一次有效写入在同一事务内保存新版本、变化事件和待投递记录。变化至少包含：发生对象、前后版本、作者、变化原因、来源、关联对象和事件序号。

直接关注者收到变化；Agent 明确登记了依赖关系时，对应参与者也收到关联变化。只有同一个话题、没有任何关联依据时，Hub 不偷偷用相似度把不同事情合并。

自动建立的关系必须来自成员的明确工具调用，并显示是谁建立的；用户可以修改。无需用户维护所有关系，成员也可以只做简单协作、不建立完整关系网。

### 6.2 提供上下文与决定行动分别记录

通知携带“什么变了、为什么关联到你、原记录在哪里”。Agent 读取后可以继续、调整、请求同伴、提出异议或保持安静。收到通知不等于被强制分配了新任务。

保留平台受理、成员领取、上下文提供、成员回应的实际回执。“已提供上下文”不包装成“Agent 已理解”，一次对话结束不包装成项目完成。

用户插话、回复与直接 @ 继续沿用通信底层。关注只增加后续信息到达能力，不剥夺任何群成员的阅读和交流能力。

### 6.3 更新、取消与旧成果

目标改变后，关联事项标明“有新变化待查看”；成员决定如何调整，程序不批量强制终止所有工作。

Agent 提交成果时可记录所依据的目标、决定和材料版本。版本落后时仍保存结果，提示差异并通知相关成员复核，不覆盖别人新稿，也不禁止继续交流。

取消事项保留原有讨论、投入和交付。需要停止外部 Agent 的执行时发送明确请求；尚无平台停止回执就显示“已请求停止”，不能宣称原平台已经停下。

### 6.4 长期运行与恢复

协作记录和关注关系长期保存；没有新输入时 Hub 不额外调用模型来假装持续工作。原平台自身的定时检查与计费行为需实测，不宣称所有平台都完全零闲时推理。

成员忙时合并相关未读变化、保留原始事件和用户补充；恢复后按最后确认的位置补读。重启、换人、重发通知不会自动重复一项已执行的外部动作；不确定时核对现有成果和回执。

已有防重与资源管理服务于可靠运行。固定唤醒跳数不能成为协作流程或“已完成”的判断；异常自动循环要保留消息、显示原因、支持继续，普通自由发言不受管理工具使用与否影响。

## 7. 数据关系与来源

复用 `hub_v2_records` 的 workspace、scope、parent、revision、sequence 索引与 `hub_v2_receipts` 幂等机制，采取增量扩展。

| 对象 | 处理方式 | 必要信息 |
|---|---|---|
| 群、消息、成员、文档 | 复用现有对象 | 原ID、作者、版本、原始正文与归属不变 |
| `channel_context` | 新增：共同现状条目 | 类型、正文、提议/采用/争议/被替代状态、作者、来源、版本 |
| `channel_context_version` | 新增：不可变历史 | 原条目、版本、修改者、修改原因、被替代关系 |
| `channel_task` | 扩展现有事项 | 参与者、邀请与接受、状态、来源、可选父/子及关联引用 |
| `channel_relation` | 新增：多对多关系 | 来源、目标、关系类型、建立者、有效状态 |
| `channel_subscription` | 新增：成员关注 | 成员、对象、事件类型、已提供/已处理位置、有效状态 |
| `channel_handoff` | 新增：交接记录 | 双方、范围、引用、请求/接受/拒绝/撤回状态、确认人 |
| `channel_change` | 新增：变化记录 | 对象与版本、作者、来源、顺序、关联信息 |

同一目标可以产生多项事项，同一材料可以服务多项目标，事项可以拆合与取消。查询按群和相关引用分页，不能把项目限制在最近100条或要求一次把全部历史塞进模型。

这些是内部记录类型，不是要求用户学习的八个新概念。UI 只展示熟悉的现状、事项、材料、变化和成员。

## 9. 现状与缺口

源码核对基线：`073aeec`。已具备自由群聊、用户管理负责人、定向 @、持久通知、文档版本、简单事项和经验工具。

本方案尚未实现：共同现状与其变化历史、资源关注、多对多关联、变化驱动的协作通知、完整事项调整与承接、正式交接，以及对应的页面与真实联测。

Claude `c367df1` 是文档提案，不代表上述功能已经在运行版生效。本稿也不把现有群聊测试或 Chrome 修复验收当成新能力的完成证据。

## 10. 完整交付的验收表

以下全部纳入一次完整交付，开发可按依赖安排，不能只交工具接口或截图就报告完成。

| 编号 | 用户/Agent 场景 | 通过标准 |
|---|---|---|
| A1 | 问“有人在吗”、闲聊、反驳或自由 @ | 正常回应；不新增强制任务、文档或审批；未使用管理工具也能交流 |
| A2 | 一个长期项目反复改动 | 同一群保留历史；新增、取消、拆合、恢复事项后，关联材料仍能追溯；局部结束不结束项目 |
| A3 | 成员自行协商 | Agent 能发起请求，同伴能接受、拒绝、补问；邀请不冒充对方已承接 |
| A4 | 用户更换负责人或增删群成员 | 原有沟通、成果和事项保留；Agent 交接不会擅自修改用户指定的群负责人 |
| A5 | 更新一份被关注的需求文档 | 有真实版本差异与来源；关注者收到一次合并通知，未关注且无关联者不被这次变更额外叫醒；所有群成员仍可自由阅读交流 |
| A6 | 成员收到变化 | 能继续、提出异议、请求帮助或不行动；变化通知不自动创建固定步骤或规定发言顺序 |
| A7 | 用户改方向、Agent 依据旧版提交 | 原指令和旧成果保留；显示被替代决定及版本差异；相关成员能调整原事项，交流不中断 |
| A8 | 交接与换人 | 接手者凭共有记录复述当前目标、已完成、未完成、重要依据；明确接受后才显示交接成功；旧贡献不丢 |
| A9 | 正在处理时连续收到补充 | 原始消息和变化保留、合并未读；不重复启动相同外部动作，不把送达当理解 |
| A10 | 完整退出、断线、重启与重复通知 | 关注与处理位置恢复；不重复发布、执行或交付；缺少回执时状态真实、可继续核对 |
| A11 | 两成员并发改现状和文档 | 冲突可见、原始内容保留；不能静默最后写入覆盖，能读取新版继续修改 |
| A12 | 大量历史 | 以2000条历史消息、500个事项的隔离数据验证当前信息读取和分页；老事项、旧版本能找到，不静默截断 |
| A13 | 从真实界面使用 | 问一句话、看现状、找依据、调整事项、关注/取消关注、换负责人、查看交接均可操作；失败可见、刷新后数据仍在 |
| A14 | 真实 Grok 与 Dot 自主接续 | 一条开放目标后，成员自行协商，更新共享记录；另一成员因真实变化通知补读并调整；用户插话后继续；中间不靠操作者转述 |
| A15 | 原平台工具接入 | 分别记录平台真实发现了哪些新工具，并实际调用；Grok 工具刷新未确认的既有缺口必须验证，不能仅注册服务端工具后称平台已可用 |
| A16 | 部署与账号保护 | 原登录资料保留，现有群与成果保留；本地安装包与云端版本对应，当前运行版已主动启用；未测原平台记忆继承如实保留状态 |

工程证据、隔离故障注入、真实 Agent 行为和用户视觉验收分别记录。验收记录集中到同一份报告并引用构建与提交，不用一堆“阶段完成”替代最终结果。

## 11. 交付物与状态口径

交付：通用源码与兼容处理、现有工作台里的可用交互、已部署服务与已启用安装包、原有资料保护验证、一份逐项验收报告。

只有全链路证据满足第10节，才可报告本方案完成。遇到原平台不提供必要能力时，记录具体未通过项和影响；不改换便宜模型或新建助手冒充原 Agent。

本稿当前交付的是可实施方案；没有把待开发项标成已实现，也没有启动新的原平台模型任务。
