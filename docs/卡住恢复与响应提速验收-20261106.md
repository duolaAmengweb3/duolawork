# 卡住恢复与响应提速验收

本轮直接处理用户报告的 Gemini 长时间卡住、Claude VPS 连接器未实际升级，以及“不同群拥堵”和“单次回复慢”两个不同问题。用户已授权实施、服务端上线及原环境验证；不再停留在前一轮方案讨论。

## 结论与当前生效范围

- 桌面和本地服务启用 `ba110400dfbbd714`，服务端更新并核对产物 SHA-256。账号资料、工作区和原生会话绑定保留。
- Gemini 在原 Antigravity CLI 会话恢复了用户消息；更新后的接收器又通过“故意漏回执 → 自动核对 → 实际补回 → 下一条正常回复”的真实验收。
- Claude VPS 保留原会话 `d581eb2c-23e7-4894-a03d-a012a6fbefce`，完成连接器升级和常驻监听恢复，自动接收并回复 Hub 单聊。
- 489 项回归通过。最后只调整资料索引说明，又运行对应 16 项检查通过。原生真实结果及部署证据见 [验收记录](../evidence/receipt-recovery-live-20261106.json)。

## Gemini 为什么会一直卡住

原终端已经空闲，但 Gemini 用旧的通知编号回复群消息；当前领取仍显示处理中，后续用户消息一直排队。不是模型还在推理，也不是所有群共用一个账号就必须排队。

这次修复包括三个环节：

1. 服务端在同一成员、同一群有新领取时，拒绝将旧通知当成本次回复或静默回执，并给出实际待处理编号。幂等重试仍返回原成功结果；没有新领取时不禁止正常补充旧消息。
2. Antigravity CLI 适配层读取精确原会话的真实运行状态。缺状态不能当空闲，权限等待不能当已经完成。
3. 公共接收管理器连续观察到原会话空闲 60 秒而仍缺回执时，先核对服务端，再向同一原会话发送一次“核对已有结果、补交回执”的提示。重启前已持久化恢复标记，避免循环提醒。仍无法收尾时明确标记未完成并释放占用，不伪造成功、不自动重做业务任务。

真实验收在 Gemini 原有单聊完成：#17 模拟只领取不回传，接收器自动触发核对，#18 实际补回；#19 是下一条正常消息，#20 正常回复。整个过程中没有人工补发恢复提示，没有换会话或修改业务文件。验收结束时七段执行会话均空闲，无遗留领取。

## 两种慢分别怎么处理

### 不同群互相排队

调度依据是原生会话身份。不同会话并发，同一会话的多个群按顺序处理，避免两路同时写同一个上下文。项目文件夹相同不等于会话相同；也不能为了提速悄悄复制用户原会话。

现有公共调度及各家适配检查覆盖 1、2、3、4、5、10、17 段，不存在两段或三段的产品上限。真实并发证据已包括三段 Antigravity CLI 和两段 Codex；不能据此声称所有原厂客户端已逐一真实验收。详见 [会话调度验收](会话调度与连接器一致性验收-20261106.md)。

本次核对 Gemini 的 X 内容、ATEL、专用验收群分别绑定独立会话；项目组与 Gemini 单聊有意共用原会话。八项绑定前后比较一致，没有自动替用户换绑。

### 已轮到这一条，回复仍慢

已减少两个可确认的开销：

- Coding 原会话收到明确通知编号后直接原子领取，去掉每次领取前多余的 `list_work` 网络往返。服务端同时验证群、成员与会话绑定，保留跨群和过期绑定拦截。
- 领取结果携带共享文档标题、版本和准确读取入口，相关正文按需读取。用户本条要求、纠正、任务状态和共享记忆不因此丢弃，不能凭标题冒充已读。

同一份项目组实测领取内容，按匹配的九篇文档版本重建旧格式为 383,068 字节，新格式为 248,499 字节，减少约 35%。其中资料部分从 139,615 字节变成 4,747 字节；仍有 182,407 字节近期消息。不能把“资料部分减少约 97%”说成“整体响应快 97%”，也不能声称已实现 20 KB 交接或完整增量上下文。

| 真实简单消息 | 发出至领取 | 领取至回群 | 合计 |
|---|---:|---:|---:|
| Gemini 原会话恢复后下一条 | 12.422 秒 | 15.387 秒 | 27.809 秒 |

## Claude 升级实际做了什么

只替换 DuolaWork 连接器程序，保留原授权、账号、项目和对话。原生 `/mcp` 重新连接使工具端加载新版本，但它不能替换已经常驻运行的旧监听进程；`/reload-plugins` 也没有重启这个已启动的监听器。

中间通过原生 Monitor 工具启动的临时监听只有 30 分钟期限，已移除，未作为最终交付。确认原会话空闲后，使用 Claude 官方 `respawn d581eb2c` 重开这一段后台会话。原生会话 ID 和项目路径保持一致，插件自己的 `when: always` 常驻监听自动启动；任务详情显示运行中，非临时超时任务。随后由 Hub 发出 #1，Claude 自动领取并回到单聊 #2，没有人工点投递。

这证明本次原环境升级和自动往返已成功，不意味着任何 Claude 原厂版本都支持无重启热更新。用户无需重新配对、登录、添加重复成员或手工拼 Hub 启动参数。

## 边界

- 修复的是可验证的卡住原因及接收开销；不声称所有网络或模型故障永久消失。
- 自动恢复只核对这条已领取消息的结果，不跨会话扫描、不自行领取其他工作、不重复执行不明结果的操作。
- 服务端回执约束适用于所有成员；原生空闲检测依赖各平台确实提供的状态，不能将 Gemini 的现场验收冒充其他平台同一故障的现场验收。
