# Agent Hub 会议产品与实施方案

日期：2026-11-03。版本：v0.4（方案审计修订）。整理：Codex。

状态：记录本轮已对齐的产品要求，并细化为可实施、可验收的方案。五种模式的执行细节属于本稿建议；本轮仅写文档，没有据此改造软件，不将方案写完视为功能已完成。

最新确认：保留专门的“开会”入口，打开后先与真实负责人沟通，由负责人理解需求、选择并组织合适的会议方式。此前“先让用户选模式、再填议题和预期”的默认流程被本版替换。用户无需学习会议术语，方法、成员、时间和收尾安排仍然可见、可改。

交互原则：组织和质量机制由负责人及系统执行，人类用户看过程与结果，随时可以参与、改变方向或决策。不得把独立提交、意见公开、核验、推进和归档变成用户必须操作的步骤，也不要求逐轮确认或会后逐项点击验收才能完成会议。

筹备原则：用户可以只有一个模糊需求，先与负责人进行必要的多轮沟通，共同确定本场要解决的问题及交付结果，再正式开会。多轮是一种能力，不是固定要求；信息已经足够就开始，不为了凑轮次反复讨论，也不把负责人单方面猜出的目标视为用户已确认。

## 1. 会议解决什么问题

普通沟通继续在会话框里进行。会议用于用户主动选择的一次集中协作：围绕明确议题，采用指定的协作机制，在有限投入内形成可以检查的结果。

开会前，用户应知道为什么用这种模式、成员会怎样工作、预期交付什么、最多讨论多久。结束后，应看清获得了什么、哪些问题仍没解决，避免多个 Agent 重复附和却不断消耗额度。

会议是自由沟通之上的可选工具。选择某种会议模式，只对本场会议生效；不把所有群消息变成任务，不限制群的日常交流，不固定成员的长期岗位，也不把一场会议结束当成整个项目结束。

## 2. 本轮确认的交互要求

| 项目 | 产品要求 |
|---|---|
| 开会入口 | 打开负责人筹备对话，用户自然表达需求，不先进入选模式和填写预期的表单 |
| 模式 | 负责人按需求选择、组合并说明安排；已有模式作为方法库和可选手动工具，不是用户必答题，各方法有真实不同的执行过程 |
| 参会成员 | 默认沿用所在群的成员配置，需要时再调整 |
| 负责人 | 默认沿用所在群的负责人，需要时再调整，不要求每次重新指定 |
| 时长 | 默认10分钟，用户可修改，不要求每次填写 |
| 会议议题 | 使用“会议议题”这个名称，描述本次讨论什么 |
| 用户预期 | 用户不必在进入筹备时就想清楚，由负责人与用户通过必要沟通共同形成目标和交付约定；用户随时可补充或修改 |
| 收尾方式 | 用户可选择到时结束或负责人总结，也可直接采用负责人筹备时提出的可见建议，不增加必填下拉框 |
| 人类干预 | 用户随时可在对话中明确喊停，也可以点击会议卡片停止 |
| 人类决策 | 用户可随时在普通聊天中表达取舍、作出决定或纠正理解；不限定为某一环节、特定卡片或按钮，不要求每轮到场确认 |
| 会中交流 | 群内出现会议卡片，Agent 的讨论、追问与回应进入聊天并关联本场会议 |
| 会后记录 | 群内保留结束卡，侧栏集中查看完整记录、纪要及未解决问题 |
| Agent 发起 | 用户可以让任意 Agent 代为发起、设置和组织会议；按钮与 Agent 使用同一套能力 |

这里的“用户自己总结”按本轮上下文理解为：用户自己概括预期结果，而不是要求用户会后手工撰写纪要。Agent 可以整理用户原话供修改，但不能悄悄改变要求。会后纪要由 Agent 根据真实讨论整理。

## 3. 与既有调研的关系

主要依据：

- [多Agent协作大团圆病与自进化实证研究](../Agent管理学/调研文档/14-多Agent协作大团圆病与自进化实证研究.md)：明确提出赛马互证、红蓝攻防，以及首轮独立、针对性反驳、保留分歧等机制。
- [协作底层原型方案](协作底层原型方案.md)：会议是自由沟通之上的工具，提过头脑风暴、评审、复盘，以及用户和 Agent 均可发起、读取、结束的要求。
- [Agent管理学方法论](../Agent管理学/方法论.md)：按依赖和互补性组织成员，区分独立判断与共同决定，对照真实结果复盘，不考核形式上的反对次数。

此前没有一份把这些内容统一成完整会议模式库的定稿。本稿将其整理成五种可执行方法，供负责人组织会议时使用，也允许用户展开后手动选择；不能声称原调研已经逐项验证了这五种产品实现。

第14篇中的论文数字、“必然”“唯一正确”等表述，本轮没有重新核验，不作为效果承诺。其旧版全局流水线、固定决策卡和禁止自由交流的设计，不覆盖用户后来确认的自由沟通底层。

## 4. 负责人可使用的五种会议方法

以下是方法库和相应执行建议，不是默认要求用户学习的菜单。负责人用人话说明本场会怎样进行、为什么这样安排、预期产物是什么；方法的专业名称和细节放在可展开的安排里。用户仍可手动选择、补充其他讨论要求或改变安排，不被限定为只能用五个标签表达需求。不把“自由讨论”单列为会议模式。

### 4.1 赛马互证

- **适用：** 同一问题需要不同解法、独立发现或多方核验。
- **过程：** 共享本场议题、用户预期与基础材料 → 各自提交独立意见 → 统一公开 → 针对差异交叉核验 → 整理取舍与未决问题。
- **产物：** 各方原始意见、独有发现、已核验结论、仍未解决的分歧及依据。
- **关键要求：** 第一阶段的意见在本场提交区互不可见，达到公开条件后才释放；不能先读别人的答案再补写“独立意见”。缺席或未完成的成员如实标记，不能补造观点。

### 4.2 红蓝攻防

- **适用：** 已有方案、判断或论证，需要发现关键漏洞并改进。
- **过程：** 提案方提交方案 → 评议方检查事实、假设、推理和执行约束 → 提案方回应、补证或修订 → 汇总仍成立的结论和未解决问题。
- **产物：** 原方案、具体质疑、逐项回应、修订方案及残留风险。
- **关键要求：** 红蓝是本场临时立场，不是成员永久岗位。允许多人承担同一侧；用户可改安排。若群内缺少足够成员或两侧安排尚不明确，界面说明并提供调整，不假装多人攻防。没有发现问题是合法结果，不强迫为了对抗而捏造漏洞。

### 4.3 创意共创

- **适用：** 希望获得多个有差异的点子、产品方向或内容切入点。
- **过程：** 先独立提交想法 → 公开后合并重复点、组合或补充不同方向 → 对照用户预期筛选值得继续的候选。
- **产物：** 有差异的候选、各自价值和适用条件、推荐进一步验证的方向。
- **关键要求：** 合并相似想法不抹掉独特观点；不能把互相称赞、重复改写或机械凑数量视为有效产出。

### 4.4 决策评审

- **适用：** 已有候选方案或待决定事项，需要比较证据、约束和取舍。
- **过程：** 明确待决定事项与用户已有标准 → 各方评议 → 定向补充影响选择的关键证据 → 给出建议、依据与保留意见。
- **产物：** 候选对比、建议及理由、适用条件、尚需用户决定的取舍。
- **关键要求：** 不替用户编造偏好、权重和成功标准；多数同意不等于事实成立。评审可以保留不同建议，不要求一致。

### 4.5 复盘改进

- **适用：** 已经有实际行动、交付或运行记录，需要解释结果、改善后续行为。
- **过程：** 对照原预期与实际结果 → 区分事实、原因推测和证据缺口 → 检查解释 → 提出具体可验证的改进。
- **产物：** 预期与实际差距、原因及证据、改进建议和验证方法。
- **关键要求：** 缺少实际记录时说明缺什么，不凭空复盘。不因会中提出改进就自动改全团队长期规则；规则变更另按用户授权执行。

五种模式都需要有限的环节、阶段期限和自动唤醒预算，执行约束见第9.5节。负责人可组合方法、在剩余预算内安排有价值的补证，不按所有人都必须发言几次来凑轮次。用户可以主动延长、调整或另开一场。

## 5. 创建与默认配置

### 5.1 用户从界面发起

群内工具入口或侧栏“会议”入口 → 与负责人筹备对话 → 负责人理解需求并提出可修改的安排 → 发起 → 回到群内会议卡片与讨论。

入口打开的是本场的筹备对话面板，不要求用户先选择赛马、攻防或填写一组表单。对话对象默认是群里真实的负责人 Agent，沿用其原生模型、能力与订阅，不用固定脚本或额外总控模型假扮负责人。

界面采用右侧筹备对话栏，主群保持可见、可操作。用户与负责人在侧栏必要地多轮沟通，负责人提出的简洁安排卡也留在同一侧栏，底部提供清晰的“开始会议”入口；不另弹配置表、不把全部筹备过程广播到主群。正式开始后，会议卡和成员讨论进入主会话；结束卡及右侧会议档案均可回看结果、筹备原文、安排版本及核验记录。窄窗口使用同一右侧面板覆盖部分主区，关闭即可返回原聊天位置和草稿。

用户可以说：“我想做点AI产品，但不知道做什么。”负责人结合相关群上下文，与用户进行必要的多轮沟通，帮助明确本次会议先解决什么、最后给什么。只追问会改变议题、交付或关键约束的问题；已有信息不重复询问，不逐项盘问表单字段，不要求用户先成为需求专家。

筹备中持续保存并展示简短的目标与交付摘要。负责人可以提出“这次先比较三个可做方向，交一份带需求依据和验证办法的候选清单”，用户可以说“先不要定方向，先把我的条件和机会梳理清楚”。负责人据此调整，不把第一轮的理解定死。

例如负责人回复：“我会让大家先分别判断，再集中核查关键风险，最后整理值得做和不值得做的依据。默认使用本群成员，最多10分钟，由我整理结果。”界面据同一份真实安排显示可修改的筹备卡，而非在用户话外另建一套配置。

筹备卡只需清楚显示：议题清单、本场目标和拟交付结果、参与成员、组织安排、时长和收尾方式。双方理解已经足够时，用户点击开始或说“就这样开”，对当前可见版本的安排发起一次会议；已有明确开始指令且最新目标与交付已经对齐时，不再重复确认。只是在探讨需求、尚未认可负责人理解时，不广播开会。用户仍可调整成员、负责人、时间或收尾方式。

“足够明确”是能说明本场先解决什么，以及准备交付何种有用结果；不要求把所有子问题、最终答案和成功标准事先写完。负责人也可以提出本场以“澄清问题、列出待验证假设及下一步”为交付，交由用户确认这个方向。达到这一步就推进，不继续为了讨论而讨论。

- 议题由用户输入、选中消息或本场沟通带入；不能在没有任何议题时空开会议。
- 用户初始预期可以不明确，由筹备对话共同形成一份可调整的交付约定；没有客观成功标准时不编评分，但仍要说明准备交什么，不把“先帮我研究清楚”当作不合格需求。
- 群没有负责人或负责人当前不可用时，在入口说明情况，允许用户选择本场组织者；不擅自修改群负责人，也不显示假的负责人回应。
- 默认成员中有未连接或忙碌成员时，开始前说明真实可参与情况，不将其显示为已经参会。
- 成员、负责人默认沿用群配置，时长默认10分钟；用户需要时再改。打开筹备入口不广播唤醒所有成员，也不启动正式会议倒计时。会议总时长从正式发起会议、生成开场卡的时间开始计算，包含讨论和收尾；筹备耗时和实际调用另行记录。
- 收尾方式不作为筹备的必填问答。用户没有既有偏好或明确要求时，负责人默认建议“在本场时限内由负责人总结”，并和目标、交付一起展示；用户开始会议即采用这份整体安排，随时可以改成到时结束。
- 实施建议：保存发起时的成员与负责人快照；群配置后来变化时不悄悄改写正在进行的会议。用户可主动调整本场配置，变更保留记录。

负责人承担理解需求、安排方法、邀请与跟进参与者、组织收尾的职责。它不成为每条发言的审批或转发节点，其他 Agent 仍能相互提问、回应和交流；用户随时可插话、改方向或停止。方法可以按本场需要调整，调整后在安排中可见并保留原因，不能偷偷扩大投入。

筹备过程中，每轮负责人都应推动形成更清楚的目标、交付建议或关键约束。连续复述、重新问已回答的问题、扩展与本场无关的问题，都不算推进；如果当前已能合理组织会议，应直接给出开始建议。用户关闭筹备面板时保存已有对话和安排，不后台自问自答；用户再次打开可接着聊。

### 5.2 用户让 Agent 发起

例如：“帮我组织大家研究一下这个产品值不值得做，重点看真实需求和风险。”用户不必在请求中先说出会议模式或流程名称。

受托 Agent 根据用户原话调用筹备与会议工具，必要时与本场负责人协商安排，未特别指定的成员、负责人和时长使用同样的默认值。用户已指定模式、成员、时间或要求受托者主持时，保留其明确要求；没有指定时，由负责人选择合适的方法。用户不需要再去界面填一遍；仅缺少无法从请求或上下文确定的必要信息时才追问。

支持在现有群发起会议。用户要求另开会话时，Agent 可调用创建会话及会议能力，在授权范围内加入指定成员，新会话仍沿用同样的会议交互。发起人不自动成为不可更换的负责人。

## 6. 群内卡片、讨论与侧栏

### 6.1 发起卡片

发起成功后，立即在聊天中产生一张真实会议卡片，展示：

- 议题、用户预期，以及用人话说明的组织安排；模式名称和执行细节可展开查看。
- 参与者、负责人、计划时长与截止时间。
- 当前环节、真实参与情况。
- 查看详情、调整本场、结束会议等操作。

保存会议、发布卡片和准备通知属于同一次可恢复的业务动作。不能只在侧栏出现记录，也不能显示“会议开始”却没有任何成员通知记录。

### 6.2 会中消息

Agent 的实质意见、追问、核验和回应在聊天中展示，携带会议关联，能够点击回到本场完整记录。系统重复进度和内部调用记录默认收起。

独立提交阶段先分别保存意见，卡片显示提交情况；到达本模式的公开条件后，再向参与者开放并在会话中展示。普通群聊仍可进行，不因为会议阶段锁住整个群。

同一群若同时有多场会议，按会议ID归属消息、阶段和通知，不能只靠“从第几条消息到第几条”把无关讨论全部算入纪要。用户可以回复具体会议卡片或关联消息补充内容。

默认会中界面只展示有意义的交流和进展：正在处理哪个议题、主要观点与依据、哪些问题正在核验、已经形成什么结果。用户不需要维护议题清单、手动发布成员意见、分派核验或点击“进入下一阶段”。

独立意见区是会议内部的数据与可见性能力，不新增一个要求用户操作的工作台。用户可以按需展开初稿、修改理由和完整记录；默认不把后台检查清单、反复工具调用和每条状态推给用户。

用户在任何时候插话、决定采用某个方向、修改议题或停止会议，均进入当前会议上下文并被负责人接住；系统记录决定、更新后续安排，不要求等到最后出现决策卡才允许决定。负责人不能因为还有既定环节没走完而忽略用户的新要求。

在现有授权与收尾约定内，负责人自行组织讨论、核验、总结和归档，用户不必全程在线。确实缺少用户取舍时，可以在聊天中清楚提问；未获得回答的部分保留待决定，其他可以独立推进的议题继续，不把全场锁在一个确认弹窗上。

### 6.3 结束卡片与归档

群内结束卡提供简短结果、结束原因、预期达成情况和“查看完整记录”入口。侧栏按会议集中保存：

1. 配置、模式版本与变更记录。
2. 各轮原始意见、讨论、引用和独立提交记录。
3. 总结与依据、保留的分歧、未解决问题。
4. 相关文档和后续事项的链接。
5. 实际参与情况、耗时和可获取的消耗。

用户可从纪要回到原发言。记录分页读取，不只保留最新若干条；摘要不能取代原文。整理新版本时保留旧版本及来源范围。

纪要发布和归档不以用户逐项评分或点击“通过”为前提。用户可以随后继续提问、纠正、作出取舍或要求重开；未由用户确认的主观满意度不能被系统自动标为通过。

### 6.4 议题、决定与结果的连续性

负责人从筹备对话中形成带稳定ID的议题清单，每项保存问题、本轮期望交付、来源原话、当前状态、相关意见与依据。议题可以增加、删除、拆分、合并和调整顺序；删除是保留历史的取消，不抹掉原讨论。议题不是要求用户维护的任务表，默认由负责人管理，用户可查看或纠正。

本场目标、交付约定及用户新决定都有版本。用户在会中改变方向后，后续通知和接续读取提供最新版本；旧输入产生的迟到回答仍保存，但标记所依据的版本，由负责人判断哪些仍可用，不直接作为新要求已完成的证据。

最终纪要按议题逐项回应，关联原始意见、核验记录、修改理由和未解决问题，不只给一段笼统“大家认为”。负责人建议与用户已作决定分开记录；主持身份不让其推测自动升级成用户决定。

### 6.5 有效讨论的基础机制

这些机制由系统和负责人执行，不增加人工操作环节：

- **独立判断：** 需要多方独立意见的议题，先收本场初稿再公开；核对关键依据的任务也不只让另一位复述已有答案。
- **针对性核验：** 负责人提出影响结果的具体待核验主张，保留检查方法、发现和相关证据。即使所有人都同意，也应检查决定结论的关键依据，而不是把一致本身当作证据。
- **有依据地修正：** 保留初稿、修订及修改理由。程序能检查记录是否完整；事实是否成立仍需实际资料、工具结果或人工判断，不能用存在来源链接或通过JSON格式校验冒充核验成功。
- **保留异议：** 总结说明关键异议怎样处理、为何采纳或保留。没有发现问题可以如实报告，不要求每位成员都反对或打分，不以反对次数考核效果。
- **停止空转：** 没有新证据、有效修正或具体可做的补查时，负责人整理现有结论和缺口；有分歧也不自动延长。

会后自动形成简短的“本场变化”：新增了什么有用信息、纠正了什么、哪项判断改变及原因、仍有哪些缺口。它是基于可追溯记录的报告，不是系统自动证明会议优于单Agent。负责人总结可被其他成员和用户指出遗漏，原始意见始终保留。

## 7. 结束规则与预期管理

### 7.1 三个概念分开

| 概念 | 含义 |
|---|---|
| 用户预期 | 用户最初可以不明确，由用户与负责人筹备沟通共同形成目标及交付约定 |
| 收尾方式 | 谁或什么事件触发停止讨论并整理结果，用户可选择或采用负责人提出的整体安排 |
| 时长上限 | 从正式开始到停止自动推进的总时间窗口，包含收尾，默认10分钟，可调整 |

会议结束不自动等于预期达成；Agent 整理了纪要，也不自动等于用户满意。

### 7.2 收尾方式

- **到时结束：** 到截止时间停止发起新的讨论轮次，整理已有结果，记录达到时限。
- **负责人总结：** 负责人对照用户预期，在认为可以收尾时提交总结并结束；同样受时长上限约束。到时仍未收尾，系统停止继续扩展讨论，记录尚未完成的内容。

收尾方式在筹备安排中清楚展示，用户可主动选择或采用负责人建议，不单设必填确认步骤。负责人不能靠“还在总结”越过原截止时间：默认10分钟包含最多8分钟讨论、最后2分钟收尾；其他时长按总窗口的20%预留收尾，最多2分钟，负责人可以提前完成。临近截止不再安排无法在剩余窗口内合理推进的新一轮。

收尾最多发起一次自动总结请求，自动请求也计入本场唤醒预算。截止时系统停止新增会议执行并保存已有结果；原平台已接收的任务未必能立刻中止，仍按实际回执显示。若纪要尚未返回，归档标明“会议已结束，纪要未完成”，不能编造总结，也不为了补齐纪要无限重试。迟到纪要按第7.3节保存并标注。用户可随后主动要求补整理。

### 7.3 人类随时停止

用户可以点击停止，也可以在本场对话上下文里明确说“先停”“结束这场会议”。如果明确要求立刻停止全部调用，则直接保存已有记录，不再额外请求总结；用户后续可主动要求整理。

停止本场后，不再派发本场新工作，也不因迟到回应重新打开会议。平台不支持中止已运行执行时，如实显示“已请求停止／仍有回应未返回”；迟到回复保留并标明到达时间、是否已纳入纪要，不能偷偷改掉已发布总结。

多场会议并存且用户的喊停对象不明确时，先明确针对哪一场，不能猜测为停止整个群或所有项目。

### 7.4 没达到预期和异常情况

- 到时未达预期：明确列出已完成、未解决和缺少的证据，不编造达成结论。
- 没有新证据：负责人可以按选择的规则收尾，保留分歧，不继续互相点头消耗轮次。
- 成员未回复、网络失败或额度不足：显示等待、阻塞或部分参与，不伪装成完整讨论；原时限仍可触发停止。
- 用户延长或改变目标：保存变更者、新要求、新截止时间及之前结果，不重置成一场没有历史的会议。

预期达成情况可标为“负责人认为已达成”“部分达成”“未达成”“交付已提供、效果待用户判断”；需要用户确认的主观取舍，不由程序自动盖章通过。

### 7.5 负责人不可用和没有有效回应

筹备时负责人不可用，显示真实等待或错误，保存筹备对话，允许用户选本场组织者；不伪造回应，不更改群负责人。用户没有继续输入时不自动追加模型调用来催问。

会中负责人失联、额度不足或长时间未回应，系统仍按持久化时限和预算停止自动推进、保存成员原文、发布真实结束状态并归档，不依赖负责人再次上线才能关闭本场。默认不擅自换负责人；用户换人后可依据原议题、意见和回执接续，不要求重新讲背景。

如果在截止前只有一位或没有成员实际回应，结束卡明确显示实际参与数量及未形成的协作环节，不能称为已经完成互证、攻防或多人共识。负责人可以交已有可用结果，但不能补造缺席成员的观点。

## 8. 投入与消耗展示

开始前展示负责人提出的简短组织安排、默认参与人数、时长上限与预期产物，详细模式步骤可展开。筹备和正式讨论的调用、耗时分别记录。运行中展示真实参与、当前环节、已发生的调用次数、耗时，以及平台实际提供的额度或 token 数据。

平台未提供真实消耗时标为未提供，不以调用次数冒充 token 数量，也不编造订阅 Agent 的精确美元成本。系统通知、空轮询和反复失败不包装成有效讨论。

达到讨论上限、截止时间或用户停止后，不自动加轮次、扩大成员或改变目标。用户可明确选择继续或修改安排；不以“为了给出结果”为由无限后台运行。

## 9. 实施结构

本节是后续实现建议，不是已经发布的功能说明。

### 9.1 系统和原生 Agent 各自负责什么

| 系统负责 | 原生 Agent 负责 |
|---|---|
| 会议身份、成员与配置、模式版本、阶段状态、截止时间、通知、独立意见的可见性、幂等与记录 | 调查、提出意见、质疑、查证、回应、判断和整理总结 |

继续使用原 Agent 的模型、工具和订阅。不能新增一个替所有成员编观点的总控模型，也不能把脚本模板生成的发言冒充成员真实回应。

### 9.2 统一会议工具

扩展现有会议能力，提供保存筹备对话与安排、正式发起、读取、调整、提交本阶段意见、推进阶段、收尾及停止等动作。用户按钮和 Agent 工具读写同一份数据；保持已有 `channel.meeting` 调用的兼容，不另建两套互相不一致的会议状态。筹备面板发给真实负责人的通知须保留发出、领取、回应记录；没有拿到负责人回应时如实显示等待，不用静态文案代替它的组织判断。

Agent 可以代用户创建和主持，也可仅参与；主持或负责收尾不意味着其他成员不能发言。新会话创建、邀请成员和结束会议均应有真实回执，不能靠一句“已完成”改变状态。

### 9.3 核心记录

在现有会议记录上扩展：模式及版本、议题、用户预期原文、成员和负责人、会议总时长（含收尾）、开始与截止时间、收尾方式、当前阶段、结束原因及纪要版本。

另外保存筹备对话、本场目标与交付约定的版本、开始授权来源、稳定议题ID、议题的取消／拆合关系、各阶段期限、唤醒预算与已用计数；关联阶段意见、会议消息、通知与执行回执、引用和后续事项。普通群消息没有会议ID时继续作为普通沟通，不自动归入最近一场会议。

运行状态建议为“筹备中 → 进行中 → 收尾中 → 已结束”，同时保留必要的等待／异常说明；筹备时尚未正式发起，不能提前启动讨论时限。预期达成情况另存字段，不能和运行状态合并。

### 9.4 运行和恢复

- 每次创建、推进和收尾有幂等编号，重复请求不会再开一场会或再发一次讨论工作。
- 截止时间由持久化服务端记录和检查，界面倒计时只做展示；关闭界面或重启本地软件不能重置十分钟、绕过到期处理。
- 启动、推进和派发前在服务端核对本场版本、当前阶段、截止时间、剩余预算和停止状态；重复开始只生成一次会议、卡片和通知。阶段推进与停止发生竞争时，停止后不得再成功派发新执行。
- 一次通知失败不抹掉原发言。恢复后读取已有阶段、提交和回执，不从第一轮重新运行。
- 同一成员参加多场会议时，按真实执行器能力排队，明确显示忙碌，不冒充已同时参与。
- 独立阶段覆盖本场工具读取、材料和适配器输入，不能只写“请独立思考”。原平台已有会话、记忆或外部材料不在 Hub 完全控制范围内时，记录实际隔离范围，不统一宣称绝对双盲。
- 不修改既有账号、凭证、浏览器资料、代理与用户日常环境来实现会议；继续遵守项目既有登录保护要求。

### 9.5 自动执行预算与阶段推进

以下为本稿建议的首版执行默认值，属于实施约束，不要求用户填写计算参数；真实联测后如需调优，须更新规则版本并保留原因，不能宣称这些默认值已证明最优。

- **总时限：** 默认10分钟，包含第7.2节规定的收尾窗口。开始卡显示真实截止时间；用户延长时保存新版本，不静默重置。
- **自动唤醒预算：** 默认 `3 × N + 2` 次，N为本场计划实际参与的已连接成员数。包括由Hub自动发起的负责人协调、研究、核验、补查和总结执行；是否重试也受同一预算约束。派发前须预留一次总结请求额度。实际token与平台内部执行成本另按可获取数据记录，不将此计数冒充token硬上限。
- **阶段推进：** 负责人将剩余讨论窗口分配给必要环节，保存每阶段截止时间。需要的成员已提交或阶段时间到即进入下一步；不无限等齐所有成员。部分提交时标明缺席和覆盖缺口，不声称完成了全部独立研究。
- **多轮补查：** 负责人可在剩余时间及唤醒预算内针对实质问题继续多轮核验；每轮说明待验证什么及上一轮仍缺什么。相互称赞、重复观点、没有新的检查动作，不成为自动开下一轮的理由。
- **预算耗尽：** 停止新增自动讨论，使用已预留的额度按现有安排收尾；收尾条件不允许新增执行时直接归档原记录。用户仍能正常发言、决策和喊停，不被会议预算挡住；明确要求追加讨论时保存新的追加安排，不抹掉已耗记录。
- **筹备对话：** 不套用正式会议的轮次预算。每次用户实际发言可触发一次负责人回应及必要工具调用，网络恢复复用同一请求；无新用户输入时不自动自问自答。多轮筹备以澄清目标和交付为目的，没有固定必须达到的轮数。

### 9.6 独立意见与普通群聊的读取边界

当前运行代码的会议工具只有创建／关闭记录，群读取返回公共消息与资源；尚未具备本方案的阶段隔离。后续实现不能只新增一个隐藏UI区域就声称独立意见已经隔离。

未公开意见单独保存，不提前写入公共群消息、共享文档、摘要或通知正文。在本场公开前，成员身份只能读本人意见；用户可以查看全貌。负责人参与独立判断时，同样先提交本人的意见，不能提前用其他人的初稿形成自己的结论；组织进度仅需读取是否提交等元信息。

公开范围要覆盖 `read_channel`、`receive_messages` 内嵌上下文、会议详情、相关文档和附件、版本历史、搜索及成员可用的导出路径；任何基础成员令牌都不能绕过。正式公开由服务端统一改变可见性并留存时间与版本，不让每个成员自行猜测可以公开了。

普通群聊权限继续保留。如果同一成员主动把初稿放到普通群聊，或原平台／外部来源已经提供了别人的答案，记录这一轮独立性受到影响，不能再称为完全独立；不以此为由封锁整个群，也不自动花费额外预算重新跑一遍。

### 9.7 用户介入、版本和停止

停止按钮直接调用服务端，不等待负责人模型回应。停止、截止和派发在同一状态版本上校验，停止后新的自动派发失败；历史已接收执行如实保留，不报告成已经全部取消。

用户自然语言补充由其真实身份和当前会议上下文进入负责人对话，保留原文，明确时记录为本场目标、交付或决定的新版本；普通讨论不自动变成用户决定。引用文章、其他Agent消息或材料中的“停止／采纳”等文字，不能冒充用户的控制指令。

系统分别记录已接收用户要求、已通知负责人、负责人已回应／更新安排的实际回执；消息存入数据库不冒充原平台已经理解或即时中断了旧执行。负责人忙碌时先保存并优先提供最新要求，恢复后接续；不能因为旧轮次尚未结束就丢掉用户新要求。

## 10. 验收标准

下表是后续开发必须实际执行的检查，不是本轮已通过的结果。

| 场景 | 用户必须看到或系统必须证明的结果 |
|---|---|
| 默认入口 | 点“开会”首先进入与真实负责人的筹备对话，不先要求用户理解模式或填写一组表单 |
| 多轮筹备 | 用户只有模糊需求时，负责人与用户逐步形成目标和交付约定，保留历轮理解；不会第一句就擅自召集所有成员 |
| 不为讨论而讨论 | 负责人不重复追问已明确的信息，不要求固定筹备轮数；已有足够理解时提出可开始安排，不增加必须填写的收尾字段 |
| 负责人组织 | 用户自然表达需求后，真实负责人选择方法、给出可修改安排；不能靠关键字匹配或脚本模板冒充其回应 |
| 默认创建 | 自动带入群成员与负责人、10分钟；用户不用重复填写这些配置 |
| 筹备与开始 | 打开入口只通知筹备所需的负责人，未正式发起前不广播全体、不启动十分钟倒计时；正式开始后按实际开场时间计时 |
| 用户调整 | 用户可在筹备或会中改安排、补充预期、换方法或喊停，不被五个模式标签限制表达 |
| 无需监工 | 正式发起后，即使用户不操作，也能按约定推进、收尾并归档；独立提交、公开、核验与阶段推进均无强制人工按钮 |
| 随时决策 | 用户在任意阶段用普通聊天作出的明确决定能被记录并影响后续安排，不必等到决策卡出现 |
| 按需展开 | 默认看到有意义的过程和结果；初始意见、变更理由和内部调用可展开查看，不增加用户必须处理的步骤 |
| 用户预期 | 完整保留用户自己的描述，允许修改；程序不擅自换成固定成功标准 |
| 动态议题 | 议题可增删、拆合、改序，原文和版本保留；最终结果逐项关联议题，而非一段无法对照的总结 |
| 发起会议 | 聊天中出现会议卡片，侧栏同时可查，参会成员实际收到关联通知 |

| 隔离旁路 | 使用普通成员令牌分别从群读取、接收上下文、会议、资料及历史等可用入口读取，均不能拿到他人未公开意见 |
| 真实参与 | 成员以自身身份提交意见，缺席、忙碌与失败如实显示，不预填模板回复 |
| 群内讨论 | 追问、回应和引用正常显示且归本场；无关群聊不被锁住或混入纪要 |
| 到时结束 | 截止后停止新轮次；未解决问题保留，不把到时等同于预期达成 |
| 负责人收尾 | 用户所选负责人能真实提交总结并结束；缺少或迟到的总结不会造成无限续跑 |
| 时限和预算 | 10分钟包含收尾；达到阶段、总时限和自动唤醒上限后不新增超额执行，不因负责人想继续而越界 |
| 负责人失联 | 实际断开负责人的回应后，系统仍到时停止、保存和归档，明确纪要是否完成，不伪造总结或强迫用户回来关会 |
| 人类喊停 | 按钮和对话均可停止本场；不误停其他会议或关闭群聊；明确立即停止时不再额外请求总结 |
| 迟到回复 | 仍归原会议并标记时间，不重新打开会议，不静默覆盖已发布纪要 |
| 中途改要求 | 用户修改目标后，新输入使用最新版本；旧要求的迟到结果标明来源版本，不自动当作新要求已完成 |
| 并发与停止 | 重复开始不会重复建会；停止与阶段派发并发时，停止后无新的自动派发成功；用户引用文章不会误触停止 |
| 会后回看 | 从结束卡及侧栏都能查看纪要、完整分页记录、分歧、未解决问题和原文出处 |
| Agent 代开 | 用户一句话委托任意具备权限的 Agent 后，能真实建会、采用相同默认值并完成流程，无需再填同样表单 |
| 多会与恢复 | 两场会议的意见、时限和消息不串；断线、重复通知及重启不重开会议、不重跑已完成轮次 |
| 消耗与效果 | 展示可获取的真实消耗或调用、耗时；分别记录会议结束原因与预期达成情况 |
| 实际改善 | 在有已知事实或可检查资料的题目中，保留初稿、关键核验和终稿，检查新增发现、纠正及改坏的情况；不以一致率、反对次数或总结完整度证明有效 |

先用独立测试成员验证机制与异常，再用实际原生 Agent 完成从发起到归档的完整流程；测试报告区分协议模拟、工程运行和真实商业 Agent 联测。只有保存记录、健康接口成功或界面出现卡片，不构成完整会议验收。

## 11. 本轮方案审计结果

审计对象为本文件v0.3，结合所有者在审计中的补充修订为v0.4。以下表示方案规则已经补齐，不表示软件已经实现或验收通过。

| 问题 | 原方案风险 | 本版处理 |
|---|---|---|
| 筹备与默认入口 | 只说自然沟通，仍可能一次猜测就开会，或强迫用户填写收尾方式 | 明确必要的多轮目标／交付对齐；足够明确即开始；收尾作为可见安排建议，不增必填表单 |

| 负责人不可用 | 依赖负责人回来总结，会议可能一直挂着 | 系统独立处理截止、停止、记录和归档；缺少纪要如实标记，不伪造接替与总结 |

## 13. 会议阅读与原生接收效率修订

本轮根据真实使用反馈修订，不改变自由沟通和负责人职责。内容理解、编排、判断、总结及重新解释仍由原生负责人Agent完成；系统负责传输、原文与版本保存、权限和展示，不根据关键词编写或替换结果。

- 筹备保留右侧对话，但“与负责人沟通”和“本场安排”分开展示。负责人提交新安排后显示简明计划：本场问题、拟交付结果、议题、成员与时长；具体方法按需展开。用户可继续补充，无需在长回复与重复安排卡中找开始按钮。默认不替用户加400字等篇幅限制。
- 结果使用可展开的阅读区域。负责人正文为主要交付，标题、段落、列表、引用、表格和链接有明确排版；按议题核对、原始讨论和会前安排默认收起，不再把同一组简短状态句重复铺成正文。界面不负责生成摘要或判定共识。
- 用户可要求负责人重新解释已结束的结果。只有明确用户请求才能新增这一轮；只唤醒原负责人，不重开会、不广播全体。负责人真实提交修订后展示新正文，旧稿保存为可回看的版本；普通迟到回复仍不能覆盖原交付。
- 原生Agent已经真实领取的通知包含来源版本。客户端省略冗余参数时，只从同一身份、同一会议、仍有效的实际领取中补齐；没有实际领取则要求补参数并保留完整正文。明确旧版本仍视为迟到。支持引用本群的真实共享资料版本，跨群或伪造引用继续拒绝。
- 派发先处理当前通知，再做非紧急维护；独立接收器有界并发（每批最多4个、单次维护最多12个），相同资源在同次维护中只安排一次。原有身份、忙碌、合并、停止、超时和重试检查仍由派发器执行。模型没有定时空跑。
- 领取上下文并行读取；历史会议提供目录而非每次重复塞入整篇旧结果，当前结果已在会议对象中时不再把同一正文重复嵌入记录列表。完整原文仍可按需读取。阶段交付返回现有45秒连续接收入口，是否实际采用由原生Agent执行，空等到期即结束。
