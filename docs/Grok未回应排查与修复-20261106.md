# Grok 未回应：2026-11-06 实际排查

## 结论与产品边界

当天同时存在正常静默、明确交办被旧跳数上限拦截、平台受理但 Agent 未领取三种情况，不能把它们统称为防刷屏。

- 明确 @ 成员或 @全员的请求必须进入收件队列，不能因为讨论较长就静默截断。
- 致谢、已采纳及没有新信息的确认可以不重复回答；明确交办需要结果或具体阻碍。没有回应不代表默认同意或验收通过。
- 平台 HTTP 受理回执不等于 Agent 已收到、正在处理或已完成。只根据真实领取和回传更新这些状态。

## 修复

1. 显式 @（含已解析的正文点名）和 @全员不受旧的因果跳数限制；历史已暂停记录不批量恢复、不重放旧工作。
2. Grok 通知获平台受理后，2 分钟仍未领取，重新通知同一投递，最多共 3 次。重新领取使用独立幂等编号，避免复用旧的 busy/empty 回执。已有执行租约或已知忙碌资源不会被重新执行。
3. 重试仍未领取时，原消息和同批补充统一显示“成员尚未接收”，保留消息和后续迟到接收能力；释放旧通知状态，使新消息不再被它无期限吸收。
4. 发送结果未知不自动重发；已有执行中断不自动重做。正常调用收到的既有领取依旧使用幂等结果。
5. 群内提示和消息详情统一区分等待接收、正在重新通知、处理中、处理已中断、已回复。API 返回合并关系和重试标记，不再把 HTTP 200 写作“已送达”。
6. 所有者恢复入口支持只选择一条原通知，避免处理一个成员问题时恢复其他旧工作。

## 验证与发布边界

- 单元覆盖：长讨论中的实际点名交接、@全员、并发维护、通知重试、合并补充、已领取不重做、忙碌释放后恢复、次数耗尽、新消息仍能发送、迟到领取、历史记录不自动重放和定向恢复。
- `tests/grok-receipt-ui.mjs`：真实 Chrome + 隔离 HTTP Hub，验证群内提示与详情状态一致、原消息可定位，以及真实认证的协议回传清除待处理。平台回执为隔离场景，不能冒充商业 Grok 验收。
- `tests/message-processing-desktop.mjs`：隔离 Electron，验证运行中和执行中断的状态文案。
- `tests/server-http.mjs`：独立服务的鉴权、并发、重启持久化和共享文件门槛。
- 发布仍遵循运行任务保护。发布和桌面启用以本轮实际日志及 `evidence/grok-receipt-release.json` 为准；构建或隔离测试通过不代表线上已生效，也不代表真实 Grok 已恢复回应。
