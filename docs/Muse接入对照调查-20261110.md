# Muse 接入对照调查

调查日期：2026-11-10。源码核查，不冒充真实 Muse 账号接入验收。

结论：别人能做的主要原因是把 Muse 网页做成了浏览器驱动服务。我们不是没有可走的路径，而是现有网页适配停留在旧任务执行链，新的群聊接入又要求 Muse 自行建立 REST connector 和拉取通知，两条链路尚未统一。不能据此断言 Muse 无法接入。

## 本次仓库实际做了什么

固定版本：[LIUFelix2004/museAPI-video @ 9f0cf4c](https://github.com/LIUFelix2004/museAPI-video/tree/9f0cf4c351b0a65fdc6bab1f2d8a18cea8e55f8c)。

- [浏览器引擎](https://github.com/LIUFelix2004/museAPI-video/blob/9f0cf4c351b0a65fdc6bab1f2d8a18cea8e55f8c/upstream/muse2api/engine.py) 启动 Chrome/CDP，把导入的登录 Cookie 装进隔离浏览器，驱动原网站输入、读取回复和附件；不是官方 Muse 模型 API。
- [上层服务](https://github.com/LIUFelix2004/museAPI-video/blob/9f0cf4c351b0a65fdc6bab1f2d8a18cea8e55f8c/server/src/muse.js) 提供视频/图片异步任务、查询、媒体下载及账号管理，给应用提供方便的 HTTP 外壳。
- chat_stream 先 ensure_page，再 reset_thread(for_chat=True)，从网页读增量文本。60ms 采样；Stop 消失后约180ms文字稳定即结束，Stop 仍存在但约5秒无变化也返回。因此“视频/聊天接口有响应”不能直接证明长时间工具执行和完整协作已结束。
- 引擎支持账号上下文、续期及云 VM 连接诊断，值得参考；会话有清理/重置策略，直接搬入会改变我们“保留原会话”的语义。
- README 的成功描述是作者报告，本次没有独立复验其真实平台账号、套餐、全部工具或长期稳定性。

## 和我们的具体差异

| 层 | 当前 DuolaWork | 对方实现 | 判断 |
| --- | --- | --- | --- |
| 网页发送 | local/muse.mjs 已能识别输入框、草稿、忙碌和批准，发带本次任务ID的请求 | CDP 模拟发送 | 我们已有基础驱动，不应说完全做不到 |
| 登录持有 | 复用 Hub 专用原浏览器与原 profile | 浏览器扩展导出 Cookie，再注入引擎自己的浏览器 | 可以沿用我们的原 profile，不必复制其账号池/凭证导出做法 |
| 任务结束 | 匹配本次ID的完整信封、非忙碌、非待批准，再稳定1200ms | DOM文本稳定和 Stop 状态；长停顿也可返回 | 都需要对真实长任务、附件、批准、断线分别验收，不能只测一句问答 |
| 新群聊通知 | cloud/collaboration/connections.mjs 对 Muse 的 muse-poll 要求原 Agent 建 connector/hook | 外部服务主动驱动网页，无需 Muse 自建通知器 | 应把已有网页驱动接入新的持久收件箱和回执生命周期 |
| 旧本地链 | local/connections.mjs 做 browser_roundtrip 与旧任务验证 | 自有 HTTP 任务队列 | 旧任务成功不等于当前群聊已自动接单 |

## 推荐落地路径

1. 在现有成员/账号身份上增加网页接收器适配，仍消费相同 Hub 收件箱，不造第二套成员、任务或权限体系。
2. 专用原浏览器、同一 profile、原会话绑定；发送前检查草稿与忙碌，任务ID落盘后再发；重连只读恢复，不盲目重发。
3. 回传携带原 turn/task/消息关联；结束依据本次实际结果和执行状态，不用5秒静默当长任务完成。网页 UI 变化、平台批准、登录过期、云VM断线分别报告。
4. 不把官方多会话能力未验证的账号显示成可无限并行。不同原生会话和同一会话排队分别验收。
5. 真正接入前测试：普通群消息→原Muse接单→实际工具/附件→回群；执行中补充不丢失；重连不重复发；原项目/历史保留；平台权限需求如实回报。

本次授权对 Muse 是调查，未迁移真实账号、未导出 Cookie、未安装第三方扩展，未把文档调研标成生产接通。2026-10-27《支持的Agent》对旧 muse2api 的结论只适用于当时固定版本，不能套用到这个更新后的浏览器引擎。
