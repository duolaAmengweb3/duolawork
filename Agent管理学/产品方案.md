# Agent Hub：围绕目标运行、能够学习的 Agent 组织

产品提案 v0.1｜2026-10-29｜来源：[方法论](方法论.md)、[调研档案](README.md)

状态：研究后的产品设计建议，尚未据此改动软件、UI、登录资料、执行规则或外部任务。文中的“应当”是设计要求，不是现有功能声明。

## 1. 扩大后的产品核心

**让人和原生 Agent 围绕共同目标，形成有明确权责、能自主推进工作、保留组织知识并根据结果改进的组织。**

用户购买的价值包括：组合原本分散的能力，完成更复杂的工作；将临时合作变成持续运营；在目标和环境变化时调整做法。减少复制粘贴和催促，是其中的具体收益，不应限制整个产品定义。

“Agent 的飞书”可以帮助理解，但产品不能只停留在群聊、文档、任务板和组织图。它应当帮助用户处理六类管理决定：做什么、谁来做、如何合作、谁来决定、怎样交付、下次改什么。

研究范围可以覆盖更大的组织；产品首先服务已经有一个或多个原生 Agent、存在持续工作需求的个人与小团队。以一个人的工作室作为容易理解的入口，不把底层能力锁定为内容运营或编码。

## 2. 三个具体使用场景

| 场景 | 用户交代的目标 | 系统应组织的工作 | 合格结果 |
|---|---|---|---|
| 持续研究与内容团队 | 持续发现值得研究的方向，形成可用选题或材料 | 多来源研究、独立判断、证据补充、选择与整理 | 有依据、适合用途的结果；没有新信息时明确说明 |
| 产品验证项目 | 研究一个需求，形成是否值得做的判断和可验证方案 | 需求证据、竞品、可实现性、原型或验证材料的依赖协作 | 可执行的验证方案与支撑材料，不只是长报告 |
| 长期业务助理团队 | 跟踪客户、供应商或项目事项并推进 | 观察变化、关联历史承诺、准备动作、处理例外 | 事项有接续、有责任；对外动作符合授权 |

这些是目标场景，第三方数据与操作能力按实际接入验证，不将用户授权等同于平台一定提供接口。

## 3. 产品的核心对象

| 对象 | 必须保存什么 | 为什么需要 |
|---|---|---|
| 组织 | 所有者、长期目标、共同约束、授权与资源 | 维持跨项目一致性 |
| 成员 | 原生 Agent 身份、接入状态、可核验能力、当前可用性 | 按实际能力安排，而不是按品牌贴岗位 |
| 目标 | 期望改变、用途、优先级、成功标准、复查条件 | 防止只做任务不实现目的 |
| 项目与工作项 | 责任、依赖、输入输出约定、状态、异常 | 能可靠交接和推进 |
| 决定 | 问题、候选、依据、异议、裁决者和理由 | 形成真正的取舍，防止聊天代替决定 |
| 成果与证据 | 内容、版本、来源、核验情况和使用反馈 | 防止空状态和混杂汇总 |
| 组织知识 | 事实、偏好、方法、决定的范围、有效性和维护人 | 让经验能够复用和更新 |
| 改进提案 | 问题记录、原因假设、规则变化、预期、验证与撤回 | 形成可解释的组织学习 |

“运行配方”对应可复用的工作安排，可以保存参与条件、交接方式与验收规则。它是起点，不是所有任务必须照着走的固定流水线。用户不必先懂这个名词才能开工。

一个成员可在不同项目承担不同职责。牵头职责属于具体工作，不要求用户为每个任务永久建立一套管理层。

## 4. 用户怎么使用

### 4.1 开始一个目标

用户说清目的，选择可参与的成员或允许系统在已有成员中建议。系统结合已知资料提出一份简短工作约定：交什么、怎么判断、谁牵头、为什么需要这些参与者、预计的资源与依赖。

已有长期授权内的小任务直接推进；缺失信息只有在影响结果或授权时才询问。不能让用户逐项填写内部任务配置。

### 4.2 自动推进，用户随时能纠偏

成员按约定发挥自己的原生能力。已确定的依赖和唤醒由程序执行；遇到语义分歧、输入不足或目标变化，由牵头成员提出处理办法。

用户一句“这不是我要的方向”，应能改变项目要求并影响后续工作。系统需要定位影响范围，避免所有成员从头重跑，也避免仅改界面文案。

### 4.3 收到成果与必要决定

默认呈现成果、依据、重要取舍和未解决项。过程可以展开查看，但不能把原始聊天量当作工作价值。

需要用户决定时，一次说清选项、差别、建议与依据。普通交接不反复弹窗；只有超出授权、无法按已有标准裁决或影响重要承诺的事项进入待决定区。

### 4.4 在长期使用中提出改进

根据真实返工、使用结果、运行失败与资源冲突形成改进建议。用户能看到改什么、为什么、下一次如何生效，以及如何撤回。

已授权的小范围方法调整可以自动执行并记录；扩大授权、修改长期目标或显著增加资源投入，需要相应决定。这里是产品的权限设计，不是在本次研究里索取新权限。

## 5. 四层实现职责

| 层次 | 负责什么 | 不应混淆什么 |
|---|---|---|
| 原生执行层 | 通过真实支持的方式唤醒、执行、回传；保留原 Agent 工具和会话能力 | 接上聊天 API 不等于接上完整 Agent |
| 组织运行层 | 工作所有权、依赖、资源、事件、状态和成果版本 | 接到消息不等于完成任务 |
| 判断与学习层 | 提出安排、分析分歧、诊断失败、形成改进提案 | 模型自评不能独自证明正确或有增益 |
| 用户工作空间 | 目标、协作、成果、决定、组织变化的可理解呈现 | 状态动画不等于真实运行 |

管理判断可以由具备条件的已有成员承担，不强制另购一个“CEO 模型”。简单路由、唯一领取、状态检查、重复事件去重等由程序承担，减少成本和随机性。

牵头成员失效时，保留工作上下文与责任记录，按已批准替补规则交接；没有可用替补就明确阻塞。不能在后台换成未经用户选择的 API 或假造继续工作的状态。

接入方式按真实能力区分：可主动调用、事件唤醒、只可读取结果、暂不可用。每个平台独立核验“唤醒—工作—交付”全链路；本稿不重新宣称此前所有平台都已接通。

## 6. 必须落地的组织机制

### 保留独立判断

需要独立提案的阶段限制对其他成员结论的提前访问，同时共享必要事实与用户标准。查看和公开时点可追溯。能做到多大程度由执行器能力决定，不能只靠提示词就宣称强隔离。

### 明确责任和决定

重要交付指定牵头责任，重要决定指定裁决者；协作者可以有多位。裁决保存依据与未采纳的关键意见。对有明确事实答案的问题优先核实，不用人数抵消证据。

### 可靠交接

接收方检查约定输入，缺少关键内容则退回或报告部分可用。重复唤醒不重复执行；旧版本交付不覆盖新成果；超时与无响应显式处理。

### 有选择地复核

核验深度跟随任务约定和错误代价。程序验证形式与运行，独立核查事实和关键推理，用户决定主观取舍。不让每项工作都经过形式化的全员审阅。

### 管理资源与优先级

考虑账号可用性、并发限制、任务依赖、截止时间和预算。订阅额度不清楚时展示未知或可观察状态，不能编造每任务精确成本。

### 组织学习

反馈先定位到目标、输入、执行、判断、整合或规则；再提出有范围的修改。每次规则变化有版本、原因和撤回方法，后续任务可证明是否应用。

### 知识维护

区分长期知识、项目事实和临时要求。允许过期、冲突、修订和删除，避免组织记忆不断膨胀却不可靠。

## 7. 工作空间怎样体现这套逻辑

本轮不画新 UI，也不覆盖已有视觉评审。以下是后续交互必须表达的内容：

- **目标与项目**：用户知道正在为什么结果工作，以及目前卡在哪里。
- **协作过程**：显示有意义的工作变化、依据和决定；原始日志按需展开。
- **成果空间**：真实可编辑、可版本化、可反馈，用户修改会进入下一次工作。
- **待决定事项**：只收需要用户做取舍的事，能看清建议与影响。
- **组织视角**：成员实际能力、资源冲突、共同知识、已有规则和改进提案。

不要求这些内容各占一个导航项。默认日常界面保持简单，管理细节按需要展开。组织机制从第一个项目开始存在，组织图不必从第一屏就塞满。

## 8. 与已有方案的关系

| 方案 | 已有价值 | 我们需要证明的额外价值 |
|---|---|---|
| GitHub＋定时任务＋约定 | 版本、异步协作、原生 Agent 独立工作，用户已经能用 | 减少人工转述、规则冲突和断裂交接，并让改进真实生效 |
| OA / 协同办公产品 | 目标、沟通、流程、知识、责任与工作记录，已有 AI 能力 | 对原生 Agent 的执行差异、状态不确定性和判断可靠性处理得更好 |
| Paperclip 等组织运行平台 | 目标、任务、委派、唤醒、预算与治理 | 面向目标用户更易用，跨原生成员的协作与学习确有收益 |
| 单个成熟 Personal Agent | 强执行、记忆、工具、定时与子任务能力 | 在需要跨成员与长期组织安排时提供增量，而不增加无用协调 |

不能声称“别人没有组织管理”或“只有我们能进化”。界面和模板容易复制；更可能形成积累的是可靠接入、真实组织事件数据、有效规则与可检验的改进方法。但只有用户结果证明有效时，这些积累才有商业价值。

已有仓库可以保留为资料与交付位置。接入时明确哪些状态由 Hub 管理、哪些文件由外部维护；用稳定标识与版本关联，避免双向覆盖。不要为了建产品先废掉用户已经运行的流程。

## 9. 完整验收：用户如何判断做对了

下面是后续实现的验收要求，本轮未执行软件验收。

| 验收场景 | 必须看到的真实证据 |
|---|---|
| 用户只提目标 | 系统形成可理解的约定并推进，用户不用逐位转述 |
| 一人足够的任务 | 只使用必要成员，解释安排，不为展示协作增加流程 |
| 多方独立研究 | 记录各自判断和依据；独立阶段不被其他结论污染 |
| 上游交付不完整 | 下游识别缺口并定向处理，不能把空文件当通过 |
| 两位成员结论冲突 | 留下补证、裁决或保留未知的记录，最终稿不混杂矛盾 |
| 成员重复唤醒或中断 | 不重复执行；状态、成果和责任能够恢复或明确阻塞 |
| 用户中途改变要求 | 后续任务采用新要求，已完成的无关工作不丢失 |
| 用户编辑成果 | 后续执行使用正确版本，历史交付仍可追溯 |
| 出现重复失败 | 提出有证据的改进，按授权生效；下一任务可证明采用了它 |
| 改进造成副作用 | 可以撤回，历史规则与结果仍保留 |
| 平台能力缺失 | 明确标示，不冒充登录、工具连通或完整自动执行成功 |
| 连续真实使用 | 同时报告可用成果、人工协调负担、资源与失败，不仅报任务完成率 |

工程通过与价值证明分别验收：前者证明机制按设计工作；后者需要真实使用记录证明组织安排带来收益。不能用模拟消息、界面截图或健康接口代替真实任务链路。

## 10. 当前建议与尚待决定的事项

本稿建议明确采用：目标驱动、原生能力保留、任务相关的动态职责、可追溯决策、真实成果验收、可撤回的组织学习。

仍需通过案例确定：哪些管理判断足以自动完成；哪些任务值得独立复核；不同用途的质量标准；个人用户愿意承担多少管理界面和使用成本。这些需要实际证据，不靠预设一组通用分数解决。

下一次开发前，以这份文档核对现有实现，形成“已有、需修改、缺失、待真实验证”的明确清单。**当前完成的是研究和产品提案，不把文档写完说成产品已经实现。**
