## 二、对“Agent 管理学”的六个推导

以下是 Codex 的分析，不是访谈逐段翻译，也不是讲者已经证实的结论。

### 1. 应当信任“某个条件下的能力”，而不是整个 Agent 品牌

一个成员擅长找公开资料，不代表它擅长付款、发稿或维护生产环境。同一个模型，换成不同资料权限、工具和上下文，结果也可能变化。

因此，组织中的能力记录至少要限定：任务类型、可用工具、输入条件、成果标准、已观察到的结果。授权则另列：允许准备草稿，是否允许公开发布，金额或范围限制是什么。

**能力证据支持授权决定，但不自动授予权限。** 不能设计成“连续成功几次就自己解锁下一档”。用户授权、错误代价与可恢复性必须一起考虑；原平台已有权限限制仍然有效。

这也使“一等公民”的定义更具体：成员可以持续承担责任、请求资源、交接和提出异议；不意味着它可以自行决定自己的权限。

### 2. 工具齐全不等于能够工作，还需要知道工作对象在哪里

把工具列表交给一个新成员，它仍可能不知道：当前哪个文件有效，哪个接口是正式的，客户现在处于哪一步，什么状态算完成。

我们的迁移建议是建立随项目维护的**工作对象与操作说明**，内容包括：

- 正在处理什么对象，谁维护它，哪个版本有效。
- 什么前置条件满足后才能操作。
- 通过哪条真实路径操作，能观察到什么变化。
- 常见例外如何识别，哪些动作需要额外授权。

这不必扩展成一套巨大知识图谱。内容项目可能只是来源清单、选题记录、稿件版本与发布渠道；研究项目可能是问题、证据、假设与决定记录。

说明也会过期，所以要有归属与更新触发条件。复制一份操作手册然后永不维护，只会让错误更稳定地复现。

### 3. 应当分别处理执行、事实、判断和业务价值

把“另一个 Agent 说可以”统一当验收，仍然可能只是互相点头。不同主张需要不同证据：

| 要证明的事 | 对应的证据 | 不能拿来顶替的东西 |
|---|---|---|
| 动作发生了 | 正确版本的文件、实际运行记录、目标系统回执 | 计划、成功动画、成员口头声明 |
| 内容有事实依据 | 来源正文与具体论断的对应关系、时间与适用范围 | 有链接、链接能打开、几位模型赞同 |
| 判断有道理 | 明确标准、替代解释、反例与取舍理由 | 语气自信、所有意见拼在一起 |
| 对用户有用 | 用户实际采用、修改负担、后续结果 | 输出数量、字数、内部评分 |

前三类检查也不能保证第四类成立。教育内容可能准确却讲不明白；新闻可能真实却没有新信息。组织要把这些差异保留下来，而不是合并成一个绿色“完成”。

### 4. 管理经验应该改变后续行为

遇到一次错误，先区分它来自哪里：目标没说清、资料缺失、能力不足、工具失败、交接丢失、规则冲突，还是评价标准不合适。

然后选择适合的修复位置：

| 问题类型 | 候选改进 | 如何检验不是写了个空规则 |
|---|---|---|
| 重复任务造成重复交付 | 稳定工作 ID 与幂等检查 | 重复触发后仍只有一份有效交付 |
| 旧稿覆盖用户新稿 | 版本约束与冲突处理 | 旧结果返回时不会覆盖新版本 |
| 来源遗漏 | 必需信息约定、缺项提示 | 缺少关键来源时不能显示事实核验通过 |
| 把临时偏好当永久规则 | 明确范围、有效期、批准与撤回 | 另一项目不受污染，撤回后不再执行 |
| 选题始终不合口味 | 保存具体采用/弃用理由，重新判断选择方法 | 新任务体现调整，同时未牺牲事实质量 |

前三类通常适合程序约束；最后一类不能靠格式校验解决。**规则的数量不是组织学习的程度，行为变化及结果才是。**

### 5. 分工的价值来自不同责任和证据路径

如果甲、乙、丙看同一份总结、回答同一个泛问题，再相互赞同，增加人数未必增加有效信息。

可以按任务需要区分：资料搜集、事实核验、方案提出、整合取舍、批准执行。不是每次都需要五个人；简单任务可以由一人完成多个职责。是否增加独立复核，要看能否引入另一条证据路径，以及错误代价是否值得。

独立性也不是换个模型名字就获得。核验者至少要能接触原始材料和明确标准，而不是只看到作者写得很有说服力的结论。最终整合者必须处理矛盾，不能用投票或平均分掩盖冲突。

### 6. 环境建设可以成为多人共享的资产

一个人逐次纠正每个 Agent，成本会随成员和任务增加。经过验证的操作方法、资料接口、模板、约束和交接约定，可以在适用任务中复用。

但复用会放大正确，也会放大错误。因此共享资产需要版本、适用范围、维护人和撤回方式；变更之后还应确认依赖它的任务是否继续有效。

这里可能形成产品积累：用户留下的不只是聊天记录，而是**哪些方法在什么条件下有效、哪些失败被修复、谁对某类结果可靠**。这是待验证的商业假设，不能仅凭保存更多日志就宣称有护城河。

## 三、这份案例不能替我们证明什么

### 1. 产出数量不能证明生产率

PR 可以拆得很细，也可能是重构、删除或返工；没有同口径任务价值、缺陷、复查时间和成本，就无法从数量换算生产率。对我们的产品也一样，任务数、消息数、报告长度只能描述活动。

更有用的观察是：约定的结果是否交付、出现了多少重要错误、用户花了多少主动协调和修补时间，以及总资源投入。不要将后台等待时长等同于人工劳动时长。

### 2. 编码的验证方式不能照搬到创作与管理

程序经常有可运行的观察路径；研究与创作则包含事实、解释、价值选择和受众反应。我们可以核查来源和约束，却不能把阅读体验、商业判断都伪装成确定的自动评分。

自动发布尤其是另一项授权。产物通过质量检查，不意味着获准向外发送；若已存在明确持续授权，也不应每次重新索取相同批准。

### 3. 评审本身也可能失败

隐去模型名称能减少品牌偏见，不能保证评审正确。多个模型可能共享错误信息；同一个测试反复优化，也可能只学会通过这个测试。

我们建议保留未参与规则调优的任务、真实失败案例和后续运行反馈。不要让执行者通过放宽标准来消除自己的失败，也不要把另一模型的高分当作客观真相。

### 4. 工程限制应跟具体问题绑定

一项约束在某个代码库合理，不表示全行业都应禁止同类写法。迁移时先说明它预防哪种错误、是否真的发生、有没有更小的约束方式，以及会限制什么合理工作。

同样，编译或静态检查通过，只能证明覆盖到的性质；不能据此宣布业务行为、性能和用户体验全部正确。

### 5. 组织管理不能被缩成质量检查

即使每个动作都正确，团队仍可能在做不值得做的事情。白皮书仍需要回答：目标如何形成、机会如何选择、资源如何分配、分歧如何裁决、什么时候停止以及如何探索未知。

本案例适合补强“能力形成—验证—授权—学习”这条研究线，不能替代完整组织理论。

## 四、给 Agent Hub 的具体设计提案

以下仅为评审提案，尚未批准或实现。不改变当前原生 Agent 接入路线，也不新增一个强制替换原模型的中央模型。

### 本轮相对已有研究，具体补了什么

| 已有方案 | 本轮补充 | 需要避免的误读 |
|---|---|---|
| 成果需要证据 | 证据要对应具体产物版本、执行环境和真实使用路径 | 旧证据不能替新结果背书 |
| 组织可以学习规则 | 要找出规则的实际执行位置，并用历史错误检验它 | 新增一条 Markdown 不等于错误已被解决 |
| 成员有能力与权限 | 能力按任务条件积累证据，授权单独决定 | 不做一个会自动解锁权限的总分 |
| 知识需要维护 | 区分知识过时、操作工具失效与产品退化 | 不能为了“维护通过”而降低原标准 |

目标驱动、明确责任、保留异议等仍沿用已有方法论，本轮没有把它们包装成新发现。

### 1. 在现有对象上补信息，不先增加一堆页面

| 现有对象 | 建议补充的内容 | 用户可以看到的表达 |
|---|---|---|
| 工作项 | 成功条件、实际执行版本、必要前置条件 | 这次要交什么，卡在哪里 |
| 成果 | 证据、未覆盖事项、事实核验与用户评价分开 | 做完了什么，哪里还需判断 |
| 成员 | 分任务类型的能力证据、工具条件与可用性 | 它适合接什么，依据是什么 |
| 授权 | 允许动作、适用项目、限制与撤回 | 能自己推进到哪一步 |
| 改进提案 | 原问题、修改位置、验证方法、版本与撤回 | 下次哪里会不同，如何确认有效 |

默认工作界面只呈现结果、重要取舍、阻塞和必要决定。内部检验细节按需展开，不把用户变成逐项填表的管理员。

### 2. 用一个具体场景说明工作如何发生

假设用户要求“跟踪 AI 新用例，每天形成值得写的选题”：

1. 先形成可修改的目标约定：什么算新用例、可参考性体现在哪里、交什么、哪些渠道有访问权。
2. 搜集成员返回候选与真实出处；不把旧文章被重新转发算作新实践。
3. 对入选候选核对用途、时间、成果证据；核不到的部分明确保留，不补造。
4. 整合成员解释选题取舍。多个来源重复同一案例只算一个案例；冲突说法要处理。
5. 用户收到选题和材料，采用、修改或弃用。系统记录具体理由，不从点击一次推断永久偏好。
6. 如果反复出现同类返工，提出一项有范围的改进；在后续真实任务中检查影响，保留或撤回。

这只是示例。教育、商业研究或开发工作需要不同约定，不能把它固定成所有用户都经过的内容流水线。

### 3. 授权与状态要真实

“可自主准备”“可在项目内更新”“可对外行动”是不同权限，不是全局信任等级。角色的名称也不赋予权限。

状态变化应由相应证据驱动。任务的结果版本改变后，旧核验只能证明旧版本；连接失效时保留成果与待办，不把历史成功当作当前可用。对跨平台无法可靠确认的状态，明确显示尚未核实。

### 4. 产品价值该如何被证明

我们要证明的是：在可接受的错误和资源投入下，用户得到更多真正可用的结果，或减少反复解释、搬运、催促与返工。

“接了十个 Agent”“自动跑一夜”“每个都有岗位”“自动写了一份复盘”都不是独立的价值证明。单个 Agent 已能做好时，产品应允许简单运行。

## 五、如何验证这些提案

这是一份验收设计，本轮未执行，不能写成已验证成果。可优先复用已有记录和小规模任务，不要求购买一套昂贵对照系统。

| 问题 | 具体检验 | 什么结果说明设计不足 |
|---|---|---|
| 是否真的验证交付 | 插入“有成功声明但没有实际产物”的记录 | 仍被显示为已核验完成 |
| 核验是否跟着版本走 | 核验后改动关键内容或返回旧稿 | 旧通过状态继续覆盖新内容 |
| 独立复核是否有用 | 放入带真实链接但结论不受原文支持的案例 | 只检查链接或复述上游结论 |
| 规则能否阻止重复错误 | 用一个历史失败重放，再看新任务 | 旧错误未拦住，或正常任务被无差别阻止 |
| 是否乱扩大授权 | 成员在多次成功后尝试越过既有动作范围 | 系统把能力表现当成新增授权 |
| 维护是否掩盖退化 | 一条用户路径失效，检查知识更新的处理 | 将原有正确预期改成失败行为，冒充维护完成 |
| 用户的负担是否减少 | 记录具体协调、核实和修补动作 | 任务数增长，人的修补反而增加 |
| 能否适应变化 | 用户更改用途或撤销一条规则 | 仍沿用旧标准，或无关项目一起变化 |

公平评价应记录任务难度、输入条件、模型/工具/规则版本和失败情况。先解释观察范围，再报告比例；未评价的任务不计为失败，不设一个没有依据的统一样本门槛。
